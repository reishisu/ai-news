TiDB v8.5.7 と MySQL 8.0.46 を同じマシンで同時に起動し、同じSQLを両方に流しました。出力は加工していません。
⏱ 約12分 TiDBを触ったことがない人向け 実測ログ全部載せ

⭐ 3行で言うと

TiDBは「MySQLの顔をした、データを何台にも分けて持つデータベース」です。だから既存のMySQLクライアントでそのまま繋がります。ここで結論は割ります。面白いのは、繋がったあとに出る差のほうです。

  1. ポートは3306ではなく4000。ここだけ変えれば mysql もPHPもそのまま繋がる TiDBがMySQLのプロトコル（通信の約束事）を実装しているからです。SELECT version() の答えも実測で載せます。

  3. Laravelを繋ぐには .env のDB設定6行を書き換える。それでも最初の migrate はエラー8256で落ちました 原因と、試した3通りの直し方の全ログを出します（この環境固有の条件も明記します）。

1TiDBは何のためのDBか

「1台に収まらない量」を、SQLのまま扱うための道具です

MySQLでデータが増えたとき、普通は困り方が2段階で来ます。①ディスクが足りない ②書き込みが1台では捌けない。

従来はアプリ側でテーブルを何台にも切り分けて（シャーディング）逃げます。TiDBは、その切り分けをデータベース側でやります。

  • 分散SQLデータベース。1台に収まらないデータを複数台へ自動で分けて置きながら、利用者からは1つのSQLデータベースに見えるようにしたものです。
  • MySQL互換。MySQL向けに書かれたSQL・ドライバ・GUIツールが、ほぼそのまま使えるように作られています（ほぼ、です。4章で差を全部出します）。
  • HTAP。Hybrid Transactional and Analytical Processing の略。注文登録のような小さく速い処理（OLTP）と、売上集計のような重い読み取り（OLAP）を1つのDBで受けることを指します。

公式ドキュメントの1行目が、そのまま定義になっています。

TiDB Docs「What is TiDB Self-Managed」— 原文
TiDB (/'taɪdiːbi:/, "Ti" stands for Titanium)
is an open-source distributed SQL database
that supports Hybrid Transactional and
Analytical Processing (HTAP) workloads. It is
MySQL compatible and features horizontal
scalability, strong consistency, and high
availability.

（TiDBは、HTAPワークロードに対応する
　オープンソースの分散SQLデータベース。
　MySQL互換で、水平スケーラビリティ・
　強い一貫性・高可用性を備える）
  • 読み方は「タイ・ディー・ビー」。発音記号が公式に書かれています。Ti は元素のチタン（Titanium）です。
  • 「水平スケーラビリティ」とは、台数を足して処理量を増やせること。1台を強いマシンに買い替える（垂直）の反対です。
バージョンの確認は「索引」ではなく「個別のリリースノート」で

2026年8月15日時点で、公式ドキュメントの stable（＝そのとき安定版として案内されている版のこと。URLの一部になっています）は v8.5系です。ただし公式サイトの中でも食い違いがあります。

実際に確認したこと
リリースノートの索引ページは 8.5.5（2026-01-15）を最新として並べています。しかし個別ページ release-8.5.7 は存在し（ページ取得が成功を意味する HTTP 200 で返る）、冒頭に Release date: July 9, 2026 と書かれています。8.5.8 は「ページなし」を意味する404でした。
教訓
索引ページは遅れることがあります。バージョンを記事や設計書に書くときは、個別のリリースノートを開いて日付を見てください。

2なぜMySQLクライアントでそのまま繋がるのか

TiDBが「MySQLプロトコル」を喋っているからです

プロトコルとは通信の約束事です。クライアントとサーバーが、どんな順番で何のバイト列をやり取りするかを決めた仕様のこと。

MySQLの場合、その約束事は「MySQL Client/Server Protocol」という名前で公開されています。Oracleの開発者向けドキュメントに、2段構えだと書かれています。

MySQL Source Code Documentation「MySQL Client/Server Protocol」— 原文
The protocol supports these features:
（中略：1・2番目はTLSとcompression）
A Connection Phase where capabilities and
authentication data are exchanged
A Command Phase which accepts commands from
the client and executes them

（能力と認証情報を交換する接続フェーズと、
　クライアントからのコマンドを受けて
　実行するコマンドフェーズ）

TiDBはこの約束事をそのまま実装しています。だから相手がMySQLかどうかを、クライアント側は気にしません。

TiDB Docs「Connect to TiDB with MySQL Tools」— 原文
TiDB supports the MySQL Client/Server
Protocol, which allows most client drivers
and ORM frameworks to connect to TiDB just as
they connect to MySQL.

（TiDBはMySQL Client/Server Protocolに
　対応しており、ほとんどのクライアント
　ドライバとORMがMySQLと同じように
　TiDBへ接続できる）
  • ORMとは、プログラムのオブジェクトとDBのテーブルを対応づける仕組み。LaravelのEloquentがこれにあたります。
  • そのまま使えるGUIツールも名指しされています。ただし出どころは別ページの「MySQL Compatibility」で、PHPMyAdmin, Navicat, MySQL Workbench, DBeaver and more と並んでいます（表記も原文のまま）。

詰まるのは1箇所だけ。ポートが3306ではなく4000

MySQLの既定ポートは3306、TiDBは4000です。ここを変え忘れるのが最初の関門です。実際にやってみました。

実行結果（TiDBだけ起動、MySQLは停止した状態）
-- port 3306 (MySQL の既定) ------------
NG
  SQLSTATE[HY000] [2002] Connection refu
  sed
-- port 4000 (TiDB の既定) -------------
OK version: 8.0.11-TiDB-v8.5.7

この Connection refused（接続を拒否された）は「そのポート＝窓口番号で誰も待っていない」という意味です。認証エラーでもファイアウォールでもありません。ポート番号を疑ってください。SQLSTATE はエラーの種類を表す5桁の標準コードで、HY000 は「その他」を意味します。

手元に立てる。1コマンドです

TiUPはTiDBのインストーラ兼管理ツール、tiup playground はお試し用のクラスタ（＝複数のプログラムが集まって1つのDBとして働く一式）をローカルに立てるコマンドです。ターミナル（黒い画面）に、そのまま1行打ちます。

TiDB Docs の例（Quick Start）
tiup playground v8.5.7 --db 2 --pd 3 --kv 3
  • --db がSQLを受けるプログラム、--kv がデータを持つプログラム、--pd が司令塔の台数です。--名前 値 という書き方をコマンドラインオプションと呼びます。
  • この 2 / 3 / 3 に意味はありません。公式ではこれは「版と台数を指定する書き方の例」として出てくるだけです。オプションを何も付けない tiup playground の既定は、TiDB・TiKV・PD・TiFlash が各1と書かれています。
  • 起動すると接続方法が画面に出ます。公式ドキュメントの案内は mysql --comments --host 127.0.0.1 --port 4000 -u root。
  • 既定では 127.0.0.1 でしか受けません。外から繋ぎたいときは --host を指定する、と公式に書かれています。

この記事の実測は、PHPの pdo_mysql（PHPからMySQL系DBへ繋ぐための標準の部品）から接続して取りました（mysql コマンドは使っていません）。使ったのは1台構成の --db 1 --kv 1 --pd 1 です。手順は _labs/2026-08-15_tidb-first/README.md に全部書いてあります。

macOSで ERROR 2059 が出たときは

公式ドキュメント「Connect to TiDB with MySQL Tools」に注意書きがあります。macOSのMySQL v9.0クライアントは mysql_native_password プラグインを正しく読み込めず、TiDBへの接続時に ERROR 2059 (HY000): Authentication plugin 'mysql_native_password' cannot be loaded が出る、と書かれています。公式の推奨はMySQL v8.0クライアントを入れて使うこと。この事象は手元では再現していません（Linux環境のため）。

3中身は3階建て — TiDB server / TiKV / PD

SQLを受けているプロセスは、データを1バイトも持っていない

プロセスとは、いま動いているプログラム1つ分のことです。MySQLは1つのプロセスがSQLの解釈もディスクへの書き込みも全部やります。TiDBは役割ごとに別プロセスに分かれています。

TiDB Docs「TiDB Architecture」— 原文
The TiDB server is a stateless SQL layer that
exposes the connection endpoint of the MySQL
protocol to the outside. ... It does not store
data and is only for computing and SQL
analyzing, transmitting actual data read
request to TiKV nodes (or TiFlash nodes).

（TiDB serverはステートレスなSQL層で、
　MySQLプロトコルの接続口を外に出す。
　データは保存せず、計算とSQL解析だけを行い、
　実際の読み取り要求はTiKV（またはTiFlash）へ
　転送する）
  • ステートレス＝そのプロセス自身が状態（データ）を持たないこと。持たないので、台数を増やす・減らす・落ちたら差し替える、が簡単になります。
  • だから2章の Store: tikv が出ます。「私の保存先はTiKVです」と名乗っています。

TiKV — テーブルも索引も、最後は巨大なキーと値の並び

TiKVはTiDBの実データを持つ保存層です。キーバリュー（鍵と値の組）で持ちます。しかもキー順に並べて持ちます。

TiDB Docs「TiDB Storage」— 原文
This is a huge Map (similar to std::Map in
C++), which stores Key-Value pairs. ...
The Key-Value pair in the Map is ordered
according to Keys' binary order

（これはキーと値の組を保存する巨大なMapで、
　組はキーのバイナリ順に並んでいる）

TiKV does not write data directly on the disk,
but stores data in RocksDB, which is
responsible for the data storage.

（TiKVはディスクへ直接書かず、
　RocksDBに保存を任せる）
  • RocksDBは、1台のマシン用の高速なキーバリュー保存エンジン。Facebook製です。TiKVはディスクへの実書き込みをこれに任せています。
  • 「キー順に並んでいる」は、あとで効いてきます。連番の主キーを使うと書き込みが一箇所に集中する理由が、これです（5章）。

Region — 256MiBで区切り、3つに複製し、過半数に書けたら成功

TiKVは、この巨大な並びをキーの範囲で切り分けます。この単位がRegionです。数字は公式に明記されています。

項目既定値意味
Regionのサイズ256 MiBデータを分ける単位
分割される閾値384 MiB超えると2つ以上に割れる
併合される閾値54 MiB下回ると隣とくっつく
複製の数3同じRegionを3台に置く
TiDB Docs「TiKV Overview」/「TiDB Storage」— 原文
These multiple replicas form a Raft group.
A replica of a Region is called a Peer.
Typically there are 3 peers in a Region.
One of them is the leader, which provides
the read and write services.

（複数の複製がRaftグループを作る。
　Regionの複製1つをPeerと呼ぶ。
　通常は3つで、うち1つがLeaderとなり
　読み書きを担当する）

However, according to Raft protocol,
successful writes only need that data is
replicated to the majority of nodes.

（Raftでは、過半数のノードに複製できれば
　書き込み成功とする）
  • Raftとは、複数台に同じ内容を同じ順番で書かせるための合意アルゴリズム。原論文はStanfordのOngaroとOusterhoutによるもので、アブストラクトでは合意の主要素を「リーダー選出・ログ複製・安全性といった要素」に分けて整理した、と書かれています（such as なので、この3つで全部という断定ではありません）。
  • 過半数＝3台なら2台。1台落ちても書き込みは成功し続けます。これが「高可用性」の中身です。
  • Store と Region は別物。Storeは保存ノード1つ（tikv-server プロセス1つ分）、Regionはデータの範囲です。混同しやすいので注意。
  • Learnerは投票しないFollower。Raftは「誰がLeaderか」を残りのノードの多数決（投票）で決めます。Learnerはその投票に参加せず、複製だけを受け取る見習い、と考えてください。

PD — できることは3つだけ。しかも命令ではなく「提案」

PD（Placement Driver）はクラスタの司令塔です。公式は "the brain" と書いています。担当は3つ。

  • メタデータの保管。メタデータとは「どのデータがどこにあるか」を書いた管理情報のこと。
  • トランザクション用の時刻（TSO）の払い出し。次の節で説明します。
  • データ配置の指示。偏ったら動かす、壊れたら作り直す。

最低3台、奇数台推奨と公式に書かれています。ここまでは想像どおりです。意外なのは、PDが出せる指示の種類です。

TiDB Docs「TiDB Scheduling」— 原文
All scheduling plans contain three basic
operators:
* Add a new replica
* Remove a replica
* Transfer a Region leader between replicas
  in a Raft group

（すべてのスケジューリング計画は
　3つの基本操作からなる:
　レプリカの追加／レプリカの削除／
　Raftグループ内でのリーダー移動）

Note that here "operators" are only
suggestions to the Region leader, which can
be skipped by Regions.

（これらの操作はRegionのリーダーに対する
　「提案」にすぎず、Region側が
　無視することもできる）
  • 司令塔ができるのは、複製を足す・減らす・リーダーを移す。それだけ。この3つの組み合わせで、負荷の偏りも故障も直します。
  • しかも強制ではありません。PDはTiKVから定期的に届くハートビート（生存報告）で状態を知り、提案を返します。Region側は従わないこともできます。
  • だから運用の勘所が変わります。「PDに命じたのにすぐ動かない」は異常とは限りません。

PDはもう1つ、時計係でもある

複数台に分かれたデータで「どちらの更新が先か」を決めるには、全員が同じ時計を見る必要があります。各サーバーのOS時刻はズレるので使えません。そこでPDが番号を配ります。これがTSO（Timestamp Oracle）です。

TiDB Docs「TimeStamp Oracle (TSO) in TiDB」— 原文
There are two parts in a TSO timestamp:
- The physical timestamp: a UNIX timestamp in
  milliseconds since 1 January 1970.
- The logical timestamp: an incrementing
  counter, used in scenarios requiring
  multiple timestamps within the same
  millisecond

（TSOは2つの部分からなる。
　物理時刻＝1970年1月1日からのミリ秒、
　論理時刻＝同一ミリ秒内で複数必要なときに
　使う増加カウンタ）
  • 1つの64bit整数に、時刻と連番が詰まっています。bitは数字を2進数で表したときの1桁のこと。公式ドキュメントによれば上位46bitが物理時刻（ミリ秒）、下位18bitが論理カウンタです。
  • これがトランザクションの前後関係を決めます。TiDBのトランザクションはGoogleのPercolatorというモデルを土台にしており、TSOはその要として説明されています。
公式ドキュメントに載っているTSOの覗き方（この記事では実行していません）
BEGIN;
SET @ts := @@tidb_current_ts;
ROLLBACK;
SELECT TIDB_PARSE_TSO(@ts);

この4行は手元で実行していないので、出力は載せません。公式ドキュメントには、TIDB_PARSE_TSO(443852055297916932) が 2023-08-27 20:33:41.687000 を返す例が載っています。

TiFlash — 集計を速くするためのもう1つの保存層

TiKVは行指向です。1件分（1行分）の項目をまとめて並べます。更新に向いています。

TiFlashは列指向です。同じ項目だけを縦に並べます。「金額の合計」のような集計で、要らない列を読まずに済みます。

どうやって同期しているのか
TiDBの原論文（VLDB 2020）のアブストラクトに書かれています。it asynchronously replicates Raft logs to learners which transform row format to column format for tuples, forming a real-time updatable column store（Raftログをlearnerへ非同期に複製し、learnerが行形式を列形式に変換して、リアルタイムに更新される列ストアを作る）。3章で出てきた「投票しないFollower＝Learner」が、ここで効いてきます。
今回は使っていません
実測は --tiflash 0（TiFlashなし）で行いました。列ストアの性能は測っていません。

ギャップロックが無い（公式ドキュメントの記述。この記事では未実測）

TiDBの公式ドキュメント「TiDB Pessimistic Transaction Mode」には、MySQL InnoDBとの差として次のように書かれています。

When TiDB executes DML or SELECT FOR UPDATE
statements that use range in the WHERE clause,
concurrent DML statements within the range are
not blocked.
...
This behavior is because TiDB does not
currently support gap locking.
何に効くか
Laravelの lockForUpdate() は SELECT ... FOR UPDATE を発行します。範囲条件で使って「この範囲に他から挿入されない」ことを前提にしているコードは、TiDBでは前提が崩れます。
ただし
この挙動差は今回測っていません。公式ドキュメントの記述として紹介するに留めます。実際の移行前には自分で並行トランザクションを流して確かめてください。なお同ドキュメントには「悲観トランザクション（＝MySQLと同じく、先にロックを取ってから更新する方式）が既定なのは v3.0.8 以降に新規作成したクラスタだけ」という但し書きもあります。

  • ID＝件数、と思っているコードは要注意。「最新のIDが1000だから1000件」は成り立ちません。
  • 複数のTiDB serverで運用すると、飛び方はさらに大きくなります。ただしこれは今回測っていません。手元は1台構成で、ALTER による採番器の作り直しで代替しました。

連番の主キーは、分散DBでは「一箇所に集中する」意味を持つ

3章を思い出してください。TiKVはデータをキー順に並べて持ち、キーの範囲でRegionに切ります。

主キーとは、その表の各行を1つに特定するための列です（多くは id）。主キーが連番だと、新しい行のキーは常にいちばん後ろのRegionに入ります。書き込みがそこ1つに集中します。これがホットスポットです。

TiDB Docs「AUTO_RANDOM」— 原文
Since the value of AUTO_RANDOM is random and
unique, AUTO_RANDOM is often used in place of
AUTO_INCREMENT to avoid write hotspot in a
single storage node caused by TiDB assigning
consecutive IDs.

（AUTO_RANDOMの値はランダムかつ一意なので、
　連続したIDによる単一ノードへの書き込み
　ホットスポットを避けるため、
　AUTO_INCREMENTの代わりによく使われる）

Laravelのマイグレーションで書く $table->id() は BIGINT UNSIGNED AUTO_INCREMENT の主キーです（上の SHOW CREATE TABLE がその証拠）。書き込みが多いテーブルほど、ここが効いてきます。

公式に載っている移行方法
ALTER TABLE t MODIFY COLUMN id BIGINT AUTO_RANDOM(5);
  • 条件があります。AUTO_RANDOM は BIGINT 列専用で、主キーに含まれ、かつ主キーの先頭列である必要があります。
  • 今回この移行は実行していません。公式ドキュメントの記述として紹介しています。
  • まず測るべきは、そのテーブルが本当に書き込みで詰まっているか。小さなアプリで先回りしてIDをランダム化する必要はありません（筆者の判断です）。
colopl/laravel-tidb を入れるべきか — 2026年8月時点では見送り

TiDB向けのLaravelドライバとして colopl/laravel-tidb というパッケージ（composer require で追加する外部部品）があります。コミュニティ製（PingCAP公式ではありません）で、$table->id() を AUTO_RANDOM に差し替えてくれます。ホットスポット問題への直球の回答です。

ただし、確認したところ2箇所の食い違いがありました。

1. 対応Laravelの版が合わない
Packagistのリリース一覧（repo.packagist.org のJSON）を取得すると、最新の v5.0.0（2025-05-02）は laravel/framework: ~12 と php: >=8.2 を要求します。一方で同じ v5.0.0 タグのREADMEには「PHP >= 8.0 / Laravel 11」と書かれています。現行のLaravelは13系なので、Laravel 13では入らない見込みです（実際に composer require は試していません）。
2. SAVEPOINTの記述が古い
READMEの「Unsupported features」に SAVEPOINT is not supported by TiDB と書かれています。しかしTiDB公式は SAVEPOINT is a feature introduced in TiDB v6.2.0 と明記しており、今回の実測でも TiDB v8.5.7 で SAVEPOINT は通りました（4章の互換表）。LaravelのネストしたトランザクションはSAVEPOINTで実装されるので、ここは死活問題です。
リポジトリのメンテ状況は未確認
GitHubのHTMLページはこの環境から403で開けず、スター数・最終コミット日・Issueの状況は確認できていません。READMEの中身は raw 経由で読んでいます。
結論（筆者の判断）
まずは素の mysql ドライバで始める。AUTO_RANDOM が必要になったら、マイグレーションで DB::statement() を書くか、そのときのパッケージの対応状況を見直す。
外部キーは使える。ただし公式が性能の警告を出している

「TiDBは外部キーが使えない」という説明を見かけますが、v8.5では違います。4章の実測でも外部キーは OK OK でした。

TiDB Docs「FOREIGN KEY Constraints」— 原文
Starting from v6.6.0, TiDB supports foreign
keys and foreign key constraints. Starting
from v8.5.0, this feature becomes generally
available.

Warning: The foreign key feature ... might
cause performance degradation, so it is
recommended to conduct thorough testing
before using it in performance-sensitive
scenarios.

GA（Generally Available）は「実験段階を抜けて、本番で使ってよい正式機能になった」という意味です。Laravelの foreignId()->constrained() は外部キーを張るので、この点は重要です。性能への影響は今回測っていません。
