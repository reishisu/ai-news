Unity WebのビルドをAWSで配ってもらう — COOP/COEP/CORPの依頼先

自社がUnity Webを作り、別会社がAWSで配る構成の話です。「ヘッダーを付けてください」をどこの誰に、何と言って頼むか。AWS公式ドキュメントの原文と、手元の実測で詰めます。
⏱ 約12分 会社をまたぐ連携 そのまま送れる依頼票つき

⭐ 3行で言うと

Unity Webのマルチスレッドには、配信サーバーが返す3本のHTTPヘッダーが要ります。ヘッダーはビルド成果物の中には入りません。自社ではどうやっても付けられないので、インフラ会社に頼むしかありません。

  1. ALBには、その3本を足す機能がありません ALBが追加できるレスポンスヘッダーは、属性名で決められた10種だけ。公式ドキュメントを取得して数えました。COOP/COEP/CORPは0件です。
  2. 正解はCloudFrontの「レスポンスヘッダーポリシー」のカスタムヘッダー AWS既製のマネージドポリシー5種には入っていません。新規に作ってもらう必要があります。
  3. 一番怖いのは、両社が親切心で付けたとき COEPが2つ並ぶと、HTML仕様の処理モデルは unsafe-none に落ちます。エラーは1件も出ず、ただ動かなくなります。

1依頼を出す前に — 公式は「無効推奨」と書いています

まず用語。ヘッダーが要るのは「あるトグルをONにしたビルド」だけです

先に言葉を揃えます。全部1行で説明します。

  • Unity Web ビルド（旧称 WebGLビルド）。Unityで作ったゲームを、ブラウザでそのまま遊べる形（HTML＋JavaScript＋WebAssembly＋データファイル）に書き出したもの。
  • WebAssembly（Wasm）。ブラウザが高速に実行できる、機械語に近い形式のプログラム。C/C++やC#で書いたコードをこの形に変換して動かします。
  • スレッド。プログラムの処理の流れのこと。複数同時に走らせて速くするのがマルチスレッドです。
  • HTTPレスポンスヘッダー。サーバーがファイル本体と一緒に返す短い指示書き。「これはWasmです」「この方針で扱ってください」などを伝えます。ファイルの中身ではないので、Unity側からは付けられません。

この記事のヘッダー3本が必要になるのは、Unityの Player 設定で「Enable Native C/C++ Multithreading」をONにしたビルドだけです。Player 設定は Unity の Edit → Project Settings → Player にあります。

そして、そのトグルの説明文はこうです。原文をそのまま貼ります。

Unity Manual 6.3 LTS「Web Player settings」— 原文
Enable this option to use the native Unity C/C++
engine code that targets WebAssembly/SharedArrayBuffer
multithreading (experimental). If this setting is
enabled, the server configuration needs to set
Cross-Origin Opener Policy (COOP), Cross-Origin
Embedded Policy (COEP), and Cross-Origin Resource
Policy (CORP) headers.
...
It's recommended to disable this option and use it
only for evaluating future web features.

（この設定を有効にすると、WebAssembly/SharedArrayBuffer
　マルチスレッドを対象とするネイティブUnity C/C++
　エンジンコードを使う（実験的）。有効にした場合、
　サーバー設定でCOOP/COEP/CORPヘッダーを
　設定する必要がある。……このオプションは無効にし、
　将来のWeb機能の評価目的にのみ使うことを推奨する）
  • (experimental) と書いてあります。さらに It's recommended to disable this option（無効にすることを推奨）とまで書かれています。
  • だから依頼の前に、社内の合意が要ります。「本番で実験的な設定をONにする」という判断です。インフラ会社に作業を頼んだあとで「やっぱりOFFで」となると、相手の工数が丸ごと無駄になります。
  • C#のスレッドは、ヘッダーを付けても動きません。同じマニュアルの Technical limitations に Managed (C#) threads aren't supported due to the lack of a multithreaded garbage collection feature in WebAssembly. とあります。速くなるのはUnityエンジン内部のC/C++処理だけです。

Q. このヘッダー3本を付けてもらうと、ゲーム内の System.Threading.Thread は動くようになる?

正解。「そのためのヘッダーだから」と思うのは自然ですが、Unityマニュアルは managed (C#) threads は非対応と明記しています。理由はWebAssemblyにマルチスレッド対応のガベージコレクション機能が無いためです。「マルチスレッドを有効にしたのにゲームロジックが速くならない」は仕様どおりで、インフラ会社の設定ミスではありません。ここを取り違えると、無実の相手を疑うことになります。

そもそも、なぜヘッダーなんて面倒なものが要るのか
SharedArrayBuffer が封じられた経緯
複数のスレッドが「同じメモリ」を直接読み書きするための入れ物が SharedArrayBuffer です。Wasmのマルチスレッドはこれが無いと成立しません。MDNの SharedArrayBuffer のページには Shared memory and high-resolution timers were effectively disabled at the start of 2018 in light of Spectre. In 2020, a new, secure approach has been standardized to re-enable shared memory. とあります。Spectre は2018年に公表されたCPUの脆弱性で、同じプロセスにある他サイトのデータを盗み見できる恐れがありました。
復活の条件が、あの3本
同ページは To use shared memory your document must be in a secure context and cross-origin isolated. と続けます。「セキュアコンテキスト（HTTPSまたはlocalhost）」かつ「クロスオリジン分離」の2条件です。この2条件目に入るための宣言が COOP と COEP、そして分離状態のページから読み込まれる素材側の許可表明が CORP です。
だから配信側の仕事になる
ヘッダーは「ファイルと一緒に返す指示書き」なので、返す側＝配信サーバーにしか書けません。Unityのビルド設定をいくらいじっても、この3本は付きません。

2ALBには「そのヘッダーを足す」機能が無い

「ALBで足しておいてください」は、原理的に通らない依頼です

ALB（Application Load Balancer）は、AWSの負荷分散装置です。届いたリクエストを複数のサーバーに振り分けます。

ALBはレスポンスヘッダーを足す機能を持っています。持っているのですが、足せる種類があらかじめ決まっています。任意の名前のヘッダーは指定できません。

ALBの設定は「リスナー属性」という名前と値の組で行い、属性名そのものがヘッダー名に対応しています。つまり属性名が用意されていないヘッダーは、存在しないのと同じです。

推測はやめて、AWS公式ドキュメントから属性名を全部抜き出します。AWSのドキュメントは末尾を .md にすると、装飾なしのテキストで取得できます。

alb_attrs.sh — ALBのレスポンス側リスナー属性を全部抜く
#!/bin/bash
U=https://docs.aws.amazon.com\
/elasticloadbalancing/latest/application

curl -sS "$U/load-balancer-listeners.md" \
  | grep -o 'routing\.http\.response\.[a-z_]*' \
  | sed 's/routing.http.response.//'

echo "--- COOP/COEP/CORP の出現回数 ---"
curl -sS "$U/load-balancer-listeners.md" \
  | grep -ci 'cross-origin-'

curl はURLを叩いて中身を表示するコマンド、grep -o は一致した部分だけを抜き出す道具、sed は文字列を置き換える道具です。長い接頭辞 routing.http.response. は全部同じなので消しています。ターミナル（WindowsならWSLやGit Bash）で実行します。

  • 紛らわしいのは access_control_* の6個です。これはCORS（JavaScriptから別オリジンのAPIを呼ぶための仕組み）用のヘッダーで、名前は似ていますがまったくの別物。ここを「CORS対応があるからCOOPも行けるはず」と読むと詰まります。

AWSの説明文も、足せるものを列挙する書き方になっています。

AWS「HTTP header modification」— 原文
Using insert headers, you can configure your Application
Load Balancer to add security-related headers to responses.
With these attributes, you can insert headers including
HSTS, CORS, and CSP.

（挿入ヘッダーを使うと、ALBにセキュリティ関連の
　ヘッダーを応答へ追加させられる。これらの属性で
　HSTS・CORS・CSPを含むヘッダーを挿入できる）

HSTS・CORS・CSP。そこにクロスオリジン分離の3本は含まれていません。

ALBの後ろがnginxやApacheなら、そこで付けられます

ALB自体は無理でも、ALBが振り分けた先（EC2やECS上のnginx / Apache）でなら付けられます。Unity公式が設定例を出しています。

Unity Manual「Set up your Nginx server configuration for Web builds」— 原文
location ~ .+\.(htm|html|js|js\.gz|js\.br)$ {
    add_header Cross-Origin-Opener-Policy same-origin;
    add_header Cross-Origin-Embedder-Policy require-corp;
    add_header Cross-Origin-Resource-Policy cross-origin;
}

Apache版も同じ3本を <FilesMatch "\.(htm|html|js|js.gz|js.br)$"> の中で Header add しています。どちらも .wasm や .data には付けていない点に注意してください。COOPとCOEPは「読み込む側のドキュメント」に効くヘッダーなので、HTMLとJSに付けば足ります。

ただし前段にCloudFrontを置くなら、ここで付けてはいけません。理由は4章です。

3正解はCloudFrontのレスポンスヘッダーポリシー

依頼先はここ。画面の場所も、Terraformの差分も特定できます

CloudFrontはAWSのCDNです。CDN（コンテンツ配信ネットワーク）は、世界中の拠点に配信サーバーを置いて、利用者に近い場所からファイルを返す仕組みのこと。Unity Webの成果物を S3（AWSのファイル置き場）に置き、CloudFrontから配るのが定番の構成です。

ここで言葉が1つ衝突します。AWSは「CDNから見た配信元（S3やALBなど）」のことをオリジンと呼びます。6章で出てくるブラウザ用語の「オリジン」（https://example.com:443 のような組）とはまったく別の意味です。以下、この章と4章の「オリジン」はAWS側の意味、つまり配信元のことだと思って読んでください。

CloudFrontには返すときにヘッダーを足す・消すをまとめた設定があります。これがレスポンスヘッダーポリシーです。AWSの説明文が、そのまま責任分界点の説明になっています。

AWS「Add or remove HTTP headers in CloudFront responses with a policy」— 原文
CloudFront can remove headers that it received from the
origin, or add headers to the response, before sending
the response to viewers. Making these changes doesn't
require writing code or changing the origin.

（CloudFrontは、配信元から受け取ったヘッダーを消したり、
　応答にヘッダーを足したりしてから閲覧者に送れる。
　この変更にコードを書く必要も、配信元を変える必要もない）

コードを書く必要も、配信元を変える必要もない。裏を返すと、こちらがビルドを作り直しても1ミリも変わらない領域だということです。「ビルドし直したのに直りません」は、この構成では起こるべくして起こります。

AWS既製のポリシーには入っていません。ここが一番の落とし穴です

CloudFrontにはマネージドポリシー（AWSがあらかじめ用意した既製の設定）があります。「セキュリティヘッダーのポリシーを当てておけば入るのでは」と考えたくなりますが、入っていません。

AWS CLI（AWSをコマンドで操作する道具）には、--generate-cli-skeleton という「入力JSONの雛形だけ出す」オプションがあります。AWSに接続しないので、認証情報が無くても実行できます。これでポリシーの枠組みを見ます。

  • マネージドポリシーは5種類あります。AWS公式ドキュメントを取得して確認したところ、CORS-and-SecurityHeadersPolicy / CORS-With-Preflight / CORS-with-preflight-and-SecurityHeadersPolicy / SecurityHeadersPolicy / SimpleCORS の5つで、COOP・COEP・CORPの記述は1件もありません（grep -ci で0件）。
  • だから Header / Value / Override の3項目からなる「カスタムヘッダー」の枠に、自分で書いてもらいます。依頼の要点は、まさにこの3項目です。

画面ならこの順。コンソールの場所まで書きます

相手会社がコンソール（ブラウザで操作するAWSの管理画面）で作業する場合の手順です。AWS公式の手順に沿っています。

  • ① CloudFrontコンソールの「Policies」ページ → 「Response headers」タブ。ここで Create response headers policy を押します。
  • ② Details パネルで名前を入力。あとで探せるように unity-web-coi のような名前を決めておくと、両社の会話が速くなります。
  • ③ Custom headers パネルに3本を追加。Security headers パネルではありません。ここが間違えやすいところです。
  • ④ Create を押したあと、Distributions → 対象 → Behaviors タブ → 対象のビヘイビアを Edit → Response headers policy で選ぶ。作っただけでは何も起きません。キャッシュビヘイビアに紐づけて初めて効きます。

キャッシュビヘイビアとは、「/game/* はこの設定で配る」のようにパスごとに挙動を決める設定単位のことです。ポリシーはこの単位に紐づくので、ゲームを置いたパスだけに限定して依頼できます。サイト全体を巻き込まずに済むので、相手会社の心理的な抵抗もかなり下がります。

Terraformで管理しているなら、差分は3ブロックです

Terraformは、サーバー設定をコードで書いて管理する道具です（IaC＝Infrastructure as Code）。相手会社がこれで管理しているなら、依頼はコードの差分として渡すのが一番速い。実際に書いて動かしたものを載せます。

main.tf（抜粋）— CloudFrontのレスポンスヘッダーポリシー
resource "aws_cloudfront_response_headers_policy" "unity_web" {
  name    = "unity-web-coi"
  comment = "COOP/COEP/CORP for Unity Web multithreading"

  custom_headers_config {
    items {
      header   = "Cross-Origin-Opener-Policy"
      value    = "same-origin"
      override = true
    }
    items {
      header   = "Cross-Origin-Embedder-Policy"
      value    = "require-corp"
      override = true
    }
    items {
      header   = "Cross-Origin-Resource-Policy"
      value    = "cross-origin"
      override = true
    }
  }
}

4両社で付けると、無言で解除される

会社をまたぐ構成で一番起きやすい事故。しかもエラーが出ません

こういう流れです。

  • ① こちらが「COOP/COEP/CORPを付けてください」と依頼する。
  • ② インフラ会社が、オリジン（ECS上のnginxなど）に3本を追加する。Unity公式のnginx設定例を見つけて、素直にその通りにやってくれた。
  • ③ 動かない。もう一度依頼する。
  • ④ 別の担当者が、今度はCloudFrontのポリシーにも3本を追加する。「念のため両方に入れておきました」
  • ⑤ さらに動かなくなる。

両方から返るので、レスポンスには Cross-Origin-Embedder-Policy が2つ並びます。ブラウザはこれを require-corp, require-corp という1つのリスト値として読み、そして効力を捨てます。

推測ではありません。HTML仕様が、まさにこの事故を表にして載せています。

WHATWG HTML Living Standard §7.1.4.1 — 原文
The processing model fails open (by defaulting to
"unsafe-none") in the presence of a header that cannot
be parsed as a token. This includes inadvertent lists
created by combining multiple instances of the
`Cross-Origin-Embedder-Policy` header present in a
given response:

  No header delivered        → "unsafe-none"
  require-corp               → "require-corp"
  unknown-value              → "unsafe-none"
  require-corp, unknown-value→ "unsafe-none"
  unknown-value, require-corp→ "unsafe-none"
  require-corp, require-corp → "unsafe-none"

（トークンとして解釈できないヘッダーがある場合、
　処理モデルは "unsafe-none" にフォールバックして
　「開く」方向に倒れる。これには、同一レスポンスに
　COEPヘッダーが複数存在して意図せずリストに
　なった場合も含む）

表の最終行を見てください。require-corp, require-corp → unsafe-none。正しい値を2回付けると、1回も付けなかったのと同じになります。

これはfail open（フェイルオープン）と呼ばれる挙動です。設定が壊れていたときに、安全側ではなく「制限なし」の側に倒れます。MDNも独立に同じことを1文で書いています。

MDN Web Docs「Cross-Origin-Embedder-Policy」— 原文
The header should only be set with just one token and an
optional report-to endpoint. Setting the header more than
once or with multiple tokens is equivalent to setting
unsafe-none.

（このヘッダーは1つのトークンと任意のreport-toだけで
　設定すべき。複数回設定したり複数トークンを与えたり
　すると unsafe-none を設定したのと同じになる）

Q. 両社が正しい値を付けた結果、ゲームが起動しなくなった。ブラウザのコンソールには何が出る?

正解。仕様は「unsafe-none にフォールバックする」としか定めておらず、重複を咎める仕組みがありません。ヘッダーは確かに返っているのに、効いていない状態です。だから両社とも「うちは正しく設定した」と主張でき、原因究明が長引きます。切り分けの第一手は、ヘッダーが「付いているか」ではなく「何個付いているか」を見ることです。

だから、付ける場所は1箇所に決めて文書に残す

CloudFrontを挟む構成なら、CloudFrontのカスタムヘッダーだけで付ける。オリジン側では付けない。これを決めて、依頼票に明記します。

それでもオリジン側で付いてしまう可能性がある場合（既存の設定が残っている、Laravelのミドルウェアが付けている等）に備えて、Origin override を true にしてもらいます。AWSの説明はこうです。

AWS「Understand response headers policies」Custom headers — 原文
When this setting is set to `true` and the origin response
contains the custom header that's in the policy, CloudFront
adds the custom header in the policy to the response that
it sends to the viewer. It ignores the header that it
received from the origin.

（この設定が true で、配信元の応答にポリシー内の
　カスタムヘッダーが含まれている場合、CloudFrontは
　ポリシー側のヘッダーを応答に足し、配信元から
　受け取ったヘッダーは無視する）
  • 「無視する」であって「並べる」ではありません。だから override = true にしておけば、オリジン側の付け忘れ・付けすぎの両方から守れます。
  • false だと、オリジン側の値が優先されます。オリジンが付けていない場合はポリシー側が使われるので、一見どちらでも動きます。あとからオリジン側に設定が増えた瞬間に壊れるのが false の怖いところです。
  • 3章のTerraformで override = true を3本とも書いているのは、この理由です。

切り分けのコマンド。1行で「何個付いているか」が分かります

ターミナルに貼る（URLは自分のゲームのHTMLに置き換える）
curl -sSI "https://例.com/game/index.html" | grep -ci "^cross-origin-embedder-policy:"
  • -I はヘッダーだけ取るオプション。本体をダウンロードしないので一瞬で終わります。
  • 結果が 1 なら正常。2 以上なら、この章の事故です。0 なら、そもそも付いていません。
  • ブラウザ側では crossOriginIsolated で見ます。ページを開いてDevTools（Chromeなら F12）の Console タブに crossOriginIsolated と打ち、true が返れば分離できています。

5同じ依頼票に書く、圧縮とContent-Type

COOP/COEP/CORPだけ直しても、たぶんまだ起動しません

Unity Webの配信には、もう2種類のヘッダーが要ります。依頼を分けると往復が増えるだけなので、同じ票に書いてしまいます。Unity公式の記述です。

Unity Manual「Deploy a Web application」— 原文
To make the browser perform decompression natively while
it downloads your application, append a Content-Encoding
header to the server response. This header must correspond
to the type of compression Unity uses at build time.
...
For WebAssembly streaming compilation to work, the server
needs to return WebAssembly files with an application/wasm
MIME type.

（ダウンロード中にブラウザ側で解凍させるには、
　サーバー応答に Content-Encoding ヘッダーを足す。
　ビルド時にUnityが使った圧縮方式と一致させること。
　……WebAssemblyストリーミングコンパイルを働かせるには、
　サーバーがWasmファイルを application/wasm という
　MIMEタイプで返す必要がある）
  • Content-Encoding。「この中身はgzip（または br）で圧縮してあります」と伝えるヘッダー。Unityは .gz / .br という拡張子でビルド成果物を出しますが、拡張子はブラウザには何の意味も持ちません。
  • Content-Type（MIMEタイプ）。「これはWasmです」という中身の種別表示。Wasmは application/wasm。これが無いと、ダウンロードしながら同時にコンパイルする高速化（ストリーミングコンパイル）が働きません。
  • Brotli（.br）とgzip（.gz）。どちらもファイルを小さくする圧縮方式で、Brotliのほうが小さくなります。

間違えたときにブラウザが出すエラーを、全部並べました

aws s3 cp は Content-Encoding を絶対に付けません

「S3に上げるだけならヘッダーは勝手に付くのでは」と思うところですが、片方しか付きません。AWS CLI（1.46.0）のソースコード awscli/customizations/s3/utils.py の338〜344行を開いて確認しました。

utils.py:338-344
def guess_content_type(filename):
    """Given a filename, guess it's content type.

    If the type cannot be guessed, a value of None is returned.
    """
    try:
        return mimetypes.guess_type(filename)[0]

Pythonの mimetypes.guess_type() は (種別, 符号化) の2つ組を返します。app.wasm.br なら ('application/wasm', 'br') のように、圧縮方式まで分かっています。ところがAWS CLIは [0] しか使わず、[1] を捨てています。

ContentEncoding が設定されるのは、同ファイル579行目の変換表に沿って --content-encoding を明示したときだけです。同じ関数をローカルで呼んで確かめました。

実行結果（S3には上げていません。CLIの関数をローカルで呼んだだけ）

  ※mimetypesの符号化推測: br

  • Content-Type は付きます。.wasm.br でも application/wasm になりました。ここは助かります。
  • Content-Encoding は付きません。「符号化推測: br」と分かっているのに、捨てられています。そのままS3に上げると、5章の expected magic word エラーになります。
  • .data.br は Content-Type すら付きません。Pythonが .data を知らないため、S3の既定値（binary/octet-stream）になります。
  • これは「アップロード手順の話」なので、依頼票に書く価値があります。相手会社が aws s3 sync でデプロイしているなら、--content-encoding を指定するか、拡張子ごとに分けて上げてもらう必要があります。

なおCloudFront側で自動圧縮を有効にしていても、二重圧縮にはなりません。AWSの説明です。

AWS「Serving compressed files」— 原文
When a response from an origin includes the
Content-Encoding header, CloudFront doesn't compress the
object, regardless of the header's value.

（配信元からの応答に Content-Encoding ヘッダーが
　含まれる場合、CloudFrontはその値にかかわらず
　オブジェクトを圧縮しない）

つまりオリジン（S3のメタデータ）で正しく申告できていれば、CloudFrontは手を出しません。逆に言えば、申告漏れのファイルはCloudFrontが勝手に圧縮しようとして、話がさらにややこしくなります。

6検証環境で必ず踏む2つの罠

罠1: http:// のIP直打ちだと、ヘッダーが完璧でも false

インフラ会社が「まず検証環境で試しましょう」と、証明書なしの http://203.0.113.10/ のようなURLを用意してくれることがあります。ここでは絶対に再現しません。

同じHTML・同じ3本のヘッダーで、localhost と IP直打ちのhttp を比べた実測です。

WHATWG HTML Living Standard §7.1.3.1 — 原文

an environment reservedEnvironment:
  1. Let policy be a new opener policy.
  2. If reservedEnvironment is a non-secure context, then

罠2: 資産を別ドメインのCDNに置くと、fetch だけ落ちます

COEPを有効にしたページは、許可を明示していない別オリジンの素材を読み込めなくなります。ここでの許可の出し方が、取得方法によって違いました。

用語の整理です。オリジンとは https://example.com:443 のようなスキーム＋ホスト＋ポートの組。ブラウザはこの単位でサイトを別物として扱います。ページと素材でオリジンが違えばクロスオリジンです。

実行結果（COEP有効ページから、別オリジンの素材を読む）
■ COEPページ→別オリジンをfetch

     CORP: cross-origin
     TypeError: Failed to fetch

     1:8822/corp/app.wasm' from origin '
     http://127.0.0.1:8821' has been blo
     cked by CORS policy: No 'Access-Con

     LOCKED_BY_RESPONSE.NotSameOriginAft

  OK CORPのみ
     CORP: cross-origin

  • <script src> は CORP だけで通ります。CORP（Cross-Origin-Resource-Policy）は、読み込まれる側のファイルに付けて「別オリジンから読み込まれてもよい」と表明するヘッダー。値は cross-origin。
  • fetch() は CORP だけでは通りません。CORSの Access-Control-Allow-Origin が別途要ります。CORPとCORSは名前が似ているだけで別物です。
  • NotSameOriginAfterDefaultedToSameOriginByCoep というエラー名を覚えてください。これが出たら「COEPを付けたせいで別オリジンの素材が落ちた」というサインです。

つまり、ゲームのページと同じCloudFrontディストリビューションから全部配るのが一番安全です。別ドメインの広告タグ・アクセス解析・フォントを埋めている場合は、COEPを入れた瞬間にそれらが落ちる可能性があります。これはインフラ会社ではなく、こちら側が事前に洗い出すべきリストです。

いきなり本番に入れず、影響だけ先に測る方法

COOPとCOEPには -Report-Only 版のヘッダーがあります。Report-Only ヘッダーとは、本番の挙動は変えず「もし有効にしたら何が壊れるか」だけを報告させるお試しモードのことです。

先に付けてもらうヘッダー（挙動は変わりません）
Cross-Origin-Opener-Policy-Report-Only: same-origin
Cross-Origin-Embedder-Policy-Report-Only: require-corp

会社をまたぐ変更では、これを1段目の依頼にすると話が通りやすくなります。「本番の挙動は変わりません、レポートを取るだけです」と言えるからです。壊れる箇所が0だと確認できてから、本番のヘッダーに切り替えます。

なお、この段階的な進め方はweb.devの解説（2021年2月更新）で紹介されているもので、この記事では実際にレポートを収集していません。レポート送信先の設定まで含めた動作は未確認です。
