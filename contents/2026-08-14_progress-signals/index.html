聞いても出てこないのは、その人が不誠実だからではありません。これには名前と査読論文があります。

Park, Im, Keil (2008) JAIS 9(7) — 原文
The mum effect - a project member's reluctance
to report bad news about a troubled project -
has been recognized as an important contributor
to project failure.

（マム効果——難航しているプロジェクトについて
　悪い知らせを報告することへのメンバーの

同じ論文は、先行研究の結果をこうまとめています。差し迫った失敗の証拠は、近くにいる人には明白でありうる（原文は "may be apparent"）。なのに、それが階層を上がらない。上がっても歪む。

いちばん効くのは、監視役として職務を与えられている人の言葉です。以下はPark らの本文が引用している Keil and Robey (2001) の被験者の発言で、原典そのものは今回読めていません（孫引き）。

Park らが引用する社内の情報システム監査人の発言
Me as a little staff auditor? ... I sure wouldn't
want to march into this guy's office and tell him
the project that he had been championing for all
these years should be put to death

（一介のスタッフ監査人の私が？…彼が何年も推進
　してきたプロジェクトを葬るべきだと、その人の
　オフィスに乗り込んで告げるなんて、絶対に
　やりたくない）
  • 報告を職務にしている人ですら黙ります。だから「言ってくれれば助けたのに」は成立しません。言える設計になっていないだけです。
  • 心理的安全性を高める、では今日は動きません。明日の朝までに結果が出る打ち手が要ります。

さらに、燃え尽きの定義そのものが「言い出せなさ」を含んでいます。WHOのICD-11（世界保健機関が作る国際疾病分類の第11版）の定義は3つの次元からなります。

WHO「Burn-out an "occupational phenomenon"」— ICD-11の定義
feelings of energy depletion or exhaustion;

increased mental distance from one's job, or
feelings of negativism or cynicism related to
one's job; and

reduced professional efficacy.

（エネルギーの枯渇または消耗の感覚／自分の仕事
　に対する心理的距離の増大、あるいは仕事に
　関連する否定的・皮肉的な感情／職業上の
　効力感の低下）

3つ目の「職業上の効力感の低下」。ここから先は筆者の解釈ですが、効力感が下がっている人ほど「進んでいません」と言い出しにくいはずです。いちばん見つけたい人ほど、いちばん申告しない。

WHOはバーンアウトを病気と認定していません
公式リリースの原文
"It is not classified as a medical condition."（医学的疾患としては分類されていない）。収載先は「健康状態や保健サービスの利用に影響する要因」の章です。「WHOが疾病認定」と書く記事は一次資料と食い違います。
職業文脈に限定されている
"Burn-out refers specifically to phenomena in the occupational context and should not be applied to describe experiences in other areas of life."（職業上の文脈における現象を特指し、人生の他の領域には適用すべきでない）
この論文の限界
Park らの研究は統制された実験室実験で、被験者は学生（平均22.8歳・平均実務経験2.6年）です。論文自身が "While the use of student subjects can limit the generalizability of results"（学生被験者の使用は結果の一般化可能性を制限しうる）と限界を明記しています。約60%が実務経験1年以上、モデルの説明力は従属変数の分散の32%。現場の観察データではありません。

同じ論文には、対策側のヒントもあります。「欠陥が納品されて影響が出始める前に、修正できる時間の窓が狭い」ことを強調すると、報告する意欲が上がる、という結果です。窓が閉じかけていることを先に見せる。これが次章につながります。

3代わりに見る信号は「時間」だと決まっている

Kanban Guideは、追跡が必須のメトリクスを4つ名指ししている

「何を見ればいいか」は、すでに一次資料で決まっています。Kanban Guide v2025.5（カンバン＝作業を見える化して流れを管理するやり方の、公式ガイド）の原文です。

Kanban Guide v2025.5 — Flow Metrics 原文
The four mandatory flow metrics to track in
Kanban are:

WIP: The number of work items started but not
finished.

Throughput: The number of work items finished
per unit of time. Note the measurement of
throughput is the exact count of work items.

Work Item Age: The elapsed time between when a
work item started and the current date.

Cycle Time: The elapsed time between when a work
item started and when a work item finished.
指標定義（訳）
WIP着手済みだが未完了の作業アイテム数
Throughput単位時間あたりに完了した作業アイテム数
Work Item Age着手された時点から現在日までの経過時間
Cycle Time着手から完了までの経過時間

この中で「この1本が何時間詰まっているか」を測れるのは Work Item Age だけです。Throughput も Cycle Time も、終わったものしか数えられません。WIPは未完了を扱いますが「何本あるか」の本数なので、誰が詰まっているかは分かりません。

つまり「詰まっている人を、本人が言い出す前に見つける」に対応する信号は、仕様上ほぼ一択です。着手からの経過時間。

いつ動くかは、過去の自分たちの実績から出す

では何時間で声をかけるのか。ここも決められています。SLE（サービスレベル期待値）——過去の実績から出す「たいていこれくらいで終わる」の線です。段落を途中で切らず、全文を貼ります。

Kanban Guide v2025.5 — Definition of Workflow 原文（全文）
A service level expectation (SLE), which is a
forecast of how long it should take a work item
to flow from started to finished. The SLE itself
has two parts: a period of elapsed time and a
probability associated with that period (e.g.,
"85% of work items will be finished in eight days
or less"). The SLE should be based on historical
cycle time and, once calculated, should be
visualized on the DoW. If historical cycle time
data does not exist, a best guess will do until
there is enough historical data for a proper SLE
calculation.
  • SLEは「期間＋確率」の2部構成。「8日」ではなく「85%が8日以内」。ここを削ると目標に化けます。
  • 85%点＝並べるだけで出る値。過去の数字を小さい順に並べ、下から85%の位置にある値を取ります。8件なら ceil(0.85×8)=7 で7番目。人が決める余地はありません。
  • 過去のサイクルタイムに基づけ、と書かれています。ただし文はここで終わりません。履歴が無ければ "a best guess will do"（当て推量で構わない）とガイド自身が続けています。「履歴が無いから出せない」はガイドの立場ではありません。
  • 使い道も書かれています。"Ensuring work items do not age unnecessarily, using the SLE as a reference."（SLEを基準に、アイテムが不必要に滞留しないようにする）

Q. 「85%が8日以内」というSLEを、社内標準として「全タスク8日以内」と言い換えた。何が壊れる?

正解。SLEは過去の実績から出た「予測」です。確率を落とすと予測が目標になります。DORAの公式ガイドは、まさにこれを落とし穴として名指ししています（"Setting metrics as a goal" / グッドハートの法則＝測るものを目標にすると、人はその数字を作りにいく）。詳しくは第6章で。

4実測：7日決め打ちは0件、SLEは1件

まず、止まっている枝が本当にあるか確かめる

対象はこのサイトのリポジトリです。gitの標準コマンドだけで見ます。

ここから用語が増えるので、先に4つだけ開きます。gitでは作業を枝（ブランチ）に分けて進め、終わったら本体の幹に合流させます。合流させる操作がマージ、保存1回ぶんの記録がコミットです。「未統合の枝」＝まだ幹に合流していない作業のこと。以降の出力はこれで全部読めます。

実行結果（2026年8月14日 15:18 UTC 実測）
$ git branch -r --no-merged origin/main
  origin/claude/add-popular-json

$ B=origin/claude/add-popular-json
$ git rev-list --left-right --count \
    origin/main...$B
8	1

出力の 8 1 は左が幹（origin/main）側、右が枝側の数です。つまり未統合の枝が1本あり、自前1コミットのまま、幹に8コミット置いていかれている状態です。

「N日以上動いていない」という決め打ちを、この実データに当てる

停滞検出のスクリプトは、たいてい「N日以上動いていない枝」を探します。Nは日数の決め打ちです。実例として、GitHub公式の actions/stale は無活動と見なすまでが60日、そこから閉じるまでが7日と宣言しています。

actions/stale の action.yml — 原文（既定値）
days-before-stale:
  default: '60'
days-before-close:
  default: '7'

60でも7でも、そのリポジトリの速度とは無関係な固定値である点は同じです。本記事の「7日」は、この決め打ちを再現するために筆者が置いた値（stale_v1.sh の DAYS=7）で、actions/stale 由来ではありません。同じ枝に当てます。

実行結果 — 7日決め打ち版（15:18 UTC）
$ ./stale_v1.sh /home/user/ai-news \
    origin/main
== 7日以上 動いていない枝 ==
検出 0件 / 未統合 1件
しきい値 7日 (決め打ち)

未統合の枝が1本あるのに、検出0件。このリポジトリのコミット間隔は838秒（約14分）が真ん中です（後の出力は秒を切り捨てて 0h13m と表示します）。7日はその約720倍。実際に止まっていた2時間47分は、7日を基準にすると0.02倍にしかなりません。

  • 「アラートが鳴らない＝健全」ではありません。しきい値が自分たちの速度と無関係なだけです。
  • 7日はこのリポジトリの履歴から出ていません。Kanban Guideは「過去のサイクルタイムに基づけ」と書いています。値が7でも60でも、決め打ちである限り同じことが起きます。

しきい値を捨てて、履歴からSLEを出す

同じ枝に対して、リポジトリ自身の履歴からSLEを計算して判定させました。実行は6分後の15:24 UTC（同時刻ではありません）。この間にコミットは無く、枝の状態は変わっていません。「標本」は計算の材料にした件数のことです。

実行結果 — SLE版（python3 flow_signals.py）
repo : ai-news
trunk: origin/main
now  : 08-14 15:24 UTC
--------------------------------
[履歴] マージから復元した標本
  サイクルタイム 2件 / レビュー待ち 2件
  5件未満。SLE には使えない
[代替] 幹の連続コミット間隔
  標本 27件 / 中央値 0h13m / 最長 2h51m

[SLE] コミット間隔(代替) の 85%点
  0h43m を超えたら声をかける
--------------------------------
■ 幹に未統合の枝 (静止時間 順)
[!] claude/add-popular-json
    静止 2h47m = SLE の 3.8x
    着手からの経過 2h47m

決め打ち0件に対して、同じ枝で1件。SLEの43分は27件の履歴を並べた85%点で、人が決めていません。

  • 倍率が出るのが効きます。「SLEの3.8倍」は「2時間47分止まっています」より判断が速い。誰に先に声をかけるかの順番になります。
  • スクリプトが自分で「使えない」と言っています。Kanban Guideが求める historical cycle time は標本2件しか取れず、コミット間隔へ降格した経緯が出力に残ります。黙って代用させないための設計です。
  • ただし「5件未満なら出さない」はガイドではなく筆者のルールです。flow_signals.py の MIN_N = 5 という定数で、Kanban Guideに5件という数字はありません。ガイドはむしろ「履歴が無ければ当て推量でよい」と書いています。厳しめに倒したのは筆者の判断です。
  • 正直に書くと、この43分はKanban Guide準拠のSLEではありません。代替指標です。理由は下のとおりです。
この実測でうまくいかなかったこと（重要）
PRデータでは測れなかった
「レビュー待ちが長いもの」をGitHubのPR（プルリクエスト＝「この枝を幹に入れてください」という申請）から測ろうとして失敗しました。reishisu/ai-news にはopen/closed合わせてPRが1件も存在せず、GitHub APIはHTTP 200で空配列 [] を返します。そのためgitのマージから復元する代理指標（topic branchの最終コミット→マージコミットまでの時間）に置き換えました。
SLEの前提を満たせなかった
マージコミットは2件ありますが、いずれも Merge remote-tracking branch origin/main、つまり git pull による統合です。復元したレビュー待ちは0.03時間と0.16時間で、topic branchの待ち時間ではありません。だから標本5件未満と判定され、コミット間隔にフォールバックしています。
リポジトリが若すぎた
全履歴が2026年8月14日 02:06〜14:35の12.5時間・30コミットしかありません。日単位・週単位の停滞は原理的に観測できません。次の検証はそのためのものです。
「静止時間」はKanban Guideに無い
Kanban Guideの Work Item Age は「着手から現在まで」です。上の出力の「静止」は最終コミットから現在までで、これは筆者が足した別の指標です。両方を並べて印字しています。

日単位の停滞は、日時を固定した検証用リポジトリで測る

実リポジトリでは12.5時間ぶんしか無いので、ここから先は合成データです。統合済み8本（レビュー待ち 1,1,2,3,4,6,10,18時間）と未統合3本を、コミット日時を固定して生成しました。何度実行しても同じ数字が出ます。

実行結果 — 検証用リポジトリに7日決め打ち
$ NOW_TS=$(date -u \
    -d '2026-08-10T00:00:00Z' +%s) \
    ./stale_v1.sh fixture main
== 7日以上 動いていない枝 ==
検出 0件 / 未統合 3件
しきい値 7日 (決め打ち)

5日間まるごと止まっている枝を取りこぼしました。レビュー待ちの真ん中が3時間の現場で、5日の沈黙は異常値そのものです。それでも7日には届きません。

なお出力の「中央値」は、スクリプトが nearest-rank の50%点をそう表示しているものです。標本が偶数だと真の中央値とはずれます（この8件なら真の中央値は3.5時間）。判定に使う85%点は nearest-rank で正しく、表示の呼び名だけが不正確です。

5検出ゼロは「健全」と「壊れている」の両方を意味する

「標本0件」の原因を、リポジトリのせいだと思い込みかけた

開発中に自分でバグを作りました。マージから標本を復元する処理が、全マージを取りこぼしていたのです。

flow_signals.py の merge_samples() — 修正箇所
for line in git(
        repo, "log", "--first-parent",
        "--merges", "--format=%ct %P",
        trunk).splitlines():
    f = line.split()
    # 修正前: if len(f) < 4:  <- 全滅
    if len(f) < 3:   # ct p1 p2 で3個
        continue

--format=%ct %P の1行は、親が2つのマージコミットで ct p1 p2 の3フィールドです。< 4 で弾いていたので、全部落ちていました。再現用に切り出したスクリプトを、記事執筆時のコミット(9c00246)に当てた結果です。

実行結果 — バグ再現（bug_repro.py）
$ python3 bug_repro.py \

怖いのはここです。「標本0件」を最初、リポジトリにマージが無いせいだと解釈しかけました。

Q. 停滞検出スクリプトが「検出0件」と出した。これは何を意味する?

正解。だから分母を必ず印字させます。第4章の「検出 0件 / 未統合 1件」は分母が1なので「見逃している」と分かる。下の「要確認 0件 / 検査 0件」は分母も0なので本当に何も無い。この2つを出力で区別できないスクリプトは、静かに嘘をつきます。

未統合の枝がゼロのケースも確かめました。例外を出さず、分母つきで終わります。

  • フォールバックした事実も出力に残す。「本来の指標が取れなかったので別のものを使った」を黙ってやると、数字だけが独り歩きします。

6何を指標にすると燃え尽きないか

DORAの指標は4つではなく5つ。MTTRは2023年に廃止されている

DORA＝Googleが続けている開発チームの大規模調査とその研究チーム。MTTR＝Mean Time To Restore（平均復旧時間）。この2つを開いた上で、前提を直します。「DORAの4つの指標」は現在の一次資料と食い違います。

dora.dev 公式ガイド — 原文
DORA has identified five software delivery
performance metrics that provide an effective way
of measuring the outcomes of the software
delivery process.

（DORAは、ソフトウェアデリバリのアウトカムを
　測定する有効な手段として5つの指標を特定した）
指標グループ取り違えやすい点
Change lead time Throughput（処理量） —
Deployment frequency Throughput（処理量） —
Failed deployment recovery time Throughput（処理量） 「MTTR」と表記／「安定性」に分類
Change fail rate Instability（不安定さ） —
Deployment rework rate Instability（不安定さ） 存在ごと省略される（5つ目を「信頼性」と書く）
  • MTTRという名前は2023年に廃止されました。理由も書かれています。従来の定義が「ソフトウェア変更が起点の障害」と「データセンター障害のような外部要因」を区別していなかったためです。
  • 復旧時間はThroughput側です。Instability側にあるのは change fail rate と deployment rework rate の2つだけ。復旧の速さを「安定性」に入れたくなりますが、公式の分類は逆です。
  • 5つ目は「信頼性」ではありません。DORA自身が履歴ページで "The 2021 report inaccurately called the 'reliability' metric the 'fifth metric'" と自社レポートを訂正しています。
  • 2014年時点では3つでした。初回研究で change fail rate が他変数と有意に相関せず、単一の潜在構成概念を形成しなかったためです。「最初から4つ」も誤りです。

このガイドの正式なURLは /guides/dora-metrics/ です。ただし旧URLの /guides/dora-metrics-four-keys/ は今も生きていて、301でそこへ転送されます（2026年8月15日に curl -I で実測）。本文が5つだと書いているページに four-keys の名残が残っているわけです。これが「4つ」という呼び名の定着に効いた、というのは筆者の推測で、裏は取れていません。

指標の使い方には、公式が名指しした落とし穴がある

同じガイドの Common pitfalls の節です。ここが「燃え尽きない指標」の設計図になります。

dora.dev 公式ガイド — Common pitfalls 原文
Setting metrics as a goal. Ignoring Goodhart's
law and making broad statements like, "Every
application must deploy multiple times per day by
year's end," increases the likelihood that teams
will try to game the metrics.

Having one metric to rule them all. Attempting to
measure complex systems with the idea that only
one metric matters. Teams should identify
multiple metrics, including some with a healthy
amount of tension between them.
  • 指標を目標にしない。グッドハートの法則を名指ししています。SLEの確率部分を落とすと、まさにこれが起きます。
  • 単一指標を持たない。しかも「互いに健全な緊張関係にあるもの」を含めろ、と書かれています。速さだけを見ると必ず壊れます。
  • チーム間で比較しない。"The goal is to improve your team's performance over time, not to compete against other teams or organizations."

SPACE（開発生産性を1つの数字で測らず、5つの次元で見ようという枠組み）の論文も、同じことを著者所属機関の公式アブストラクトで書いています。ただし本文はACM側が403で読めておらず、引用できるのはこの1文だけです。

SPACE 論文アブストラクト（Microsoft Research 公開ページ）
...it cannot be measured by a single metric or
dimension.

（それは単一の指標や次元では測定できない）

DORAの2024年レポート：良いリーダーがいても、燃え尽きは防げない

ここがいちばん通説とぶつかります。原文をそのまま貼ります。

2024 Accelerate State of DevOps Report (v.2024.3) — 原文
We examined whether having strong leaders, good
internal documents, and a user-centered approach
to software development can help counteract the
effect of shifting priorities on burnout. The
answer is: They can't. An organization can have
all these positive traits and, if priorities are
unstable, employees will still be at risk of
experiencing burnout.

強いリーダーシップ、良質な内部ドキュメント、ユーザー中心の開発。この3つが揃っていても、優先順位が不安定なら燃え尽きのリスクは残ると検証されています。

ただし「方針転換をするな」ではありません。レポートは明確に否定しています。

同レポート — 原文
To be clear, we believe that the problem is not
with changing priorities themselves. Business
goals and product direction shift all the time.
It can be good for organizational priorities to
be malleable. We believe it is the frequency with
which priorities change that has a negative
impact on employees' well-being. ... Chronic
instability increases uncertainty and decreases
perceived control. This combination is an
excellent recipe for burnout.
  • 問題は変更そのものではなく頻度です。「柔軟であることは良いことでありうる」とまで書かれています。
  • 効くのは2つだけ。レポートの結論は「(1)優先順位を安定させる (2)日々の作業が優先順位の変動の影響を受けないよう遮蔽する」以外に打ち手は多くない、というものです。
  • 燃え尽きの定義がWHOとずれています。DORAの定義には「職場ストレス起因」「職業文脈限定」という ICD-11 の制約がありません。両方を同じものとして引用すると定義が混ざります。

Q. 「優先順位を安定させよう」と決めた。DORA 2024が観測したのは?

正解。デリバリ性能＝出荷の速さと安定さのことです。原文は "We find that when priorities are stabilized, software delivery performance declines. It becomes slow and less stable in its delivery." DORA自身が "we find this to be an unexpected finding"（予想外の発見である）と書いています。トレードオフとして提示するのが正確で、「安定させれば全部良くなる」は一次資料と食い違います。

プラットフォームを入れれば燃え尽きが減る、とも限らない
2024レポートの観察
内部開発者プラットフォーム利用時に、変更の安定性が「驚くべきことに14%低下」しました。原文では change failure rate と rework rate が有意に上昇したとされ、さらに "instability in combination with a platform is linked to higher levels of burnout"（プラットフォームと不安定さの組み合わせが、より高い燃え尽き水準と結びつく）と書かれています。
断定はされていません
DORA自身は因果を断定せず複数の仮説を併記しています。ここで言えるのは「プラットフォーム＝認知負荷減＝燃え尽き減」という売り文句が、一次資料の観察と自動的には一致しない、という点だけです。
数値について
優先順位の不安定さ→燃え尽きの推定効果量は、本文では "substantial increases in burnout" と定性的にしか書かれておらず、数値は図の中にあります。PDFからのテキスト抽出では軸ラベルの断片しか取れず、正確な効果量は特定できませんでした。14%だけが本文中の数値です。

指標の定義そのものにも、版番号と正誤表が要る

最後に、地味ですが効く話です。DORAはレポートPDFにバージョン番号を刻印し、正誤表を公開しています。

Errata for the 2025 DORA Report — 原文
To track revisions, report PDFs are stamped with
a version number. The initial version of the 2025
report was v. 2025.1. The latest version is
v. 2025.2.

誤植1文字（stabilty → instability）まで公開して訂正しています。指標を運用するなら、指標の定義にも版管理と訂正の仕組みが要る——これは筆者の意見ですが、一次資料がその実例です。

7明日から動かすもの

朝会の質問を1つ変えるより、しきい値を1つ計算するほうが速い

この記事で一次資料から取れたことを、順番に並べます。

  • 「進捗どうですか」を、翌日の実行可能な計画を作る場に変える。スクラムガイド2020が求めているのはそれです。3つの質問は2016年版までの規定で、2017年版では一例、2020年版には残っていません。
  • 本人の申告を待たない。報告を職務にしている監査人ですら黙ります。申告経路とは別に、時間の信号を持ちます。
  • 見る信号は「着手からの経過時間」。まだ終わっていない仕事に使えるフローメトリクスは、これだけです。
  • しきい値は自分たちの履歴から出す。日数の決め打ちは、実データで検出0件でした。値が7でも60でも同じです。
  • 指標は複数、互いに緊張関係のあるものを混ぜる。単一指標はDORAとSPACEの両方が否定しています。
  • 指標より先に、優先順位の変更頻度を見る。良いリーダーシップでは相殺できない、と検証されています。

手を動かす順番です（1〜4は自分のリポジトリがある人向け。ターミナルでリポジトリのフォルダに入って打ちます）。0 / 5

🎉 これで「言い出すまで気づかない」は減らせます

最後に注意を1つ。この記事の実測のうち、日単位の停滞は合成データでしか測れていません。実リポジトリの履歴が12.5時間しか無かったためです。あなたのリポジトリで走らせたときの数字が、記事と同じになる保証はありません。
