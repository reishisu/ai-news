Unity Webが本番だけ動かない。原因はビルドではなくサーバー

ローカルで動いたビルドが、置いた瞬間に起動しない。その条件をブラウザで実測し、Unity公式の記述と突き合わせます。
⏱ 約6分 実測 + 公式ドキュメント 設定はコピペで足りる

⭐ 3行で言うと

  1. Unity Webのマルチスレッドは、HTTPヘッダー2本が無いと丸ごと死にます ビルド設定ではなく、配信サーバー側の設定で決まります。ここが盲点です。
  2. ヘッダーが無いと SharedArrayBuffer は「存在しない」扱いになります 値が空なのではなく、参照した瞬間に ReferenceError。実測しました。
  3. そもそもC#のスレッドは使えません。これは仕様です Unity公式が理由まで書いています。「重い処理を別スレッドへ」が通りません。

1症状 — ローカルでは動いたのに

ビルドは同じ。置き場所を変えただけで起動しなくなる

Unityの「Build And Run」では問題なく動きます。同じ成果物をサーバーに上げると、ロード画面から先に進まない。

Unityのビルド設定を疑って何時間も溶かす典型です。ビルドは悪くありません。

  • 「Build And Run」は自前のローカルサーバーを立てています。そのサーバーが必要なヘッダーを付けてくれるので動きます。
  • 本番のホスティングは何も付けません。だから同じファイルでも結果が変わります。
  • エラーが分かりにくい。コンソールに出るのは SharedArrayBuffer is not defined 系で、Unityの文字は出てきません。

Q. ローカルで動いて本番で動かない。まず疑うのは?

正解。成果物が同じなら、違うのは配信の仕方だけです。次でその「違い」を実際に測ります。

2条件をブラウザで実測する

同じHTMLを、ヘッダーだけ変えて2通り配信した

Unityを持ち出さなくても、条件はブラウザだけで確かめられます。ヘッダー2本の有無だけが違うサーバーを立てました。

coi.py — ヘッダーの有無を切り替えるだけのサーバー
class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.send_header("Content-Length", str(len(PAGE)))
        if self.path.startswith("/coi"):
            self.send_header("Cross-Origin-Opener-Policy", "same-origin")
            self.send_header("Cross-Origin-Embedder-Policy", "require-corp")
        self.end_headers()
        self.wfile.write(PAGE)
実行結果（node probe.js）
ブラウザ: 141.0.7390.37

■ ヘッダーなしで配信した場合
  crossOriginIsolated   false
  SharedArrayBuffer     なし / 作れない (ReferenceError)
  WebAssembly           あり
  WebGL2                あり
  WebGPU                あり
  論理コア数            4

■ COOP + COEP を付けて配信した場合
  crossOriginIsolated   true
  SharedArrayBuffer     あり / 作れる
  WebAssembly           あり
  WebGL2                あり
  WebGPU                あり
  論理コア数            4
  • SharedArrayBuffer は「値が無い」のではなく「存在しない」。typeof で見ると undefined、直接触ると ReferenceError です。だから if (SharedArrayBuffer) と書くと、そこで落ちます。
  • WebAssembly・WebGL2・WebGPUはヘッダー無しでも使えます。止まるのはスレッド関連だけ。だから「描画は出るのに固まる」といった中途半端な壊れ方をします。
  • 判定は1行で書けます。self.crossOriginIsolated が true かどうか。これがマルチスレッド可否とほぼ同義です。

3Unity公式が要求しているヘッダー

推測ではなく、マニュアルに3本が明記されています

実測は実測として、Unityが何を要求しているかを公式マニュアルで確認しました。原文はこうです。

Unity Manual (6000.0)「WebGL technical overview」— 原文
The Web platform supports multithreading, when your document is
within a secure context. The following HTTP response headers must
be set by the server.

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Resource-Policy: cross-origin
  • Unityは3本挙げています。私が実測したのは上2本で、これだけで crossOriginIsolated は true になりました。3本目の Cross-Origin-Resource-Policy は今回検証していません。Unityが挙げている以上、まとめて設定するのが安全です。
  • 「secure context」も条件です。つまり https://（または localhost）である必要があります。社内の http://192.168.x.x で配ると、それだけで条件を外します。
  • ヘッダーはサーバーの担当です。Unity側の設定をいくらいじっても付きません。
COEP を付けると外部リソースが読めなくなる場合があります
何が起きるか
Cross-Origin-Embedder-Policy: require-corp を付けると、外部から読み込む画像・スクリプト・フォントなどが、相手側の許可なしには読めなくなります。広告タグや外部の解析タグを埋めていると、そちらが先に壊れます。
対処
読み込み先が Cross-Origin-Resource-Policy や CORS のヘッダーを返しているか確認します。返していない外部リソースは、自分のサーバー経由に置き換えるのが確実です。マルチスレッドを使わない構成なら、そもそもヘッダーを付けないという判断も成立します。

4C#のスレッドは使えない

ヘッダーを正しく付けても、C#のスレッドは動きません

ここが一番の落とし穴です。ヘッダーを整えても、使えるようになるのはC/C++側のスレッドだけです。

Unity Manual — 原文
Managed (C#) threads aren't supported due to the lack of a
multithreaded garbage collection feature in WebAssembly.

Although Unity provides multithreading support for native C/C++
code, the Web platform doesn't yet support C# multithreading due
to limitations of WebAssembly. This means that applications built
using the Web platform must run on a single C# thread.
  • C#側は1スレッドで動かすしかありません。他プラットフォーム向けに System.Threading で組んだ処理は、そのままでは持ち込めません。
  • 公式の代替案は Awaitable。マニュアルは「複雑な非同期処理には Awaitable を使うことを推奨する。多くの場合 System.Threading.Tasks.Task を置き換えられる」としています。
  • C/C++スレッドも実験的な扱いです。Player設定の Native C/C++ Multithreading を有効にする必要があります。

Q. 重い計算でフレームが落ちる。Unity Webでの正しい打ち手は?

正解。C#スレッドは選択肢に入りません。ヘッダーはC/C++スレッドを解禁するための前提であって、C#を並列にする手段ではありません。ここを混同すると、ヘッダーを直したのに何も速くならない、という結果になります。

ほかにも刺さりやすい制限
ソケットが使えない
ブラウザがIPソケットへの直接アクセスを許さないため、System.Net 名前空間のネットワーククラスはサポートされません。通信はHTTPかWebSocketに寄せる必要があります。
コードの動的生成ができない
WebはAOTプラットフォームのため System.Reflection.Emit は使えません。これはiOSや多くのコンソールと同じ制約です。
GCの動き方が違う
ブラウザがWebAssemblyのスタックへの直接アクセスを塞いでいるため、ガベージコレクションが毎フレームの最後に1回だけ走ります。他プラットフォームのように複数フレームに分散されません。フレーム末尾のスパイクとして観測されます。

5配信サーバー別の設定

コピーして貼るだけの設定

Unityが挙げている3本をまとめて設定します。あわせて https で配ること。

nginx
add_header Cross-Origin-Opener-Policy   "same-origin"   always;
add_header Cross-Origin-Embedder-Policy "require-corp"  always;
add_header Cross-Origin-Resource-Policy "cross-origin"  always;
Apache (.htaccess)
Header always set Cross-Origin-Opener-Policy   "same-origin"
Header always set Cross-Origin-Embedder-Policy "require-corp"
Header always set Cross-Origin-Resource-Policy "cross-origin"
Cloudflare Pages / Netlify（_headers ファイル）
/*
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp
  Cross-Origin-Resource-Policy: cross-origin

GitHub Pages では設定できません。レスポンスヘッダーを変更する手段が無いため、マルチスレッドを使うUnity Webビルドは置けません。単一スレッド構成なら問題なく動きます。

設定できたかの確認（1コマンド）
$ curl -sS -D - -o /dev/null "https://あなたのサイト/" \
    | grep -i "cross-origin"

cross-origin-opener-policy: same-origin
cross-origin-embedder-policy: require-corp
cross-origin-resource-policy: cross-origin

ブラウザ側からも1行で確認できます。開発者ツールのコンソールで crossOriginIsolated と打つだけです。true が返れば成功。
