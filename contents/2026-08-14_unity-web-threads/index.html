Unity Webのマルチスレッドに必要なHTTPヘッダー

ローカルと本番で何が変わるのか。マルチスレッドの前提条件をブラウザで実測し、Unity公式マニュアルの原文と突き合わせます。
⏱ 約6分 実測 + 公式ドキュメント 設定はコピペで足りる

⭐ 3行で言うと

  1. 対象は Native C/C++ Multithreading を有効にしてビルドしたときだけです この設定を使うなら、配信サーバー側のHTTPヘッダーが要ります。ヘッダーとは、サーバーがファイル本体と一緒に返す「添え状」のこと。ブラウザはこれを読んで扱い方を決めます。
  2. ヘッダーが無いと SharedArrayBuffer は「存在しない」扱いになります 値が空なのではなく、参照した瞬間に ReferenceError。素のページで実測しました。
  3. そもそもC#のスレッドは使えません。これは仕様です Unity公式が理由まで書いています。「重い処理を別スレッドへ」が通りません。

1症状 — ローカルでは動いたのに

まず前提。ヘッダーが要るのは「実験的な設定を有効にしたビルド」だけ

最初に適用範囲を切ります。Unity公式のサーバー設定ページは、ヘッダーが必要になる条件をはっきり限定しています。

Unity Manual (6000.0) Nginx設定ページ — 原文
If you built your project with Enable Native C/C++
Multithreading activated in the Player settings, you
need to set specific server headers. These headers
include Cross-Origin Opener Policy (COOP),
Cross-Origin Embedded Policy (COEP), and Cross-Origin
Resource Policy (CORP).

訳: Player設定で Enable Native C/C++ Multithreading を有効にしてビルドしたなら、サーバー側で特定のヘッダーを設定する必要がある。COOP・COEP・CORPである。

裏を返すと、この設定を有効にしていない既定のビルドは、ヘッダーが無くても動きます。Unity公式のNode.jsサンプルも「マルチスレッド対応でビルドしたなら true、そうでなければ false」と書き分けています。以降はすべて有効にした場合の話です。

ビルドは同じ。置き場所を変えると、返ってくるヘッダーが変わる

Unityの「Build and Run」はUnity自前のローカルサーバーで動きます。本番のホスティングは別物です。成果物が同じでも、返ってくるヘッダーまで同じとは限りません。

「Technical limitations」— Build and run limitations 節
Unity uses a web server with only basic functionality
to host web builds created with Build and Run
(menu: Edit > Build Profiles > Build and Run).
  • 公式に書いてあるのは「自前のサーバーで配る」ところまで。そのサーバーがCOOP/COEPを返すかどうかは未確認です。参考文献に挙げた公式ページを読みましたが、Build and Run とクロスオリジン関連ヘッダーを結びつける記述はどこにもありませんでした。
  • ヘッダーはサーバーの担当です。Unity側のビルド設定をいくらいじっても付きません（3節の原文）。だから疑うべきはビルドではなく配信です。
  • 「ロード画面から進まない」という症状は、この記事では未確認です。Unityエディタでの実機ビルド検証はしていません。確かめたのはブラウザ側の前提条件だけで、その範囲を2節に全部出します。

以降、ブラウザの開発者ツールを使います。Windows / Linux は F12、macOS は Command + Option + I。または画面を右クリック →「検証」→「Console」タブ。JavaScriptのエラーはここに出ます。

Q. ローカルで動いて本番で動かない。まず疑うのは?

正解。成果物が同じなら、違うのは配信の仕方だけです。次でその「違い」を実際に測ります。

2条件をブラウザで実測する

同じHTMLを、ヘッダーだけ変えて2通り配信した

Unityを持ち出さなくても、条件はブラウザだけで確かめられます。ヘッダー2本の有無だけが違うサーバーを立てました。

測る対象は crossOriginIsolated です。これは「このページはクロスオリジン分離済み」というブラウザ側の状態を表します。HTML仕様は、この能力を「クロスオリジン分離を必要とするAPIを使ってよいか」を表す真偽値と定義しています。

その代表が SharedArrayBuffer、つまり複数スレッドで同じメモリを共有する仕組みです。仕様上、能力が false のままワーカーへ渡そうとすると例外になります。

HTML Standard 2.7.3 StructuredSerializeInternal — 原文
If IsSharedArrayBuffer(value) is true:
  If the current settings object's cross-origin
  isolated capability is false, then throw a
  "DataCloneError" DOMException.

そしてCOOPとCOEPが、その分離をサーバーから宣言するヘッダーです。ヘッダー → 分離 → 共有メモリの順に効きます。ここを実際に測ります。

  • 1. coi.py で2つのURLを配る。返すHTMLは1バイトも同じで、/coi のときだけヘッダー2本を足します。
  • 2. probe.js でブラウザを自動操作する。Playwrightでchromiumを起動し、両方のURLを開いて判定値を集めます。
  • 3. 並べて出力する。違いがヘッダー以外に無いので、差はヘッダーのせいだと言えます。
coi.py — ヘッダーの有無だけを切り替えるサーバー（抜粋）
COOP = "Cross-Origin-Opener-Policy"
COEP = "Cross-Origin-Embedder-Policy"
COI = [(COOP, "same-origin"),
       (COEP, "require-corp")]


class H(hs.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header(*HTML)
        if "/coi" in self.path:
            for k, v in COI:
                self.send_header(k, v)
        self.end_headers()
        self.wfile.write(PAGE)

出力の SAB は SharedArrayBuffer の略です（狭い画面で折り返さないよう縮めています）。

仕様は「共有メモリを渡せない」と書いていました。実際のChromium 141では、その手前で変数ごと存在しませんでした。

  • SharedArrayBuffer は「値が無い」のではなく「存在しない」。typeof で見ると undefined、直接触ると ReferenceError です。だから if (SharedArrayBuffer) と書くと、そこで落ちます。
  • WebAssemblyとWebGL2はヘッダー無しでも使えました。止まるのはスレッド関連だけ。だから「描画は出るのに固まる」といった中途半端な壊れ方をします。
  • WebGPUは判定を保留します。navigator.gpu は両方の条件で存在しましたが、requestAdapter() はどちらも nullでした。ヘッドレスかつGPUの無いこの環境ではアダプタを取得できず、ヘッダーの影響は測れていません。「APIが在る」と「使える」は別だ、という例でもあります。
  • 判定は1行で書けます。self.crossOriginIsolated が true かどうか。これがマルチスレッド可否とほぼ同義です。

3Unity公式が要求しているヘッダー

推測ではなく、マニュアルに3本が明記されています

実測は実測として、Unityが何を要求しているかを公式マニュアルで確認しました。原文はこうです。

「Technical limitations」— Multithreading support 節 Notes
The Web platform supports C/C++ multithreading only if
you enable Native C/C++ support in the Web Player
settings.

The Web platform supports multithreading, when your
document is within a secure context. The following HTTP
response headers must be set by the server.

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Resource-Policy: cross-origin

訳: Web版がC/C++マルチスレッドに対応するのは、Web用Player設定でNative C/C++サポートを有効にした場合だけである。／Web版がマルチスレッドに対応するのは、文書が secure context にあるときである。次のHTTPレスポンスヘッダーをサーバーが設定しなければならない。

  • Unityは3本挙げています。私が実測したのは上2本で、これだけで crossOriginIsolated は true になりました。3本目の Cross-Origin-Resource-Policy は今回検証していません。Unityが挙げている以上、まとめて設定するのが安全です。
  • 「secure context」も条件です。つまり https://（または localhost）である必要があります。社内の http://192.168.x.x で配ると、それだけで条件を外します。
  • ヘッダーはサーバーの担当です。Unity側の設定をいくらいじっても付きません。
COEP を付けると外部リソースが読めなくなる場合があります
何が起きるか
Cross-Origin-Embedder-Policy: require-corp を付けると、外部から読み込む画像・スクリプト・フォントなどが、相手側の許可なしには読めなくなります。広告タグや外部の解析タグを埋めていると、そちらが先に壊れます。
対処
読み込み先が Cross-Origin-Resource-Policy や CORS のヘッダーを返しているか確認します。返していない外部リソースは、自分のサーバー経由に置き換えるのが確実です。マルチスレッドを使わない構成なら、そもそもヘッダーを付けないという判断も成立します。

4C#のスレッドは使えない

ヘッダーを正しく付けても、C#のスレッドは動きません

ここが一番の落とし穴です。ヘッダーを整えても、使えるようになるのはC/C++側のスレッドだけです。

「Technical limitations」— Lack of managed threading support 節
Managed (C#) threads aren’t supported due to the lack of
a multithreaded garbage collection feature in
WebAssembly.
同ページ「Multithreading support」節（冒頭）
Although Unity provides multithreading support for
native C/C++ code, the Web platform doesn’t yet support
C# multithreading due to limitations of WebAssembly.
This means that applications built using the Web
platform must run on a single C# thread.

訳: WebAssemblyにマルチスレッド対応のガベージコレクションが無いため、マネージド（C#）スレッドは非対応。UnityはネイティブC/C++コードのマルチスレッドには対応するが、Web版はWebAssemblyの制限によりC#のマルチスレッドにまだ対応していない。Web版で作ったアプリケーションは単一のC#スレッドで動かさなければならない。

  • C#側は1スレッドで動かすしかありません。他プラットフォーム向けに System.Threading で組んだ処理は、そのままでは持ち込めません。
  • 公式の代替案は Awaitable。同じ Multithreading support 節の記述で、訳すと「Web版で複雑な非同期処理を行う推奨のやり方は Awaitable を使うことであり、多くの場合 System.Threading.Tasks.Task を置き換えられる」です。
  • C/C++スレッドも実験的な扱いです。場所は Edit > Project Settings > Player を開き、Webのタブ → Other Settings → Configuration の中の Enable Native C/C++ Multithreading。1節のヘッダーが要るのは、ここを有効にしたときだけです。
  • Unity自身が「切っておけ」と書いています。Web Player settings の原文は「It’s recommended to disable this option and use it only for evaluating future web features.」（このオプションは無効にし、将来のWeb機能を評価する目的にのみ使うことを推奨する）。まずこの設定が本当に要るかを疑うのが先です。

Q. 重い計算でフレームが落ちる。Unity Webでの正しい打ち手は?

正解。C#スレッドは選択肢に入りません。ヘッダーはC/C++スレッドを解禁するための前提であって、C#を並列にする手段ではありません。ここを混同すると、ヘッダーを直したのに何も速くならない、という結果になります。

ほかにも刺さりやすい制限
ソケットが使えない
ブラウザがIPソケットへの直接アクセスを許さないため、System.Net 名前空間のネットワーククラスはサポートされません。通信はHTTPかWebSocketに寄せる必要があります。
コードの動的生成ができない
WebはAOTプラットフォームのため System.Reflection.Emit は使えません。これはiOSや多くのコンソールと同じ制約です。
GCの動き方が違う
ブラウザがWebAssemblyのスタックへの直接アクセスを塞いでいるため、ガベージコレクションが毎フレームの最後に1回だけ走ります。他プラットフォームのように複数フレームに分散されません（ここまでがマニュアルの記述）。実際のフレーム時間にどう出るかは、本記事ではプロファイリングしていません。

5配信サーバー別の設定

コピーして貼るだけの設定（貼る場所と反映のしかたつき）

Unityが挙げている3本をまとめて設定します。あわせて https で配ること。

なおUnity公式の例は、この3本を .htm / .html / .js などに絞って付けています。下は全レスポンスに付ける簡略版です。細かく絞りたいときは参考文献の公式ページを見てください。

nginx
add_header Cross-Origin-Opener-Policy   "same-origin"   always;
add_header Cross-Origin-Embedder-Policy "require-corp"  always;
add_header Cross-Origin-Resource-Policy "cross-origin"  always;
Apache (.htaccess)
Header always set Cross-Origin-Opener-Policy   "same-origin"
Header always set Cross-Origin-Embedder-Policy "require-corp"
Header always set Cross-Origin-Resource-Policy "cross-origin"
Cloudflare Pages / Netlify（_headers）
/*
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp
  Cross-Origin-Resource-Policy: cross-origin
  • nginx は設定ファイルの server ブロックの中へ。保存したら nginx -t で構文を検査し、nginx -s reload で反映します。
  • Apache はビルドを置いた公開ディレクトリ直下の .htaccess へ。mod_headers が有効なら、保存した時点で反映されます。
  • _headers は拡張子なしのテキストファイル。Cloudflare Pagesは静的アセットのディレクトリ（＝ビルド出力先）、Netlifyは publish directory に置きます。どちらも置いただけでは効かず、再デプロイが要ります。

GitHub Pages については、置けないと筆者は考えています。レスポンスヘッダーを追加する手段が提供されていないためです。ただしUnity・GitHubのどちらも、この組み合わせについて明示していません（筆者の判断であることを参考文献にも書いています）。単一スレッド構成なら、そもそもこの3本は要りません。

設定できたかの確認
curl -sS -D - -o /dev/null \
    https://あなたのサイト/ \
  | grep -i cross-origin \
  | sed 's/: /:\n  /'

最後の sed は、狭い画面でも読めるように折り返しているだけです。3本そろって返れば成功。返らなければ、サーバーに反映されていません。

参考までに、2節の検証サーバー（COOPとCOEPの2本だけ付ける版）へ同じコマンドを打った結果です。

実行結果（2節の検証サーバーに対して）
Cross-Origin-Opener-Policy:
  same-origin
Cross-Origin-Embedder-Policy:
  require-corp

ブラウザ側からも1行で確認できます。さきほどのコンソールで crossOriginIsolated と打つだけです。true が返れば成功。

訂正と追記

公開後の事実検証で、裏の取れない記述が見つかりました。2026年8月15日に次の6点を直しています。

  • 参照した文書名が誤っていました。「WebGL technical overview」と書いていましたが、当該ページの実際のタイトルは「Technical limitations」です（URLは同じ）。ページ本文に “technical overview” という語はありません。3節の見出しと参考文献を直しました。
  • 適用条件が抜けていました。ヘッダー3本が必要なのは Enable Native C/C++ Multithreading を有効にしてビルドした場合だけです。公式のサーバー設定ページがそう限定しています。1節の冒頭に前提として置き直しました。
  • 「Build And Runのサーバーがヘッダーを付けてくれる」を削除しました。Unityが自前のサーバーを使うことは公式に書かれていますが、そのサーバーがCOOP/COEPを返すという記述は見つかりませんでした。未確認と明記しています。
  • Unityビルドでの症状を断定していた箇所を外しました。「ロード画面から進まない」「コンソールにUnityの文字は出ない」は実機検証をしていません。実測した素のページでの ReferenceError と分けて書き直しました。
  • 「WebGPUはヘッダー無しでも使えます」を撤回しました。再測定したところ navigator.gpu は存在するものの、requestAdapter() はヘッダーの有無にかかわらず null。この環境では可否を判定できません。2節の実行結果を測り直して差し替えました。
  • GCの「フレーム末尾のスパイクとして観測されます」を削除しました。マニュアルにその記述は無く、本記事でもプロファイリングをしていません。
