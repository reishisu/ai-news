npmのロックファイルが固定しないもの — install と ci の違い

package-lock.json を16通りの方法でいじめて、何が固定されて何が固定されていないかを測りました。ログは加工していません。
⏱ 約12分 実測ログ全部載せ npm 10 と npm 12 で比較

⭐ 3行で言うと

「自分の環境では動くのに、CI（自動でテストや公開をするサーバー）だと落ちる」。この定番の事故を、ロックファイルがあっても起きる形で再現しました。

用語だけ先に。package.json は「このくらいのバージョンなら何でもいい」という注文書、package-lock.json（lock）は「実際に何が入ったか」の納品書です。納品書をリポジトリに入れておけば、誰がインストールしても同じ物が入る——はずでした。

  1. lockの registry.npmjs.org は、取得先ではなく「今の設定先」を指している lockを1文字も変えずに設定だけ差し替えたら、7個すべてを手元の別サーバーから取ってきて、警告ゼロで成功しました。ただしこれはこの文字列のときだけ。社内ミラーなど別のURLが書かれた lock は、設定を変えてもそのURLへ取りに行きます（3章で両方測っています）。
  2. 「npm install は package.json を見る／npm ci は lock を見る」は嘘 npm ci は package.json を読んでいます。読んだ上で lock と答え合わせして、合わなければ落ちています。
  3. 2026年7月、npm 12 が前提を壊した npm-shrinkwrap.json が黙って無視されるようになりました。npm ci なら止まりますが、npm install だと何も言わずに別のバージョンが入ります。

目次

  1. 同じ package.json から、別のツリーが生えた

  4. lockを揃えても、lockの外が揃っていない

1同じ package.json から、別のツリーが生えた

直接書いた依存は1個。勝手に変わったのは4箇所

package.json は「このライブラリの、このくらいのバージョンなら何でもいい」という幅の宣言です。実際に何が入るかは、インストールした瞬間に決まります。

その「瞬間」の違いだけで結果がどう変わるか。chalk: ^4.0.0 だけを書いた package.json で測りました。^ は「4系のうちなら上げてよい」という印です（正確な範囲は6章）。

出力は左が名前、右がバージョンです。1個しか頼んでいないのに7個出てきます。頼んだライブラリが使っているライブラリまで芋づるで入るためです。この枝分かれ全体を依存ツリーと呼びます。以降「ツリー」はこれのことです。

実行結果（2026年8月15日 UTC 実測 / npm 10.9.7）
== A: 2020-05-01 時点 ==
@types/color-name  1.1.1
ansi-styles        4.2.1
chalk              4.0.0
color-convert      2.0.1
color-name         1.1.4
has-flag           4.0.0
supports-color     7.1.0
== B: 今日 ==
ansi-styles        4.3.0
chalk              4.1.2
color-convert      2.0.1
color-name         1.1.4
has-flag           4.0.0
supports-color     7.2.0
  • 入る個数まで変わりました。7個 → 6個。@types/color-name が消えたのは、ansi-styles が 4.3.0 で依存をやめたからです。
  • 自分で書いた行は1行だけ。なのに変わった箇所は4つ。chalk、ansi-styles、supports-color、そして消えた1個。
  • 「時期の違い」は --before で作りました。npm install --before=2020-05-01 は、その日以前に公開されたバージョンだけで解決します。別マシンを用意しなくても差を作れます。

では lock があるとどうなるか。2020年5月時点で作った lock を、今日そのまま npm ci にかけました。

実行結果（6年前のlockを今日 npm ci）
@types/color-name  1.1.1
ansi-styles        4.2.1
chalk              4.0.0
color-convert      2.0.1
color-name         1.1.4
has-flag           4.0.0
supports-color     7.1.0

上のAと1行も違いません。npm ci は「今が何年何月か」を一切見ていません。

そもそも、なぜ lock が必要なのか
「同じ範囲なら同じ結果になる」わけではない
Yarn（npm と同じ役割の、別のパッケージマネージャ）の公式ドキュメントは、インストールの Resolution 段階についてこう書いています。The exact way a dependency version is privileged over another isn't standardized outside of the regular semver guarantees.（どの依存バージョンが他より優先されるかの正確な方法は、通常の semver の保証を超えては標準化されていない）。ここでいう semver はバージョン番号の付け方の取り決め、レジストリはパッケージが置いてある配布サーバーのことです。つまり、同じ package.json・同じレジストリでも、解決するツールが違えば結果が変わりえます。
lock の目的は3つ
7つのパッケージマネージャを横断した論文（Gamage ほか、EMSE 2026）の抄録は、lock の役割を「ビルド時間の短縮」「取得したパッケージの完全性の検証」「環境と時間をまたいだ再現性の担保」と整理しています。今回読めたのは抄録だけなので、本文の比較表の内容には触れません。

2「installはpackage.json、ciはlock」は嘘

npm install も lock に従う。lockは1文字も書き換わらなかった

こういう説明を見たことがあるかもしれません。「npm install は最新の適合バージョンを入れて lock を書き換える。npm ci は lock だけを見る」。出どころはこの章の最後で特定します。

両方とも間違いです。まず前半から測ります。lock には chalk 4.0.0、package.json には ^4.0.0。chalk 4.1.2 がすでに公開されている状態で npm install しました。

実行結果（lockが範囲を満たしている状態で npm install）
@types/color-name  1.1.1
ansi-styles        4.2.1
chalk              4.0.0
color-convert      2.0.1
color-name         1.1.4
has-flag           4.0.0
supports-color     7.1.0
package-lock.json は変化なし

4.1.2 は入りませんでした。lock は1文字も書き換わっていません。公式ドキュメントに、そう書いてあります。

npm Docs「npm-install」— How npm install uses package-lock.json
In essence, package-lock.json locks your dependencies to
specific versions, but package.json is the source of truth
for acceptable version ranges. When the lockfile's versions
satisfy the package.json ranges, the lockfile wins. When
they conflict, package.json wins and the lockfile is
updated.

（要するに package-lock.json は依存を特定バージョンに固定
　するが、「許容される範囲」の真実の源は package.json で
　ある。lock のバージョンが範囲を満たしているときは lock
　が勝つ。衝突するときは package.json が勝ち、lock が更新
　される）

npm ci は package.json を読んでいる。読んだ上で落としている

次に後半。lock は chalk 4.0.0 のまま、package.json だけ ^4.0.0 → ^5.0.0 に変えて npm ci しました。出力に出てくる node_modules は、ダウンロードした本体が実際に置かれるフォルダです。

実行結果（package.jsonだけ動かして npm ci / npm 10.9.7）

chalk@5.6.2 という数字は、lock のどこにも書かれていません。npm ci が package.json の ^5.0.0 からいま解決した結果です。

npm CLI 12.0.2 のソースに、何をしているかが書いてあります。

npm/cli — lib/utils/validate-lockfile.js（原文コメント）
// compares the inventory of package items in the tree
// that is about to be installed (idealTree) with the inventory
// of items stored in the package-lock file (virtualTree)

（これからインストールしようとしているツリー(idealTree)の
　構成品目を、package-lock に保存されている品目
　(virtualTree)と比較する）
  • npm ci は package.json から「理想のツリー」を作り直します。それを lock 由来のツリーと突き合わせ、食い違ったら落とす。バイパスではなく答え合わせです。
  • エラー文言も同じファイルの中にあります。バージョン違いは Invalid:、lockへの追加忘れは Missing: と分かれています。
実行結果（package.jsonに ms を足して lock を放置 / npm 10.9.7）
npm error Missing: ms@2.1.3 from lock 
file

では、この「lockだけを見る」という説明はどこから来たのか。npm 自身の告知が出どころです。

npm Blog「Introducing `npm ci`」2018年3月5日 — 原文
npm ci bypasses a package's package.json to install modules
from a package's lockfile. This ensures reproducible builds
—you are getting exactly what you expect on every install.

（npm ci はパッケージの package.json をバイパスして、
　lockfile からモジュールをインストールする）

2018年の一文です。このページは今も HTTP 200 で生きています（2026年8月14日確認）。200 は「ページが正常に表示できた」、404 は「そのページは無い」を表すコードです。8年前の説明が、現在の実装と真逆のまま引用され続けています。

Q. npm ci が「lockとpackage.jsonがズレている」で落ちたとき、node_modules はどうなっている?

正解。公式ドキュメントは「node_modules があれば npm ci が始まる前に自動で削除される」と書いているので、「まず全消しする」と読んだ人は1番を選びます。ですが実装（lib/commands/ci.js）のコメントは Only remove node_modules after we've successfully loaded the virtual tree and validated the lockfile（仮想ツリーの読み込みとlockの検証に成功したあとでのみ node_modules を削除する）。上の実測でも、落ちた後に node_modules/chalk の 4.0.0 がそのまま残っていました。つまり npm ci の失敗は、壊れかけの node_modules を作りません。逆に、検証に通ったときは本当に消えます（node_modules に置いたマーカーファイルが消えることを確認済み）。

3lockの registry.npmjs.org からは取ってこない

lockは registry.npmjs.org と言っている。実際は 127.0.0.1 から7個取ってきた

package-lock.json を開くと、各パッケージに resolved という項目があります。https://registry.npmjs.org/chalk/-/chalk-4.0.0.tgz のようなURLです。ここから取ってくる、と思いますよね。

手元にニセのレジストリ（＝パッケージを配るサーバー）を立てて、npm の設定ファイル .npmrc の1行だけ差し替えて測りました。127.0.0.1 は「自分のPC自身」を指すアドレスです。lock は1文字も変えていません。

7個すべてが手元のサーバーから来ました。警告は1つも出ていません。（ログの /npm は npm 自身の更新チェックです。）

これは事故ではなく仕様です。公式ドキュメントが明言しています。

npm Docs「package-lock.json」File Format — 原文
resolved: The place where the package was actually resolved
from. In the case of packages fetched from the registry, this
will be a url to a tarball. [...] registry.npmjs.org is a
magic value meaning "the currently configured registry".

（resolved はパッケージが実際に解決された場所。
　[...] registry.npmjs.org は「現在設定されている
　レジストリ」を意味するマジックバリューである）
  • マジックバリューなのは、この文字列のときだけです。registry.npmjs.org と書かれた resolved は「今の設定先」を指す合言葉になります。社内ミラー（社内に置いたレジストリの複製）やプロキシに向けたら、そちらから来ます。
  • npm には omit-lockfile-registry-resolved という設定まであります。公式ドキュメントいわく、resolved キーを書かない lock を作る設定です。resolved がそもそも取り外し可能な情報だという裏付けになっています。

ただし resolved が別ホストなら、設定を変えてもそのURLへ取りに行く

ここで止めると嘘になります。マジックバリューは registry.npmjs.org という文字列に対してだけ働きます。lock に別のホスト名が書かれていたら、話は逆です。

私設レジストリを2台立てました。8871で lock を作り、resolved にそのURLが書かれた状態で、設定だけ8872に向けて npm ci しました。

実行結果（resolved が 8871 / 設定は 8872 / npm 10.9.7）
-- lock の resolved --
http://127.0.0.1:8871/demo-lib/-/demo-
lib-1.0.0.tgz
-- registry を 8872 にして npm ci --

added 1 package in 281ms
8871(lockのURL) への取得: 1
8872(設定した先) への取得: 0

設定した先には1度も取りに行っていません。lock に書かれたURLがそのまま使われました。

  • だから2通りある、という話です。registry.npmjs.org で作った lock は設定に従い、社内ミラーで作った lock はそのミラーを指し続けます。
  • 効いてくるのは、CIだけ設定が違うときです。手元は社内ミラー、CIは公開レジストリ——このとき lock の resolved がどちらを向いているかで、取りに行く先が決まります。

取得元がどちらでも、中身は固定される

では取り放題かというと違います。同じミラーの chalk だけを、中身の違う自作 tarball（パッケージを1個にまとめた圧縮ファイル）にすり替えて測りました。

lock の integrity が効きました。この sha512- という書式は npm 独自のものではありません。公式ドキュメントは integrity を「Standard Subresource Integrity string」と説明し、定義を W3C の規格に外注しています。

W3C「Subresource Integrity」Working Draft, 2026年3月20日 — 原文
This specification defines a mechanism by which user agents
may verify that a fetched resource has been delivered
without unexpected manipulation.

（この仕様は、取得したリソースが予期しない改変を受けずに
　配送されたことをユーザエージェントが検証できる仕組みを
　定義する）

つまり lock が確実に守っているのは中身のほうです。取得元が固定されるかどうかは、resolved に何と書かれているかで変わります。

この穴を、別の実装は明示的に塞いでいます
pnpm は「指定した分だけ」レジストリ名込みでキーを書く
pnpm（npm と同じ役割の、別のパッケージマネージャ）の公式ドキュメントにこうあります。If you install from more than one registry, use namedRegistries aliases for the packages that must come from a specific one. Since v11.20.0, pnpm records those packages in the lockfile under registry-qualified keys (<name>@<registryName>:<version>), so a package cannot be quietly substituted by another registry that publishes the same name and version. [...] Packages installed without an alias are resolved through the default registries configuration as before.（複数のレジストリからインストールするなら、特定の1つから来なければならないパッケージには namedRegistries のエイリアスを使うこと。v11.20.0 以降、pnpm はそれらのパッケージをレジストリ修飾キーで lock に記録する。これにより、同じ名前とバージョンを公開する別のレジストリによって静かにすり替えられることがなくなる。[...] エイリアス無しでインストールされたパッケージは、これまでどおり既定のレジストリ設定を通して解決される）。全パッケージが自動でそうなるわけではありません。それでも「lockがレジストリを固定していない」という認識が、別実装の設計変更として文書に残っています。
ただし npm でも中身のすり替えは検知されます
上の EINTEGRITY のとおりです。危ないのは「同じ名前・同じバージョンで、中身も含めて別物を正規に公開しているレジストリ」に向いてしまった場合です。

4lockを揃えても、lockの外が揃っていない

同じlockで npm ci した2台。片方だけファイルが増えた

インストール時にコードを走らせるパッケージがあります（postinstall など）。lock はこれを記録しています。ただし記録しているのは「持っている」という事実だけです。ここから先の「破壊的変更」は、上げると今までの書き方が通らなくなる種類の変更を指します。

postinstall で ran.txt を作るだけの自作パッケージを依存にして、まったく同じ lock を npm 10 と npm 12 の両方で npm ci しました。

実行結果（同じlock / npm 10.9.7 と npm 12.0.2）
-- lock のエントリ --
hasInstallScript: true
-- npm 10 で ci --
ran.txt: できた
-- npm 12 で ci (同じ lock) --
npm warn install-scripts 1 package
had install scripts blocked because
they are not covered by allowScripts:
npm warn install-scripts
hello-dep@1.0.0 (postinstall: node -e
"require('fs').writeFileSync(process.e
nv.INIT_CWD+'/ran.txt','ran')")
ran.txt: できない

lock は同じ。入るパッケージも同じ。それでもディスクの中身が違います。

これは npm 12.0.0（2026年7月8日）の破壊的変更です。

npm/cli CHANGELOG v12.0.0 — BREAKING CHANGES
Dependency lifecycle scripts are now blocked by default
unless allowed by the root package's `allowScripts` policy.
After installing, run `npm install-scripts approve` to record
approvals and `npm rebuild` to execute newly approved
scripts.

（依存の lifecycle スクリプトは、ルートパッケージの
　allowScripts ポリシーで許可されない限り既定でブロック
　されるようになった）

「ルートパッケージ」は自分のプロジェクト本体のことです。では、許可はどこに保存されるのか。インストール時にOS別のバイナリを取ってくる esbuild（JavaScriptのビルドツール）で測りました。

実行結果（npm 12 で install-scripts approve）
-- approve --
Approved esbuild:
  added esbuild@0.21.5
-- 許可は package.json に書かれる --
{"esbuild@0.21.5":true}
-- lock 側に allowScripts はあるか --
lock: false
-- 0.23.0 に上げると再びブロックされる --

install.js)
  • 許可は lock ではなく package.json に書かれます。しかも esbuild@0.21.5 とバージョン込みのキーで。
  • バージョンを上げると許可が外れます。公式ドキュメントいわく、既定は「あなたがレビューした特定バージョンに限定」する形。--no-allow-scripts-pin を付ければ名前だけのエントリになります。
  • これは「第二のロック」です。バージョンの固定（lock）とは別に、実行許可の固定を package.json 側に置いた形になっています。
なぜ 2026年に npm がここまでやったのか
GitHub 自身の説明
GitHub Security Lab の記事（2025年9月22日）は、On September 14, 2025, we were notified of the Shai-Hulud attack, a self-replicating worm that infiltrated the npm ecosystem via compromised maintainer accounts by injecting malicious post-install scripts into popular JavaScript packages. と書き、対応として「500以上の侵害パッケージを npm レジストリから即時削除した」と述べています。攻撃の入口が post-install スクリプトだったという点が、上の既定ブロックとつながります。この記事の技術的詳細を独立に検証してはいないので、ここでは「GitHub がそう説明している」以上のことは言いません。
pnpm が先行していた
pnpm の公式ドキュメントは To mitigate this, pnpm v10 disables the automatic execution of postinstall scripts in dependencies. と書いています。npm 12 はこの設計に追随した形です。

lockは「自分がどのフラグで作られたか」を覚えていない

もう1つ、lock の外にある状態があります。lock を作ったときのコマンドのオプション（＝フラグ。以下フラグと書きます）です。

peer 依存は「自分と一緒に入るはずの相手」の宣言です。AがBの1系を要求しているのに、あなたがBの2系を頼むと両立しません。この衝突する状態を小さなパッケージで自作して、--legacy-peer-deps（衝突を無視して進めるフラグ）付きで lock を作り、CIを想定してフラグ無しで npm ci しました。

実行結果（フラグ付きで作ったlockを、フラグ無しでci / npm 10.9.7）
-- 素の install --
npm error code ERESOLVE
-- --legacy-peer-deps 付き --

added 2 packages in 268ms
-- その lock でフラグ無し ci --
npm error code ETARGET
npm error notarget No matching 
version found for libx@^1.0.0.

Q. CIで npm install ではなく npm ci を使えと言われるのは、なぜ?

正解。ここでいう「凍結」はlock から1ミリも動かさないモードのことです。これは npm 固有の既定値の話であって、lock 一般の性質ではありません。pnpm と Yarn（どちらも npm と同じ役割の別のパッケージマネージャ）を見ると分かります。pnpm の公式ドキュメントは When pnpm detects that it is running in CI, it switches to frozen-lockfile mode automatically.、Yarn は If the --immutable option is set (defaults to true on CI), Yarn will abort with an error exit code if the lockfile was to be modified と書いています。どちらもCIでは既定で凍結し、人間に選ばせていません。1番について: 出所は2018年の npm 公式告知の npm ci is fast—in some cases, twice as fast as using npm i です。in some cases という留保が、引用の過程で落ちています。今回、速度は測っていません。3番について: 2章のとおり、npm install も lock を読みます。

6「全部ピン留めしろ」は査読論文に否定されている

直接依存を固定すると、攻撃に晒されるリスクがむしろ上がる

ここまで読むと「範囲指定をやめて全部固定すればいい」と思うはずです。これを定量的に否定した論文があります。

He, Vasilescu, Kästner「Pinning Is Futile」FSE 2025 — 抄録
By simulating dependency resolutions over historical time
points, we find that pinning direct dependencies not only
(as expected) increases the cost of maintaining vulnerable
and outdated dependencies, but also (surprisingly) even
increases the risk of exposure to malicious package updates
in larger dependency graphs due to the specifics of npm's
dependency resolution mechanism.

（過去の時点における依存解決をシミュレートした結果、直接
　依存のピン留めは、予想どおり脆弱で古い依存を保守する
　コストを増やすだけでなく、驚くべきことに、npm の依存
　解決機構の特性ゆえに、大きな依存グラフではむしろ悪意
　あるパッケージ更新に晒されるリスクを増大させる）

理由は 5.1節に書かれています。ここでいう「浮動」は範囲指定にしていて上がりうる依存、「重複」は同じパッケージの別バージョンが同時に入ることです。

同論文 5.1節 — 原文
The deduplication process interacts with pinning: If more
dependencies are pinned, the dependency graph resolution has
fewer opportunities to deduplicate a specific package and
will be more likely to create larger dependency graphs with
multiple versions of the same package. Those different
versions may also then include additional dependencies [...]

（重複排除の処理はピン留めと干渉する。固定する依存が増える
　ほど、依存グラフの解決は特定のパッケージをまとめる機会を
　失い、同じパッケージの複数バージョンを含むより大きな依存
　グラフを作りやすくなる。それら別バージョンがさらに別の
　依存を連れてくることもある）

同じ論文は、lock の限界も書いています。

同論文 2節 Background and Related Work — 原文
A lock file ensures the reproducibility of npm builds, but it
has two limitations: (1) it is restricted to applications
(the root of the dependency graph) whereas components used
as dependencies cannot pass their lock decisions to
downstream applications; [...] (2) it is not designed (hence
very difficult) to be manually maintained, so floating
version constraints in package.json will still cause
automatic updates every time a lock file is generated.

（lock は npm ビルドの再現性を保証するが、二つの限界が
　ある。(1) 依存グラフの根であるアプリケーションに限定
　され、依存として使われるコンポーネントは自身のロック
　判断を下流に渡せない。(2) 手作業での保守を想定して
　いないため、package.json 中の浮動バージョン制約は、
　lock が生成されるたびに自動更新を引き起こし続ける）
  • lock はアプリのためのものです。ライブラリを作っている人の lock は、それを使う側には届きません。
  • lock を commit しているのは半分以下。同論文 5.2節は、データセット中の GitHub リポジトリの 44.21% が lock をリポジトリに入れていたと報告しています。
  • 独立した別チームの研究も同じ方向です。Rahman ほか（ASE 2025）の抄録は floating-minor is the least likely to result in vulnerable dependencies（^1.2.3 相当が最も脆弱になりにくい）と述べています。こちらは抄録のみ読了で、本文は読んでいません。

ただし ^ の意味は、パッチを書くかどうかで正反対になる

範囲指定を使うなら、^ が実際に何を許すかは知っておく必要があります。npm の解決に使われている node-semver の README に脱糖規則が書いてあります。

node-semver README — Caret Ranges（[...] は中略）
Allows changes that do not modify the left-most non-zero
element in the `[major, minor, patch]` tuple.

* `^1.2.3` := `>=1.2.3 <2.0.0-0`
* `^0.2.3` := `>=0.2.3 <0.3.0-0`
* `^0.0.3` := `>=0.0.3 <0.0.4-0`
[...]
When parsing caret ranges, a missing `patch` value desugars
to the number `0`, but will allow flexibility within that
value, even if the major and minor versions are both `0`.

* `^1.2.x` := `>=1.2.0 <2.0.0-0`
* `^0.0.x` := `>=0.0.0 <0.1.0-0`
[...]

原文が言っている [major, minor, patch] がそのまま鍵です。バージョンは 1.2.3 のようにメジャー.マイナー.パッチの3つの数字でできています。キャレットは「左端の0でない数字を動かさない範囲まで上げてよい」という意味になります。

末尾の -0 はプレリリース版よけです。手元の semver 7 で確かめたところ、2.0.0-beta は <2.0.0-0 に入らず、<2.0.0 のほうは（プレリリースを含める設定にすると）入りました。

書き方許す範囲実質
^1.2.3>=1.2.3 <2.0.0-0マイナーもパッチも上がる
^0.2.3>=0.2.3 <0.3.0-0マイナーは上がらない
^0.0.3>=0.0.3 <0.0.4-0一切上がらない
^0.0.x>=0.0.0 <0.1.0-00.1.0未満を全部許す

同じキャレットで、^0.0.3 は一切更新を許さないのに ^0.0.x は0.1.0未満を全部許す。パッチ値を書くか x にするかで正反対です。

そして、この ^ は自分で選んだものではないかもしれません。npm 公式ドキュメントいわく、save-prefix の既定値は "^"。npm install なにか と打つたびに、キャレットが自動で書き込まれています。

時間で守るという別の考え方
npm の min-release-age
npm 11.10.0（2026年2月11日）で追加された設定です。公式ドキュメントいわく If set, npm will build the npm tree such that only versions that were available more than the given number of days ago will be installed.（設定すると、指定日数より前に公開されたバージョンだけを入れる）。既定は null（無効）です。今回この設定は動かしていません。
pnpm は既定で1日
pnpm の公式ドキュメントは In pnpm v11, this defaults to 1440 (1 day), meaning newly published packages will not be resolved until they are at least 1 day old. と書いています。公開直後の悪意あるバージョンを踏みにくくする、という発想です。

7今日やること

lockを置くだけでは足りない。揃えるものが4つある

ここまでの実測から、リポジトリに残っていない状態を並べます。以下は標準や規格ではなく、この記事の実測から導いた筆者の運用上の目安です。

  • npm 自身のバージョンを揃える。同じ lock でも npm 10 と npm 12 で結果が違いました（4章）。CIの設定ファイルにバージョンを書いてください。
  • lock を作ったときのフラグを揃える。--legacy-peer-deps を手元で使っているなら、CIにも同じものを渡す。エラー文面は原因を教えてくれません（4章）。
  • 取得先レジストリを意識する。lock の resolved が registry.npmjs.org なら設定した先から、社内ミラーのURLならそのミラーから来ます（3章）。手元とCIで .npmrc の registry が違うなら、lock がどちらを向いているかを見てください。
  • CIでは npm ci を打つ。pnpm と Yarn はCIを検知して自動で凍結しますが、npm は打たない限り凍結しません（5章のクイズ）。

1番目と4番目は、書く場所が決まっています。GitHub Actions なら .github/workflows/ の中の .yml ファイルです。

.github/workflows/ci.yml（該当部分だけ）
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
    with:
      node-version: '22.22.2'
  - run: npm i -g npm@12.0.2
  - run: npm ci

バージョンの数字は自分の環境に合わせて置き換えてください（手元で node -v と npm -v を打った値です）。この YAML 自体は、GitHub Actions を動かせない環境のため実行して確かめていません。効くのは「npm のバージョンを書き残す」という一点です。

確認するところまでやり切るためのリストです。0 / 5

🎉 「自分の環境では動く」の穴が、だいぶ埋まりました

今回、測れなかったこと

正直に書きます。この記事で扱えなかった論点があります。

  • OS別のネイティブバイナリは測っていません。rollup や esbuild のような、OSごとに違う中身を入れる必要があるパッケージの話です（入らなくてもエラーにしない依存を optionalDependencies と言います）。これが lock でどう扱われるか。package-lock.json が os / cpu フィールドを持つことは公式ドキュメントで確認しましたが、実際の分岐は一度も動かしていません。関連する npm/cli の issue は、このセッションの通信制限で本文を1つも読めませんでした。
  • 別マシン・別OSでの再現はしていません。「時期の違い」は --before、「環境の違い」は npm のメジャーバージョン差で代用しました。Docker が動かない環境だったため、本物のCIコンテナとの比較もしていません。
  • 速度は測っていません。「npm ci は2倍速い」とは書けません。出所の2018年の告知にある in some cases 以上のことは言えません。

ターミナル出力について1つ。npm が出す長い行を npm 側で40桁に折る方法が見つからなかったため、掲載したコマンドはすべて末尾に fold -s -w 38 か grep を含めた形で実行しています。出力を手で書き換えた箇所は1つもありません。

作業中の失敗も2つ記録しておきます。cut -c11- で npm error の接頭辞を落とそうとしたら、npm warn は接頭辞が9文字なので tarball が arball に化けました。もう1つ、ミラー実験で前回のキャッシュとサーバーが残っていて、ミラーに1度もアクセスしていないのに「added 7 packages」と出ました。まさに「成功したように見えるが実は別の物を見ている」です。キャッシュを毎回作り直して測り直しました。
