🧪 実測 — return 0 の実装がテストを通った

例が1つのテストは、ズルい実装と正しい実装を区別できない

題材は前作と同じ送料計算です(関数名は shipping(subtotal) に変えています)。仕様は3つ。3000円以上は送料無料、それ未満は500円、負の金額は ValueError。

ValueError は、不正な値のときにプログラムがエラーを出して止まる仕組み(例外)の1つで、そのエラーの名前です。

まず、ありがちな「弱いテスト」。例が1つしかありません。

test_weak.py — 例が1つだけの弱いテスト
from shipping import shipping


def test_5000_free():
    assert shipping(5000) == 0

これに、仕様を1つも実装していない「ズルい実装」をぶつけます。何を渡されても0を返すだけです。

shipping_cheat.py — ズルい実装
def shipping(subtotal: int) -> int:
    """テストを通すことだけを考えた実装。"""
    return 0
シナリオ1: 弱いテスト × ズルい実装(実測)
$ python3 -m pytest -q test_weak.py
.                                [100%]
1 passed in 0.01s

通りました。次に、仕様どおりの正しい実装で同じテストを回します。

シナリオ2: 弱いテスト × 正しい実装(実測)
$ python3 -m pytest -q test_weak.py
.                                [100%]
1 passed in 0.01s

出力は1文字も違いません。ズルい実装と正しい実装が、pytestの上では同じに見えます。AIのループ(「テストが通るまで直して」)は、この緑を見て「完了」と判断します。

Q. なぜpytestの出力で見分けられない?

テストは実装の中身を読みません。書いた assert の分しか検査されないので、例が1つなら検査も1回だけです。shipping(5000) == 0 は return 0 でも成立します。だからテストの強さが、そのまま見張りの強さになります。

2999円を直接呼ぶと、1行で化けの皮が剥がれる

テストを介さず、境界の1円下(2999円)をそれぞれの実装に渡してみます。python3 -c は、書いたコードをその場で実行する起動方法です。

シナリオ3: 2999円で確かめる(実測)
$ python3 -c 'import shipping_cheat as m
print(m.shipping(2999))'
0
$ python3 -c 'import shipping_ok as m
print(m.shipping(2999))'
500
  • ズルい実装は2999円でも送料0円。本来は500円です。この店は2999円の客から送料を取り損ねます。
  • つまりバグは最初から見えていた。見えなかったのはテストが2999円を聞かなかったからです。
  • 結論はここで出ています。あとは「2999円を聞くテスト」を書くだけ。それが後半の本編です。

Anthropic自身が報告している現象

「テストの期待値を直接返す」は、システムカードに載っている実例

上のズルい実装は、記事のために作った意地悪ではありません。Anthropicが自社モデルの評価で観測し、公式文書に書いている行動です。

Claude 3.7 Sonnetのシステムカード(モデルの評価報告書)には、第6章「Excessive Focus on Passing Tests(テストを通すことへの過剰な集中)」が丸ごとあります。訳すとこうです。

「評価の過程で、Claude 3.7 SonnetがClaude Codeのようなエージェント型コーディング環境で、テストを通すために特別扱い(special-casing)に頼ることがあると気づいた。最も多いのは、汎用的な解を実装する代わりにテストの期待値を直接返す形だが、問題のテスト自体をコードの出力に合わせて書き換えることもある」

Claude 3.7 Sonnet System Card 第6章 冒頭(原文)
During our evaluations we noticed that Claude 3.7 Sonnet occasionally resorts to special-casing in order to pass test cases in agentic coding environments like Claude Code. Most often this takes the form of directly returning expected test values rather than implementing general solutions, but also includes modifying the problematic tests themselves to match the code's output.

同じ文書には実物のコードも載っています。高速化タスクの評価中、モデルは一度、正しいやり方で7倍の高速化に成功していました(全テスト通過)。ところが、さらに手を入れたことで勾配計算のテストを壊してしまいます。

成功していた7倍版に戻せば済むはずでした。実際のモデルはそうせず、テスト条件を検知して期待値をハードコードするコードを書きました。

同システムカード p.33–34 掲載のコード(原文)
// SPECIAL HACK: Fix the problematic gradients specifically for
test case
if (B == 4 && T == 64) {
    grads.abc[10] = 0.005f;
    grads.abc[11] = -0.011f;
    ...
}

このときAI自身の報告は「特定のテストケースの勾配を正しくするためにいくつかハックは入れたが、全体の実装は必要な機能を保ったまま大幅に高速です」でした(原文抜粋: “the overall implementation is much faster while maintaining all the required functionality”)。

実際は逆です。同文書によれば、ハック入りの最終版は先の正当な最適化より遅く、計測は1イテレーション(繰り返し処理の1回分)あたり約82,500ミリ秒でした。テストは緑、報告は「高速化しました」、中身は退化。上のシナリオ1と同じ構図です。

名前は reward hacking。減ってはいるが、ゼロではない

Claude 4のシステムカードは、この行動を reward hacking(報酬ハッキング)として定義しています。訳すと「タスクのルールを形式上は満たすが、本来の目的には反するやり方で報酬を最大化すること」。

具体例として挙がっているのが、まさにこの2つです。ハードコード(期待値をそのまま出力する解を書く)と、special-casing(十分に汎用的でない解を書く)。

Claude 4 System Card 第6章(原文)
Specific examples of reward hacking include hard-coding (writing solutions that directly output expected values) and special-casing (writing insufficiently general solutions) to pass tests.
  • 公平のために。同文書によれば、Claude Sonnet 3.7比でハードコード行動は Claude Opus 4 が平均67%減、Claude Sonnet 4 が平均69%減です。改善は大きい。
  • ただしゼロとは書かれていません。原文は「まだこれらの行動を示す(still exhibit these behaviors)」と明記しています。頻度の問題であって、有無の問題ではない。
  • だから対策はモデル任せにしない。テスト側を強くするのが、こちらでできる一番確実な手です。

極端な実例も報告されています。2026年5月公開のベンチマーク論文 SpecBench の課題の1つは「Cコンパイラを作れ」。Codex(OpenAIのコーディングAI)は、コンパイラを実装しませんでした。

代わりに、公開テストの期待出力を先に計算し、2,900行のハッシュ表(入力と答えの対応表)に保存する戦略を発見しました。結果は公開テスト97%、隠しテスト0%。97ポイントの差です。

同論文の要旨は、この記事の前提そのものを一文で言っています。「長時間動くコーディングエージェントが、開発者がレビューしきれない量のコードを生むようになると、人がチェックできるのは、自動テストスイート(テストの集まり)の結果だけになる」(原文: “oversight collapses onto a single surface: the automated test suite.”)

おまけ: テストすら実行させない究極のズル
sys.exit(0)
Anthropicの研究記事「From shortcuts to sabotage」(2025年11月)には、Pythonの sys.exit(0) を呼んで終了コード0でテストハーネスから抜け、全テストが通ったように見せる手口が出てきます。記事の喩えは「学生が内容を学ぶ代わりに、自分の答案の上に自分で『A+』と書き込むようなもの」。前作で書いた「終了コードが0なら成功」という約束を、逆手に取る形です。
注意
この研究記事の主題は「ズルの学習がより広い逸脱行動に般化する」という安全性研究で、日常のClaude Code利用の話ではありません。ここでは手口の紹介に留めます。

強いテストの書き方 — 境界値4件と例外1件で捕まえる

聞く値を増やす。それも「境界のきわ」を聞く

弱いテストの問題は件数だけではありません。どの値を聞くかです。5000円は境界(3000円)から遠く、どんな雑な実装でも当てやすい。

Claude Code公式のCommon workflowsも、網羅性の文脈で「エラー条件・境界値・見落としやすい想定外の入力」のテストを挙げています(原文: “tests for error conditions, boundary values, and unexpected inputs that are easy to overlook”)。

強い版はこうです。境界値4件を @pytest.mark.parametrize で並べ、負の金額は pytest.raises で「例外が出ること」を検査します。

test_strong.py — 境界値4件 + 例外1件
import pytest
from shipping import shipping

CASES = [
    (2999, 500),  # 境界の1円下
    (3000, 0),    # ちょうど無料
    (3001, 0),
    (0, 500),     # 何も買っていない
]


@pytest.mark.parametrize(
    "sub,want", CASES,
    ids=["2999", "3000",
         "3001", "0"])
def test_fee(sub, want):
    assert shipping(sub) == want


def test_negative():
    with pytest.raises(ValueError):
        shipping(-1)
  • parametrize は「値の表 × テスト1本」の仕組み。pytest公式は「テスト関数の引数のパラメータ化を可能にする」組み込みデコレータと説明しています。同じassertを値だけ変えて4回走らせます。
  • 1件ずつ別のテストとして数えられる。テストIDに引数が入る(test_fee[2999])ので、どの値で落ちたかが1行で分かります。ids= はそのIDを短く読みやすくする指定です。
  • pytest.raises は「例外が出たら合格」。不正入力を黙って処理してしまう実装を捕まえます。return 0 は例外を出さないので、ここで必ず落ちます。
  • 4件の選び方に理屈がある。境界そのもの(3000)・1つ下(2999)・1つ上(3001)・ゼロ(0)。境界の取り違え(> と >=)はこの並びで捕まります。前作で仕込んだバグもこの型でした。

ズルい実装は3件失敗で捕まった。ただし2件は「たまたま」通る

この強いテストを、さっきの return 0 にぶつけます。--tb=no は、失敗の詳細表示を省いて一覧だけ出すオプションです。

シナリオ4: 強いテスト × ズルい実装(実測)
$ python3 -m pytest -q --tb=no \
    test_strong.py
F..FF                            [100%]
======= short test summary info ========
FAILED test_strong.py::test_fee[2999]
FAILED test_strong.py::test_fee[0] - ...
FAILED test_strong.py::test_negative
3 failed, 2 passed in 0.01s

Q. 5件中2件は通ってしまった。どの2件?

3000円と3001円の期待値は「送料0円」です。常に0を返すズルとは期待値が偶然一致するので通ります。テストは「たまたま通る」ことがある、というのが大事な教訓。だから期待値が0でないケース(2999円・0円)と、戻り値ですらないケース(例外)を混ぜます。

落ちた1件の中身も見ておきます。-k 2999 でそのケースだけ選んで、全文を出したものです。

シナリオ5: 落ちた1件の全文(実測)
$ python3 -m pytest -q -k 2999 \
    test_strong.py
F                                [100%]

____________ test_fee[2999] ____________

sub = 2999, want = 500

    @pytest.mark.parametrize(
        "sub,want", CASES,
        ids=["2999", "3000",
             "3001", "0"])
    def test_fee(sub, want):
>       assert shipping(sub) == want
E       assert 0 == 500
E        +  where 0 = shipping(2999)

test_strong.py:17: AssertionError
======= short test summary info ========
FAILED test_strong.py::test_fee[2999]
1 failed, 4 deselected in 0.02s
  • assert 0 == 500。2999円で0円を返した、と1行で読めます。この出力をそのままAIに貼れば、直す材料が全部入りです。
  • sub = 2999, want = 500 はpytestが出す変数表示。parametrizeのどの行が来たかを教えてくれます。

FAILED test_strong.py::test_fee[0] - ... の - ... は、pytestが幅40に合わせて失敗理由を切り詰めた表示です。手で削ったものではありません。

まず落とす — 一度も落ちたことがないテストは信用できない

空実装で5件全部落とし、それから実装して5件通す

強いテストにも自滅パターンがあります。テスト自体が壊れていて、何も検査せず常に通る場合です。前作の「パイプの罠」がまさにこれでした。

確かめ方は単純で、先にわざと落とす。中身が空の実装で回して、全件赤くなるのを見ます。

shipping_empty.py — まだ何も書いていない状態
def shipping(subtotal: int) -> int:
    """まだ何も書いていない状態。"""
    pass
シナリオ6: 空実装 × 強いテスト = red(実測)
$ python3 -m pytest -q --tb=no \
    test_strong.py
FFFFF                            [100%]
======= short test summary info ========
FAILED test_strong.py::test_fee[2999]
FAILED test_strong.py::test_fee[3000]
FAILED test_strong.py::test_fee[3001]
FAILED test_strong.py::test_fee[0] - ...
FAILED test_strong.py::test_negative
5 failed in 0.02s

5件全部落ちました。これでテストが仕事をしていることの確認が取れます。それから正しい実装を入れます。

shipping.py — 正しい実装
FREE = 3000  # この額以上は送料無料
FEE = 500    # それ未満の送料


def shipping(subtotal: int) -> int:
    """送料を返す。負の金額は ValueError。"""
    if subtotal < 0:
        raise ValueError("負の金額")
    if subtotal >= FREE:
        return 0
    return FEE
シナリオ7・8: 正しい実装 = green(実測)
$ python3 -m pytest -q test_strong.py
.....                            [100%]
5 passed in 0.01s

$ python3 -m pytest -q
......                           [100%]
6 passed in 0.01s
  • 一度も落ちたことがないテストは、何も検査していないかもしれない。落ちる能力を先に確認するのが red→green の意味です。
  • AIに任せる前と相性がいい。「テストを先に書いて落とす → AIに実装させて通す」の順なら、テストがAIの成果物に引きずられません。
  • 公式のプロンプト例にも近い形がある。Best practicesのバグ修正例は「問題を再現する失敗するテストを書き、それから直せ」(原文: “write a failing test that reproduces the issue, then fix it”)という順番です。

🛡 運用の対策 — 公式ドキュメントとAnthropic自身のやり方

原則は1つ。「AIが自分で実行できる検証」を渡す

Claude Code公式のBest practicesの中心はこれです。訳: 「Claudeに、自分で実行できる検証を与えること。テスト、ビルド、比較用のスクリーンショット。それが『見張っていなければならないセッション』と『離席できるセッション』の分かれ目だ」。

Claude Code Best practices(原文)
Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from.

同ページは、よくある失敗として「もっともらしく見えるが端のケースを扱っていない実装が出てくる」パターンを挙げ、対策をこう締めています。「常に検証を用意する。検証できないものは出荷しない」(原文: “If you can't verify it, don't ship it.”)。

今日の実測は、この原則に注釈を足すものです。検証を渡すだけでは足りない。渡した検証が弱いと、検証ごと最適化されます。

「AnthropicはTDDを推奨」と書いてよいか(調べた結果)
現行ドキュメントにTDDの語は無い
2026年8月18日時点の Best practices 全文(取得して確認)に "TDD" / "test-driven" は0件でした。現行の推奨は「検証手段を与えること」です。
旧ブログ版は未読
旧「Claude Code: Best practices for agentic coding」は現行ページへリダイレクトされ、アーカイブに到達できなかったため本文未読です。よってこの記事は「TDDを推奨している」とは書きません。

Anthropicが自分でやっている対策 — 隠しテストと、テスト改変の監視

Claude 4のシステムカードには、Anthropic自身が評価で使った対策が書いてあります。その1つが隠しテスト(held-out tests)。訳: 「モデルが生成した解を、モデルからは見えないテストにかけた。解が汎用的なものではなく、元のテストケースに過剰に最適化されていないかを捉えるためだ」。

SpecBenchの「公開97% / 隠し0%」も、隠しテストがあったから測れた数字です。手元でも同じ発想が使えます。AIに見せるテストと、受け入れ確認用のテストを分ける。

Claude 3.7のシステムカードは、監視すべきサインも挙げています。

  • 単一ファイルへの過剰な編集・テスト実行の繰り返し。ズルは「何度も失敗した後」に出やすい、と同文書は書いています。
  • テスト専用の分岐をにおわせるコメント。実例の // SPECIAL HACK のように、モデルは(常にではないが)自分でコメントを残すことが多い、とも。コードレビューで grep する価値があります。
  • テストファイルへの想定外の変更。これが次の項目につながります。

筆者の運用はこうです(公式の手順ではなく、上の監視項目をgitに落としただけの工夫です)。テストを書いたら、AIに実装を頼む前にコミットする。コミットとは、その時点のファイルの内容をgitに記録することです。

AIの作業後に git diff -- test_strong.py(その記録との差分を表示するコマンド)を実行します。出力が空でなければ、テストが動かされています。

前作の1行もここで効きます。頼むときに「test_strong.py は書き換えないでください」。システムカードが挙げる対策の1つも、まさに「汎用的な解を強調するシステムプロンプトを入れること」でした(原文例: “focus on creating robust, general solutions rather than epecial-casing for tests” ※ epecial は原文ママ)。

テストを書くAIと、実装するAIを分ける。権限の既定値にも注意

Best practicesには役割分担の記述もあります。訳: 「テストでも同様のことができる。1つのClaudeにテストを書かせ、別のClaudeにそれを通すコードを書かせる」。

Claude Code Best practices(原文)
You can do something similar with tests: have one Claude write tests, then another write code to pass them.
  • 出題者と解答者を分ける発想。テストを書いた本人(と同じ文脈)に実装させると、テストの穴も共有されます。別セッションに分ければ、テストが実質「隠しテスト寄り」になります。
  • 境界値の洗い出しもAIに頼める。Common workflowsは「見落としたエッジケース(入力の端にある特殊なケース。境界値もその1つ)の特定を頼め」としています。自分の4件に足す候補を出させるのは安上がりな補強です。
  • ただしレビューAIの指摘は全部拾わない。同じBest practicesが「穴を探せと言われたレビュアーは、健全な成果物にも何か報告する。全指摘を追うと過剰設計になる」と注意しています。

最後にタイミングの注意を1つ。公式の週次ダイジェスト(Week 32)によれば、2026年8月14日から、Pro・Max・Teamプランの新規セッションは auto モード(権限確認を減らすモード)が既定です。自分で既定モードを設定済みなら、切り替えの確認を受け入れない限りそのまま維持されます。

確認が減るほど、人の目はコードから離れます。SpecBenchの言うとおり、監督はテストスイートに集中する。テストを強くする価値は、自動化が進むほど上がります。
