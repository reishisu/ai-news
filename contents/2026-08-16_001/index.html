Claude Code 2.1.233が、昨日「直った」と書いたBash権限修正をそのまま巻き戻した

8/14 ✓ 公式確認済 Claude Code v2.1.233 ⚠ 前回記事の訂正

巻き戻した理由もリリースノートに書かれています。Windowsでcd <dir> && <command> > fileというごく普通のコマンドを打つたびに、auto modeが手動承認を求めてくるようになった、という回帰(regression)です。セキュリティ側に寄せた修正が実用性を壊し、1日で戻された形です。

  • TodoWriteが新しいモデルから消えた。原文は「Todo/task-tracking tools (TaskCreate/Get/Update/List, TodoWrite) are no longer available on Opus 4.8, Sonnet 5, Fable 5, Mythos 5, and newer models」。復活させるには環境変数CLAUDE_CODE_ENABLE_TODO_TOOLS=1が要ります。TodoWriteを前提にした自動化やCLAUDE.mdの指示は、モデルを新しくした時点で黙って効かなくなります。
  • NTLM資格情報の漏洩経路が塞がれた。Windowsのパスを\??\というNTデバイスプレフィックスで書くと、UNCパス(\\サーバ名\共有名形式のネットワークパス)の検証をすり抜けられた、という不具合です。原文は「closing an NTLM credential-leak vector」。

GitHub OAuth Appが更新トークンに対応 — ついでに「リダイレクトURIが1個のアプリはずっとワイルドカードだった」と公表された

OAuth Appとは、GitHubのログイン情報を使って外部サービスと連携するためのアプリ登録です(似た仕組みのGitHub Appとは別のカテゴリ)。機能追加は3つです。OAuth Appが期限付きアクセストークン(APIを呼ぶための一時的な鍵)と更新トークン(鍵が切れる前に取り直すための鍵)を選べるようになり、リダイレクトURIを最大10個登録でき、GitHub App / OAuth Appの両方でワイルドカード照合を明示的にオン・オフできるようになりました。

ただし読者に効くのは最後の1文です。原文をそのまま引きます。「Apps with only one redirect URI have wildcard matching enabled. This is a legacy behavior of GitHub that is now visible and controllable.」つまり今日穴が空いたのではなく、ずっと空いていたものが見えるようになったということです。

  • リダイレクトURIとは、認可コードの届け先。ユーザーがGitHubで「許可」を押した後、GitHubがブラウザを飛ばす先のURLです。ここを乗っ取られると、認可コードごと他人のサイトに渡ります。ワイルドカード照合が有効だと、登録したURLの周辺(サブドメインや追加パス)にも飛べてしまいます。
  • GitHub自身が危険性を明記している。「Wildcard matching can be abused if the site being redirected to does not have strong control over its routes (e.g., if it hosts user content).」ユーザー投稿をホストするサイトが対象になっている場合は特に危ない、ということです。
  • 新規アプリは短命トークンが既定でON。offline_accessスコープを付けると、有効期限8時間のアクセストークンと6か月の更新トークンが返ります。SDKが更新トークンのフローに未対応なら、SDKを直すまで無効化できると公式が案内しています。
  • GitHub Enterprise Server 3.23に入る。「These improvements will all be included in GitHub Enterprise Server 3.23.」自社ホストのGHESを使っている場合の到達時期はここです。

Claudeの出力に透かしが入る — ただしコードにはほとんど入らず、入るのはコメントのほう

8/14 ✓ 公式確認済 EU AI Act 全世界適用

今後のClaudeは、生成テキストに透かし(watermark)を埋め込みます。目的はEU AI法への対応です。開発者にとっての本題は「コードには透かしがほとんど入らない。入りうるのはコード中のコメント」という点で、Anthropic自身がその理由まで説明しています。

仕組みは「次の単語をどれにしても同じくらい良い」場面で、乱数の代わりに鍵を使って単語を選ぶというもの。原文は「Instead of using an arbitrary random number generator to pick the next word, watermarking uses the key and a few words that come before to settle what word the model should pick.」だから、正確さが要求される場所では透かしが使えません。

  • 追加トークンも隠し文字も無い。原文は「Nothing is added to the text and there are no hidden characters」「Watermarking doesn't require extra tokens, and will not be more expensive」。「ゼロ幅スペースが埋め込まれる」といった話は、公式が明確に否定しています。
  • 事実の記述ほど透かしが薄い。「Watermarking is sparser on factual passages where there are fewer choices」。コードも同じ理屈で、「a piece of code would break if a different term was chosen」場面には適用されません。ただし「such as comments within code」では使われうる、と明記されています。
  • EUの法律なのに全世界に適用される。理由は「we don't yet have a durable way to scope it by region」。地域ごとに切り分ける確実な方法がまだ無いから、というのが公式の説明です。日本の読者も対象です。
  • 検出APIは「近日」で、今は存在しない。「We will soon be offering a watermark detection API. We're in the process of working out the details of its implementation.」現時点では読者側で検証できません。
  • 透かしは「Claudeが関与した」しか言えない。「It cannot distinguish "Claude wrote this" from "Claude heavily edited this."」「軽い編集ではおそらく完全には消えない(Light editing probably won't remove the watermark completely)」、全単語を書き換える完全なリライトなら消える、とも書かれています。

公式は「a version of the SynthID-Text approach published by Google DeepMind in a Nature paper in 2024」と書いています。参照先の書誌はCrossrefで照合しました(Dathathri ほか「Scalable watermarking for identifying large language model outputs」Nature 634, 818-823, 2024-10-23)。ただし論文本文は未取得なので、中身の主張はこの記事では扱いません。系譜としてはScott Aaronsonの2022年の提案まで遡る、とも書かれています。

Laravel 13.25のqueue:pauseを実機で動かした — queue:continueは誤記ではなく、正式な別名だった

8/11 ✓ 公式確認済 ✓ 実機検証済 Laravel 13.25.0 キュー

キューとは、時間のかかる処理(メール送信、画像変換など)を後回しにするための待ち行列です。ワーカー(queue:work)がそれを順番に取り出して実行します。ワーカーを止めずに、新しいジョブを拾うのだけを一時停止するqueue:pause自体はLaravel 12.xからあります。13.25.0で入ったのは、全接続の全キューをまとめて止める・戻す--allのほうです(CHANGELOGの表記も「Add a global pause switch for queues」)。

ところが公式ドキュメントは同じ節の中で、再開コマンドをqueue:continueとqueue:resumeの2通りで書いています。誤記なのか。この環境にLaravelを立てて確かめました。

S3の403エラーに「どのポリシーで拒否されたか」のARNが載るようになった — ただし明示的Denyのときだけ

8/13 ✓ 公式確認済 S3 IAM

S3で403 Access Deniedが出たとき、原因のポリシーを名指しで教えてくれるようになりました。ARNとは、AWSのリソース1つ1つに付く一意の識別名のことです。同じ種類のポリシーが複数あるとき、これまでは1つずつ手で見比べるしかありませんでした。
