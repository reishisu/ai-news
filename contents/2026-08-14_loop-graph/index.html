ループエンジニアリングとグラフエンジニアリングの整理

Claude Code（ターミナル上で動き、人の代わりにファイルを読み書きしコマンドを実行するコーディングエージェント）での実践を前提に、ループエンジニアリングとグラフエンジニアリングを整理します

⭐ この記事の3行まとめ

  1. ループエンジニアリングは「終了条件だけ決めて、あとは回させる」設計 人が毎回プロンプトを打つのをやめ、エージェント（自分で判断してファイルを読み書きし、コマンドを実行するAI）自身に次の一手を決めさせます。
  2. 成否を分けるのは停止条件。機械が判定できる形に落とせるかがすべて 「読みやすくして」は永遠に終わらず、「テストが全部通る」は必ず止まります。
  3. グラフエンジニアリングは、ループが破綻し始めたときの次の一手 作業をノード（1つの作業単位）に分け、順序・分岐・戻り先を先に決めます。最初から使うと複雑になるだけです。

🧭 なぜ「ループ」を設計する話になったのか

変わったのは能力ではなく「誰が次の一手を決めるか」

AIに開発を任せるやり方は数年で段階的に変わってきました。2026年に入って広まったのは、プロンプトを書くのではなく、プロンプトを出し続けるループのほうを書くという考え方です。

  • これまでは人がループの中にいた。実行して、結果を見て、次の指示を出す。この判断を毎回人が担っていました。
  • いまは人がループの外に出る。人が決めるのは「どうなったら終わりか」だけで、途中の判断はエージェントに委ねます。
  • だから設計対象が変わった。プロンプトの上手さより、終了条件・失敗時の戻り方・手を出す境界の設計が成果を左右します。
用語の扱いについて
注意
2つの語で扱いが違います。「ループエンジニアリング」はAnthropic自身が公式ブログの表題に使い、ループの定義も置いています。一方「グラフエンジニアリング」はAnthropicの公開ドキュメント全文を検索しても1件も出てきません（2026年8月15日時点）。後者は完全にコミュニティ側の呼び名なので、この記事では機能の根拠にはせず、使われ方の紹介にとどめています。

🔁 ループエンジニアリング — 終了条件を決めて回させる

「実行 → 確認 → 直す」を、条件を満たすまで自分で繰り返させる

ループエンジニアリングとは、1回の指示で仕上げることを最初からあきらめ、「作業と検証の繰り返し」と「そこから抜ける条件」のほうを設計するやり方です。1発の出力の質を上げるのではなく、雑でもいいから回して収束させる、という発想の転換になります。

流行語のように使われている言葉ですが、Anthropic自身も2026年6月30日の公式ブログで「Loop engineering」を表題に掲げ、ループを「停止条件が満たされるまで作業のサイクルを繰り返すエージェント」と定義しています。同ブログは冒頭で「ループが何を指すのかXで探すと答えがいくつも出てくる」と認めたうえで、Claude Codeチームとしての定義を置く、という書き方をしています。

なお日本語での言い回しは、ほぼ同じ趣旨の定義文がまさお氏のnote記事にあり、この記事もその整理を出発点にしています（参考文献参照）。

  • ループの最小構成は4つ。やること(目標)、実行、結果の確認、そして止まる条件。このうち最後が抜けると永久に回ります。
  • 1周の粒度は小さくする。1周で1つのテストを通す、1ファイルだけ直す、くらいが扱いやすいです。大きすぎると失敗時の巻き戻しが重くなります。
  • 回数の上限は必ず付ける。条件判定が甘くても、上限があれば暴走が事故になりません。
Claude Codeでの入口 — /goal と /loop（選ぶ軸は「終わり方」ではない）
そもそも「/」で始まる表記は何か
Claude Codeの入力欄に /goal つづきの条件… のように打ち込む組み込みコマンドです。公式用語集はコマンドを「プロンプトに /name と入力して呼び出す再利用可能な指示」と定義しています。ターミナルのシェルに打つのではなく、Claudeと話している入力欄に打ちます。
「ターン」とは
あなたが1回メッセージを送ってから、Claudeが応答を終えるまでの1往復です（公式用語集の定義）。途中で何回ツールを使っても1ターンです。後で出てくる「20ターンで打ち切る」は、この往復を20回試してダメなら諦める、という意味になります。
/goal
完了条件を渡すと、1ターン終わるたびに作業役とは別の小さな高速モデル（評価役）が条件の成否を判定します。「満たした」または「達成不可能」と判定されるまで、あなたが打たなくても次のターンが始まります。評価役はコマンドを実行せず、会話に出てきた内容だけで判定するので、条件はClaude自身の出力で証明できる形に書く必要があります。
/loop
次のターンが時間の経過で始まります。間隔もプロンプトもどちらも省略でき、間隔を省くとClaudeが毎回1分〜1時間の範囲で待ち時間を自分で選びます。固定スケジュール（cron）になるのは間隔を明示したときだけです。CI（コードを保存するたびに自動でテストを回す仕組み）の結果待ちや、デプロイ（作ったものを本番環境に反映する作業）の見張りには、この動的モードが向きます。
公式ブログはループを4種類に分けている
「ターン駆動（あなたのプロンプトで始まり、Claudeが完了と判断したら終わる）」「ゴール駆動＝/goal」「時間駆動＝/loop と /schedule」「先回り型（イベントや時刻で始まり、人がリアルタイムでは関与しない）」の4つです。分類の軸は何で始まるか・何で止まるか・どの機能を使うか・どんなタスクに向くか。同ブログは「すべてのタスクが複雑なループを必要とするわけではない。いちばん単純な解から始めよ」とも書いています。
使い分けの軸は「次の一手をいつ始めるか」
公式ドキュメントは、この2つを停止条件ではなく開始条件で並べています。/loopは時間で止まるのではありません。止めるのは人か、Claude自身の完了判断です。
手段次のターンが始まるのは止まるのは
/goal 前のターンが終わったとき モデルが条件成立、または達成不可能と判定したとき
/loop 時間間隔が経過したとき 人が止めるか、Claudeが作業完了と判断したとき
原文（goal.md の比較表・セルの文字列をそのまま。表の余白とリンク記法だけ除いています）
Approach: /goal
Next turn starts when:
  The previous turn finishes
Stops when:
  A model confirms the condition is met or judges it impossible

Approach: /loop
Next turn starts when:
  A time interval elapses
Stops when:
  You stop it, or Claude decides the work is done

🛑 停止条件の書き方が9割

「機械が判定できる条件」しか、ループは止められない

ループ設計でいちばん失敗するのがここです。人間の主観でしか判定できない条件を渡すと、エージェントは終わったかどうか分からず回り続けます。

  • コマンドの終了ステータスに変換する。コマンドは終わるときに成功／失敗の合図（終了ステータス）を返します。この合図をそのまま判定に使うのが最短です。「テストが通る」「型チェック（データの種類の食い違いを機械が検出する処理）が通る」「lint（書き方の乱れを機械が指摘するツール）の指摘が0件」は、いずれもコマンド1本で真偽が確定します。
  • 数を数えられる形にする。「未対応の項目が0件になる」「失敗しているテストが0件になる」のように、残数で表現すると進捗も見えます。
  • 主観的な目標は、代理指標に置き換える。「読みやすくして」ではなく「1関数50行以下にする」「循環的複雑度（処理の分岐の多さを数値化した指標）を10以下にする」と書けば止まります。数値そのものは現場ごとに決めてよく、この50や10は筆者のチームでの目安です。
  • それでも保険は必要。公式ドキュメントも、条件文の中に or stop after 20 turns のようなターン数・時間の句を入れて上限を切る書き方を挙げています。20ターン＝20往復ぶん試してダメなら諦める、ということです。
もう少し詳しく
置き換えの例
「バグを直して」→「再現手順のテストを追加し、それが通る」。目標を先にテストとして書くと、ループの停止条件がそのまま手に入ります。
評価役はコマンドを実行しない
公式ドキュメントによれば、/goal の評価役モデルは自分でコマンドを走らせたりファイルを読んだりしません。会話に出てきた内容だけで判定します。だから「npm test が通る」はClaudeが実際にテストを走らせ、その結果が会話に出ていることで初めて成立します。停止条件には「どう証明するか」まで書いてください。
最初の一歩
いきなり大きな改修に使わず、「関数にJSDoc（関数の説明を決まった書式でコードに書き添えるコメント）を付ける、20ターンで打ち切り」のような小さく安全なタスクで挙動を掴むのが安全です。JSDocが分からなければ「READMEに各コマンドの説明を追記する」でも同じ練習になります。

🕸 グラフエンジニアリング — 破綻し始めたら点と線に分ける

1つのループで抱えきれなくなったら、作業をノードに割る

グラフエンジニアリングは、エージェントの処理をノード(作業単位)・エッジ(次にどこへ行くか)・ステート(引き継ぐ情報)として明示的に設計する考え方です。ループは「自分自身に戻るエッジを1本持つ、最小のグラフ」と捉えられます。

  • ノードは作業単位。AIモデルの呼び出しに限らず、普通のコード実行や人間の承認ステップもノードとして置けます。
  • エッジは「次にどこへ行くか」。条件分岐・並列・失敗時の戻り先を、実行前に決めておける点がループとの決定的な違いです。
  • ステートは引き継ぐ情報。各ノードが何を受け取り何を返すかを決めると、途中から再開したりノードを差し替えたりできます。
  • 強みは再現性と分離。どこで失敗したかが特定でき、失敗したノードだけ作り直せます。
もう少し詳しく
ループとの関係
対立する概念ではありません。ループは1つのエージェントの動作サイクルを制御し、グラフは複数ノードのつながりの構造を制御します。実際にはグラフの各ノードの中でループが回ります。
注意
グラフ化すると設計と保守のコストが増えます。単純な繰り返し作業に持ち込むと、得られる恩恵より複雑さのほうが勝ちがちです。
参考

⚖️ ループのままか、グラフへ移すかの判断

「ループが失敗している兆候」が出てから移す

先にグラフを描きたくなりますが、まずはループで回して、破綻の兆候が出てから分割するほうが結果的に速いです。判断材料は次の4つです。

  • 同じ失敗を繰り返し始めたら。ループが自力で抜け出せないなら、その工程を独立したノードに切り出して条件を変える余地を作ります。
  • 複数の領域にまたがるなら。調査・実装・検証・文書化のように必要な文脈が違う作業は、1つのループに詰め込むと文脈が混ざって精度が落ちます。
  • 並列に走らせたいなら。独立した作業を同時に進めたい時点で、それはもうグラフです。
  • 途中に人の承認を挟みたいなら。承認をノードとして置けるのはグラフの利点です。
逆に、ループのままでいい場合
そのままでよい典型
対象が1つの領域に収まっていて、停止条件がコマンド1本で判定でき、失敗しても最初からやり直せば済む作業。テストを通す、lintを潰す、型エラーを消す、といった収束型のタスクが該当します。
考え方
グラフは「速くするための道具」ではなく「壊れにくくするための道具」です。壊れていないうちは入れなくて構いません。

🛠 Claude Codeでの組み立て方

ループは/goalで、グラフはサブエージェントとワークフローで表現する

Claude Codeには、ループとグラフをそれぞれ担う道具が揃っています。1つのセッションで回すか、役割ごとに分けるかが最初の分岐点です。

  • ループを回す: /goal と /loop。前のターンが終わり次第すぐ次を回したいなら/goal、時間をあけて見に行きたいなら/loop。選ぶ軸は「次のターンをいつ始めるか」です。どちらも上限を添えます。
  • ノードを分ける: サブエージェント。公式ドキュメントの定義は「独自のコンテキストウィンドウ・独自のシステムプロンプト・限定したツール権限で動く専門アシスタント」。調査役・実装役・検証役のように役割ごとに文脈を分離でき、読み取り専用の調査役を別に立てれば本体の文脈が汚れません。
  • 順序と分岐を決める: ダイナミックワークフロー。Claudeが書いたJavaScriptのスクリプトが多数のサブエージェントを指揮する仕組みです。公式ドキュメントいわく「スクリプトがループと分岐と中間結果そのものを保持する」ため、Claudeの文脈には最終結果だけが残ります。エッジとステートをコードに落とす、という意味でまさにグラフです。
  • エッジに条件を仕込む: フック。フックは、ツール実行の前後やセッション開始時など決まった地点で自動的に走る処理で、設定ファイルに書いておきます。モデルの気分ではなく決まった場所で必ず発火する点が肝です。編集後にテストを走らせる、危険なコマンドを止めるといった遷移条件を、プロンプトの言い聞かせではなく仕組み側に持たせられます。
  • 定期実行はセッションの外へ。/loop はセッション（Claude Codeを起動してから終えるまでの一続きの作業）に紐づき、会話を変えると消え、作成から7日で自動失効します。毎朝の定型作業のように長く回したいものは、クラウドで動くRoutines（公式ブログは /schedule でループをクラウドへ移す、と書いています）、自分のPCで動くデスクトップのスケジュールタスク、またはGitHub Actionsに出したほうが安定します。
組み立てのコツ
まず手で1周やる
自動化する前に、自分で1周分の作業をやってみて、判断していた箇所を書き出します。その判断がそのままエッジの条件になります。
検証を独立させる
実装したエージェント自身に「できましたか?」と聞くと甘い判定になりがちです。検証を別ノードに分けると精度が上がります。公式ブログも同じことを書いています——「レビュー役は文脈が新しいぶん偏りが少なく、本体エージェントの推論に引きずられない」。/goal の評価役が作業役と別モデルなのも、同じ理屈です。
ログを残す
どのノードで何回失敗したかが残っていないと、次にどこを分割すべきか判断できません。ループが失敗した記録こそがグラフ設計の材料になります。

訂正と追記

2026年8月15日: /goal と /loop の説明が公式ドキュメントと食い違っていたので直しました

公開後の検証で、この記事の中核である停止条件の説明そのものに誤りが見つかりました。読者が使い分けを間違える内容だったため、公式ドキュメントに合わせて書き直しています。

  • 誤: 「終わりが状態で決まるなら/goal、時間で決まるなら/loop」。正しくは、時間が決めるのは次のターンが始まるタイミングであって、終わりではありません。/loop の停止条件は「人が止めるか、Claudeが作業完了と判断したとき」です。#loop と #practice の該当箇所を、公式の2軸（開始条件・停止条件）に沿って書き直しました。
  • 誤: 「/loop は指定した処理を一定間隔で繰り返す」。間隔は省略でき、省略した場合はClaudeが毎回1分〜1時間の範囲で待ち時間を動的に決めます。固定スケジュールになるのは間隔を明示したときだけでした。記事が勧める「外部の状態を待つ」用途にはむしろ動的モードが合うため、加筆しました。
  • 誤: 「ループエンジニアリングは公式に定義された用語ではない」。今回、公式ドキュメントの全文からAnthropicの公式ブログ「Loop engineering: Getting started with loops」（2026年6月30日）への参照を見つけ、本文を取得して確認しました。同ブログはループを「停止条件が満たされるまで作業のサイクルを繰り返すエージェント」と明確に定義しています。「公式に定義がない」は誤りだったので撤回します。一方「グラフエンジニアリング」は公式ドキュメント全文検索で0件で、こちらはコミュニティ由来の呼び名という記述のままです。
  • 出典の欠落を補いました。ループエンジニアリングの定義文が、本文中でリンクしていたnote記事の一文とほぼ逐語一致していました。定義を自分の言葉で書き直したうえで、由来を本文と参考文献の両方に明示しています。
  • 参考文献に一次資料が1件も無い状態でした。Claude Codeの機能について断定的に書いているのに、根拠が全件コミュニティ記事という構成だったため、公式ドキュメント5件を実際に取得して読み、一次資料として追加しました。確度ラベルの表示も規定の4種類に統一しています。
