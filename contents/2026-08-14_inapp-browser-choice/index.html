アプリ内ブラウザの3択は、Cookieがどこに貯まるかの3択

アプリの中でWebページを開く方法は3つあります。見た目はほぼ同じ。中身はまったく別物です。どこが分かれ目なのかを実測し、規格と公式ドキュメントの原文で裏を取りました。
⏱ 約9分 RFC 8252 原文つき 判断表あり

⭐ 3行で言うと

スマホアプリの中でWebページを開くとき、選べる部品は3つです。WebView / Custom Tabs (Android) / SFSafariViewController (iOS)。この記事は、その3つが何で分かれているのかの話です。

  1. 分かれ目はCookieとストレージの置き場。見た目ではありません 同じ端末で同じサイトを開いても、置き場が違うだけで片方はログイン済み、片方は未ログインになりました。実測を載せます。
  2. WebViewでログインさせるのは規格上 MUST NOT。Googleは実際に閉めました RFC 8252 の禁止条項と、Googleが2021年9月30日にブロックを始めた告知の原文を並べます。パスワードの全打鍵を盗めることも実演しました。
  3. 「SFSafariViewController = iOS版 Custom Tabs」は一次資料では成り立ちません Androidの公式は「共有Cookieジャー」と明記しています。Appleは共有すると書いておらず、共有したいなら別のAPIを使えと書いています。

目次

  1. 3択は「データ置き場」の3択だと規格が定義している
  2. 実測。置き場が違うだけでログインが消えた
  3. WebViewは全打鍵とHttpOnly Cookieを盗める
  4. 「SFSafariViewController = iOS版Custom Tabs」は成り立たない
  5. Googleのドキュメントが、Googleのコードと矛盾している
  6. 審査で落ちるのは、この2行に書いてある
  7. 判断表 — 今日どれを選ぶか

13択は「データ置き場」の3択だと規格が定義している

「アプリ内ブラウザ」は感覚的な呼び名ではなく、定義された用語です

アプリの中にWebページが出てくるとき、実装は3通りあります。どれも画面上は「アプリの中にWebが出た」に見えます。

ところがこの3つは、IETFの規格に用語として定義されています。しかも「見た目」ではなく「アプリがデータに触れられるか」で分けられています。

RFC 8252「OAuth 2.0 for Native Apps」§3 Terminology — 原文
"embedded user-agent"  A user-agent hosted by the native app making the authorization request that forms a part of the app or shares the same security domain such that the app can access the cookie storage and/or inspect or modify page content.

"in-app browser tab"  A programmatic instantiation of the browser that is displayed inside a host app but that retains the full security properties and authentication state of the browser.

"web-view"  A web browser UI (user interface) component that is embedded in apps to render web pages under the control of the app.

訳すと、こうです。

  • embedded user-agent（埋め込みユーザーエージェント）。アプリ自身がホストしていて、アプリがCookieストレージに触れる、かつ／またはページ内容を検査・改変できるもの。
  • in-app browser tab（アプリ内ブラウザタブ）。アプリの中に表示されるが、ブラウザの完全なセキュリティ特性と認証状態を保持するもの。
  • web-view。アプリの制御下でページを描画する、埋め込み用のUI部品。

どれがどれに当たるかも、同じRFCの付録に名指しで書かれています。

RFC 8252 Appendix B.1 / B.2 — 原文
B.1.  iOS Implementation Details
   Apps can initiate an authorization request in the browser, without the user leaving the app, through the "SFSafariViewController" class or its successor "SFAuthenticationSession", which implement the in-app browser tab pattern.

B.2.  Android Implementation Details
   Apps can initiate an authorization request in the browser, without the user leaving the app, through the Android Custom Tab feature, which implements the in-app browser tab pattern.
  • WebView = embedded user-agent。アプリがCookieとページの中身に手を出せる側です。
  • Custom Tabs と SFSafariViewController = in-app browser tab。手を出せない側、という整理になっています。
  • ただし、この付録は2017年10月時点の話です。RFC自身がそう断っています。ここが4章の伏線になります。
RFC 8252 Appendix B 冒頭 — 原文（予防線）
The implementation details herein are considered accurate at the time of publishing but will likely change over time.  It is hoped that such a change won't invalidate the generic principles in the rest of the document and that those principles should take precedence in the event of a conflict.

2実測。置き場が違うだけでログインが消えた

同じ端末・同じサイト・同じユーザー。置き場を分けた瞬間にANONになる

規格の話だけだと信じにくいので、手元で作りました。

まずログインするだけの最小サイトを立てます。ログインすると sid というCookieを配り、ついでにブラウザ側の保存領域（localStorage）に初回だけランダムな印を1個置きます。この印が同じ値なら同じ保存領域を見ている、という判定に使います。

次に、ブラウザのデータ置き場（プロファイル）を切り替えて4回開きます。置き場が別＝WebView相当、置き場が本体と同じ＝アプリ内ブラウザタブ相当です。

実行結果（node exp1_share.js ./prof）
1 本体ブラウザ(ログイン実行)
  status: LOGGED_IN alice
  sid   : alice
  ls.tag: uqks3q
2 アプリAのWebView(別領域)
  status: ANON
  sid   : (なし)
  ls.tag: 07m9r4
3 アプリBのWebView(別領域)
  status: ANON
  sid   : (なし)
  ls.tag: k74coh
4 アプリ内タブ(本体と同領域)
  status: LOGGED_IN alice
  sid   : alice
  ls.tag: uqks3q
  • 2と3は、ログイン画面すら通っていません。Cookieが無いので ANON。印も 07m9r4 / k74coh と別値で、保存領域ごと別だと分かります。
  • 4はログイン操作を1回もしていないのに LOGGED_IN alice。印まで本体と同じ uqks3q です。置き場を共有しただけで認証状態が付いてきました。
  • アプリAとアプリBも互いに別。同じ端末に入れた2つのアプリが同じサイトを開いても、ログインは共有されません。

この「毎回ログインし直し」を、RFCはセキュリティとは別の欠点として名指ししています。Googleも同じことを書いています。

Google Developers Blog（2021年6月29日）— 原文
The sandboxed storage environment of an embedded webview disconnects a user from the single sign-on features they expect from Google.

Q. 4の「アプリ内タブ」は、ログイン操作を一度もしていないのに LOGGED_IN alice になりました。なぜ?

正解。何も同期していません。Cookieファイルが置いてある場所が同じだった、それだけです。逆に言えば「ログイン状態を引き継ぐ／引き継がない」は、部品の見た目ではなくどのディレクトリを見るかで決まります。3択の本体はここです。

ここは正直に書きます。実機のAPIそのものは動かしていません

この実測はLinux + Chromiumで行いました。iOS/Androidの実機や、SFSafariViewController・Custom Tabs・WKWebViewそのものは動かしていません。

では何を測ったのか
「アプリがコンテキストを共有できるか／隔離されるか／制御できるか」というブラウザ側の性質だけです。それをChromiumの永続コンテキスト（launchPersistentContext）のデータディレクトリ切り替えで再現しました。
測っていないこと
各プラットフォームのAPIが実際にどちらの領域を使うか（例: SFSafariViewControllerがSafari本体と共有するのか隔離されるのか）は、この環境では検証できません。そこは一次資料の記述だけを根拠にしていて、4章でその記述を全部貼ります。
もうひとつの差異
用意されていた playwright-core の参照先パスが存在せず、実体のあった scratchpad/node_modules/playwright-core@1.62.1 を使いました。結果には影響しませんが、指定と違う点として記録しておきます。
使ったコード全文（server.js / exp1_share.js）

依存は playwright-core だけです。node server.js を別プロセスで動かした状態で、rm -rf prof && node exp1_share.js ./prof を実行しました。

server.js — ログインするだけの最小サイト
// 認可サーバのつもりの最小サイト (依存なし)
// node server.js  → http://127.0.0.1:8863
const http = require('http');
const PORT = 8863;

function page(user) {
  const status = user ? 'LOGGED_IN ' + user : 'ANON';
  return `<!doctype html><meta charset="utf-8"><title>idp</title>
<h1 id="status">${status}</h1>
<form method="POST" action="/login">
<input id="u" name="u" autocomplete="off">
<input id="p" name="p" type="password" autocomplete="off">
<button id="go" type="submit">login</button>
</form>
<p id="ls"></p>
<script>
  // 初回だけランダムな印を保存する(同じ値=同じ保存領域)
  if (!localStorage.getItem('tag')) {
    localStorage.setItem('tag', Math.random().toString(36).slice(2, 8));
  }
  document.getElementById('ls').textContent =
    'localStorage.tag=' + localStorage.getItem('tag');
</script>`;
}

http.createServer((req, res) => {
  const cookie = req.headers.cookie || '';
  const m = /(?:^|; )sid=([^;]+)/.exec(cookie);
  const user = m ? decodeURIComponent(m[1]) : null;

  if (req.method === 'POST' && req.url === '/login') {
    let body = '';
    req.on('data', c => body += c);
    req.on('end', () => {
      const p = new URLSearchParams(body);
      const u = p.get('u') || 'anon';
      res.writeHead(302, {
        'Set-Cookie': [
          'sid=' + encodeURIComponent(u) + '; Path=/; HttpOnly; Max-Age=86400',
          'theme=dark; Path=/; Max-Age=86400'
        ],
        'Location': '/'
      });
      res.end();
    });
    return;
  }
  res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
  res.end(page(user));
}).listen(PORT, '127.0.0.1', () => console.log('listening ' + PORT));
exp1_share.js — 置き場を切り替えて4回開くだけ
// 実験1: プロファイル(データ置き場)が別か同じかで
// ログイン状態が引き継がれるかを測る
const { chromium } = require('playwright-core');
const URL = 'http://127.0.0.1:8863/';
const EXE = '/opt/pw-browsers/chromium';

async function open(label, dir, doLogin) {
  const ctx = await chromium.launchPersistentContext(dir, {
    executablePath: EXE, args: ['--no-sandbox'],
  });
  const page = await ctx.newPage();
  await page.goto(URL);
  if (doLogin) {
    await page.fill('#u', 'alice');
    await page.fill('#p', 'hunter2');
    await Promise.all([page.waitForNavigation(), page.click('#go')]);
  }
  const status = await page.textContent('#status');
  const cookies = await ctx.cookies(URL);
  const sid = cookies.find(c => c.name === 'sid');
  const ls = await page.evaluate(() => localStorage.getItem('tag'));
  console.log(label);
  console.log('  status: ' + status);
  console.log('  sid   : ' + (sid ? sid.value : '(なし)'));
  console.log('  ls.tag: ' + (ls || '(なし)'));
  await ctx.close();
}

(async () => {
  const P = process.argv[2]; // プロファイル置き場
  await open('1 本体ブラウザ(ログイン実行)', P + '/browser', true);
  await open('2 アプリAのWebView(別領域)', P + '/appA', false);
  await open('3 アプリBのWebView(別領域)', P + '/appB', false);
  await open('4 アプリ内タブ(本体と同領域)', P + '/browser', false);
})();

3WebViewは全打鍵とHttpOnly Cookieを盗める

パスワードは hunter2 でした。打った瞬間にホスト側へ流れます

1章の定義に「アプリがページ内容を検査・改変できる」とありました。それが具体的に何を意味するのかを、そのまま実演します。

ホストアプリの立場で、ページにキー入力を全部拾うコードを仕込みます。ユーザーはIDとパスワードを普通に打つだけです。

実行結果（node exp2_spy.js）
盗んだ入力キー:
  alicehunter2
盗んだCookie(HttpOnly):
  sid=alice httpOnly=true
  • alicehunter2 は、ユーザーが打った alice と hunter2 の連結です。パスワードが平文で復元できています。
  • httpOnly=true なのに値が見えています。HttpOnlyは「ページのJavaScriptから読めない」フラグであって、ホストアプリから読めない保証ではありません。
  • 特殊な攻撃コードは使っていません。使ったのは公開APIだけ。全文は下の折りたたみにあります。

これは想定外の穴ではありません。RFCが理由として明記している内容そのものです。

RFC 8252 §8.12 Embedded User-Agents — 原文
This best current practice requires that native apps MUST NOT use embedded user-agents to perform authorization requests and allows that authorization endpoints MAY take steps to detect and block authorization requests in embedded user-agents.

In typical web-view-based implementations of embedded user-agents, the host application can record every keystroke entered in the login form to capture usernames and passwords, automatically submit forms to bypass user consent, and copy session cookies and use them to perform authenticated actions as the user.
  • MUST NOT。ネイティブアプリは認可リクエストに埋め込みユーザーエージェントを使ってはならない、と書かれています。任意の推奨ではありません。
  • MAY のほうも重要です。「認可エンドポイント側が検出してブロックしてよい」と明記されています。これが次の話につながります。

Googleは2021年9月30日に、実際にブロックを始めました

規格の MAY は、主要IdPの契約上の禁止事項として実装されています。

Google「OAuth 2.0 Policies — Use secure browsers」— 原文
A developer must not direct a Google OAuth 2.0 authorization request to an embedded user-agent under the developer's control. Embedded user-agents include, but are not limited to, software libraries that allow a developer to insert arbitrary scripts, alter the default routing of a request to the Google OAuth server, or access session cookies.
Google Developers Blog（2021年6月29日）— 原文
All embedded webviews will be blocked starting on September 30, 2021.

Android — Embedded webviews implementing or extending Android WebView do not comply with Google's secure browser policy for its OAuth 2.0 Authorization Endpoint.

iOS & macOS — Embedded webviews implementing or extending WKWebView, or the deprecated UIWebView, do not comply with Google's secure browser policy for its OAuth 2.0 Authorization Endpoint.
  • クラス名で名指しされています。android.webkit.WebView と WKWebView、そして非推奨の UIWebView。「うちのWebViewは大丈夫」という余地はありません。
  • 代替も同じ文書に書かれています。Androidは Custom Tabs、iOSは SFSafariViewController。
  • つまりWebViewを選ぶ = Googleログインが動きません。設計上の好みの問題ではなく、機能が落ちます。
2025年の最新BCPでは、この話は更新されたのか

2025年1月に RFC 9700（BCP 240, OAuth 2.0 セキュリティのベストカレントプラクティス）が出ています。念のため全文を検索しました。

結果
webview / web-view / embedded user-agent のいずれも、本文に一度も出てきません。ネイティブアプリについては RFC 8252 を参照する形で委譲されています。
意味するところ
「WebViewを使うな」の一次規範は、2026年の時点でも2017年の RFC 8252 が唯一の出典のままです。古い文書だから無効、ではありません。上書きされていないから有効です。

4「SFSafariViewController = iOS版Custom Tabs」は成り立たない

Androidは「共有する」と書いてある。Appleは書いていない

ここが、この記事でいちばん誤解されている場所です。2つの公式ドキュメントを並べます。

Android Developers「Overview of Android Custom Tabs」— 原文
Custom Tabs are powered directly by the user's preferred browser and automatically share the state and features offered by it. You don't need to write custom code to manage requests, permission grants, or cookie stores.

Shared cookie jar and permissions model so users don't have to sign in to sites they are already connected to, or re-grant permissions they have already granted.
Apple「SFSafariViewController」— 原文
An SFSafariViewController object presents a self-contained web interface inside your app. […] Interactions with the web interface aren't visible to your app, and you can't access AutoFill data, browsing history, or website data. You don't need to secure data between your app and Safari. To share data between your app and Safari, use ASWebAuthenticationSession instead.
  • Androidは Shared cookie jar と明記しています。「すでにサインイン済みのサイトに再ログインしなくて済む」という利点として書かれています。
  • Appleは「共有する」と一言も書いていません。書いてあるのは self-contained（自己完結）と、共有したいなら ASWebAuthenticationSession を使えという誘導です。
  • この2つは同じものではありません。「iOS版Custom Tabs」という説明を見たら、そこで一度止まってください。

Apple公式の言い回しだけだと弱いので、API側の傍証も挙げます。SFSafariViewControllerは自前のデータストアを持っています。

  • SFSafariViewController.DataStore が iOS 16 で追加されました。APIメタデータの introducedAt が 16.0（iOS / iPadOS / Mac Catalyst）です。
  • clearWebsiteData(completionHandler:) があります。アプリ側から消せるウェブサイトデータが存在する、ということです。Safari本体の共有ストアなら、アプリが消せるはずがありません。
  • ただし、このページには散文の説明が一切ありません。APIシグネチャとメタデータだけ。だから「アプリ間で隔離されているか」までは、これでは言えません。7章の未確認欄に回します。

Appleは2017年に、共有機能を「同意ダイアログ付きの別API」へ隔離した

では、iOSでブラウザとログイン状態を共有する道はどこにあるのか。SFAuthenticationSession の説明文が答えです。

Apple「SFAuthenticationSession」（iOS 11 導入 / iOS 12 で非推奨）— 原文
A class that manages sharing a one-time login between Safari and an app, which can also provide automatic login for associated apps.

Along with the login, this class manages sharing cookies and website data.

If an application uses `SFAuthenticationSession`, users are prompted by a dialog to give explicit consent, allowing the application to access the website's data in Safari.
  • 「Cookieとウェブサイトデータの共有を管理する」のはこのクラスです。SFSafariViewControllerではありません。
  • 共有には明示的な同意ダイアログが必要です。ユーザーが黙って共有される設計ではなくなりました。
  • APIメタデータ: introducedAt: 11.0 / deprecatedAt: 12.0 / renamed: ASWebAuthenticationSession。iOS 12で今の名前になりました。

そして現行の ASWebAuthenticationSession には、共有するかどうかのスイッチが1つだけ付いています。

Apple「prefersEphemeralWebBrowserSession」— 原文
Set prefersEphemeralWebBrowserSession to `true` to request that the browser doesn't share cookies or other browsing data between the authentication session and the user's normal browser session.

Safari always respects the request. In macOS, someone can choose a different default browser that might or might not respect the request.

The value of this property is `false` by default.
  • 既定値は false。つまり既定では、通常のブラウザセッションとCookieを共有します。SSOを効かせたいならこのまま、効かせたくないなら true。
  • 共有スイッチは認証専用APIの中にしかありません。汎用のアプリ内ブラウザ（SFSafariViewController）にはこの property がありません。

Androidも2025年に、同じ形へ寄せてきました

「認証は汎用アプリ内ブラウザから分離する」という方向は、いま両OS共通です。

  • AuthTabIntent が androidx.browser 1.9.0 に入りました。安定版のリリースは2025年7月30日です。iOSの ASWebAuthenticationSession に対応する、認証専用の入口です。
  • リダイレクト先の検証まで面倒を見ます。HTTPSのリダイレクトURLを使う場合、アプリとURLが同一組織の所有であることを Digital Asset Links で証明する必要があり、失敗すると RESULT_VERIFICATION_FAILED が返ります。
  • iOS側にも似た保証があります。ASWebAuthenticationSession は「同じcallback URLスキームを複数のアプリが登録していても、呼び出したアプリのセッションだけがコールバックを受け取る」とドキュメントに書かれています。自前WebViewでは得られない保証です。

正しい対応づけは、1対1ではなく3段構えです。

  • 1段目: WebView ↔ WKWebView。どちらもアプリ専用の置き場。認可には使えません。
  • 2段目: Custom Tabs ↔ SFSafariViewController。ここだけ非対称です。Androidは共有Cookieジャー、iOSは自前ストア。
  • 3段目: Auth Tab ↔ ASWebAuthenticationSession。認証専用。ここが「ブラウザのログインを引き継ぐ」唯一の道です（iOSでは）。
RFCの定義は、iOSでは半分しか成り立っていません

1章の定義を思い出してください。in-app browser tab は「ブラウザの完全なセキュリティ特性と認証状態を保持するもの」でした。

ずれている点
RFC は Appendix B.1 で SFSafariViewController をその実装例に挙げています。しかしAppleの現行ドキュメントに従う限り、SFSafariViewController は Safari の認証状態を持ち込みません。定義の後半が、iOSの汎用アプリ内ブラウザについては現在成立していないことになります。
ただし、RFCは古びていません
Appendix B の冒頭に「実装詳細は変わりうる。矛盾したら本文の原則が優先」と書いてあります（1章に原文を貼りました）。さらに同じ文の中で or its successor "SFAuthenticationSession" と、後継APIまで名前を出しています。RFCの公開は2017年10月で、SFAuthenticationSession が入った iOS 11 の出荷時期と重なります。
読み方
規格が時代遅れになったのではなく、規格が自分で退避路を用意していたという話です。原則（＝アプリがCookieに触れられる方式を認可に使うな）は今も生きています。
「iOS 11で共有をやめた」という説明について（未確認）

検索するとよく出てくる「SFSafariViewControllerは iOS 9 と 10 では Safari とCookieを共有していたが、iOS 11 でやめた」という説明があります。これを裏付けるApple自身の一次資料は、見つけられませんでした。

何が確認できて、何ができないか
Appleの現行ドキュメントは「いま どうなっているか」しか書いていません。移行そのものを述べた公式文書（リリースノート、WWDCセッション等）に到達できませんでした。
過去版を見に行こうとしましたが
archive.org（Wayback Machine）は当環境のegress許可リストに入っておらず、Host not in allowlist で届きません。
この記事での扱い
「iOS 11 で変わった」とは書きません。書けるのは SFAuthenticationSession の introducedAt: 11.0 というAPIメタデータの事実だけで、そこから先は状況証拠に基づく推論です。

5Googleのドキュメントが、Googleのコードと矛盾している

「実行時に確認する方法はない」と書いてある。確認するAPIは1年前からあります

Custom Tabs には、iOSの prefersEphemeralWebBrowserSession に相当するスイッチが2025年に入りました。

androidx.browser「CustomTabsIntent.Builder#setEphemeralBrowsingEnabled」— 原文
setEphemeralBrowsingEnabled — Added in 1.9.0
Sets whether to enable ephemeral browsing within the Custom Tab. If ephemeral browsing is enabled, and the browser supports it, the Custom Tab does not share cookies or other data with the browser.

注目してほしいのは and the browser supports it の部分です。ブラウザ側が対応していれば、という条件付きです。

では、対応しているかどうかをどう調べるのか。Chrome公式ドキュメントはこう書いています。

developer.chrome.com「Custom Tabs — Browser support」（最終更新 2026年8月13日 UTC）— 原文
Caution: It is currently not possible to programmatically check on an Android device, if an installed browser supports a specific Custom Tab feature. While most features are progressive enhancements, if you require a particular feature you must manually confirm if the user's default browser and browser version support it.

「プログラム的に確認することはできない」。ところが、確認するAPIは実在します。

androidx.browser「CustomTabsClient」— 原文
isEphemeralBrowsingSupported — Added in 1.9.0
public static boolean isEphemeralBrowsingSupported(@NonNull Context context, @NonNull String provider)
Checks whether the Custom Tabs provider supports Ephemeral Browsing.

static boolean isAuthTabSupported(@NonNull Context context, @NonNull String provider) — Checks whether the Custom Tabs provider supports Auth Tab.
  • リリースノートに日付まで残っています。1.9.0-alpha04（2025年5月20日）で Added capability check API for Ephemeral Browsing と Added Auth Tab capability check API。安定版 1.9.0 は2025年7月30日。
  • より新しく更新されたドキュメントが、1年以上前に入ったAPIを「無い」と書いています。Chrome側ページの最終更新は2026年8月13日です。
  • 実害は「防御的に書きすぎる」こと。機能検出できない前提で組むと、使える環境でも共有オフを諦める実装になります。

Q. AndroidのCustom Tabsで「ブラウザとCookieを共有しない」モードが使えるかどうか、実行時に確認できる?

正解。1つ目を選んだ人は悪くありません。Chrome公式ドキュメントにいまもそう書いてあるからです。これは同じGoogleの中でドキュメントとAPIリファレンスがずれている実例で、こういうときはAPIリファレンスとリリースノートのほうが強い証拠です。実際に入ったコードとバージョン番号が残っているので。

Custom Tabs は「Chromeの機能」ではありません

同じChrome公式ページに、設計思想が書かれています。

developer.chrome.com「Custom Tabs — Browser support」— 原文
Built on top of the Intent system, Custom Tabs are a collection of configurable option requests that are sent to the end user's preferred browser. It is up to each browser to implement the various options. The availability of Custom Tabs features can vary between Android browsers due to implementation differences.

Custom Tabs はユーザーの既定ブラウザに送る「お願いの束」です。実装するかは各ブラウザ次第。iOSのように「必ずWebKit」という保証はありません。

未確認
実際のAndroidブラウザ（Chromeを含む）が EXTRA_ENABLE_EPHEMERAL_BROWSING をどのバージョンから実装しているかは、一次資料を見つけられませんでした。Chrome側の機能比較ページにも setEphemeralBrowsingEnabled は載っていません。だからこそ、上の capability check API を実際に呼ぶ価値があります。

6審査で落ちるのは、この2行に書いてある

「見えない SFSafariViewController」は明文で禁止されています

アプリ内ブラウザ絡みでリジェクトされる条項は、App Store Review Guidelines に2つあります。原文で確認します。

App Store Review Guidelines 5.1.1 (vii) — 原文
SafariViewController must be used to visibly present information to users; the controller may not be hidden or obscured by other views or layers. Additionally, an app may not use SafariViewController to track users without their knowledge and consent.
  • 0pxで隠してCookieを同期させる、という定番の裏技が明文で潰されています。「他のビューやレイヤーで隠したり覆い隠したりしてはならない」。
  • ユーザーの認識と同意なしのトラッキング目的も禁止です。
  • UI設計の制約もあります。Appleのクラス解説には Don't embed an SFSafariViewController as a child view controller in your app、必ず present(_:animated:completion:) でモーダル表示せよ、とあります。画面の一部として埋め込む設計は取れません。
App Store Review Guidelines 2.5.6 — 原文
Apps that browse the web must use the appropriate WebKit framework and WebKit JavaScript. You may apply for an entitlement to use an alternative web browser engine in your app. Learn more about these entitlements for the EU and Japan.

「エンタイトルメントを申請できる」と書いてあるので、抜け道があるように読めます。実際にはほぼ通れません。条件を読むとこうです。

枠誰が取れるか主な条件
EU アプリをEU限定で配布している開発者 既定ブラウザのエンタイトルメントを持たないこと。Web Platform Tests 90% / Test262 80% を通すこと。アプリの主目的がWebブラウジングであること
日本 browser engine steward（独自ブラウザエンジンの運営を主業務とする組織） サードパーティCookieを既定でブロック。ストレージをトップレベルサイト単位でパーティション分割。同一開発者の別アプリであっても、ユーザーの明示的許可なくCookieを含む状態を同期しない
  • 「アプリ内ブラウザを自前エンジンで作りたい」の答えは、実質ノーです。ブラウザベンダー向けの枠であって、一般的なアプリの選択肢ではありません。
  • 日本枠の要件が、この記事のテーマそのものです。「Cookieがどこに貯まるか」「アプリ間で同期していいか」が、規制の側から条件として書かれています。
日本の開発者は、ガイドライン本文からは日本向けページに辿り着けません

2.5.6 の Learn more about these entitlements for the EU and Japan. のリンク先を実際に開きました。

何が起きているか
唯一のリンク先は /support/alternative-browser-engines/。ページタイトルは Using alternative browser engines in the European Union で、本文中に Japan は0件です。
日本向けはどこにあるか
別URL（/support/alternative-browser-engines-jp、タイトル Using alternative browser engines in Japan）に存在します。要件もEU版とは違います（EU版は「アプリがEU限定配布であること」、日本版は「組織が browser engine steward であること」）。
実害
ガイドライン本文のリンクだけを辿った日本の開発者は、自分に適用される条件に到達できません。URLを直接叩く必要があります。

There is no single "correct" way to load web content. In certain situations, WebView is going to be the right technology to use. For example, if you are exclusively hosting your own content inside your app, or if you need to inject javascript directly from your app.
