1何が起きたか

CSSを直してpushした。数時間後、スマホで見たらまだ崩れていた

このサイトでコードブロックの表示が壊れていました。CSSを直して、pushして、確認して、直っていました。

なのにスマホで開いたら崩れたまま。ファイルは正しい。サーバーにも正しいものが乗っている。それでも崩れている。

  • 手元では直っている。だから原因がコードだと思い込むと、永遠に見つかりません。
  • 犯人はコードの外にいます。ブラウザが「もう持ってるから取りに行かない」と判断していました。

Q. サーバー上のCSSは新しい。それでも古い表示になるのはなぜ?

正解。ブラウザは前回受け取った「◯秒間は聞きに来なくていい」という指示を守っています。サーバーには1回もリクエストが飛んでいません。次の章で、実際に飛んでいないことを確認します。

2犯人を実測で捕まえる

GitHub Pagesは「600秒は聞きに来るな」と言っている

推測せず、実物を見ます。このサイトのCSSにヘッダーだけ取りに行きました。

実行結果（2026年8月14日 実測）
$ curl -sS -D - -o /dev/null "https://reishisu.github.io/ai-news/css/article.css"

HTTP/2 200

  • max-age=600 が犯人。「受け取ってから600秒間は、このファイルをサーバーに確認しなくていい」という意味です。
  • ETagがあっても関係ありません。ETagは「聞きに行ったとき」に使う照合用。600秒のあいだ、そもそも聞きに行きません。
  • GitHub Pagesではこの値を変えられません。ヘッダーを自由に設定できるホスティングではないので、別の手で解決する必要があります。
もう少し詳しく
HTMLはどうなっているのか
HTMLにも同じ max-age=600 が付きます。ただしHTMLは戻る・進む・リンク遷移で新しく取り直される機会が多く、CSSより先に新しくなりがちです。この「寿命のズレ」が崩れの正体です。
expires と cache-control
両方ありますが、cache-control が優先されます。expires は古いブラウザ向けの保険です。

3崩れる瞬間を再現する

HTMLとCSSの寿命が違う。だからズレた組み合わせが生まれる

言葉より図が速いので、先に貼ります。

これを本当に作れるか、手元で確かめます。まずGitHub Pagesと同じ指示を返すサーバーを立てます。

serve.py — 確認用サーバー
#!/usr/bin/env python3
"""HTML は毎回聞きに来させ、CSS は600秒キャッシュさせる。"""
import functools, http.server, socketserver

class Handler(http.server.SimpleHTTPRequestHandler):
    def end_headers(self):
        if self.path.split("?")[0].endswith((".css", ".js")):
            self.send_header("Cache-Control", "max-age=600")   # GitHub Pages と同じ値
        else:
            self.send_header("Cache-Control", "no-cache")
        super().end_headers()

    def log_message(self, fmt, *args):
        with open("access.log", "a", encoding="utf-8") as f:
            f.write(f"{self.command} {self.path}\n")

socketserver.TCPServer.allow_reuse_address = True
handler = functools.partial(Handler, directory="pub")
with socketserver.TCPServer(("127.0.0.1", 8802), handler) as httpd:
    httpd.serve_forever()

6回も操作したのに、サーバーに届いたのは3回だけ。1〜4はサーバーに1度も来ていません。

  • F5は効きません。いまのChromeは、リロードでHTMLは確認し直しますが、CSSや画像は確認しません。

  • デプロイし直しても効きません。同じ理由です。「反映されない」の大半はこれです。

Q. なぜ5と6は直ったのに、この2つでは解決にならない?

正解。しかもこれが一番怖いところで、開発者はシークレットウィンドウで確認しがちです。自分の目には直って見えるので「直した」と判断して、読者の画面だけが壊れたまま残ります。

典型的な流れ

「自分では再現しないが、他人の環境では再現する」表示バグは、まずキャッシュを疑ってください。コードを読み直すのは、そのあとです。

58文字で直す

URLの末尾に中身のハッシュを付ける。それだけ

ブラウザはURLが1文字でも違えば別のファイルとして扱います。この性質を使います。

やること（HTMLのこの1箇所）
変更前: <link rel="stylesheet" href="css/style.css?v=6afc843a">
変更後: <link rel="stylesheet" href="css/style.css?v=6afc843a">

大事なのはこの8文字を手で書かないことです。手で書くと必ず忘れます。ファイルの中身から自動で作ります。

_build_index.py — このサイトで実際に動いているコード
def asset_versions():
    """{'css/article.css': 'a1b2c3d4', ...} を返す(内容ハッシュの先頭8桁)。"""
    versions = {}
    for rel in ASSETS:
        path = HERE / rel
        if path.is_file():
            versions[rel] = hashlib.sha256(path.read_bytes()).hexdigest()[:8]
    return versions


def add_cache_busting(html, versions):
    """既存の ?v=... を捨てて、現在の内容ハッシュを付け直す。"""
    for rel, ver in versions.items():
        name = rel.split("/")[-1]
        html = re.sub(
            r'((?:href|src)="[^"]*' + re.escape(name) + r')(?:\?v=[0-9a-f]+)?(")',
            lambda m: f"{m.group(1)}?v={ver}{m.group(2)}",
            html,
        )
    return html
  • 日付や連番ではなく、中身のハッシュにする。中身が変わっていないのにURLが変わると、変える必要のないファイルまで再ダウンロードさせてしまいます。
  • 既存の ?v= を一度消してから付け直す。これを忘れると ?v=aaa?v=bbb のように壊れます。上の正規表現の (?:\?v=[0-9a-f]+)? がその処理です。
  • ビルド時に全ページへ一括で付ける。人間が書く場所を1つも残さないのがコツです。
ヘッダーを自由に設定できる環境なら、もっと良い形にできます
理想の組み合わせ
HTMLは Cache-Control: no-cache（毎回確認させる）、ハッシュ付きのCSS/JSは max-age=31536000, immutable（1年間、確認すらさせない）。URLが変わったときだけ取り直されるので、速さと確実さが両立します。
GitHub Pagesの場合
ヘッダーを変更できないため、全ファイルが max-age=600 のままです。それでも ?v= を付けておけば「新HTML × 旧CSS」の崩れは起きません。HTMLが新しくなった時点で、CSSのURLも一緒に新しくなるからです。
