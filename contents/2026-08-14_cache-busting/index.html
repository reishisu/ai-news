1何が起きたか

CSSを直してpushした。数時間後、スマホで見たらまだ崩れていた

このサイトでコードブロックの表示が壊れていました。CSSを直して、pushして、確認して、直っていました。

なのにスマホで開いたら崩れたまま。ファイルは正しい。サーバーにも正しいものが乗っている。それでも崩れている。

  • 手元では直っている。だから原因がコードだと思い込むと、永遠に見つかりません。
  • 犯人はコードの外にいます。ブラウザが「もう持ってるから取りに行かない」と判断していました。

Q. サーバー上のCSSは新しい。それでも古い表示になるのはなぜ?

正解。ブラウザは前回受け取った「◯秒間は聞きに来なくていい」という指示を守っています。サーバーには1回もリクエストが飛んでいません。次の章で、実際に飛んでいないことを確認します。

2犯人を実測で捕まえる

GitHub Pagesは「600秒は聞きに来るな」と言っている

推測せず、実物を見ます。curl（URLを叩いて、返ってきた通信の中身をそのまま表示するコマンド）で、このサイトのCSSのヘッダーだけ取りに行きました。

実行結果（2026年8月15日 00:45 UTC 実測）
$ U=https://reishisu.github.io
$ curl -sS -D - -o /dev/null \
    "$U/ai-news/css/article.css" \
    | grep -Ei "cache-control|etag|expires"

etag: "6a7fb033-455d"
expires: Sat, 15 Aug 2026 00:51:51 GMT
cache-control: max-age=600

grep は、出てきた行の中から指定した語を含む行だけを抜き出す道具です。ヘッダーは全部で24行返ってきますが、いま見たいのは3行だけなので絞っています。

  • max-age=600 が犯人。「受け取ってから600秒間は、このファイルをサーバーに確認しなくていい」という意味です。
  • ETagがあっても関係ありません。ETagは「聞きに行ったとき」に使う照合用。600秒のあいだ、そもそも聞きに行きません。
  • GitHub Docs には、この値を変える手段が書かれていません。公式の「GitHub Pages limits」と「What is GitHub Pages」を取得して全文を検索しましたが、cache-control も max-age もカスタムヘッダーの記述も0件でした（2026年8月15日確認）。「変えられない」と断定できる根拠は見つからなかったので、ここでは「公式に方法が示されていない」とだけ言います。どちらにせよ、別の手で解決したほうが確実です。
もう少し詳しく
HTMLはどうなっているのか
HTMLにも同じ max-age=600 が付きます。それでもHTMLのほうが先に新しくなる理由は2つです。(1) リロードすると主リソース（＝HTML）だけは検証される（4章のChromiumの説明）。(2) 初めて開くURLのHTMLは手元に無いので必ず取りに行くが、CSSは他のページを見たときのものがもう残っている。この「寿命のズレ」が崩れの正体です。
戻る・進むは新しくならない
直感に反しますが、履歴の「戻る」はむしろ古い表示をそのまま出す側です。RFC 9111 §6 は「履歴機構は、期限切れの表現であっても以前の表現を表示してよい」と書いています（原文: a history mechanism can display a previous representation even if it has expired）。§4.2 にも「鮮度はキャッシュの動作にのみ適用され、ユーザーエージェントに再描画や再読み込みを強制するものではない」という注記があります。
expires と cache-control
両方ありますが、cache-control が優先されます。expires は古いブラウザ向けの保険です。

3崩れる瞬間を再現する

HTMLとCSSの寿命が違う。だからズレた組み合わせが生まれる

言葉より図が速いので、先に貼ります。

これを本当に作れるか、手元で確かめます。まずGitHub Pagesと同じ指示を返すサーバーを立てます。

serve.py — 確認用サーバー
#!/usr/bin/env python3
"""HTML は毎回聞きに来させ、CSS は600秒キャッシュさせる。"""
import functools, http.server, socketserver

class Handler(http.server.SimpleHTTPRequestHandler):
    def end_headers(self):
        if self.path.split("?")[0].endswith((".css", ".js")):
            self.send_header("Cache-Control", "max-age=600")   # GitHub Pages と同じ値
        else:
            self.send_header("Cache-Control", "no-cache")
        super().end_headers()

    def log_message(self, fmt, *args):
        with open("access.log", "a", encoding="utf-8") as f:
            f.write(f"{self.command} {self.path}\n")

socketserver.TCPServer.allow_reuse_address = True
handler = functools.partial(Handler, directory="pub")
with socketserver.TCPServer(("127.0.0.1", 8802), handler) as httpd:
    httpd.serve_forever()
  • ① このファイルを serve.py という名前で保存。置き場所はどこでも構いません。
  • ② 同じ場所に pub フォルダを作る。確認用のHTMLとCSSはこの中に置きます（次のスクリプトが自動で作ります）。
  • ③ python3 serve.py を実行し、http://127.0.0.1:8802 を開く。この記事の実測は、まさにこのコードを動かして取りました。

次に、クラス名を変えるよくある改修をします。HTMLの class="title" を class="headline" にして、CSSも合わせて書き換える。ごく普通の作業です。

クラス名はHTML側に付けた名札です。CSS側は「title という名札の付いた場所を赤にする」と名指ししています。名札を headline に付け替えると、title しか知らない古いCSSは、どこも名指しできなくなります。

4効かない対処、4つ

思いつく手を順に全部試しました。半分は無駄でした

CSSを緑に書き換えたあと、色が変わるかどうかで判定します。赤のままなら効いていないということです。

notwork.js は、3章と同じサーバーに対して「もう一度開く／リロード／ファイルの更新日時を新しくする／別タブ／シークレット／強制リロード」を順にやらせ、そのつど見出しの色を測るだけのスクリプトです。repro.js と同じ作りなので、中身は3章の折りたたみを見てください。

   → style.css を緑に書き換えて公開した

1. もう一度開く        rgb(220, 40, 40)
2. リロード(F5)        rgb(220, 40, 40)
3. 更新日時を新しく    rgb(220, 40, 40)

6回も操作したのに、サーバーに届いたのは3回だけ。0（初回）と5（シークレット）と6（強制リロード）で、1〜4はサーバーに1度も来ていません。

これは不具合ではなく仕様どおりです。HTTPの規格そのものに、そう書いてあります。

RFC 9111「HTTP Caching」§4.2 — 原文
When a response is fresh, it can be used to satisfy subsequent
requests without contacting the origin server, thereby improving
efficiency.

（新鮮なうちは、オリジンサーバーに問い合わせることなく
　後続のリクエストに使ってよい）

ではF5はなぜ効かないのか。これもChrome側が公式に説明しています。2017年に挙動を変えたときのアナウンスです。

Chromium Blog（2017年1月26日）— 原文
Chrome now has a simplified reload behavior to only validate
the main resource and continue with a regular page load.

（リロードでは主リソースだけを検証し、あとは通常の読み込みに進む）
  • F5が確認するのはHTMLだけ。CSSや画像は確認しません。仕様変更の理由は速度で、リロードが28%速くなり検証リクエストが60%減ったと報告されています。
  • ファイルの更新日時も効きません。そもそも聞きに来ないので、サーバー側で何をしても届きません。
  • デプロイし直しても効きません。同じ理由です。「反映されない」の大半はこれです。

Q. なぜ5と6は直ったのに、この2つでは解決にならない?

正解。しかもこれが一番怖いところで、開発者はシークレットウィンドウで確認しがちです。自分の目には直って見えるので「直した」と判断して、読者の画面だけが壊れたまま残ります。

この罠がバグを世に出す仕組み
典型的な流れ
直す → シークレットで確認 → 直っている → 公開 → 読者「まだ崩れてます」 → 自分で見ると直っている → 原因不明で迷走。
見分け方
「自分では再現しないが、他人の環境では再現する」表示バグは、まずキャッシュを疑ってください。コードを読み直すのは、そのあとです。

58文字で直す

URLの末尾に中身のハッシュを付ける。それだけ

ブラウザはURLが1文字でも違えば別のファイルとして扱います。この性質を使います。

ここで言うハッシュとは、ファイルの中身から計算した8桁の文字列のことです。中身が1文字でも変われば、まったく別の値になります。逆に中身が同じなら、何度計算しても同じ値です。

やること（HTMLのこの1箇所）
変更前: <link rel="stylesheet" href="css/style.css">
変更後: <link rel="stylesheet" href="css/style.css?v=6afc843a">

大事なのはこの8文字を手で書かないことです。手で書くと必ず忘れます。ファイルの中身から自動で作ります。

_build_index.py — このサイトで実際に動いているコード
def asset_versions():
    """{'css/article.css': 'a1b2c3d4', ...} を返す(内容ハッシュの先頭8桁)。"""
    versions = {}
    for rel in ASSETS:
        path = HERE / rel
        if path.is_file():
            versions[rel] = hashlib.sha256(path.read_bytes()).hexdigest()[:8]
    return versions


PRE_BLOCK = re.compile(r"<pre\b[^>]*>.*?</pre>", re.S | re.I)


def add_cache_busting(html, versions):
    """既存の ?v=... を捨てて、現在の内容ハッシュを付け直す。

    <pre> の中(記事に載せたコード例)は書き換えない。
    """
    def bust(chunk):
        for rel, ver in versions.items():
            name = rel.split("/")[-1]
            chunk = re.sub(
                r'((?:href|src)="[^"]*' + re.escape(name) + r')(?:\?v=[0-9a-f]+)?(")',
                lambda m: f"{m.group(1)}?v={ver}{m.group(2)}",
                chunk,
            )
        return chunk

    out, last = [], 0
    for m in PRE_BLOCK.finditer(html):
        out.append(bust(html[last:m.start()]))
        out.append(m.group(0))          # コード例はそのまま残す
        last = m.end()
    out.append(bust(html[last:]))
    return "".join(out)
  • 日付や連番ではなく、中身のハッシュにする。中身が変わっていないのにURLが変わると、変える必要のないファイルまで再ダウンロードさせてしまいます。
  • 既存の ?v= を一度消してから付け直す。これを忘れると ?v=aaa?v=bbb のように壊れます。上の正規表現の (?:\?v=[0-9a-f]+)? がその処理です。
  • ビルド時に全ページへ一括で付ける。人間が書く場所を1つも残さないのがコツです。
  • ただし、コード例まで書き換えないこと。この <pre> をよける処理は後から足しました。理由は次の折りたたみに書きます。
この記事は、自分が紹介した道具に壊されました

公開直後の版では、上の「やること」の欄が変更前と変更後で1文字も違わない状態になっていました。記事の結論そのものが消えていたわけです。

何が起きていたか
最初の add_cache_busting() はHTML全体に正規表現をかけていました。記事の <pre> に書いたサンプルの href="css/style.css" も「本物のリンク」と見なされ、ビルドのたびに ?v=6afc843a を注入されていました。しかも同じスクリプトが記事ファイルに書き戻すので、手で直しても次のビルドで必ず元に戻ります。
どう直したか
置換対象を <pre>…</pre> の外側だけに限定しました（上のコードがその修正版です）。あわせて、記事側のサンプルは引用符を &quot; で書いて、正規表現に当たらないようにしてあります。二重の保険です。
教訓
HTMLを正規表現で書き換える処理は、「説明のために書かれたHTML」と「本物のHTML」を区別できません。生成物を書き戻す種類のスクリプトほど、範囲を狭く切ってください。
ヘッダーを自由に設定できる環境なら、もっと良い形にできます
理想の組み合わせ
HTMLは Cache-Control: no-cache（毎回確認させる）、ハッシュ付きのCSS/JSは max-age=31536000, immutable（1年間、確認すらさせない）。URLが変わったときだけ取り直されるので、速さと確実さが両立します。
GitHub Pagesの場合
ヘッダーを変える方法が公式に案内されていないので、実測では全ファイルが max-age=600 のままでした。それでも ?v= を付けておけば「新HTML × 旧CSS」の崩れは起きません。HTMLが新しくなった時点で、CSSのURLも一緒に新しくなるからです。

6あなたのサイトを今すぐ確認する

1コマンドで、自分のサイトが何秒嘘をつくか分かります

URLを自分のCSSに置き換え、ターミナル（WindowsはPowerShell）で実行
curl -sS -D - -o /dev/null "https://あなたのサイト/css/style.css" | grep -i "cache-control\|etag"

縦棒（|）は「左の結果を右に渡す」という意味で、grep -i "cache-control\|etag" は返ってきた行から cache-control と etag だけを抜き出す指定です。2章で使ったものと同じです。

  • max-age が0以外で、URLに ?v= が無い。→ その秒数だけ崩れる可能性があります。今日やるべきです。
  • max-age=0 か no-cache。→ 崩れませんが、毎回ダウンロードするので表示が遅くなります。
  • URLにハッシュが入っている。→ 対策済みです。何もしなくて大丈夫。

  • 「HTMLは戻る・進むで新しく取り直される機会が多い」を削除しました。RFC 9111 §6 は逆のことを書いています。履歴機構は期限切れの表現でも表示してよく、§4.2 にも「鮮度はキャッシュの動作にのみ適用され、再描画や再読み込みを強制しない」という注記があります。HTMLが先に新しくなる本当の理由は、リロード時に主リソースだけ検証されること（4章の出典と同じ）と、初訪問のURLはHTMLだけ手元に無いことの2つでした。2章の説明を差し替えています。

  • 4章のブロックを2つに分けました。「実行結果（node notwork.js）」の中に、実際には access.log を数えた結果が混ざっていました。notwork.js にログを読む処理はありません。コマンドと出力が1対1になるよう分割し、両方とも再実行して同じ結果になることを確認しています。

  • 「GitHub Pagesではヘッダーを変えられません」を撤回しました。GitHub Docs の該当ページ2本（GitHub Pages limits / What is GitHub Pages）を取得して全文を検索しましたが、cache-control・max-age・カスタムヘッダーのいずれも記述がありません。「変えられない」と断定する根拠が無いため、「公式に方法が示されていない」という書き方に改めました。

あわせて、初めて読む人が止まりやすかった箇所（HTMLとCSSが別ファイルであること、サーバーの起動手順、repro.js の中身、クラス名の役割、ハッシュの意味、コマンドを打つ場所）に説明を足しました。実務者向けの内容は削っていません。
