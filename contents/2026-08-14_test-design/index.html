テスト設計の優先順位 — カバレッジより「壊れて困る順」

同じアプリに、同じ4つのバグを1行ずつ入れて、どのテストが落ちるかを全部測りました。実行できるコードと生の出力を全部載せます。
⏱ 約12分 実測ログ全部載せ コピペで再現できる

⭐ 3行で言うと

  1. 行カバレッジ100%のテストは、4つのバグのうち1つしか見つけられなかった 同じアプリでカバレッジ59.1%のテストは4つ全部見つけました。数字が高いほうが負けています。
  2. どの層を厚くするかは好みではない。壊れ方ごとに、落ちる層が完全に分かれる 4通りの壊し方 × 3つの粒度で検出マトリクスを実測しました。素通りする組み合わせがはっきり出ます。
  3. Googleが出している粒度の配分は2つあって、食い違っている テストを3つの粒度に分けたときの件数比です。2015年のブログは70/20/10、2020年の書籍は80/15/5。比率を目標にするのは、カバレッジ100%と同じ罠です。

先に言葉を1つだけ。カバレッジとは、テストを走らせたときにプログラムの何行が実際に通ったかの割合です。100%は「全行を通した」という意味であって、通っただけで、中身が正しいかを確かめたとは言っていません。この記事はその差を実測します。

この記事に出てくる言葉（知っている人は飛ばしてください）
粒度 — ユニット / 結合 / E2E
テストの「どこまで動かすか」の段階です。ユニット＝関数1つを単体で呼ぶ。結合＝複数のファイルを繋いで呼ぶ。E2E（End-to-End）＝アプリを端から端まで、利用者と同じ入口から動かす。この3つの違いが、この記事の主題です。
ステートメント / 未到達
カバレッジは物理的な行数ではなく実行される文（ステートメント）の数で数えます。未到達＝テスト中に一度も実行されなかった文のことです。
PR / CI
PR（プルリクエスト）＝「この変更を取り込んでください」とチームに出す申請。ここでレビューされます。CI＝コードを送るたびに自動でテストを走らせる仕組み（サーバー）。
flaky / 偽陽性
flakyなテスト＝コードを1文字も変えていないのに、通ったり落ちたりするテスト。落ちても本当のバグではないので、その失敗は偽陽性（誤検知）です。
モック
本物の部品の代わりに、決まった値を返す偽物を差し込むこと。速く書けますが、差し替えた部分の仕様が変わっても気づけません。
アサート / オラクル
アサート＝「結果はこうなるはずだ」とテストに書き込む行。その「正解はこれ」の部分をまとめてオラクルと呼びます。第6章のキーワードです。
スタックトレース
エラーが出たとき、どのファイルの何行目を通ってそこに来たかの経路が上から順に出力されたもの。第3章で読み方が効いてきます。

1カバレッジ100%が、59.1%に負けた

同じアプリ、同じ4つのバグ。数字が高いほうが1個しか見つけなかった

席数割引つきの請求計算という、小さなアプリを書きました。app/ は物理90行、カバレッジが数える単位（ステートメント）では44です。そこに1行だけ書き換えるバグを4通り用意します。

テストセットは2つ。片方は行カバレッジ100%、もう片方は59.1%。どちらが多く見つけるかを測りました。

実行結果（python3 run_cov.py）未到達＝一度も実行されなかった文
テストセット  cov%  未到達 検出
----------------------------------
cov_only      100.0     0行 1/4
3粒度セット    59.1    18行 4/4

(app/ の総ステートメント数: 44)
  • 100%のほうが 1/4。見つけられた1つは、実行するとその場でクラッシュするバグだけでした。金額がズレる3つは全部素通りしています。
  • 59.1%のほうが 4/4。18行が一度も実行されていないのに、4つ全部を捕まえました。
  • これはカバレッジ計測のバグではありません。100%のほうは本当に全行を通しています。通しているだけです。

なぜこうなるのか。100%側のテストが何をアサート（「結果はこうなるはずだ」と書き込むこと）しているかを見れば一瞬でわかります。次のコードは読み飛ばして、その下の1文だけ読んでも通じます。

t_cov_only.py — カバレッジを稼ぐためだけのテスト（抜粋）
def test_1():
    for s in (1, 9, 10, 49, 50, 500):
        r = price.volume_discount_rate(s)
        assert isinstance(r, float)
        assert price.monthly_subtotal(s) > 0
    with pytest.raises(ValueError):
        price.volume_discount_rate(0)


def test_2():
    for plan in ("monthly", "annual"):
        inv = bill.make_invoice(3, plan)
        assert inv is not None
        assert "total" in inv
    with pytest.raises(ValueError):
        bill.make_invoice(3, "weekly")

アサートしているのは isinstance、> 0、is not None、in だけ。「金額がいくらか」を一度も見ていません。だから割引率が変わっても、税の計算が変わっても、落ちません。

意地悪に書いたわけではありません。カバレッジの数字だけを目標にすると、人はこの形に収束します。これは20年前から言われていることです。

Martin Fowler「Test Coverage」(2012年4月17日) — 原文
If you make a certain level of coverage a target, people
will try to attain it. The trouble is that high coverage
numbers are too easy to reach with low quality testing.

（ある水準のカバレッジを目標にすれば、人はそれを達成
　しようとする。厄介なのは、低品質なテストでも高い
　カバレッジ数値はあまりに簡単に届いてしまうことだ）

経験則だけではありません。査読付きの実証研究もあります。31,000個のテストスイートを生成して測ったものです。

Inozemtseva & Holmes, ICSE 2014 — Abstract より
Our results suggest that coverage, while useful for
identifying under-tested parts of a program, should not
be used as a quality target because it is not a good
indicator of test suite effectiveness.

（カバレッジは、プログラムのテスト不足の箇所を特定
　するには有用だが、テストスイートの有効性の良い指標
　ではないため、品質目標として使われるべきではない）
  • 「欠落を見つける道具」としては有用。18行が未到達だ、という情報には価値があります。
  • 「品質目標」としては使えない。目標にした瞬間、上の isinstance だらけのテストが正解になります。

Q. カバレッジ100%のテストが4個中1個しか見つけなかった。その1個はどんなバグ?

正解。PRICE を PRICE_YEN に改名して参照側を直し忘れたバグです。実行した瞬間に NameError で落ちるので、値を一切見ていないテストでも巻き添えで落ちます。逆に言うと、値を見ないテストが検出できるのは「クラッシュする壊れ方」だけ。金額が静かに間違う壊れ方は全部通ります。

2壊れ方ごとに、落ちる層は決まっている

ユニットだけが落ちる壊し方と、E2Eだけが落ちる壊し方がある

同じアプリに、粒度の違うテストを3組書きました。ユニット（関数1つを単体で呼ぶ）12件、結合（複数のファイルを繋いで呼ぶ）4件、E2E（アプリを端から端まで、利用者と同じ入口から動かす）3件です。

そこへ4通りの壊し方を1つずつ入れて、どれが落ちるかを全部測ります。壊し方は「元の1行を、右の1行に差し替える」という形で定義しました。

bugs.py — 壊し方の定義（1行だけ置換する）
BUGS = [
    ("b1 境界ズレ", "app/price.py",
     "    if seats >= 10:",
     "    if seats > 10:"),
    ("b2 年割無視", "app/bill.py",
     "        months = ANNUAL_PAID_MONTHS",
     "        months = 12"),
    ("b3 出力取違", "app/api.py",
     '            "amount_due": inv["total"],   # 税込',
     '            "amount_due": inv["subtotal"],'),
    ("b4 改名漏れ", "app/price.py",
     "PRICE = 1000  # 1席あたり月額(税抜)",
     "PRICE_YEN = 1000  # 1席あたり月額(税抜)"),
]
実行結果（python3 run_matrix.py）P=全通過 2F/12＝12件中2件が失敗
壊し方         unit  intg   e2e
-------------------------------
(なし)          12P    4P    3P
b1 境界ズレ   2F/12    4P    3P
b2 年割無視     12P  2F/4  1F/3
b3 出力取違     12P    4P  2F/3
b4 改名漏れ   5F/12  3F/4  2F/3

きれいに分かれました。1つの層で全部は取れません。

  • b1（割引の境界を1席ズラす）はユニットだけが落ちた。結合とE2Eは素通り。理由は単純で、結合とE2Eは3席と60席という代表値しか使っておらず、境界の10席を一度も踏んでいないからです。
  • b2（年払いを10ヶ月分から12ヶ月分に）はユニットが全部通った。ユニットは price.py しか見ていないので、bill.py のプラン計算は視界に入りません。
  • b3（APIが税込ではなく税抜を返す）は結合まで全部通った。落ちたのはE2Eだけ。金額の計算は全部正しくて、外に出す1個のキーだけが間違っているからです。
  • b4（定数の改名漏れ）は全層が落ちた。クラッシュ系はどこからでも見えます。

つまり「ユニットを何%にするか」は最初に決める問いではありません。先に決めるのはどの壊れ方が怖いかで、それが決まれば必要な層は自動的に決まります。

この順番は、業界標準の資格シラバスが第一原理として置いているものと同じです。

ISTQB CTFL シラバス v4.0.1 (2024年9月15日) 1.3 テストの7原則 より
2. Exhaustive testing is impossible. Testing everything
is not feasible except in trivial cases (Manna 1978).
Rather than attempting to test exhaustively, test
techniques [...], test case prioritization [...], and
risk-based testing [...], should be used to focus test
efforts.

（網羅的テストは不可能である。すべてをテストすること
　は、些末な場合を除いて実行可能ではない。網羅的に
　テストしようとするのではなく、テスト技法、テスト
　ケースの優先順位付け、リスクベースドテストを用いて
　テストの労力を集中させるべきである）

同じシラバスに、優先順位の付け方も3種類だけ挙がっています。カバレッジベースは、そのうちの1つでしかありません。

戦略何で順番を決めるか今回の実測との対応
リスクベース リスク分析の結果。重要なリスクを覆うテストから実行する 「壊れて困る順」はこれ。b1〜b4を先に列挙する形
カバレッジベース カバレッジ（例: 命令カバレッジ）が高いものから実行する 実測ではこれで選ぶと isinstance 群が勝つ
要求ベース 要求の優先度。優先度はステークホルダーが定義する ビジネス側が「割引は絶対」と言えばb1が最優先になる

同じ考え方を、Googleの書籍はもっと短く言い切っています。

Software Engineering at Google 第11章 (2020年) — 原文
The straightforward answer is: test everything that you
don't want to break.

（率直な答えはこうだ: 壊れてほしくないものを全部
　テストせよ）

同じ章には「ビヨンセ・ルール」という名前も付いています。If you liked it, then you shoulda put a test on it.（気に入ってたなら、テストを付けとくべきだったね）。無関係な変更で自分のプロダクトが壊れたなら、直してテストを足す責任は自分にある、という運用ルールです。

リスクの大きさを「計算」するやり方も書いてあります
定量的アプローチ
ISTQBシラバス 5.2.3 では、リスクレベルを「発生可能性 × 影響」の掛け算として計算する、と書かれています。定性的にやるならリスクマトリクスを使う、とも。b1〜b4に発生可能性と影響を付ければ、そのまま順位表になります。
欠陥は偏る
同シラバスの原則4は「欠陥は偏在する」。少数のコンポーネントが欠陥の大半を含む、というパレートの法則の一例で、実際に観測された偏りはリスクベースドテストの重要な入力になる、と書かれています。全ファイルに均等にテストを配る根拠はここにありません。

同じ検証をE2Eで書くと、1件あたり約17倍かかる

次はコストです。同じ内容の検証を200件ずつ、粒度[小]と粒度[大]で書いて実行時間を測りました。

実行結果（python3 run_time.py）3回実行の最良値
粒度     件数   合計s  1件ms
------------------------------
小 unit   200   0.34    1.7
大 e2e    200   5.71   28.6
  • 再現するのは倍率のほうです。4回測り直して 16.8 / 16.4 / 17.0 / 16.6倍。絶対値は実行ごとに15〜20%動きますが、約17倍という比はどの回でも変わりません。引くなら倍率だけにしてください。
  • 「1件ms」の定義。pytestプロセス全体の実時間 ÷ 200件です。ユニット側の合計0.3秒はほとんどがpytestの起動費（約0.25秒）なので、1.7msは起動費の按分であって、ユニット1件の限界コストではありません。実際の差はもっと開きます。

そしてここで測ったE2EはDBもネットワークもブラウザも入っていません。Pythonのサブプロセスを起動してJSONを1往復させるだけです。現実のE2Eはこれより確実に遅いので、この17倍は下限です。

コードを1文字も変えていないのに、CIが混むと1〜4割が落ちる

遅いだけなら待てばいい。問題は、遅いテストが時計に触れた瞬間にflaky——コードを1文字も変えていないのに通ったり落ちたりするテスト——の種になることです。

同じE2Eを200回、空いている状態とCPUを埋めた状態（CI＝コードを送るたびに自動でテストを走らせるサーバーが混んでいる状況の再現）で計りました。

マイクロ秒 (1000us = 1ms)

----------------------------------
小unit           0       0       4
大e2e        22476   25031   37370
大(混雑)     21478   46749   95005

  空いてる時  超過   0/200 (0.0%)

  • 「空いているときの中央値の2倍」という素直なタイムアウトを置いただけ。空いていれば0/200回しか超えないのに、CPUを埋めるとこの回は82/200回超えました。
  • テストのコードも対象のコードも1文字も変わっていません。変わったのはCIが混んでいるかどうかだけです。
  • この数字自体が大きくぶれます。同じスクリプトを条件を変えずに6回走らせた混雑時の超過率は 43.5% / 41.0% / 23.0% / 16.5% / 16.5% / 14.5%。負荷の掛かり方に依存するので、「混雑させると1〜4割が超過する」以上の精度では言えません。上の 41.0% は、その6回のうちの1回です。
  • 逆に、空いているときの 0/200 は6回とも再現しました。ぶれているのは「混雑させたときにどれだけ壊れるか」であって、「混雑させると壊れる」こと自体はぶれていません。

flakyが増えると何が壊れるか。Googleが自社の数字で書いています。

John Micco「Flaky Tests at Google and How We Mitigate Them」(2016年5月27日)
What we find in practice is that about 84% of the
transitions we observe from pass to fail involve a flaky
test! [...] It is quite common to ignore legitimate
failures in flaky tests due to the high number of
false-positives.

（実際に見出すのは、パスから失敗への遷移として観測
　されるもののうち約84%がflakyテストを伴うということ
　だ。偽陽性の数が多いために、flakyテストの中の正当な
　失敗が無視されることは非常によくある）

同じ記事は「全テスト実行の約1.5%がflakyな結果を報告する」とも書いています。平均的なプロジェクトが1000テストを持つなら、毎回15件が理由なく赤くなる計算です。

ただしこの数字は引用に注意が必要です。2020年の書籍 Software Engineering at Google は「Googleのflaky率は0.15%前後で推移している」と書いていて、10倍違います。前者は明示的に「テスト実行(test runs)」が分母、後者は分母が書かれていません。「何を分母にした何%か」が違えば、同じ現象でも数字は簡単に10倍変わります。どちらの資料も相手に言及していないので、この差は本記事では説明できません。引くなら年と分母をセットにするしかありません。

Q. E2Eで見つけたバグを直すとき、Fowlerが勧めている手順は?

正解。Fowlerは高レベルテストを「第二の防衛線」と呼び、そこで失敗が出たということは機能コードにバグがあるだけでなく、ユニットテストが欠けているか間違っているのだと書いています。だから直す前にユニットで再現する。そうすればユニットがそのバグを死んだままにしてくれる、と。E2Eを足すと、上で見たとおり「原因の場所を教えないテスト」が1件増えるだけです。

70/20/10 と 80/15/5。同じ会社が5年差で別の数字を出している

As a good first guess, Google often suggests a 70/20/10
split: 70% unit tests, 20% integration tests, and 10%
end-to-end tests.

　明示的なオラクルシグナルを持たなかった）

「オラクルシグナル」は、テストの中の「正解はこれだ」と書いてある部分のことです。同じabstractに、こうも書かれています。「明示的なアサーションを欠くテストファイルは、振る舞いを検証せずにコードを実行するだけである。したがってテストファイルの存在に基づく品質ゲートは、検証の強度を過大評価する」

第1章の t_cov_only.py と同じ形です。「テストが増えた」「カバレッジが上がった」をゲートにすると、AI時代には特に嘘をつきます。

Metaの線引きは精神論ではなく、3段のフィルタ列

では「AIに書かせてよい範囲」はどこか。Metaが本番投入している TestGen-LLM の論文に、実装された機械的な条件として書かれています。

フィルタ落とす条件論文の記述
1. ビルド 既存インフラ内でビルドできない 即座に破棄し、以降の検討から外す
2. パス（'passes'） 初回実行でパスしない／5回の実行すべてではパスしない 前半はバグか誤ったアサーションかを自動判別できないため破棄。後半は同じフィルタの中で flaky とみなして破棄
3. カバレッジ増 カバレッジが実際に増えない 改善と非退行の検証可能な保証を満たせないものは破棄

Instagram の Reels / Stories での評価は、75%が正しくビルド、57%が安定してパス、25%がカバレッジを増加。そして最後は必ず人間のレビューを通します。

  • 数え方に注意。論文自身は「all three filters」（3つのフィルタすべて）と書いています。初回パスと5回連続は同じ 'passes' フィルタの中身であって、別段ではありません。「4段」と紹介している二次情報を見たら、そこは再分割です。
  • 推奨の73%が本番投入のために受け入れられました。裏を返せば、3段のフィルタを全部通ったものでも27%は人間が却下しているということです。
  • 「適用した全クラスのうち11.5%を改善」という数字には注意が必要です。同じ論文のIntroductionの貢献リストでは「10%」と書かれていて、食い違っています。論文はこの差を明示的に説明していません。前者はtest-a-thon期間、後者は「より一般的に」の運用を指すようにも読めます。
  • フィルタ2の後半は、この記事の第3章の実測とそのまま対応します。flakyを持ち込まないという条件を、5回繰り返し実行という単純な方法で機械化しているだけです。

線引きは「リグレッション防止」か「バグ探し」かで反転する

最後にもう1本。2026年7月の再現研究が、カバレッジという指標がAI生成テストで意味を持つかどうかを条件付きで整理しています。

Zhao, Zhou, Cohen 再現研究 arXiv:2607.22880 (2026年7月24日) — Abstract より
[...] in regression-style settings where the code
provided to the LLM can be reasonably assumed bug-free,
these metrics can provide meaningful signals when
comparing across models; in another common scenario
where the code-under-test may already be buggy and the
goal is to expose the bug within the code-under-test,
they no longer serve as reliable indicators.

（LLMに与えられたコードがバグフリーだと合理的に仮定
　できるリグレッション的な設定では、これらの指標は
　モデル間比較において意味あるシグナルを提供しうる。
　一方、テスト対象コードが既にバグを含んでいる可能性が
　あり、その中のバグを暴くことが目標である、もう一つの
　よくあるシナリオでは、これらはもはや信頼できる指標
　ではない）
  • いま動いている振る舞いを、あとで壊さないよう固定したい（リグレッション防止）なら、AIに書かせてよい。コードが正しい前提なので、生成テストがパスすることに意味があります。TestGen-LLMのフィルタ列も、まさにこの前提の上に立っています。
  • 「この実装、たぶんバグってる」を暴きたいなら、AIに任せてはいけません。AIは目の前のコードの振る舞いをそのまま写し取るので、バグごと仕様として固定します。第2章のb1〜b4のような「壊れて困る壊れ方」を先に列挙するのは、人間の仕事です。
  • この論文も本文PDFは未読です。abstractページのみ読んでいます。査読は通っていて、comments欄に「Accepted at ISSTA 2026; to appear in Proceedings of the ACM on Software Engineering (PACMSE), Vol. 3」と記載があります。ただし併記されている DOI 10.1145/3832093 は、Crossref API も doi.org も現時点では404で解決しません（ACM側の登録待ちと思われます）。

ついでに、この再現研究は2014年のICSE論文（第1章で引いたもの）と真逆の結果も出しています。2014年の論文は「テストスイートのサイズを揃えるとカバレッジと有効性の相関は落ちる」＝サイズこそが本当の原因（交絡因子）だという結論でした。再現研究は「LLM生成テストについては、テストスイートのサイズが支配的な交絡因子である証拠はほとんど見つからなかった」としています。「カバレッジは相関しないと研究で示されている」という言い切りは、2026年時点ではもう安全ではありません。

Q. AIに「このモジュールのテストを書いて」と頼むとき、いちばん危ないのはどれ?

正解。再現研究が条件付けしているとおり、AIが有効なのはコードがバグフリーだと仮定できる場合だけです。動作未確認の実装にテストを書かせると、AIは現在の振る舞いを読み取ってそれをアサートするので、バグがそのまま「仕様」として固定されます。しかもテストは全部緑になるので、誰も疑いません。

7明日から変えること

会議で配分を決めるより先に、壊れて困る壊れ方を5つ書く

今回の実測から言えるのは、配分の最適値ではありません。壊れて困る壊れ方を先に列挙すれば、どの層に何件必要かは配分表を見なくても決まるということだけです。

やめること代わりにやること根拠
全体カバレッジに閾値ゲート 差分の未到達行をPRに名指しで出す 実測: 全体は7.1pt しか動かない／FSE 2019（第5章）
「まず80%」を目標にする 壊れて困る壊れ方を先に5つ書く 全体の目標として80%を薦める一次資料は見つからず（第4章）
層の比率を会議で決める 壊れ方ごとに検出できる層を確かめる 実測: b1はunitのみ、b3はe2eのみ（第2章）
E2Eで見つけたバグをE2Eで塞ぐ 直す前にユニットで再現してから直す Fowler「Test Pyramid」第二の防衛線（第3章）
担当を口約束の表で決める CODEOWNERS にパスとして書く GitHub Docs（テスト固有の機能ではない・第5章）

「十分にテストしたか」の判定も、数値ではなく体感条件に置き換えられます。Fowlerの2つの条件です。

Martin Fowler「Test Coverage」— 原文
I would say you are doing enough testing if the
following is true: You rarely get bugs that escape into
production, and You are rarely hesitant to change some
code for fear it will cause production bugs.

（次が真なら十分にテストしていると私は言う: 本番に
　漏れ出るバグがめったに起きないこと。そして、本番バグ
　を引き起こすのが怖くてコードを変えるのをためらう、
　ということがめったにないこと）

逆に「テストしすぎ」のサインも書かれています。コードへの単純な変更が、テストへの過大に長い変更を引き起こすなら、それはテストに問題があるサイン。第5章の「配線を固定するテスト」を増やしすぎると、ここに来ます。
