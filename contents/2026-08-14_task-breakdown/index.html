一番大きいタスクを速くしても、納期は1日も縮まない

「ログイン機能を作る」を7個に割って、実際に計算しました。縮めるべき場所は直感と違います。
⏱ 約7分 リード向け テンプレ配布 50行のスクリプト付き

⭐ 3行で言うと

  1. 作業量の合計と、終わるまでの日数は別物 合計7日ぶんの作業が、並行にすれば4.5日で終わります。分解の目的はこれです。
  2. 一番大きいタスクを半分にしても、全体は1日も縮まなかった 実際に計算した結果です。4.5日のまま変わりません。
  3. 縮むのは「余裕ゼロの道」を縮めたときだけ。しかも縮めると道が移る だから毎回計算し直します。50行のスクリプトを置いておきます。

1まず7個に割ってみる

「ログイン機能を作る」は、そのままでは誰も着手できない

このままIssueにすると、担当者はどこから手を付けるかを自分で決めるところから始めます。そこで止まります。

実際に割ります。基準は「明日の朝これを見て、すぐ手が動くか」だけです。

ログイン機能を作る → 7個
A  仕様を1枚にまとめる        0.5日   前提なし
B  APIの入出力を決める        0.5日   A のあと
C  DBのテーブルを決める        0.5日   A のあと
D  認証APIを実装する          2.0日   B と C のあと
E  ログイン画面を作る          1.5日   B のあと
F  入力エラーの表示を作る       1.0日   E のあと
G  つないでE2Eテストを書く      1.0日   D と F のあと
  • 1タスクは0.5〜2日に収める。3日を超えたら、まだ中で何か決まっていません。もう1段割ります。
  • 「◯◯のあと」を必ず書く。ここを書かない分解は、ただのリストです。順番が決まらないので並行にできません。
  • 調査タスクは作らない。「調べる」は終わりが定義できません。「Bを決めて1枚に書く」のように、成果物で書きます。

Q. 分解して「5日」と見積もったタスクがある。どうする?

正解。5日と言えてしまうのは、中身が見えていないからです。見えていれば「2日と1日と2日」に分かれます。大きい見積もりは、実力ではなく解像度の問題です。

2依存関係を書くと、並行にできる形が見える

7個を線でつなぐと、2本の道に分かれる

  • Aが終わるまで誰も動けません。だからAは最優先で、しかも一番短くすべきです。ここが詰まると全員が止まります。
  • BとCは同時にやれます。2人いれば0.5日で両方終わります。1人なら1日かかります。
  • Eは「Bのあと」でDを待ちません。APIの入出力さえ決まれば、画面はモックで作り始められるからです。この1本を分けられるかどうかが分岐点です。
Eを「Dのあと」にしてしまうと何が起きるか
よくある書き方
「APIができてから画面を作る」。自然に見えますが、これだと E は D の完了（3.0日時点）まで開始できません。全体は 3.0 + 1.5 + 1.0 + 1.0 = 6.5日になります。2日の損です。
分けるための条件
Bで入出力の形だけ先に確定させること。中身の実装は後でいい。ここを合意しておけば、画面はダミーの応答で進められます。

3計算する（50行）

目で追うと間違えるので、書かせて計算させる

タスクが7個ならまだ目で追えます。15個を超えると人間には無理です。計算させます。

critical_path.py — 依存関係から最短日数を出す
# id, 名前, 日数, 依存(先に終わっている必要があるタスク)
TASKS = [
    ("A", "仕様を1枚にまとめる",        0.5, []),
    ("B", "APIの入出力を決める",        0.5, ["A"]),
    ("C", "DBのテーブルを決める",        0.5, ["A"]),
    ("D", "認証APIを実装する",          2.0, ["B", "C"]),
    ("E", "ログイン画面を作る",          1.5, ["B"]),
    ("F", "入力エラーの表示を作る",      1.0, ["E"]),
    ("G", "つないでE2Eテストを書く",     1.0, ["D", "F"]),
]


def schedule(tasks):
    """各タスクの最早開始日と最早終了日を出す。"""
    days = {t[0]: t[2] for t in tasks}
    deps = {t[0]: t[3] for t in tasks}
    start, finish = {}, {}

    def finish_of(tid):
        if tid in finish:
            return finish[tid]
        s = max([finish_of(d) for d in deps[tid]], default=0.0)
        start[tid] = s
        finish[tid] = s + days[tid]
        return finish[tid]

    for tid in days:
        finish_of(tid)
    return start, finish


def critical_path(tasks, finish, deps):
    """終わりから逆にたどって、全体の長さを決めている一本道を出す。"""
    end = max(finish, key=lambda k: finish[k])
    path = [end]
    while deps[path[-1]]:
        prev = max(deps[path[-1]], key=lambda d: finish[d])
        path.append(prev)
    return list(reversed(path))

4一番大きいタスクを縮めてみる

2日のタスクを1日にした。全体は1日も縮まなかった

遅れそうなとき、まず一番大きいタスクに人を足したくなります。この例ではD（認証API、2.0日）です。やってみます。

Dを 2.0日 → 1.0日 にした結果
=== 一番大きい D を 2.0日 → 1.0日 に縮めた ===
D   認証APIを実装する          1.0   1.0   2.0   1.5日
E   ログイン画面を作る         1.5   1.0   2.5   0.0日  ←余裕なし

全部を1人で順番にやると : 6.0 日
人を足して並行にやると   : 4.5 日      ← 変わっていない
全体の長さを決めている道 : A → B → E → F → G

作業量は7日から6日に減りました。それでも終わる日は1日も動きません。Dは元々余裕のある道にいたからです。

今度は余裕ゼロのE（1.5日 → 0.5日）
=== 余裕なしの E を 1.5日 → 0.5日 に縮めた ===
D   認証APIを実装する          2.0   1.0   3.0   0.0日  ←余裕なし
E   ログイン画面を作る         0.5   1.0   1.5   0.0日  ←余裕なし
F   入力エラーの表示を作る     1.0   1.5   2.5   0.5日

全部を1人で順番にやると : 6.0 日
人を足して並行にやると   : 4.0 日      ← 0.5日 縮んだ
全体の長さを決めている道 : A → B → D → G   ← 道が移った
  • 縮めていいのは、余裕ゼロのタスクだけ。それ以外に人を足すのは、作業量を減らしているだけで納期には効きません。
  • 縮めると道が移ります。今回は E を縮めた瞬間、Dが余裕ゼロになりました。1回縮めたら必ず計算し直す。
  • 0.5日しか縮まなかったことにも意味があります。「1日ぶん頑張っても半日しか効かない」と分かれば、そもそも別の手を探せます。

Q. 納期に間に合わない。人を1人足せる。どこに入れる?

正解。条件が2つ重なっているのがポイントです。「余裕ゼロの道の上にある」かつ「その中で大きい」。片方だけだと効きません。なお、人を足すこと自体に引き継ぎのコストがかかるので、それも日数に足して計算してください。

5分解でよくある失敗3つ

兆候が出た時点で気づけば、まだ間に合います

失敗先に出る兆候手当て
割りすぎ
30分単位まで刻む		 タスクの更新作業そのものに時間が溶ける。誰も一覧を見なくなる 0.5日を下限にする。それ未満は親タスクの中のチェックリストへ
依存を書かない
リストにしただけ		 着手できるタスクが常に1個しかない。人が余っているのに進まない 各タスクに「◯◯のあと」を1行足す。それだけで並行できる形が見える
終わりが決まっていない
「調査」「対応」「改善」		 進捗を聞くと毎回「だいたい8割です」と返ってくる 成果物の名前に書き換える。「調べる」→「比較表を1枚出す」
  • 「だいたい8割」は最強の危険信号です。終わりが定義されていないタスクは、永遠に8割のままです。
  • 割りすぎの害は見えにくい。細かく割るほど正しく管理している気分になりますが、更新コストだけが増えます。
  • 迷ったら「明日の朝、これを見て手が動くか」。動かないなら大きすぎ、管理が面倒なら小さすぎです。

3. 「◯◯のあと」が書いてあるか
4. 触るファイル・画面が具体名で書けるか

前提
この計算は、見積もりが正しいことを前提にしています。見積もりが雑なら結果も雑です。ただし「どこを見るべきか」の当たりを付ける用途なら、雑な見積もりでも十分に役立ちます。
人を足すコストは含まれていない
上の計算は、人を足せばすぐ並行に動ける前提です。実際には引き継ぎと立ち上がりの時間がかかります。遅れているプロジェクトに人を足すとかえって遅れる、という指摘は古くからあります（Brooksの法則）。足した人の立ち上がり日数も、タスクとして計算に入れてください。
