タスク分解とクリティカルパス — どこを縮めると納期が動くか

「ログイン機能を作る」を7個に割って、実際に計算しました。縮めるべき場所は直感と違います。
⏱ 約7分 リード向け テンプレ配布 動かせるスクリプト付き

⭐ 3行で言うと

  1. 作業量の合計と、終わるまでの日数は別物 合計7日ぶんの作業が、並行にすれば4.5日で終わります。分解の目的はこれです。
  2. 一番大きいタスクを半分にしても、全体は1日も縮まなかった 実際に計算した結果です。4.5日のまま変わりません。
  3. 縮むのは「全余裕ゼロの道」を縮めたときだけ。しかも縮めると道が増える 今回は1本だった道が2本になりました。だから毎回計算し直します。動かせるスクリプトを置いておきます。

1まず7個に割ってみる

「ログイン機能を作る」は、そのままでは誰も着手できない

このままIssueにすると、担当者はどこから手を付けるかを自分で決めるところから始めます。そこで止まります。

実際に割ります。基準は「明日の朝これを見て、すぐ手が動くか」だけです。

ログイン機能を作る → 7個
A  仕様を1枚にまとめる        0.5日   前提なし
B  APIの入出力を決める        0.5日   A のあと
C  DBのテーブルを決める        0.5日   A のあと
D  認証APIを実装する          2.0日   B と C のあと
E  ログイン画面を作る          1.5日   B のあと
F  入力エラーの表示を作る       1.0日   E のあと
G  つないでE2Eテストを書く      1.0日   D と F のあと
  • 1タスクは0.5〜2日に収める。3日を超えたら、まだ中で何か決まっていません。もう1段割ります。
  • 「◯◯のあと」を必ず書く。ここを書かない分解は、ただのリストです。順番が決まらないので並行にできません。
  • 調査タスクは作らない。「調べる」は終わりが定義できません。「Bを決めて1枚に書く」のように、成果物で書きます。

Q. 分解して「5日」と見積もったタスクがある。どうする?

正解。5日と言えてしまうのは、中身が見えていないからです。見えていれば「2日と1日と2日」に分かれます。大きい見積もりは、実力ではなく解像度の問題です。

2依存関係を書くと、並行にできる形が見える

7個を線でつなぐと、2本の道に分かれる

  • Aが終わるまで誰も動けません。だからAは最優先で、しかも一番短くすべきです。ここが詰まると全員が止まります。
  • BとCは同時にやれます。2人いれば0.5日で両方終わります。1人なら1日かかります。
  • Eは「Bのあと」でDを待ちません。APIの入出力さえ決まれば、画面はモックで作り始められるからです。この1本を分けられるかどうかが分岐点です。
Eを「Dのあと」にしてしまうと何が起きるか
よくある書き方
「APIができてから画面を作る」。自然に見えますが、これだと E は D の完了（3.0日時点）まで開始できません。全体は 3.0 + 1.5 + 1.0 + 1.0 = 6.5日になります。2日の損です。
分けるための条件
Bで入出力の形だけ先に確定させること。中身の実装は後でいい。ここを合意しておけば、画面はダミーの応答で進められます。

3計算する（全余裕を出す）

目で追うと間違えます。この記事の初版が実際に間違えました

7個でも目では追えません。この記事の初版は、C（DB設計）を「余裕なし」と表示していました。実際には半日の余裕があります。詳細は訂正と追記に書きました。

計算させます。ポイントは後ろ向きの計算を必ずやることです。ここを省くと、初版と同じ間違いをします。

critical_path.py（抜粋）— 前向きと後ろ向きの2回計算する
# id, 名前, 日数, 依存(先に終わっている必要があるタスク)
TASKS = [
    ("A", "仕様を1枚にまとめる",     0.5, []),
    ("B", "APIの入出力を決める",     0.5, ["A"]),
    ("C", "DBのテーブルを決める",    0.5, ["A"]),
    ("D", "認証APIを実装する",       2.0, ["B", "C"]),
    ("E", "ログイン画面を作る",      1.5, ["B"]),
    ("F", "入力エラーの表示を作る",  1.0, ["E"]),
    ("G", "つないでE2Eテストを書く", 1.0, ["D", "F"]),
]


def forward(days, deps):
    """前向き計算。最早開始(ES)と最早終了(EF)を出す。"""
    es, ef = {}, {}

    def ef_of(t):
        if t not in ef:
            es[t] = max([ef_of(d) for d in deps[t]], default=0.0)
            ef[t] = es[t] + days[t]
        return ef[t]

    for t in days:
        ef_of(t)
    return es, ef


def backward(days, deps, span):
    """後ろ向き計算。最遅開始(LS)を出す。全余裕はここでしか出ない。"""
    succ = {t: [] for t in days}
    for t in deps:
        for d in deps[t]:
            succ[d].append(t)
    ls = {}

    def ls_of(t):
        if t not in ls:
            lf = min([ls_of(s) for s in succ[t]], default=span)
            ls[t] = lf - days[t]
        return ls[t]

    for t in days:
        ls_of(t)
    return ls

この2つを使って、全余裕は引き算1回で出ます。

critical_path.py（抜粋）— 全余裕を出している行
    es, ef = forward(days, deps)
    span = max(ef.values())
    ls = backward(days, deps, span)
    ...
    for tid, name, d, _ in tasks:
        tf = round(ls[tid] - es[tid], 6)

上に載せたのは計算部分だけの抜粋です。表を整形して表示する部分は省いています。そのままでは何も表示されません。全文（112行）は critical_path.py に置きました。

2. 全文を critical_path.py という名前で保存する
3. そのフォルダで python3 critical_path.py と実行する

あとは TASKS の中身を自分のタスクに書き換えるだけです。

  • 「全余裕」の列が全部です。0.0日のタスクは、1時間遅れたら納期が1時間延びます。ここだけ毎日見ればいい。
  • 0.5日の余裕があるのは C と D の2つ。どちらも半日遅れて納期に影響しません。この2人に毎日進捗を聞く必要はありません。
  • 見るべきはA・B・E・F・Gの5つ。7個全部を追いかけるより、5個に集中したほうが早く異常に気づけます。

この「全余裕」という言葉には、まぎらわしい兄弟がいます。NASAのスケジュール管理ハンドブックが、両方をはっきり定義しています。

NASA/SP-2010-3403, p.48, 5.8.3 Float (Slack) より原文
Total float is defined as the amount of time that a task or milestone can slip before affecting the project end date.

Free float is defined as the amount of time a task or milestone may move into the future from its early finish date before affecting its immediate successor task(s).

全余裕は納期に効くまでの余裕、自由余裕はすぐ次のタスクに効くまでの余裕です。同じ文書はこう続けます。自由余裕を、プロジェクト全体の進捗管理に使うべきではない（"it should generally not be used as a means of monitoring and managing schedule performance for the total project"）。初版はここを取り違えていました。

本当に「納期への余裕」になっているか、遅延を入れて確かめた

定義を写しただけでは検算になりません。各タスクを全余裕ぶんちょうど遅らせ、次にそこから0.1日だけ足して遅らせ、全体日数がどう動くかを見ました。

7個とも、全余裕ぶんなら 4.5日 のまま。0.1日でも超えると 4.6日 に延びます。列の意味が定義どおりであることの確認です。スクリプトは verify_float.py（34行）。

4一番大きいタスクを縮めてみる

2日のタスクを1日にした。全体は1日も縮まなかった

遅れそうなとき、まず一番大きいタスクに人を足したくなります。この例ではD（認証API、2.0日）です。やってみます。

実行結果 ②／③ — Dを 2.0日 → 1.0日 にした結果
=== D を 2.0→1.0日 に縮めた ===

* B  APIの入出力を決める      0.5   0.0
  C  DBのテーブルを決める     0.5   1.5
  D  認証APIを実装する        1.0   1.5

* F  入力エラーの表示を作る   1.0   0.0

並行にやると      :  4.5 日

「並行にやると」の行が 4.5日 のまま動いていません。作業量は7日から6日に減りました。それでも終わる日は1日も動きません。Dは元々余裕のある道にいたからです。

むしろDの余裕が 0.5日 から 1.5日 に増えただけでした。余裕を増やす作業に人を投入したことになります。

=== E を 1.5→0.5日 に縮めた ===

* A  仕様を1枚にまとめる      0.5   0.0
* B  APIの入出力を決める      0.5   0.0
* C  DBのテーブルを決める     0.5   0.0
* D  認証APIを実装する        2.0   0.0
  E  ログイン画面を作る       0.5   0.5
  F  入力エラーの表示を作る   1.0   0.5

1人で順番にやると :  6.0 日
並行にやると      :  4.0 日
納期を決めている道 :
  A → B → D → G
  A → C → D → G

今度は 4.5日 → 4.0日。0.5日 縮みました。そして最後の2行に注目してください。道が1本から2本に増えています。

  • 縮めていいのは、全余裕ゼロのタスクだけ。それ以外に人を足すのは、作業量を減らしているだけで納期には効きません。
  • 縮めると道が移り、しかも増えます。E を縮めた瞬間、C と D が全余裕ゼロに変わり、納期を決める道が2本になりました。1回縮めたら必ず計算し直す。
  • 0.5日しか縮まなかったことにも意味があります。「1日ぶん頑張っても半日しか効かない」と分かれば、そもそも別の手を探せます。

Q. 納期に間に合わない。人を1人足せる。どこに入れる?

正解。条件が2つ重なっているのがポイントです。「全余裕ゼロの道の上にある」かつ「その中で大きい」。片方だけだと効きません。道が2本以上あるときは、両方に乗っているタスク（この例ではD）を先に狙うと効率がいいです。なお、人を足すこと自体に引き継ぎのコストがかかるので、それも日数に足して計算してください。

5分解でよくある失敗3つ

兆候が出た時点で気づけば、まだ間に合います

失敗先に出る兆候手当て
割りすぎ
30分単位まで刻む		 タスクの更新作業そのものに時間が溶ける。誰も一覧を見なくなる 0.5日を下限にする。それ未満は親タスクの中のチェックリストへ
依存を書かない
リストにしただけ		 着手できるタスクが常に1個しかない。人が余っているのに進まない 各タスクに「◯◯のあと」を1行足す。それだけで並行できる形が見える
終わりが決まっていない
「調査」「対応」「改善」		 進捗を聞くと毎回「だいたい8割です」と返ってくる 成果物の名前に書き換える。「調べる」→「比較表を1枚出す」
  • 「だいたい8割」は最強の危険信号です。終わりが定義されていないタスクは、永遠に8割のままです。
  • 割りすぎの害は見えにくい。細かく割るほど正しく管理している気分になりますが、更新コストだけが増えます。
  • 迷ったら「明日の朝、これを見て手が動くか」。動かないなら大きすぎ、管理が面倒なら小さすぎです。

前提
この計算は、見積もりが正しいことを前提にしています。見積もりが雑なら結果も雑です。ただし「どこを見るべきか」の当たりを付ける用途なら、雑な見積もりでも十分に役立ちます。

訂正と追記

初版は「余裕」の定義を取り違えていました（2026年8月15日訂正）

公開後の検証で、スクリプトが出していた「余裕」は全余裕ではなく自由余裕（free float）だったことが分かりました。記事の解説文は全余裕の説明で、表の数字は自由余裕。中身が食い違っていました。

初版の記述実際直した内容
C は「0.0日 ←余裕なし」 C の全余裕は 0.5日。半日遅らせても納期は 4.5日 のまま 後ろ向き計算（LS/LF）を足して全余裕を出すようスクリプトを書き直し、3つの出力を貼り直した
「Dだけ0.5日の余裕がある」 0.5日の余裕があるのは C と D の2つ 「C と D の2つ」に修正
Eを縮めた出力で、Eに「←余裕なし」が付いたまま「道が移った」と書いていた Eの全余裕は 0.5日 で道の上にいない。同じブロック内で矛盾していた 出力が正しくなり矛盾が解消。あわせて道が2本に増えることも分かった
「50行のスクリプト」 実際に走らせていたファイルは86行。記事に載っていたのは39行の抜粋で、そのままでは何も表示されない 行数の主張をやめ、書き直した全文（112行）を critical_path.py として同梱。抜粋であることと動かし方も明記
「15個を超えると人間には無理」 15という数字の根拠を示せませんでした 数値を削除。代わりに、実際に間違えた例（この訂正そのもの）を置いた
出力の行末に手書きの注記（← 変わっていない など） スクリプトはその文字を出力していません 注記を本文へ移し、pre の中は素の出力だけに戻した
  • 結論は変わっていません。一番大きいDを半分にしても 4.5日 のまま、Eを縮めると 4.0日。ここは初版と同じです。
  • 変わったのは「誰を毎日見るか」。初版に従うとC（DB設計）の担当者を無駄に追いかけることになります。ここが実害でした。
  • 原因は一次資料に当たらなかったこと。全余裕と自由余裕を定義した資料を読まずに実装し、コメントだけ全余裕の定義で書いていました。
