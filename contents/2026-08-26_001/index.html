Claudeの記憶が1つになった — チャットで話したことがCoworkにも出る

8/25 公開 Claudeを使っている人 既定の変更 Claude

Anthropicが8月25日に、Claudeのメモリー（過去の会話から覚えておく仕組み）の作りを変えたと発表しました。

まず用語です。Claude Cowork は、チャット画面ではなくクラウド側でまとまった作業を走らせるほうのClaudeです（公式の説明にも「When Cowork runs a task in the cloud」とあります）。そのCoworkが、今回はじめて記憶を持ちました。しかも中身はチャットと同じものです。

公式ブログ（冒頭）
Starting today, the memory you use in chat is the same as in Claude Cowork.

つまり、チャットで一度説明したことを、Coworkに作業を頼むときに説明し直さなくてよくなったということです。逆向きも同じで、Coworkで出てきたことがチャットに戻ります。

変わったのは置き場所だけではありません。書き込む時点も変わりました。

同ブログ（書き込む時点）
Claude now adds topics to memory as you chat, instead of summarizing conversations after they end.

これまでは「会話が終わってから要約する」形でした。今は話している最中に項目が足されます。「これ覚えておいて」と言う必要はありません。裏返すと、言うつもりのなかったことも、その場で残ります。

残ったものは、設定の Topics に短いファイルの一覧として出ます。1つずつ読めて、直せて、消せます。会社の旧名を1か所直せば、以降の会話すべてに効く、という説明です。

センシティブな話題の扱い（既定はオフ。オンにしても保存しないものがある）

健康・人種・民族・信条・政治・性自認などは、既定では記憶に入りません。設定でオンにすると入るようになり、保存のたびに通知が出ます。オンにする前の分は遡って保存されません。いつでも切れます。

オンにしても保存しないものが別にあります。公式の記述では、社会保障番号などの識別番号、犯罪歴、在留資格、および利用規約（AUP）に反するものです。保存できなかったときはClaudeがその旨を伝えます。

既定がどうなっているかは、契約しているプランで変わります。

同ブログ（プランごとの既定）
Memory is on by default on Free, Pro and Max plans across web, desktop, and mobile. Note that saving sensitive topics in memory is off by default. On iOS and Android, update to the latest version of the mobile app to get the most recent updates. For Team and Enterprise, admins control availability for their organization, and memory is off for individual users until they turn it on.

個人で使っている人（Free / Pro / Max）は、何もしなくても既にオンです。会社のTeam / Enterprise契約なら、管理者が組織として可否を決め、そのうえで各自が入れるまではオフです。

  • 個人で使っているなら。設定の Settings > Memory を開き、Topics に何が入っているかを一度見る。
  • 会社で使っているなら。管理者に、組織として有効にするかを確認する。個人側は自分で入れるまでオフ。
  • iOS / Android を使うなら。アプリを最新版に更新する（公式が明記している条件）。
  • 今やること。Topicsを見て、業務で残ってほしくないものが無いか確かめる。

Laravel 13.27.0 — in_array と doesnt_contain の判定が厳密比較に変わった

8/25 公開 Laravelを使っている人 挙動が変わる Laravel

Laravel 本体の v13.27.0 が、8月25日23:16（JST）に Packagist（Composerが取りに行くパッケージの置き場）へ出ました。版番号の真ん中が上がった更新ですが、入力チェック（バリデーション）の判定基準が2つ変わっています。

いつ自分の環境に来るかというと、composer.json の指定が ^13.0 のような形なら、次に composer update を実行したときです。放っておいて勝手に上がることはありません。

変わったのは、引数が1つ増えただけです。実際に2つの版からファイルを取って並べると、こうなります（- が v13.26.1、+ が v13.27.0）。

2つの版でソースを比べる
$ bash laravel_strict.sh
-- validateInArray
- in_array($value, $otherValues)
+ in_array($value, $otherValues, true)
-- validateDoesntContain
- in_array($parameter, $value))
+ in_array($parameter, $value, true))
-- validateContains
- in_array($parameter, $value))
+ in_array($parameter, $value))

第3引数の true が付きました。PHPの in_array は、これが無いと型を揃えてから比べます。付けると型も一致しないと通りません。

どのくらい違うのかを、この環境のPHP 8.4.19で実際に流しました。[1, 0, 'abc'] の中を探した結果です。loose が今までの判定、strict がこれからの判定です。

PHP 8.4.19 で実行
$ php strict.php
value  loose  strict
'1'    match  -
0.0    match  -
'ABC'  -      -
true   match  -
NULL   match  -

つまり、フォームから来た文字列の "1" は、比較先が数値の 1 だともう通りません。JSONのボディやクエリ文字列で型がばらつくAPIほど当たります。

contains だけ元のままなのは、同じ版の中でいったん厳密化してから取り消されたためです（#61320 を #61330 で差し戻し）。3つまとめて変わったと思い込むと、テストの想定を間違えます。

  • 使っているか調べるなら。プロジェクトの一番上で grep -rn "in_array:\|doesnt_contain:" app/ routes/。
  • 当たったら。比較先の配列と入力の型を揃えるか、integer などの型ルールを前段に置く。
  • 今やること。上のgrepで0件なら対応は不要。1件でも出たら、上げる前にテストを流す。

ECSが自分でタスクを退避するようになった — Fargateでも勝手に置き換わる

8/25 公開 ECS on Fargate を使っている人 挙動が変わる AWS

先に用語です。ECS は、コンテナ（アプリ一式を箱詰めして動かす仕組み）をまとめて運転するAWSのサービスです。動かし方が2通りあり、土台のサーバーをAWSに任せるのが Fargate、自分で用意するのが EC2 です。ECSで動くコンテナのひとまとまりをタスクと呼びます。

AWSが8月25日、この ECS に AGENT_CONNECTIVITY という状態変更イベントを追加したと告知しました。

ECSのホストにはエージェントという常駐プログラムがいて、ECSの制御側とやり取りしています。ディスク（EBSボリューム）の劣化やネットワーク障害でこの線が切れると、実際には動いていないのに「動いていることになっている」状態が起きます。それを検知する話です。

AWS の告知（自動復旧の範囲）
For ECS Managed Instances and AWS Fargate, ECS automatically performs recovery - automatically draining running tasks and launching replacement capacity while deregistering impaired instances.

読むべきは Fargate が対象に入っていることです。こちらが指示していなくても、動いているタスクが落とされて別のタスクに置き換わります。EC2で動かしている場合は自動復旧はされず、イベントを受けて自前で入れ替える形です。

追加費用は無く、商用リージョンとGovCloud（US）の全リージョンで使えるとされています。

タスクは止められる前に SIGTERM（終了しなさいという合図）を受けます。合図から強制終了までの猶予は、タスク定義（コンテナの起動設定を書いたJSON）の stopTimeout で決まります。

  • 確認すること。タスクが SIGTERM を受けてから終わるまでの処理と、タスク定義の stopTimeout。
  • あわせて。ALB（アクセスを複数のタスクへ振り分ける装置）の登録解除の待ち時間が短すぎないか。
  • 今やること。本番ではなく検証環境でタスクを1つ止め、接続が切れずに復帰するか見る。復帰するなら対応は不要。

Chrome 152 と Android System WebView 152 が同じ日に出た — 修正327件のうちCriticalが10件

8/26 公開 WebViewを積んでいる人 セキュリティ Chrome

Chrome 152 の安定版が、日本時間の8月26日未明に出ました。デスクトップだけでなく、Android System WebView も同じ 152.0.7977.64 に切り替わっています（Chromiumの公開ダッシュボードで確認）。

WebViewは、アプリの中でWebページを表示する部品です。アプリを更新しなくても、端末側のWebViewが更新されれば中身の挙動は変わります。だから自社アプリのリリース予定とは無関係に効きます。

この版で直ったセキュリティ問題を、公式の告知本文から数えました。

Chrome 152 の修正を重大度と部品で数える
$ python3 count_cves.py

High        61
Medium     184
Low         72
-- 部品ごと
ANGLE       27
CustomTabs  10
WebGL        3
WebView      2

部品名で見ると、この読者に効く順に並びます。ANGLE はWebGLの描画をOSのグラフィックスAPIへ橋渡しする層で、Unity Web のビルドが必ず通る場所です。Custom Tabs は、アプリからブラウザを開く仕組みです。

Criticalの10件には、ANGLEの use-after-free（解放済みのメモリを使ってしまう不具合。攻撃に使われやすい）が1件あります（CVE-2026-79282）。WebViewやCustom Tabsを積んでいるアプリは、端末のWebViewが152に上がるまで穴が残ります。アプリ側でできることは無く、端末の更新待ちです。

なお、告知には「バグの詳細は、多くの利用者が更新を終えるまで公開を制限する」という但し書きがあります。個別の再現手順は今の時点では読めません。

検証端末でこれだけ見れば足ります。0 / 3

152では XSLT の削除も段階的に始まる

Chromeの機能一覧（chromestatus）で 152 を引くと、Deprecate and remove XSLT が「段階的な適用（stepped rollout）」と「延命用のオリジントライアル」の両方に載っています。ブラウザ側でXSLTを使ってXMLを整形しているページは、152以降で順次動かなくなります。

ただし何%から切るかの数値は、この一覧からは取れません。数字は書きません。自社に <?xml-stylesheet や XSLTProcessor を使っているページがあるかだけ、先に確かめておくと安全です。

  • WebViewを積んでいるなら。上のチェックリストを検証端末で一周する。アプリの再ビルドは要らない。
  • 今やること。端末のWebViewが152に上がるのを待つだけ。アプリ側の対応は不要。
