Terraform 1.16.0 の destroy = false は、消さずに管理から外す機能だった

8/27 公開 Terraformを使う人 新機能 Terraform

Terraform 1.16.0 が日本時間8月27日2時47分に出ました。新機能の中に、lifecycle ブロックの新しい書き方があります。

まず用語です。lifecycle ブロックは、リソースの作り直し・消し方についての注文をTerraformに伝える場所です。state は「Terraformが今いくつ何を管理しているか」を記録したファイルで、実体（AWS上の本物のリソース）とは別物です。

CHANGELOGにはこう書いてあります。

CHANGELOG 1.16.0 の原文
Resource lifecycle blocks now support destroy = false to prevent a resource from being destroyed.

「破棄されるのを防ぐ」と読めます。それなら以前からある prevent_destroy と同じに見えます。ところが公式ドキュメントの説明は違いました。

公式ドキュメント（lifecycle の destroy）
Set to false to remove a resource from state without destroying the actual infrastructure resource.

「実体を破棄せずに、state から取り除く」。まるで別の機能です。どちらが本当か、実際に動かして確かめました。

検証は、AWSではなく local_file（ローカルにファイルを1つ作るだけのリソース）で行いました。実体がただのファイルなので、消えたか残ったかを ls で直接見られるからです。認証情報も要りません。

main.tf（抜粋）
resource "local_file" "memo" {
  filename = "${path.module}/hello.txt"
  content  = "consider me infrastructure\n"

  lifecycle {
    destroy = false
  }
}

apply でファイルを作り、state に載っていることを確認してから destroy を打ちました。

terraform destroy の出力（実行したもの）
Plan: 0 to add, 0 to change,
      0 to destroy.

Warning: Some objects will no
longer be managed by Terraform

Terraform will discard its
tracking information for the
following objects, but it will
not delete them:
 - local_file.memo

Destroy complete!
Resources: 0 destroyed.

「0 destroyed」。エラーにはならず、destroy は成功しています。そのうえで実体を見ると、

destroy の後に確認した結果
$ ls -l hello.txt
-rwxr-xr-x 1 root root 27 hello.txt

$ head -1 hello.txt
consider me infrastructure

$ terraform state list
(出力なし = stateは空)

ファイルは残り、state だけが空になりました。ドキュメントのほうが正しく、CHANGELOGの書きぶりが誤解を招く形だったことになります。

名前の似た2つは、こう違います。

書き方destroy を打つと実体は
destroy = false 成功する（0 destroyed） 残る
prevent_destroy = true エラーで止まる 残る
何も書かない 成功する 消える

怖いのは、これをAWSでやったときです。destroy が成功して「消えた」と思っても、ALBもFargateのタスクも生きています。Terraformからは見えなくなるので、誰も気づかないまま課金だけが続きます。戻すには import し直すしかありません（出力の警告文にもそう書かれています）。

1.16.0 の UPGRADE NOTES（上げる前に見る1件）

この版の UPGRADE NOTES は1件だけです。原文は「bastion_host_key is now correctly applied by provisioners. Review your provisioner configurations to verify the configured key is correct before upgrading.」

踏み台サーバー経由の provisioner を使っている場合、これまで効いていなかった鍵の指定が効くようになります。間違った鍵が書いてあると、上げた後で初めて繋がらなくなります。上げる前に設定を見ておくこと、と書かれています。

今やること。1.16.0 に上げる予定があるなら、provisioner の bastion_host_key を先に確認する。destroy = false は「消さない」ではなく「Terraformの管理から外す」と覚える。破棄を止めたいなら prevent_destroy = true のほう。

Unity 6000.6 で WebGPU が experimental を外れた — ただし既定では有効にならない

8/24 告知 Unity Webを作る人 新機能 Unity Web

このセクションだけは更新が少ないため直近1週間まで見ています。8月24日の話です。

Unity 6000.6（6.6）で、WebGPU が実験的機能ではなくなりました。公式マニュアルを新旧で比べると、表記が変わっています。

バージョンマニュアルの見出し本文
6000.3 WebGPU (Experimental) WebGPU is experimental… と明記
6000.6 WebGPU experimental の語が消えた

用語です。WebGPU は、ブラウザからGPUを使うための新しい仕組みです。いま Unity Web が使っている WebGL2 より新しく、できることが多い代わりに、対応していないブラウザがまだあります。

大事なのは、正式サポートになっても勝手には切り替わらないことです。公式マニュアルの手順では、Player Settings の Graphics APIs の一覧に自分で WebGPU を足す必要があります。

足したあと、WebGL2 を一覧に残すかどうかを決めます。Unity は一覧の先頭のAPIを優先し、ブラウザが対応していなければ次のものに落とす、という順で試します。だから WebGL2 を下に残しておけば、WebGPU 非対応のブラウザから来た人にも動きます。逆に WebGL2 を消すと WebGPU のみになります。

両方を残すと、開発とテストの手間は増える

公式マニュアルは、両方を残す利点（対応していないブラウザの人にも届く）と欠点を並べて書いています。欠点のほうは「2つのグラフィックスAPIをサポートすることになるので、開発とテストがより複雑になる」という趣旨です。

つまりどちらが正解と決めてはいません。誰に届けたいかで決める、という書き方です。社内向けで対象ブラウザを絞れるなら WebGPU のみ、一般公開なら WebGL2 を残す、が素直な分け方になります。

今やること。いま 6000.6 に上げる予定が無いなら対応は不要。上げるなら、Graphics APIs の一覧を開いてWebGL2 を残すかどうかだけ決める。何もしなければ、これまでどおり WebGL2 のまま動きます。
