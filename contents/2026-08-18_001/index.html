Issueのタイトルを書くだけでCIのランナーを乗っ取れた — 壊されたのは、GitHub公式が「推奨」と書いている書き方

8/17公開 ✓ 一次資料確認済 ⚠ 修正済み(6/23) GitHub Actions セキュリティ

Wiz Researchの報告です。原文はこうです。「Wiz Red Agent identified a script injection vulnerability in snowflakedb/snowflake-connector-net. The issue allowed an unauthenticated user to execute arbitrary commands within a GitHub Actions runner by opening a GitHub issue with a specially crafted title.」

GitHub Actionsは、リポジトリに置いたYAML(設定を書くためのファイル形式)の手順を実行するCI(継続的インテグレーション。コードの変更を自動でチェック・処理する仕組み)です。ランナーとは、その手順を実際に走らせるマシンのこと。Issueは、GitHub上で「この機能が欲しい」「ここが動かない」と報告・要望を書くためのチケットで、誰でもタイトルを自由に付けられます。ログイン不要の第三者がIssueを立てるだけで、そのマシン上でコマンドが動きました。混入は6月18日、発見と修正は6月23日、公開が8月17日です。

おもしろいのは、脆弱性が入った経緯のほうです。原文を引きます。

Wiz Research — 混入の経緯(原文)
The merged PR replaced the repository's
sanitized input pattern with direct

AI-assisted security review did not

もともと安全だった書き方が、マージされたPRで直接展開に置き換わり、AI支援のセキュリティレビューはそれを指摘しなかった——という二重の失敗です。差分はこうなっていました。マージとは、提案された変更を本体に取り込むことです。以下の-で始まる行は削除された行、+で始まる行は追加された行を表します(この記法をdiffと呼びます)。

安全な書き方が、直接展開に置き換わった

-   ISSUE_TITLE: ${{ github.event.issue.title }}
- run: jq -n --arg title "$ISSUE_TITLE" ...
+ run: TITLE=$(echo '${{ github.event.issue.title }}' | sed ...)

これはGitHub Actionsの設定ファイル(YAML形式)の一部です。${{ }}はGitHubが値を実際の文字列に置き換える書き方で、jqやsedはその文字列を安全に加工するためのコマンドです。変更前は、Issueのタイトルを一度env:の中間変数に入れてから使っていました。変更後は、タイトルの文字列を直接コマンドの中に埋め込んでいます。

一見するとsedでエスケープ(記号を無害な文字列として扱わせる処理)しているので安全に見えます。順番が逆です。原文は「The sed escaping runs after GitHub's template expansion, a single quote in the title breaks out of echo '...' and allows arbitrary command execution.」

では正解は何か。GitHub公式のドキュメントに、そのまま書いてあります。

GitHub Docsが示している書き方
- name: Check PR title
  env:
    TITLE: ${{ github.event.pull_request.title }}
  run: |
    if [[ "$TITLE" =~ ^octocat ]]; then

「実際にこう壊れた」の直後に、「公式はこう書けと言っている」が並びます。壊れたPRが消したのは、まさにこのenv:経由のパターンでした。なお同じページは、インラインスクリプトより先に「アクションを使う」こと自体を最も推奨する方法として挙げています。env:経由は、インラインスクリプトを使う場合の中での推奨です。

もう1つ、効いていなかったガードがあります。同じワークフローには実行を絞るためのif:が付いていました。書いてあるのに、常にtrueでした。読んでみてください。

正解。Wiz Researchの原文はこうです。「on issues events, github.event.pull_request is always null. So the condition reduces to (null != 'whitesource-for-github-com[bot]'). ACMのメール検証が廃止される — 既存証明書の更新が止まるのは2027年9月30日

8/13公開 / 8/17再掲 ✓ 公式確認済 ⚠ 提供終了 ACM CloudFront / ALB

ACM(AWS Certificate Manager)は、HTTPSの証明書を無料で発行・自動更新してくれるAWSのサービスです。ALB(Application Load Balancer、アクセスを複数のサーバーに振り分ける仕組み)やCloudFront(AWSのCDN)に付けている証明書は、たいていこれです。発行するとき、そのドメインが自分のものだと証明する方法が2つあります。メール検証とDNS検証。前者が廃止されます。

原文はこうです。「AWS Certificate Manager (ACM) will discontinue support for email-validated public certificates by September 30, 2027. If you use email validation for your ACM public certificates, you need to migrate to DNS validation before that date.」

期日何が終わるか
2027年1月1日新しいAWSリージョンで、メール検証の新規提供を終了
2027年3月31日全リージョンで、新規証明書へのメール検証提供を終了
2027年9月30日メール検証を使う既存証明書の更新を終了
2028年3月15日CA/B Forum全体でメール検証による発行・更新が不可(発行済みは有効期限まで有効)

最後の1行はAWSの都合ではありません。CA/B Forumは、認証局とブラウザベンダーが証明書の運用ルールを決めている業界団体です。原文は「In November 2025, they voted to end support for email-based domain validation effective March 15, 2028.」——業界全体の決定なので、AWS以外に移しても同じ話になります。

移行手順そのものは短いです。ただし時間制限があります。

AWS Security Blog — 移行手順(原文)
When you update a certificate to DNS
validation, ACM provides a CNAME record
to add to your DNS configuration, and
you have 72 hours to add that record.
During this window, the certificate
continues to function normally on email
validation.
  • 72時間の壁は、会社をまたぐと現実的な制約になる。DNSは、ドメイン名とサーバーの場所を対応させる仕組みです。そのドメインの設定(ゾーン)を管理する場所を「DNSのゾーン」、そこに追加する1件の設定を「レコード」、AWSが要求する形式のレコードを「CNAMEレコード」と呼びます。ACMを触るのはインフラ担当の会社、DNSのゾーンを持っているのは別の会社(あるいは自社の情シス)、というのはよくある構成です。「CNAMEを1本足してください」を72時間以内に通せる連絡経路があるかを、期日ではなく今日確認しておくのが安全です(これは筆者の運用上の意見です)。
  • 切り替え中もHTTPSは切れない。原文に「During this window, the certificate continues to function normally on email validation.」とあります。CNAMEを足すまでの間、メール検証のまま動き続けます。ダウンタイムを心配して先延ばしする理由にはなりません。
  • DNS検証は自動更新される。そもそもメール検証は、更新のたびにドメイン連絡先のメールを人間が開いて承認する必要がありました。DNS検証にすればその作業が消えます。廃止は、実質的に「手作業をやめろ」という話です。
