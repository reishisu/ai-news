ComfyUIとrembgでキャラ立ち絵を量産する — 背景除去が本体まで消える原因と対策

サイトのサムネイルに使うキャラ立ち絵80枚を、ComfyUIで生成してrembgで切り抜いた記録です。数値は全部実測で、ログは無加工です。
⏱ 切り抜きは1枚18〜28秒 切り抜きはGPU不要 事故4件・全部原因特定済み

⭐ 3行で言うと

  1. 生成時間のばらつきの正体は「諦めたジョブの残り時間」。ComfyUIのワーカーは1本です。こちらが諦めてもサーバーは描き続け、次のジョブはその後ろに並びます。22回諦めて11.0時間捨てていました。
  2. 背景除去は1回では終わりません。切り抜きは4段のパイプラインになり、その4段が1つずつ事故を起こしました。ツインテール・影・黒い服が消え、戻した髪は真っ黒でした。
  3. onnxruntimeは既定でメモリを返しません。両モデルを載せた実測で13,077MiBまで伸び、80枚の一括処理は途中で落ちました。設定1行で1,014MiBになり、切り抜きのマスク(alpha)は1画素も変わりませんでした。

180枚の立ち絵を作って、サムネイルに流し込む

作ったもの: 5人×16ポーズ=80枚。黒背景で生成して、透過PNGにする

このサイトのサムネイルにはキャラの立ち絵が載っています。その画像はフォルダから読むだけなので、画像を置き換えれば全記事のサムネイルが替わります。

今回はその素材を一新しました。ComfyUIで5人×16ポーズ=80枚（832×1216・黒背景）を生成し、背景除去モデルrembgで透過PNGに切り抜きます。

生成はGPUのある手元のPC。切り抜きから公開までは、GPUなしの環境で全部回りました。

この記事は「うまくいった手順」ではなく、途中で起きた事故と、その原因を画素単位で特定した記録です。同じ作業をする人が同じ穴に落ちないために書いています。

「ランダムに遅い」なら、諦めた直後だけ8連続で遅くなる理由がありません。遅さには構造があります。

ComfyUIのワーカーは1本。こちらが諦めても、サーバーは描き続ける

原因はComfyUIの作りにあります。ジョブを実行するワーカーは、起動時に1本だけ立ち上がるスレッドです。ソースコードにそのまま書いてあります。

ComfyUI main.py の原文（ワーカーの定義と起動。この1回だけ）
def prompt_worker(q, server_instance):
(中略)
    threading.Thread(target=prompt_worker, daemon=True, args=(prompt_server.prompt_queue, prompt_server,)).start()

起動オプションの一覧（cli_args.py 全315行）にも、ワーカーを増やす指定はありません。ジョブは1本の行列に並び、前が終わるまで次は始まりません。

そして、投げた側がタイムアウトで諦めても、サーバーには伝わりません。サーバーは重いジョブを描き続け、次に投げたジョブはその後ろに並びます。だから「諦めた直後の1枚」は必ず遅い。ばらつきに見えたものの正体は、前のジョブの残り時間でした。

対策: 諦めるときに、必ず降ろす

直し方は単純で、諦めるときにサーバー側からもジョブを降ろします。APIは2つで、ジョブの状態によって使い分けます。

諦めるときに叩くAPI
# 順番待ちのジョブを行列から外す
POST /queue      {"delete": ["<prompt_id>"]}

# 実行中のジョブを中断する
POST /interrupt  {"prompt_id": "<prompt_id>"}

/interrupt は、渡した prompt_id が実行中のものと一致した時だけ中断します。別のジョブを巻き添えにしない作りです。

ComfyUI server.py の原文（/interrupt の照合部分。行頭の字下げは詰めた）
should_interrupt = False
for item in currently_running:
    # item structure: (中略)
    if item[1] == prompt_id:
        logging.info(
            f"Interrupting prompt {prompt_id}")
        should_interrupt = True
        break

効果は、偽のComfyUIサーバー（挙動だけ模したローカルHTTPサーバー）で新旧を比べて確かめました。同じ12枚を投げ、3〜4枚目だけ40秒かかる設定です（他は1秒。実物のGPUではなく縮小した時間での比較です）。

待ち方全体受け取った諦めたサーバーが描いた
旧: 諦めるだけ 83.4秒 2枚 10枚 5枚
新: 降ろしてやり直す 39.1秒 11枚 1枚 11枚

旧のいちばんの問題は時間ではありません。サーバーは5枚描いたのに、スクリプトは2枚しか受け取っていない。描き上がった3枚を、受け取らずに捨てていました。

3切り抜きは4段 — そして4段全部が事故った

rembg 1回では終わらない。掃除・除去・補完を足して4段になった

切り抜きの本体は rembg の birefnet-general-lite というモデルです。もう1つ、補完用に isnet-anime も使います。rembg の README にはこう書かれています。

rembg README「Models」の原文（リンク部分は中略）
- birefnet-general-lite (中略): A light pre-trained model for general use cases.

- isnet-anime (中略): A high-accuracy segmentation for anime character.

モデルは初回実行時に ~/.rembg/models へ自動でダウンロードされます（birefnet 224MB / isnet 176MB）。

ただしモデル1回では、黒背景の絵は綺麗になりません。実際のパイプラインは4段です。

  • 1段目: rembg（birefnet-general-lite）。背景除去の本体。床の影も、髪と肩の間のような「囲まれた背景」も抜ける。→ 事故2
  • 2段目: 縁の掃除（dark_assist）。rembgが取り残した輪郭の黒いフチを、透明になった画素の隣から広げて消す。→ 事故4
  • 3段目: 浮遊物の除去（drop_islands）。本体から離れて浮いた装飾（ハートやキラキラ）を消す。→ 事故1
  • 4段目: 欠けの補完（repair_holes）。rembgが消してしまったキャラの一部を、isnet-animeの結果で埋め戻す。→ 事故3

結論を先に書きます。この4段は、1段ずつ全部事故を起こしました。以下、見つけた順に書きます。事故1は3段目、事故2は1段目、事故3は4段目、事故4は2段目の話です。

4事故1: 「離れた塊を消す」が距離を見ていなかった

消えたのは装飾ではなく、切り離されたツインテールだった

浮遊物の除去（drop_islands）は、キャラの周りに浮く装飾マークを消す係です。ところが旧実装は「離れた塊を消す」と言いながら、大きさしか見ていませんでした（最大の塊の5%未満を削除。距離は測っていない）。

rembgが髪の細いところを切ると、ツインテールの先・袖・手が本体から切り離されます。それが「小さい塊」として、装飾と一緒に消えていました。

そこで、消える塊の「大きさ」と「本体からの距離」を、修正前の実装のまま代表12枚で測りました（islands.py。現行コードでは事故が直っているため、同じ測り方では再現しません。数値は切り抜きコードの注記にも転記してあります）。

  • 切れた体の一部は、距離1〜20px。kurumi/sleepy 13,738px・距離2.0、hinata/ok 8,280px・距離2.8。ほぼ接している。
  • 本物の装飾は、距離50〜110px。hinata/celebrate 8,206px・距離107.6。大きさは同格でも、距離は1桁違う。

大きさでは分けられませんが、距離でははっきり分かれます。修正は「30px以内の塊は、大きさに関わらず残す」。消すのは小さく、かつ離れているものだけにしました。

段ごとに「その段が新たに透明にした、元は明るい画素」を数えると、壊していたのがこの最終段だと分かります（修正前の実装で測った記録: stage_and_model.py）。

  • kotoha/thumbsup。rembg単体の欠け 65px。縁の掃除が足した欠け 0px。旧・浮遊物の除去が足した欠け 20,753px。
  • kotoha/panic。271px ／ 0px ／ 10,206px。
  • hinata/money。4,732px ／ 0px ／ 40,974px。縁の掃除は明るい欠けを1pxも足していない。桁違いに足していたのは最終段。

5事故2: birefnetがツインテールごと消す — もう1つのモデルで埋める

hinata/sleepy はツインテールが2束・合計39,594px消えていた

距離を直しても、消える髪は残りました。今度は切り離されたのではなく、birefnetが最初からツインテールを背景と判定していたのです。hinata/sleepy では24,144pxと15,450pxの2つの束が丸ごと消えました。

isnet-anime は、この髪を残せます。ならモデルを替えればよいかというと、そうはいきません。isnet は逆に「囲まれた背景」を大量に残します。80枚の差分を取ると、残した背景は合計565,472px。73枚に400px以上の塊があり、最大は hinata/celebrate の62,682pxでした（model_diff.py）。

どちらか一方を選ぶ必要はありません。消えた本体（金髪）は明るく、残る背景（黒）は暗い。ここで言う「明るさ」はRGB3チャンネルの最大値で、0（黒）〜255（白）です。だから「isnetが不透明 かつ birefnetが透明 かつ 元画像が明るい」画素だけを戻せば、両方の良い所を取れます。

「明るい」のしきい値は、固定値を振って決めました（union3.py）。

しきい値残る穴戻した画素のうち明るさ100未満
552,996px7,798px
854,505px1,367px
1004,516px0px
1504,517px0px

55まで下げると、hinata/money の背景の焦げ茶（最大チャンネル67）まで戻ってしまい、髪の横に茶色の塊が出ました（目視で確認）。100なら暗い画素の巻き込みが0になり、戻る量もほとんど減りません。100を採用しました。

失敗した案: 背景の色からしきい値を自動で決める（自分の誤りを見本に自分を直す循環）

最初は「絵ごとに背景の明るさを測って、しきい値を自動で決める」案を作りました（union2.py）。これは失敗です。

birefnetが消した髪も「外周から繋がる透明領域」＝背景の見本に入ってしまいます。hinata/sleepy では金髪（明るさ254）が見本に混ざり、しきい値が266まで上がりました。明るさは最大255なので、何も戻らないしきい値です。

モデルの誤りを、モデルの誤りを含んだデータで直そうとする循環でした。固定値に戻して解決です。

6事故3: 戻した髪が真っ黒 — rembgは消した画素のRGBも潰す

alphaだけコピーしたら、髪の形をした真っ黒な塊が出た

補完の実装で、isnet側から透明度（alpha）だけをコピーしました。すると戻ったツインテールが真っ黒になりました。rembgのremove()は、透明にした画素のRGBを黒に潰します。alphaだけ戻すと「不透明な黒」になるのです。

数字でも確かめました。hinata/sleepy で戻したのは38,826画素。

recut_final_log.txt（抜粋）
(中略)
  [27/80] hinata/sleepy  23秒  モデルが消してしまったキャラを38826個の画素だけ戻しました(isnet-anime で補完)
(中略)

alphaだけの版では、この38,826画素の平均RGB差（元画像との3チャンネル合計の差）が536。ほぼ真っ黒です。RGBも元画像からコピーする修正で、不透明画素全体の平均RGB差は25.93から1.81になりました（alpha_only_rgb.py と fix_check.py。2前後は縁のアンチエイリアス処理ぶんで正常）。

本題は、なぜ見逃したかです。確認を「元画像の透明部分をマゼンタで塗った絵」でやっていました。それは元画像を見ているだけで、出来上がったPNGのRGBを一度も見ていません。確認は必ず、出来上がったPNGそのものを背景に載せて行うこと。この教訓は第9節のチェックリストに入れてあります。

7事故4: 影と黒いズボンが消えていた — そして指標には映らなかった

「暗い限り無制限に広がる」掃除が、影とズボンと線画を食っていた

最後の事故は縁の掃除（dark_assist）です。rembgが透明にした画素と外周の黒を種にして、暗い（max(RGB)<46）画素を辿って消す係ですが、旧実装は暗い限り無制限に広がっていました。

透明領域がキャラの暗い部分に接していると、黒が繋がっている先まで全部消えます。組んだ腕の下の影、黒いショートパンツ丸ごと、髪の輪郭線が食われていました。

広がりに上限（段数）を付けて、消える画素数を測りました（grow.py）。

対象2段4段8段無制限
hinata/stop18,88419,84220,64341,184
hinata/smug13,36513,94014,43638,209
kotoha/angry7,3477,8118,25130,786

2〜8段の差は小さく、無制限だけが2〜4倍に跳ねます。目視でも2〜8段なら影とズボンは残り、髪と肩の隙間の掃除はrembgの段で既に済んでいて差がありません。取り残しのフチは1〜3pxなので、上限4段にしました。

Q. 黒いショートパンツを丸ごと消していたのは、どの段でしょう?

縁の掃除です。筆者は最初、浮遊物の除去を疑って外しました。事故1の犯人だったからです。しかし消える画素を可視化すると、あちらが触っていたのは脚の先だけで、ズボン本体を食っていたのは「暗い限り無制限に広がる」縁の掃除でした。前科があるからといって今回も犯人とは限りません。

なぜ全部の検査をすり抜けたか — 指標が「明るい欠け」しか数えていなかった

この事故のいちばん怖い所は、事故1〜2で作った検査を全部すり抜けたことです。それまでの指標は「元画像が明るい（>55）のに透明」だけを数えていました。影・線画・黒い服は暗いので、消えても指標に1pxも映りません。

実際、途中の測定では「縁の掃除の欠けは全枚で0px」という中間結論を出していました。それはこの指標の産物です。欠けを数えるときは、明るい側と暗い側の両方を見ること。

813,077MiBが1,014MiBになる — onnxruntimeのメモリアリーナ

80枚一括は26枚目で死んだ。原因はモデルではなく、返さないメモリ

rembgが内部で推論に使っているエンジンがonnxruntimeです。80枚を一括で切り抜くスクリプトは、26枚目でOOM killされました（メモリを使い切ったプロセスをOSが強制終了すること。終了コード137がその印です。OSの記録では約13.3GiBを使っていました。RAM16GBの環境です）。段階を追ってRSS（プロセスが実際に使っているメモリ）を測ると、犯人はモデルの大きさではありませんでした。

  • 既定のまま。birefnetのセッション作成で643MiB → 推論1回で7,576MiB → 2回で12,198MiB（ここで頭打ち）→ isnetを足して推論すると13,077MiB。推論するたびに膨らむ（mem_default.py）。
  • アリーナを切る。両モデルを載せて推論しても1,014MiB。モデル2つ（224MB+176MB）に見合う量に収まる（mem2.py）。

onnxruntimeは既定で、推論に使ったメモリを解放せずに持ち続けます（メモリアリーナ）。公式ドキュメントに1行で書いてあります。

ONNX Runtime Python API「enable_cpu_mem_arena」の原文
Enables the memory arena on CPU. Arena may pre-allocate memory for future usage. Set this option to false if you don’t want it. Default is True.

切り方は、SessionOptionsを1つ作ってrembgに渡すだけです。

アリーナを切ってrembgのセッションを作る
import onnxruntime as ort
from rembg import new_session

opts = ort.SessionOptions()
opts.enable_cpu_mem_arena = False
session = new_session("birefnet-general-lite", sess_opts=opts)

気になるのは出力が変わらないかですが、同じ絵をアリーナ有り・無しで推論して、切り抜きのマスク(alpha)を全画素比べると差は0でした。1画素も変わりません（1枚での確認。比べたのはalphaで、速度以外の代償は見つかっていません）。

mem2.py の出力（最終行）
  アリーナ有無での alpha の差: 0

代償は速度で、birefnetの推論1回が8〜20秒から27〜30秒になりました。一括処理では、遅くなっても落ちないほうを取ります。

  • hinata/money の前髪右上に4,516pxの欠けが残っている。背景の焦げ茶と接する場所で、isnet-animeも同じ所を消すため、2モデルの合成では埋まらない（measure_cast.py。80枚中、本当の穴はこの1枚）。
  • 欠けの指標は、まだ「明るい側」だけ。暗い側の損傷を網羅的に数える指標は未確立で、今は目視に頼っている。
  • birefnet-general（非lite）がアリーナ無効で動くかは未確認。移行前のコードコメントに「推論中に約14GB使う」と記録があるが、アリーナを切った設定では測り直していない。
暗い側の指標として「囲まれた透明」を数える案が没になった理由

「キャラの内側に囲まれた透明領域＝食われた跡」と数える案を測りました（arm_gap_check.py）。結果は使い物になりませんでした。

修正で良くなったはずの絵で数値が増えます（shirase/smug 4,026px → 13,551px）。影やズボンを復元すると、その周りの正しい透明領域が「囲まれた」判定に変わるためです。減る絵と増える絵が混ざり、方向が揃わないので指標として没にしました。測った記録ごと残してあります。
