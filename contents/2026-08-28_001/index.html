Claude Code 2.1.248 に --restricted が付いた — コマンドを実行させない起動モード

8/28 5:35 公開 Claude Code を使う人 新機能 セキュリティ

Claude Code 2.1.248 に、起動オプション --restricted が増えました。付けて起動すると、コマンドやコードを走らせる道具が全部外れます。

外れるのは Bash・PowerShell・REPL などの実行系と、WebFetch（ネットからページを取ってくる道具）です。残るのはファイルの読み書きだけで、それも作業ディレクトリの中に閉じ込められます。

道具だけの話ではありません。設定ファイルの読み方も変わります。

公式ドキュメント（CLI reference の --restricted）
Start in restricted mode. Use it when an evaluation harness drives claude on a shared machine and Claude Code must not run commands or read that machine’s user and project settings. Claude Code removes the built-in tools that run commands or code, and WebFetch, unless you name them individually in --tools, not through its default preset. It also confines the built-in file tools to the working directories, loads only managed settings and --settings, and refuses bypassPermissions. Requires Claude Code v2.1.248 or later

つまり ~/.claude/settings.json のような個人の設定・プロジェクトの設定・ローカルの設定を読みません。読むのは組織が配る managed settings と、コマンドラインで渡した --settings だけです。

「他人の機械の設定を当てにしないで動かしたい」ときのためのモードだと、公式ドキュメントは書いています。共有マシンで採点用のハーネスが claude を回す場面が例に挙がっています。

実際に動くのか確かめました。この環境に入っているのは 2.1.248 です。bypassPermissions（権限の確認を全部飛ばす指定）を一緒に渡すと、起動せずに終了します。

実行した結果（幅40桁で取得）
$ claude --restricted \
    --permission-mode bypassPermissions \
    -p "say hi"
Error: bypassPermissions not supported in restricted mode
[exit 1]

終了コードは 1 でした。警告して続行するのではなく、止まります。CIやスクリプトから呼んでいるなら、この違いは効きます。

--safe-mode と何が違うのか

同じヘルプの並びに --safe-mode もありますが、狙いが逆です。--safe-mode は CLAUDE.md・スキル・プラグイン・フック・MCPサーバー・カスタムコマンドといったカスタマイズを全部止めて、壊れた設定を切り分けるためのものです。道具そのものは残ります。

--restricted は逆に、道具のほうを削って、その機械に手を出させないためのものです。片方は自分の設定を疑うとき、もう片方は他人の機械を守るときに使います。

今やること。共有マシンや採点環境で Claude Code を無人で走らせているなら、--restricted を付けられるか検討する。そうでなければ対応は不要。

/ultrareview が *.tfvars をクラウドへ上げていた — 追跡下に置いた人だけ効く

8/28 5:35 修正 クラウドセッションを使う人 セキュリティ

同じ 2.1.248 に、修正が1行あります。不具合の修正ですが、これは載せます。何が外へ出ていたかが分かると、更新するかどうかの判断が変わるからです。

CHANGELOG 2.1.248 の原文
Fixed `/ultrareview` and locally seeded cloud sessions uploading uncommitted edits to `prod.env`-style and `*.tfvars` files, or to editor swap, temp, and backup copies of credential files (e.g. `key.pem.tmp`, `id_rsa.swo`); they now stay on your machine

Q. クラウドセッションに送られるのは、次のどれ？

2つ目です。公式ドキュメントに「Untracked files are not included」と明記されています。だから今回の id_rsa.swo のような一時ファイルが上がったのは、それがうっかり追跡下に入っていた場合です。.gitignore に書いてあるファイルは元から対象外でした。

クラウドセッションは、手元のリポジトリを丸ごと束ねて向こうへ送ります。そうしないと同じ状態を再現できないからです。その束に何が入るかは、公式ドキュメントに書いてあります。

公式ドキュメント（Send local repositories without GitHub）
The bundle includes your full repository history across all branches, plus any uncommitted changes to tracked files.

Untracked files are not included; run git add on files you want the cloud session to see

ここが今回の勘所です。入るのは追跡下にあるファイルの未コミットの変更だけで、追跡していないファイルは元から入りません。

つまり key.pem.tmp や id_rsa.swo が上がったのは、それがうっかり git add されていた場合です。エディタが落ちた拍子にできた一時ファイルを、git add -A でまとめて拾ってしまう事故は起きます。

読者のスタックで直接効くのは *.tfvars です。Terraform に渡す変数を書くファイルで、AWSのキーやDBのパスワードが入ります。

自分が該当するかは、リポジトリで1行叩けば分かります。

追跡下に危ないファイルがあるか数える
$ git ls-files | grep -cE \
    '\.tfvars$|prod\.env|\.pem$|id_rsa'
0

0 なら、この不具合では何も出ていません。1以上なら、そのファイルが未コミットの変更を持ったまま /ultrareview かクラウドセッションを回した覚えがないか確かめてください。

Anthropicは「they now stay on your machine（今後は手元に留まる）」と書いていますが、いつから混ざっていたのか、上がった先で何が起きたのかは書かれていません。公表されていないので、推測しません。

今やること。上の1行を叩く。0 なら対応は不要。1以上で /ultrareview かクラウドセッションを使ったことがあるなら、2.1.248 へ上げたうえで、その鍵や資格情報を作り直すか検討する。

Composer 2.10.3 はセキュリティ修正が4件 — CIで composer install を回しているなら上げる

8/27 20:34 公開 PHPを使う人 セキュリティ Composer

PHPのパッケージ管理ツール Composer に 2.10.3 が出ました。CHANGELOGの先頭4行が、全部 Security: です。

Composer CHANGELOG（2.10.3 の先頭4行）
* Security: Validate package bin paths against path traversal using symlinks (GHSA-96h3-5x6v-m776, CVE-2026-59944)
* Security: Fixed command injection via malicious Perforce url (GHSA-rvx4-ffvw-m9q3)
* Security: Sanitize URL-embedded usernames/token in a few more places (#13044)
* Security: Fixed matching of gitlab URLs to avoid possible credential leak to the wrong domain (#12988)

上から順に、日本語にするとこうなります。

  • 1行目。パッケージの実行ファイルの置き場所を、シンボリックリンクで意図した外へ逃がせた（CVE-2026-59944）
  • 2行目。細工した Perforce のURL経由で、コマンドを実行させられた
  • 3行目。URLに埋め込まれたユーザー名やトークンが、出力にそのまま出ていた箇所が残っていた
  • 4行目。GitLabのURLの判定が甘く、別のドメインへ資格情報が漏れうる状態だった

1行目がいちばん広く効きます。パッケージの実行ファイルを置く処理は composer install の中で走るので、悪意あるパッケージを1つ入れるだけで踏みうる経路です。つまり composer install を回している場所すべてが対象になります。

2行目の Perforce は、Composer が Perforce のリポジトリを扱うときの処理です。Perforce を使っていない構成で踏むかどうかは、CHANGELOGの1行からは判断できません。公式が影響条件を書いていないので、ここは推測しません。

影響を受けるバージョンの範囲は、まだ公表されていません。Packagist のセキュリティアドバイザリDBを引くと、収録されているのは 2.10.2 のときの3件（2026年7月20日）までで、2.10.3 の4件はまだ入っていません。CVE-2026-59944 も NVD で totalResults: 0 でした。

なので「自分の版は安全か」は、いま判定できません。2.10.3 に上げるかどうかで考えるしかない段階です。

Composerを直接使っていなくても効く場所

Composer は Laravel の開発でしか使わないように見えますが、実際にはこの3か所に居ます。

(1) 開発マシン。(2) CIのジョブ（composer install --no-dev を回す）。(3) コンテナイメージのビルド段（FROM composer:2.10.x や COPY --from=composer）。(3) を忘れると、CIだけ直って本番のビルドは古いまま残ります。

今やること。手元は composer self-update。CIとDockerfileでComposerの版を固定している箇所を探して、2.10.3 以上にする。

GitHub Actions の実行履歴が10月1日から消えるようになる — 既定90日、400日ではなくなる

8/28 6:50 公開 GitHub Actionsを使う人 既定の変更 締切あり

これまで、ワークフローの実行履歴・チェック・ステータスは設定に関係なく400日以上残っていました。2026年10月1日から、artifacts と logs と同じ保持期間の設定に従うようになります。

GitHub Changelog（What's changing の直前）
Starting October 1, 2026, checks, workflow runs, and statuses will be governed by the same Actions retention setting that already controls how long artifacts and logs are kept, with a default of 90 days. Until now, checks, workflow runs, and statuses were retained for 400+ days regardless of your retention configuration.

設定を触っていないリポジトリは既定の90日になります。400日 → 90日は、4分の1以下です。

パブリックリポジトリは上限も90日です。組織やEnterpriseで上限を決めていれば、リポジトリ側はそれを超えて延ばせません。

2つ、注意点があります。

  • 遡らない。「The change is not retroactive」。設定を延ばしても、既に消えたものは戻りません
  • 課金は下がる方向。artifacts と logs は Actions のストレージ課金に乗るので、設定より長く残っていたぶんが消えると請求は減ります

効くのは「90日より前の実行を見る運用」をしている場合です。障害の事後調査や、監査で「いつ誰が何をデプロイしたか」を実行履歴で追っているなら、10月1日より前に手を打つ必要があります。

今やること。90日より前の実行履歴を見る運用があるか確かめる。無ければ対応は不要（むしろ請求が減る）。あるなら、10月1日までに保持期間を延ばすか、必要な履歴を外へ出す。

Google Play に技術品質要件が増えた — メモリとDEXが2027年2月から審査対象になる

8/27 2:00 公開 Androidアプリを出す人 提出要件の変更 締切あり

Google Play が「技術品質要件（technical quality requirements）」という新しい枠を作りました。これまでクラッシュ率やANR率で見ていた「悪い挙動のしきい値」に、メモリとコード最適化が加わります。

超えると何が起きるかも書かれています。

Android Developers Blog（Enforcement timeline の節）
Starting in February 2027, apps and games must meet their respective bad behavior thresholds for Memory usage (Anonymous RSS + Swap), Bitmap memory usage and DEX code optimization. (中略)

Apps and games that do not meet these thresholds may see reduced app visibility and publishing capabilities on Google Play.

「app visibility（ストアでの見つかりやすさ）と publishing capabilities（公開の機能）が制限されるかもしれない」。ストアに出せなくなる可能性がある、という書き方です。

なぜ WebView の話なのか。測るのは Anonymous RSS + Swap、つまりアプリが自分で確保したメモリです。WebView はページごとにレンダラのプロセスを持ち、画像はビットマップとして乗ります。Webの画面を抱えるアプリほど、ここに効いてきます。

しきい値は Play Console のヘルプ側にあります。判定は直近28日ぶんの90パーセンタイル値で、端末の搭載RAMごとに分かれます。アプリとゲームでは別の表が用意されていて、ゲームのほうが緩いです。

端末のRAMアプリ 前面ゲーム 前面

ビットマップは別枠です。前面にはしきい値がありません。背景と user-perceived services が 200 MB 超、cached が 400 MB 超で違反になります。「見えていない状態でビットマップを抱え続けるな」という設計です。

DEX（Androidのバイトコード）は、R8 などで最適化・圧縮・難読化それぞれ25%以上が要ります。対象はDEXがアプリで10 MB超、ゲームで50 MB超のものだけです。

もう1つ、ログイン機能を持つアプリへの要件が2027年4月から入ります。機種変更したとき、新しい端末で初回起動しただけでログイン済みになる（Zero-Tap Sign-In）ことが必須になります。ゲームは現時点で対象外です。

ここに今年の締切が1つ混ざっています。

Play Console ヘルプ（Exceptions and scope）
Apps integrating with Block Store, on or before September 30, 2026, to restore a user's sign-in state are considered compliant with this requirement.

2026年9月30日までに Block Store を入れていれば、2027年4月の要件を満たしたものとして扱われます。残り1か月ちょっとです。

日付の粒度に注意（「2月1日」とは書かれていない）

公式は「Starting in February 2027」「From February 2027」としか書いていません。何日から、は公表されていません。本文にも「Additional details will be provided later this year（詳細は年内に出す）」とあります。

Block Store の 2026年9月30日だけが日付まで確定しています。ここだけは動かせません。

今やること。Play Console → Android vitals の Memory を開いて、自分のアプリのP90が上の表を超えていないか見る。ログイン機能があるなら、9月30日までに Block Store を入れるかどうかを今月中に決める。

ベンチマークの点数を「カンニングしていない」と暗号で示す試みが始まった

8/27 公開 ベンチマークを読む人 評価手法

モデルのベンチマークには、ずっと不信の種がありました。そのモデルが、事前にテスト問題を見ていたかもしれないという問題です（benchmark contamination、ベンチマーク汚染）。

これまでの外部評価には、原理的な二択がありました。

やり方渡すもの困ること
評価者が問題を渡すテストのプロンプト提供元に問題が見えてしまう
提供元がモデルを渡すモデルの重み知的財産が外に出る

DeepMind は、Google Cloud の Confidential Space（中身を外から覗けない計算環境）を使って、どちらも渡さずに評価するやり方を試したと発表しました。

Google DeepMind ブログ（How double-blind evaluations work）
By using Confidential Space within Google Cloud’s Confidential Computing portfolio, we can cryptographically verify that both the external evaluation data and the proprietary model remain private to their respective owners.
