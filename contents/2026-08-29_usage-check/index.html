11日で $2,830.08。この機械はAIに毎日長時間の作業をさせているので極端な例ですが、だからこそ確かめる意味がありました。Max プランの月額は公式ページの表記で「From $100」です。もしAPIの従量課金で同じことをしていたら、11日で月額の28倍を払っていた計算になります。

表の読み方を2つ。まず日によって10倍近い波があります（最小 $60.42、最大 $578.34）。使い方が同じでも、長い作業を回した日は跳ねます。次に、8/29 の行が小さいのはその日の途中で撮ったからです。当日の行は1日の終わりまで確定しません。

表には出しませんでしたが、生の出力ではモデル別の内訳行も付きます。この機械のログには複数の系統のモデルが混ざって記録されていて、換算はモデルごとの単価で行われています。ここから、この数字の出どころと、この$を何と読むべきかを順に確かめます。

2数字の出どころは、全部自分の機械の中

会話ログに、1メッセージずつ使用量が書いてある

Claude Code は会話のログを、自分の機械の ~/.claude/projects/ にJSONL形式で残しています。プロジェクトごとにフォルダが切られます。

ログの置き場所
$ ls ~/.claude/projects/
-home-user-ai-news-video
-tmp-claude-0--home-user-ai-news-video-(中略)-scratchpad
-workspace-ai-news-dev

この中の1行1行に、そのやり取りが使ったトークン数が usage として記録されています。実物から1件抜き出すとこうです。

ログ1行の usage（整形して表示）
{
 "input_tokens": 2,
 "output_tokens": 449,
 "cache_read_input_tokens": 506458,
 "cache_creation_input_tokens": 2811
}

4つの数字の意味はこうです。input は新しく打った入力、output はAIの返答、cache_read は前に送った文脈の読み直し、cache_creation はその文脈をキャッシュに積んだ分。この1件では、新しい入力が2トークンに対して、キャッシュの読み直しが50万トークンあります。会話が長くなるほど、毎回のやり取りは「過去の読み直し」が支配的になります。この比率は第5章でもう一度出てきます。

つまり使用量の確認に、どこかのサイトにログインする必要はありません。数える材料は最初から手元に全部あります。これを読みやすくしてくれるのが、次の ccusage です。

3入れるものは1つも無い。npx ccusage で表が出る

インストールせずに1回だけ実行する

ccusage はコミュニティ製のコマンドで、いまのログを読んで表にします。npx で呼べばインストールは不要です。

日別の表（実際の出力・末尾だけ）
$ npx ccusage daily
(中略)
│ 2026     │ All        │        │       20 │    6,037 │
│ 08-29    │            │        │          │          │
(中略)
│ Total    │            │        │   22,429 │ 6,058,0… │ $2823.76 │

公式サイトはこのツールをこう説明しています。

ccusage 公式サイトより（原文）
Reads local usage logs from Claude Code, (中略) without uploading your data

ローカルのログを読む。データはアップロードしない。第2章で見た経路のとおりです。

期間の切り口も変えられます。月ごとの合計と、日付で絞る --since も実際に叩きました。

月ごとの合計（実際の出力・抜粋）
$ npx ccusage monthly
(中略)
│ 2026-08  │ All        │        │   22,441 │ 6,063,3… │ $2827.26 │
日付で絞る
$ npx ccusage daily --since 20260827   # 8/27以降だけ

細かい注意を1つ。第1章の表（合計 $2,830.08）とこの表（$2,823.76）、月次（$2,827.26）は数分ずれた別々のスナップショットで、撮っている間もこのセッション自身がログを増やしているので末尾が一致しません。使うときは1回の出力の中で読んでください。

4その$は、請求額ではない

ツール自身が「推定」と書いている

ここがこの記事でいちばん大事な1行です。ccusage の公式サイトは、この$の意味をこう書いています。

ccusage 公式サイトより（原文）
Estimate USD spend from token counts and model pricing, with cache token accounting where available

トークン数とモデルの単価から推定（Estimate）した金額です。APIの従量課金で使っている人には概算の目安になりますが、Pro や Max の定額プランなら、これは請求額ではありません。定額プランの請求は月額のままです。

では定額の人に何の役に立つのか。「APIで払ったら幾らぶん使ったか」が分かります。第1章の $2,830 は、月額 From $100 のプランで11日にそれだけの量を使った、という意味です。逆にこの換算値が月額を下回り続けるなら、APIの従量課金のほうが安い、という判断材料にもなります。

コメント欄の「課金の確認に時間がかかる」は、おそらくこの区別が曖昧なまま、請求のページと使用量の画面を行き来していた時間です。定額プランなら、月の請求は変わりません。確かめる意味があるのは請求ではなく量のほうで、量はこの1行で出ます。ここが切り分けられると、確認は速くなります。

5トークンの96%は、キャッシュの読み出しだった

ツールを使わずに、生ログを自力で数える

ccusage を信用してよいかも、自分で確かめられます。ログを直接数える16行のスクリプトを書きました（全文は _labs/count_tokens.py）。依存ライブラリはありません。

生ログの合計（種類別）
$ python3 count_tokens.py
input_tokens                             18,201
output_tokens                         9,631,726
cache_read_input_tokens           3,687,253,350
cache_creation_input_tokens         126,936,427

合計38億トークンのうち、36.9億（96%）が cache_read——前に送った文脈をキャッシュから読み直した分です。純粋な新しい入力（input_tokens）は1.8万しかありません。

なぜここまで偏るのか。Claude Code は毎回のやり取りで、それまでの会話・開いているファイル・作業の指示を丸ごと文脈として持ち直します。その持ち直しがキャッシュ読み出しです。第2章で見た「新しい入力2トークンに対して読み直し50万」が、何千回も積み重なった結果が36.9億です。

これが分かると、表の読み方が変わります。「38億トークン」という数字だけ見て慌てる必要はありません。キャッシュ読み出しは単価の安い区分で、ccusage の換算も先ほどの原文どおり「with cache token accounting」——区分ごとの単価で計算されています。

65時間の枠は blocks で見る

「上限に当たりそうか」は、この画面がいちばん近い

定額プランの使用量は5時間の枠で数えられます。ccusage blocks は、ログをこの枠に区切って見せてくれます。いまの枠がどれだけ進んだかも出ます。

いまの5時間枠（実際の出力・抜粋）
$ npx ccusage blocks
(中略)
│ 8/29/20… │ ACTIVE     │ -      │ 5,557,3… │     3.2% │    $6.17 │
│ 12:00:00 │            │ fable… │          │          │          │
│ AM (0h   │            │        │          │          │          │
│ 33m      │            │        │          │          │          │
│ elapsed, │            │        │          │          │          │
│ 4h 26m   │            │        │          │          │          │
│ remaini… │            │        │          │          │          │
(中略)
│ (assumi… │ PROJECTED  │        │ 463,260… │   263.9% │  $514.20 │

読み方はこうです。いまの枠は開始33分・残り4時間26分。もしいまのペースが5時間続いたら、推定した枠の263.9%——つまり超える見込み、と出ています。

実務での使いどころは「あと何時間で枠が明けるか」です。上限に当たって作業が止まったとき、この画面の remaining を見れば、再開できる時刻の見当が付きます。

1つ正直に書いておきます。この画面の「枠の上限」は表示に (assuming 175,534,… token limit) とあるとおり、過去の実績から仮定した値です。プランの本当の上限そのものを返すAPIは、今回の実測の範囲では見つけていません（第9章）。「当たりそうかの目安」として使うのが正しい距離感です。

7どの作業が食ったかは session で見る

1回の作業ごとに、換算$が1行ずつ出る

「今日は多かった」の次に知りたいのは何に使ったかです。ccusage session は、会話のまとまり（セッション）ごとに1行にしてくれます。

セッション別（実際の出力・抜粋）
$ npx ccusage session
(中略)
│ wf_b9cf… │ Claude     │ -      │      258 │  153,118 │   $10.90 │
│          │            │ opus-5 │          │          │          │
│ wf_d5a1… │ Claude     │ -      │      218 │  102,544 │    $8.12 │
│ wf_843b… │ Claude     │ -      │       56 │   17,366 │    $3.56 │

この機械では、動画パイプラインが並列で走らせた下請け作業（wf_ で始まる行）が1行ずつ見えました。大きい作業から順に潰すという当たり前の節約が、初めて数字でできるようになります。

8/cost は -p だと、いつも0ドル

Claude Code 本体のコマンドが見ているもの

Claude Code には /cost というコマンドがあります。これを画面を開かない実行（claude -p）で叩くと、こうなります。

-p で /cost を叩く
$ claude -p "/cost" < /dev/null
Total cost:            $0.0000
Total duration (API):  0s
Total duration (wall): 2s
Total code changes:    0 lines added, 0 lines removed

何度やっても $0.0000 です。壊れているのではありません。/cost が数えるのは「いまのセッション」だけで、-p は毎回まっさらなセッションを作って即終了するからです。「昨日どれだけ使ったか」をこれで見ることはできません。

同じ方法で /usage も叩きましたが、出力は上とまったく同じ形でした。プランの消化率のような画面は、-p からは出せませんでした。

-p で /usage を叩く
$ claude -p "/usage" < /dev/null
Total cost:            $0.0000
Total duration (API):  0s
Total duration (wall): 1s
Total code changes:    0 lines added, 0 lines removed

では /cost はいつ使うものか。対話で長い作業をしている最中に、いまの作業がどれだけ食っているかをその場で見るためのものです。作業単位の振り返りなら第7章の session、日をまたぐ集計なら daily。守備範囲が違うだけで、どれも壊れてはいません。

おまけの実測を1つ。コマンドの末尾に < /dev/null を付けているのは飾りではありません。付けずに叩くと、3秒待ってから警告が出ます。

付けないとこうなる
$ claude -p "/cost"
Warning: no stdin data received in 3s, proceeding without it. If piping from a slow command, redirect stdin explicitly: < /dev/null to skip, or wait longer.

結果は同じですが毎回3秒待たされます。スクリプトに入れるなら付けておくものです。

9見たいものごとに、道具が違う

3つの問いに、3つの答え

ここまでを整理すると、「使用量を確かめたい」は実は3つの別の問いでした。

見たいもの道具今回の実測
日ごと・月ごとの量と換算$npx ccusage daily / monthly✓ 動いた（第1・3章）
いまの5時間枠の消化と見込みnpx ccusage blocks✓ 動いた（第6章）
どの作業が食ったかnpx ccusage session✓ 動いた（第7章）
プラン上限に対する公式の%対話画面の /usage─ 未確認（下の注）
今回試していないこと
  • 対話画面の /usage は開いていません。この実測は無人実行の環境で取ったので、対話セッションの画面そのものを出せませんでした。第7章のとおり -p 経由では代わりになりません。
  • APIの従量課金アカウントでの突き合わせはしていません。換算値と実請求の差は、このログでは検証できません。
  • ccusage の他エージェント対応（Codex 等）は試していません。今回は Claude Code のログだけです。

10毎朝の1行にする

覚えて帰るのは3つ

コメント欄の質問は「課金の確認にいつも時間がかかる」でした。今回の実測での答えはこうなります。

  • 朝に npx ccusage daily を1回。昨日の行だけ見る
  • 使いすぎた日は blocks で、どの5時間に集中していたかを見る
  • $の桁に驚いたら、第4章を思い出す。それは請求額ではなく換算値

最後に、確認そのものに時間を使いすぎないことです。数字は毎日見ても、打ち手は「大きい作業を減らす」「枠が明けるまで待つ」の2つしかありません。朝の1行で足りる理由は、打ち手が少ないからです。

この記事のコマンドと出力は、すべて _labs/2026-08-29_usage-check/ に再現一式ごと置いてあります。bash run_all.sh で同じものが出ます（数字はあなたのログの中身になります）。
