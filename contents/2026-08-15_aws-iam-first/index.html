AWSのアクセス制御の地図 — IAMのユーザー・ロール・ポリシーは何が違うのか

「IAMというものがあるらしい」から読み始められるように書きました。根拠はAWS公式ドキュメントの原文と、認証情報の要らないローカル検証だけです。AWSアカウントには何も作っていません（有効な認証情報が無く、実行できないため）。
⏱ 約14分 IAMを触ったことがない人向け 公式原文を隣に貼る

⭐ 3行で言うと

サーバーやファイル置き場をインターネット越しに借りられるサービス群、それが AWS（Amazon Web Services）です。使い始めると、まず IAM という壁にぶつかります。結論はここで割ります。覚えることは「誰か」と「何をしてよいか」の2つだけです。

  1. AWS自身が「IAMユーザーは基本的に使うな」と公式ドキュメントに書いている 入口で作らされるアレが非推奨です。代わりに使うのがロールで、この記事の主役はそちらです。

1IAMは何を守っているのか

最初のログインは「全部できてしまう」状態。そこから権限を削る仕組みがIAM

AWSアカウントとは、AWSを使うための契約単位です。作ったサーバーもファイルも請求も、全部この単位でまとまります。

アカウントを作ると、まずルートユーザーという持ち主用のログインが1つできます。これは何でもできてしまいます。公式ドキュメントの原文がこれです。

AWS「What is IAM?」IAM User Guide — 原文
When you create an AWS account, you begin with
one sign-in identity called the AWS account
root user that has complete access to all AWS
services and resources. We strongly recommend
that you don't use the root user for everyday
tasks.

（AWSアカウントを作ると、すべてのAWSサービスと
　リソースに完全なアクセス権を持つ「ルートユーザー」
　という1つのサインインIDから始まる。日常作業に
　ルートユーザーを使わないことを強く推奨する）

「完全なアクセス権」は、請求情報も、アカウントの解約も、他人の権限の書き換えも含みます。だから日常作業では別の入口を作って、そちらの権限を絞る。それをやる仕組みが IAM（Identity and Access Management）です。

同ページ — IAMの定義
You use IAM to control who is authenticated
(signed in) and authorized (has permissions)
to use resources.

（IAMは、誰が認証され(サインインし)、誰が認可
　される(権限を持つ)かを制御するために使う）
  • 認証（Authentication）。「あなたは本当にその人か」を確かめること。ログインの部分です。
  • 認可（Authorization）。「その人がこの操作をしてよいか」を判定すること。ログインした後の部分です。
  • IAMが扱うのはこの2つだけ。逆に言うと、IAMの話で迷ったら「今どっちの話をしているか」を確認すれば大抵ほどけます。

お金の心配は先に消しておきます。公式ドキュメントに「追加料金なし」と明記されています。

同ページ — 料金
AWS Identity and Access Management (IAM), AWS
IAM Identity Center and AWS Security Token
Service (AWS STS) are features of your AWS
account offered at no additional charge.

（IAM、IAM Identity Center、AWS STS は
　追加料金なしで提供されるアカウントの機能）
知っておくと後で助かる「IAMはすぐには反映されない」

同じページに、初見では意味が分からないが後で必ず刺さる一文があります。

原文
IAM, like many other AWS services, is
eventually consistent.

（IAMは他の多くのAWSサービスと同様、
　結果整合性である）

結果整合性とは、変更がすぐ全体に反映されるとは限らず、少し遅れて揃う性質のことです。つまり権限を付けた直後に試すと、まだ拒否されることがあります。「設定は合っているのに動かない」と思ったら、少し待ってもう一度試してください。

2ユーザーとロールの決定的な差は2つだけ

AWSは「IAMユーザーを使うな」と公式に書いている

IAMユーザーとは、AWSアカウントの中に作る「人やプログラム1つ分のログイン情報」です。名前と認証情報を持ちます。

AWS「IAM users」IAM User Guide — 原文
An IAM user is an entity that you create in
your AWS account. The IAM user represents the
human user or workload who uses the IAM user
to interact with AWS resources. An IAM user
consists of a name and credentials.

（IAMユーザーはAWSアカウント内に作るエンティティ。
　人やワークロードを表し、名前と認証情報から成る）

エンティティとは、IAMで「操作する主体になれるもの」（ユーザーやロール）のこと。ワークロードとは、人ではない利用者 ―― アプリやバッチ処理のことです。

ここまでは普通です。同じページの冒頭に、こう書いてあります。

同ページ 冒頭のImportant枠 — 原文
IAM best practices recommend that you require
human users to use federation with an identity
provider to access AWS using temporary
credentials instead of using IAM users with
long-term credentials. We recommend that you
only use IAM users for specific use cases not
supported by federated users.

（人間のユーザーには、長期の認証情報を持つIAM
　ユーザーではなく、IDプロバイダとのフェデレーション
　＋一時的な認証情報を使わせることを推奨する。
　IAMユーザーは、フェデレーションで対応できない
　特定のユースケースに限って使うことを推奨する）
  • 長期の認証情報とは。パスワードやアクセスキー（プログラムからAWSを操作するためのIDとパスワードに相当する長い文字列）のように、こちらで消すまでずっと使えるもののことです。
  • フェデレーションとは。社内のログイン基盤などAWSの外にあるIDでAWSに入れるようにする仕組み。入るときにロールを借りる形になります。
  • だからIAMユーザーは「最後の手段」。入門記事で最初に作らされることが多いですが、AWS自身の推奨はそうではありません。

ロールは「必要な人が一時的に借りる権限のセット」

ではロールとは何か。定義の原文がそのまま答えになっています。

AWS「IAM roles」IAM User Guide — 原文
However, instead of being uniquely associated
with one person, a role is intended to be
assumable by anyone who needs it. Also, a role
does not have standard long-term credentials
such as a password or access keys associated
with it. Instead, when you assume a role, it
provides you with temporary security
credentials for your role session.

（ロールは1人に固有に結びつくのではなく、必要と
　する者が誰でも引き受けられることを意図している。
　またロールはパスワードやアクセスキーのような
　標準的な長期の認証情報を持たない。代わりに、
　引き受けたときにそのセッション用の一時的な
　セキュリティ認証情報が提供される）
  • 差その1: 持ち主が固定されない。ユーザーは1人に紐づく。ロールは必要な人・サービスが借ります。
  • 差その2: 長期の認証情報が無い。ロールにはパスワードもアクセスキーも存在しません。漏れる鍵がそもそも無いのが最大の利点です。

「引き受ける（assume）」の実体は、AWS STS（Security Token Service。一時的な認証情報を発行する係）への AssumeRole というAPI呼び出しです。APIとは、プログラムから機能を呼び出すための窓口のこと。AWSの操作は、画面から押したボタンも含めて全部この窓口を通ります。返ってくるものも公式に書かれています。

AWS STS API Reference「AssumeRole」— 原文
Returns a set of temporary security
credentials that you can use to access AWS
resources. These temporary credentials consist
of an access key ID, a secret access key, and
a security token.

（AWSリソースにアクセスするための一時的な
　セキュリティ認証情報のセットを返す。この一時
　認証情報は、アクセスキーID・シークレット
　アクセスキー・セキュリティトークンから成る）

寿命も明記されています。既定1時間、最短15分、ロール側の上限は1〜12時間です。

同ページ DurationSeconds — 原文
The value specified can range from 900 seconds
(15 minutes) up to the maximum session
duration set for the role. The maximum session
duration setting can have a value from 1 hour
to 12 hours. ... By default, the value is set
to 3600 seconds.

この差は、AWS CLI（AWSをコマンドで操作する公式ツール）の入力欄を見るだけでも出ます。--generate-cli-skeleton は通信せずに入力JSONの雛形だけを表示するオプションです。ここに載せたのは、この環境で実際に打った出力です。

実行結果（aws-cli/1.46.0・AWSへは通信していない）
$ aws iam create-access-key \
    --generate-cli-skeleton
{
    "UserName": ""
}

$ aws sts assume-role \
    --generate-cli-skeleton \
    | grep -E "RoleArn|Session|Duration"
    "RoleArn": "",
    "RoleSessionName": "",
    "DurationSeconds": 0,
  • アクセスキーの発行に、期限を指定する欄がありません。入力は UserName だけ。作ったら消すまで生き続けます。
  • ロールを借りる側には DurationSeconds があります。時間が来たら勝手に死にます。

もうひとつ、初学者が引っかかる落とし穴があります。ロールを引き受けている間、元の自分の権限は使えません。

AWS「IAM roles」— 原文
A user who assumes a role temporarily gives up
his or her own permissions and instead takes
on the permissions of the role.

（ロールを引き受けたユーザーは、自分の権限を
　一時的に手放し、代わりにロールの権限を得る）

Q. IAMユーザーとIAMロールの、いちばん大きな違いはどれ?

正解は真ん中。権限の強さに差はありません。どちらも貼り付けたポリシー次第で、管理者権限にもできます。「ロール＝サービス用」も誤りで、人間がフェデレーションでAWSに入るときもロールを引き受けます。差は認証情報の持ち方だけ ―― ロールは長期の鍵を持たず（原文: a role does not have standard long-term credentials）、引き受けた瞬間に期限付きの3点セットが発行されます。

グループはログインできない。権限をまとめる箱にすぎない

IAMユーザーグループは、ユーザーをまとめる箱です。箱にポリシーを付けると、中の全員に効きます。ただしグループ自体はログインできず、ポリシーの主体としても書けません。

AWS「IAM user groups」— 原文
You cannot identify a user group as a
Principal in a policy (such as a
resource-based policy) because groups relate
to permissions, not authentication, and
principals are authenticated IAM entities.

（グループは認証ではなく権限に関わるものであり、
　プリンシパルは認証されたIAMエンティティなので、
　ポリシーのPrincipalにグループは書けない）
  • プリンシパル（Principal）とは。AWSに対して操作を行える「主体」。ルートユーザー・IAMユーザー・ロールなどが該当します。
  • グループは入れ子にできません。中に入れられるのはユーザーだけで、グループの中にグループは置けません（同ページ: User groups can't be nested）。
  • 1人が複数のグループに属せます。権限は足し算になります。

3ポリシーはJSON。欄は5つ覚えれば読める

いちばん短いポリシーは4行。ここから積み上げれば全部読める

ポリシーとは、「どの操作を、どのリソースに、許可するか／拒否するか」を書いたJSONの文書です。これを人やロールやリソースに貼り付けて、初めて権限が生まれます。

この先ずっとJSONが出てくるので、先に2つだけ言葉を置きます。

  • JSONとは。データを書き表す形式の1つです。記号の意味は5つだけ ―― { } は1つのまとまり、[ ] は並び（複数入れられる）、: は「名前とその値」の区切り、, は項目どうしの区切り、" " は文字列。この5つが分かれば、以降のJSONは全部読めます。
  • Amazon S3とは。ファイルを置いておくAWSのサービスです。入れ物をバケット、その中の1ファイルをオブジェクトと呼びます。この記事の例はほとんどS3です（s3: で始まる操作名がそれです）。

公式ドキュメントに載っている最小の例がこれです。

AWS「IAM JSON policy elements: Version」掲載のサンプル（原文のまま・行末の空白のみ除去）
{
  "Version":"2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListAllMyBuckets",
      "Resource": "*"
    }
  ]
}
欄意味必須か
Versionポリシー言語の文法バージョン実質いつも書く
Statementルール1件分。複数書ける必須
EffectAllow か Deny必須
Action操作名（s3:GetObject など）必須
Resource対象をARNで指定許可ポリシーでは必須
Principal誰が、を指定する主体リソース側のポリシーで必須
Condition追加の条件任意
Sidルールに付ける名札任意・動作に影響なし

ARN（Amazon Resource Name）は、AWS上のモノを世界で1つに特定する住所のような文字列です。arn:aws:s3:::my-bucket/* のような形をしています。

"Version": "2012-10-17" は日付ではない

最初に必ず「これ何の日付？」となる欄です。更新日ではなく、ポリシー言語の文法バージョンです。

AWS「IAM JSON policy elements: Version」— 原文
The Version policy element specifies the
language syntax rules that are to be used to
process a policy.
...
2012-10-17. This is the current version of the
policy language, and you should always include
a Version element and set it to 2012-10-17.

（Version要素は、そのポリシーを処理するときの
　言語構文規則を指定する。2012-10-17 が現行版で、
　常にこの値を書くべきである）
  • 選べる値は2つだけ。2012-10-17 と、旧版の 2008-10-17。旧版は新規にも更新時にも使うなと公式が書いています。
  • つまり実質1択。考えずに 2012-10-17 と書いてください。
  • IAMの「ポリシーバージョン」とは別物。同ページの冒頭で明確に区別されています（This Version JSON policy element is different from a policy version.）。
写経のときに引っかかる細かい規則（3つ）
欄の並び順に意味は無い
公式の要素リファレンスに The order of the elements doesn't matter—for example, the Resource element can come before the Action element. とあります。Action より先に Resource を書いても同じです。
Action と NotAction は同居できない
同ページ: you cannot use both Action and NotAction in the same policy statement. 同様に Principal/NotPrincipal、Resource/NotResource も排他です。
Statementが複数あるときは論理OR
上から順に上書きされるのではありません。公式は If a policy includes multiple statements, AWS applies a logical OR across the statements when evaluating them. と書いています。どれか1つが許可すれば許可です（ただしDenyは別枠。5章）。

Effect の Allow は大文字始まり。小文字だと落ちます

公式ドキュメントに一行で書かれています。The Effect value is case sensitive.（Effectの値は大文字小文字を区別する）

これは実際に落とせます。Terraform（インフラの構成をコードで書く道具）で effect = "allow" と小文字にして terraform validate（書式と型の検査）を通すと、こうなりました。

実行結果（Terraform v1.14.3 / provider aws 6.60.0）

4許可ポリシーと信頼ポリシーは見た目で分かる

ロールに関わるポリシーは2種類。「何ができるか」と「誰が借りてよいか」

ここがIAMで最初に詰まる場所です。公式ドキュメントの委任（delegation）の説明が、そのまま答えです。

AWS「IAM roles」Delegation — 原文
To delegate permission to access a resource,
you create an IAM role in the trusting account
that has two policies attached. The
permissions policy grants the user of the role
the needed permissions to carry out the
intended tasks on the resource. The trust
policy specifies which trusted account members
are allowed to assume the role.

（アクセスを委任するには、2枚のポリシーを付けた
　IAMロールを作る。許可ポリシーは、ロールの利用者に
　必要な操作の権限を与える。信頼ポリシーは、
　どの相手がそのロールを引き受けてよいかを定める）
  • 許可ポリシー（アイデンティティベースポリシー）。そのロールで何ができるかを書きます。
  • 信頼ポリシー（trust policy）。そのロールを誰が借りてよいかだけを書きます。ロールに必ず1枚付きます。
  • 必須なのは信頼ポリシーだけ。上の原文は「委任するときは2枚付けたロールを作る」という話です。許可ポリシーが0枚のロールも作れます（何もできないロールになるだけ）。「必ず2枚」ではありません。

信頼ポリシーの正体も公式に書かれています。これは「ロールというモノに貼られたリソースベースポリシー」です。S3バケットポリシーと同じ仲間です。

AWS「Policies and permissions in IAM」— 原文
The most common examples of resource-based
policies are Amazon S3 bucket policies and IAM
role trust policies.

（リソースベースポリシーの最も一般的な例は、
　S3バケットポリシーとIAMロールの信頼ポリシー）

ではJSONを2枚並べます。どちらもAWS公式ドキュメントに載っている実例をそのまま貼ります（{{...}} はAWS側の穴埋め表記です）。

信頼ポリシー（ECSタスクロール用・AWS公式の例）
{
   "Version":"2012-10-17",
   "Statement":[
      {
         "Effect":"Allow",
         "Principal":{
            "Service":[
               "ecs-tasks.amazonaws.com"
            ]
         },
         "Action":"sts:AssumeRole",
         "Condition":{
            "ArnLike":{
            "aws:SourceArn":"arn:aws:ecs:{{us-west-2}}:{{111122223333}}:*"
            },
            "StringEquals":{
               "aws:SourceAccount":"{{111122223333}}"
            }
         }
      }
   ]
}
許可ポリシー（S3を読むだけ・AWS公式の例）
{
   "Version":"2012-10-17",
   "Statement":[
      {
         "Effect":"Allow",
         "Action":[
            "s3:GetObject"
         ],
         "Resource":[
            "arn:aws:s3:::{{my-task-secrets-bucket}}/*"
         ]
      }
   ]
}

見分け方は1行で済みます。

信頼ポリシー許可ポリシー
Principalある（必須）書けない
Resource無いある（必須）
Actionほぼ sts:AssumeRoleやりたい操作
種類リソースベースアイデンティティベース
答えている問い誰が借りてよいか何ができるか

Principal を許可ポリシーに書けないのは、主体は「貼り付けた相手」そのものだからです。公式の説明がそのままです。

AWS「Policies and permissions in IAM」Principal — 原文
If you are creating an IAM permissions policy
to attach to a user or role, you cannot
include this element. The principal is implied
as that user or role.

（ユーザーやロールに貼る許可ポリシーを作る場合、
　この要素は書けない。プリンシパルはその
　ユーザーやロール自身であると暗黙に決まる）

サービスプリンシパルとは、人ではなくAWSサービス自身を表すプリンシパルです。ecs-tasks.amazonaws.com のようにドメイン風の名前で書きます。上の信頼ポリシーは「ECSのタスクなら、このロールを借りてよい」と言っています。

先に危険なほうを言っておきます。信頼ポリシーに "Principal": {"AWS": "*"} と書くと、そのロールは全世界の誰でも借りられます。IAMは止めてくれません。根拠は次の折りたたみに入れました。

信頼ポリシーの Condition は飾りではない／Principal に * は書けてしまう

上の例に付いていた aws:SourceArn と aws:SourceAccount の意味です。公式ドキュメントの Important 枠がこう書いています。

AWS「Amazon ECS task IAM role」— 原文
When creating your task IAM role, we
recommend that you use the
aws:SourceAccount or aws:SourceArn
condition keys in the trust relationship
policy associated with the role to scope
the permissions further to prevent the
confused deputy security issue.

混乱した代理問題（confused deputy）とは、権限を持つサービスが第三者にだまされて、代わりに悪い操作をしてしまう問題です。「ECSなら誰でも」ではなく「私のアカウントのECSだけ」に絞るのがこのConditionの役目です。

ここで絶対に誤解してはいけないことを1つ足します。信頼ポリシーの Principal に書くARNは、その一部をワイルドカードにできません（AWS「IAM roles」: When you create a trust policy, you cannot specify a wildcard (*) as part of an ARN in the principal element.）。

しかし "Principal": {"AWS": "*"} は書けてしまいます。これは「ARNの一部」ではなく丸ごとワイルドカードなので、上の制限に当たりません。書いた瞬間に、そのロールは全世界の誰でも借りられる状態になります。AWSの警告がこれです。

wildcard (*) in the Principal element of a
resource-based policy with an Allow effect
unless you intend to grant public or anonymous
access. ... This is especially true for IAM
role trust policies, because they allow other
principals to become a principal in your
account.

（Allow効果のリソースベースポリシーの
　Principal に * を使うことは、公開／匿名
　アクセスを与える意図が無い限り、強く
　非推奨。とくにIAMロールの信頼ポリシーで
　そうである。他のプリンシパルを自アカウント

同じページには Do not leave your role accessible to everyone! という一文もあります。「IAMが防いでくれる」ではありません。防ぐのは書く人です。

ロールを作るときに信頼ポリシーを忘れることはできません。AWS CLIで試すと、AWSに接続する前に止められます。

実行結果（引数不足のクライアント側エラー・通信なし・末尾1行を38桁で折り返し）

5判定順 — 書かなければ全部拒否、Denyは必ず勝つ

公式が3行にまとめてくれている

user, which has full access.
Requests must be explicitly allowed by a
policy or set of policies following the
evaluation logic below to be allowed.
An explicit deny overrides an explicit allow.

（既定ではすべてのリクエストが暗黙的に拒否される
　― フルアクセスを持つルートユーザーを除く。
　許可されるにはポリシーで明示的に許可される
　必要がある。明示的な拒否は明示的な許可に勝つ）
  • 暗黙的な拒否（implicit deny）。何も書かなければ全部拒否。これが初期状態です。
  • 明示的な拒否（explicit deny）。ポリシーに Deny と書いた拒否。どこか1枚にでもあれば、他が何枚許可していても拒否です。
  • だから Deny は慎重に。あとから正当な許可を足しても、その Deny がある限り通りません。

この順序を目で見るために、公式の記述をそのまま書き写した114行のPythonのおもちゃを作って動かしました。AWSの本物のエンジンではありません（そこは後述します）。出力に出てくる MFA は多要素認証のことで、パスワードに加えてスマホのコードなど2つ目の確認を求める仕組みです（8章で戻ってきます）。

Q. ユーザーに管理者権限のポリシーを付けた。同時に、別のポリシーで s3:DeleteObject を Deny にした。結果は?

正解は3つめ。ポリシーに強弱も順番もありません。「管理者だから通る」も「あとから付けたほうが上書きする」も誤りです。判定は「明示的なDenyが1つでもあるか」を先に見て、あれば即座に拒否（原文: An explicit deny overrides an explicit allow.）。この性質は、事故を止める安全装置として使えます ―― 「絶対に消させたくない」なら、許可を削るのではなくDenyを1枚置くほうが確実です。

和集合と積集合が混ざるのが、IAMの分かりにくさの正体

ポリシーが複数種類あるとき、足し算になるものと掛け算になるものがあります。公式の Policy evaluation logic に両方書かれています。

組み合わせ結果
アイデンティティベース ＋ リソースベース（同一アカウント）和集合（union）。どちらかが許可すれば許可
アイデンティティベース ＋ 権限境界積集合（intersection）。両方が許可して初めて許可
どれか1枚にでも明示的なDeny常に拒否

権限境界（permissions boundary）は、「このユーザー／ロールは、どんなポリシーを貼られてもここまで」という上限を決める上級機能です。権限を与える機能ではありません。上の実行結果の「境界:dynamodbのみ」で Deny になっているのがこれです。

同様に、AWS Organizations の SCP（Service Control Policy。アカウント全体に上限をかける仕組み）も積集合です。「自分のポリシーは正しいのに拒否される」ときは、上限側を疑ってください。

このおもちゃ実装で何をやっていないか（正直に）

  • AWSのポリシーシミュレータは実行していません。iam simulate-principal-policy はAWSへのAPI呼び出しなので、この環境では実行できません。
  • 意図どおり動くことだけは固定してあります。pytest 10件が通っています（10 passed in 0.01s）。

使う人が別人だから。片方はAWS、片方はあなたのアプリ

  • AWS Fargate。サーバー（EC2インスタンス）を自分で用意せずにコンテナを動かせる方式。公式定義は run containers without having to manage servers or clusters of Amazon EC2 instances。

正解は真ん中。S3を読むのはコンテナの中のアプリのコードなので、タスクロールです。実行ロールに足してもアプリからは1バイトも使えません ―― 公式が they aren't directly accessible by the containers in the task と明記しています。1つめを選んだ人は、たぶん「実行」という語から「アプリの実行に使う権限」を連想したはずです。ここでの「実行」はタスクを起動する側を指します。

実行ロールに付けるマネージドポリシーの中身は、6行しかない

AWSマネージドポリシーとは、AWSがあらかじめ用意して管理してくれるポリシーです。実行ロールに付ける定番がこれです。中身を見れば役割が分かります。

  • ECRのプライベートリポジトリからイメージを取得する。

7最小権限を具体的に書く
