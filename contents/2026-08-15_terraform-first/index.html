1IaCが解決するのは「1回目」ではなく「2回目」

管理画面でポチポチ作るほうが、1回目は速い

AWSの管理画面でサーバーを1台作るのに、Terraformは要りません。画面を開いてボタンを押すほうが速いです。

問題は2回目です。「本番と同じものを検証環境にもう1組」と言われた瞬間に詰みます。何をどう押したか、誰も正確には覚えていません。

  • IaC（Infrastructure as Code）とは。サーバーやネットワークの構成を、画面をクリックして作るのではなくテキストファイルに書き、そのファイルから作る考え方です。
  • プロビジョニングとは。サーバーやファイルなどの実体を、実際に用意することです。Terraformがやるのはこれです。
  • Terraform とは。設定ファイルに書いた内容を、クラウドのAPIを叩いて実際に作る・変える・消すツールです。
  • AWS / クラウド / API とは。クラウドは「インターネット越しにサーバーを借りる仕組み」、AWS（Amazon Web Services）はその代表格でAmazonが提供するものです。APIは「人が画面を操作する代わりに、プログラムが命令を送るための窓口」です。Terraform は画面ではなくこの窓口を使います。

ここで大事なのは、Terraformに書くのが手順書ではないことです。公式の説明がそのまま答えになっています。

HashiCorp「What is Terraform?」— 原文
Terraform configuration files are
declarative, meaning that they describe
the end state of your infrastructure.
You do not need to write step-by-step
instructions to create resources
because Terraform handles the
underlying logic.

（Terraform の設定ファイルは宣言的で、
　インフラの最終状態を記述する。

　引き受けるから）
  • 宣言的（declarative）とは。「こういう手順で作れ」ではなく「最終的にこうなっていてほしい」を書く書き方です。今の状態との差分は Terraform が計算します。
  • だから同じファイルを何度実行しても増えません。「3台ほしい」と書いてあれば、3台あるときは何もしません。2台なら1台足します。

2.tf ファイルには「ブロック」と「引数」しかない

最初の1ファイル。これを丸ごと読みます

この記事の実測に使った設定ファイルの全文です。ECSクラスター（AWSでコンテナを動かすための入れ物）を1つ作る、という内容です。

main.tf — 実際に動かしたファイルの全文
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "ap-northeast-1"

  # 認証情報なしで plan まで進めるためのダミー。
  # 本番の設定には絶対に書かない。
  access_key                  = "dummy"
  secret_key                  = "dummy"
  skip_credentials_validation = true
  skip_requesting_account_id  = true
  skip_metadata_api_check     = true
  skip_region_validation      = true
}

resource "aws_ecs_cluster" "app" {
  name = "tf-hello"

  tags = {
    Env = "sandbox"
  }
}

初見だと記号だらけに見えますが、登場する文法は2種類だけです。Terraform の設定は HCL（HashiCorp Configuration Language）という書式で、その仕様書にはこう書いてあります。

HCL Native Syntax Specification — 原文
The structural language consists of
syntax representing the following
constructs:

- Attributes, which assign a value to a
  specified name.
- Blocks, which create a child body
  annotated by a type and optional
  labels.
- Body Content, which consists of a
  collection of attributes and blocks.

（構造言語は次を表す構文からなる。
　属性: 名前に値を割り当てる。
　ブロック: 型と任意のラベルで注釈された
　　子ボディを作る。
　ボディ内容: 属性とブロックの集合）
  • 引数（argument）とは。name = "tf-hello" のような 名前 = 値 の1行です。HCLの仕様では attribute（属性）と呼ばれます。Terraform公式も「HCLのドキュメントでは argument ではなく attribute という語を使うのが普通」と注記しています。同じものです。
  • ブロック（block）とは。resource "aws_ecs_cluster" "app" { … } のように、波かっこで囲まれた設定のかたまりです。
  • ラベル（label）とは。ブロック名の後ろに続く引用符付きの文字列です。resource なら1つ目が型、2つ目が自分で付ける名前です。

この3語で、さっきのファイルは全部読めます。

書いてあるもの種類意味
terraform { } ブロック（ラベル無し） Terraform 自体への設定。どのプロバイダが要るかをここで宣言する
required_providers { } ブロック（入れ子） 必要なプロバイダの一覧。terraform ブロックの中にしか置けない
source = "hashicorp/aws" 引数 ソースアドレス。プロバイダの入手元（Terraform Registry 上の場所）
version = "~> 6.0" 引数 バージョン制約。使ってよい範囲の指定であって、具体的な版は init が決める
provider "aws" { } ブロック（ラベル1つ） 相手先ごとの設定。リージョンや認証をここに書く
resource "aws_ecs_cluster" "app" { } ブロック（ラベル2つ） 作る対象そのもの。1ブロック＝1つの実体
  • プロバイダ（provider）とは。AWS や Docker など、相手先ごとの通信を担当するプラグインです。Terraform 本体には入っていません。別にダウンロードされます。ここが3章の話に繋がります。
  • リソース（resource）とは。Terraform が作る対象そのものです。公式は「Terraform言語の主目的はリソースを宣言すること。他の言語機能はすべて、リソース定義を柔軟で便利にするためだけに存在する」と書いています。
  • 引数の一覧は Terraform ではなくプロバイダのドキュメントを見ます。公式リファレンスにも「個々のリソースがどの引数をサポートするかはプロバイダが決める」とあります。aws_ecs_cluster に何が書けるかは AWSプロバイダのページで調べます。

Q. resource "aws_ecs_cluster" "app" の2つ目の "app" は何?

正解。AWS側に付く名前は name = "tf-hello" のほうです。"app" はTerraformの中だけの呼び名で、この2つは完全に別物です。この「型.名前」の組（aws_ecs_cluster.app）をリソースアドレスと呼び、6章で見る plan の出力にもこの形で出てきます。混同すると、plan の # aws_ecs_cluster.app will be created を見て「app という名前のクラスターができる」と誤読します。

ファイル名と、書く順番について（先に知らないと必ずハマります）
main.tf という名前に意味はない
公式は「Terraform言語のコードは .tf 拡張子のプレーンテキストファイルに保存される」とだけ定めています。拡張子が .tf なら名前は何でも構いません。慣習で main.tf / variables.tf / outputs.tf に分ける人が多いだけです。
ファイルを分けても分けなくても動作は同じ
公式の原文はこうです。Terraform evaluates all of the configuration files in a module, effectively treating the entire module as a single document.（モジュール内の全設定ファイルを評価し、実質的にモジュール全体を1つの文書として扱う）。分けるのは読み手の都合であって、動作には影響しません。
書いた順に実行されるわけではない
これが最大の誤解ポイントです。公式は The ordering of blocks and the files they are organized into are generally not significant（ブロックの順番も、どのファイルにあるかも、一般に意味を持たない）と書いています。実行順は依存関係から自動で決まります。
サブディレクトリは読まれない
モジュールとは、1つのディレクトリにある .tf ファイル群のことです。公式は「モジュールはそのディレクトリの最上位の設定ファイルだけで構成され、入れ子のディレクトリは完全に別のモジュールとして扱われる」と明記しています。terraform コマンドを実行したディレクトリがルートモジュールで、読まれるのはそこの .tf だけです。

Q. 本番のデータベースの plan に -/+ と # forces replacement が出た。何が起きる?

正解。-/+ は「その場で直せない変更」を意味します。「設定を1文字変えただけ」でも、変えた項目によっては作り直しになります。~（その場で更新）と見た目が似ているので、慌てて読むと取り違えます。本番で -/+ を見たら、まず # forces replacement が付いている行を探してください。そこが原因です。その項目の変更を諦めるか、別の手順（新しく作ってから切り替える）を検討することになります。
