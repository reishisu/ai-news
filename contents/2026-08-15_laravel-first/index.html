1入れるものは4つ。公式のインストール手順の冒頭に書いてある

迷う余地はありません。公式が名指ししています

「何をインストールすればいいのか」は、Laravel公式のインストール手順に書いてあります。ページの1文目ではなく、「Installing PHP and the Laravel Installer」節の冒頭です。訳ではなく原文を貼ります。

Laravel 13.x「Installation」— Installing PHP and the Laravel Installer 節の冒頭・原文
Before creating your first Laravel application,
make sure that your local machine has PHP,
Composer, and the Laravel installer installed.
In addition, you should install either Node and
NPM or Bun so that you can compile your
application's frontend assets.

（最初のLaravelアプリを作る前に、手元のマシンに
　PHP・Composer・Laravelインストーラが入っている
　ことを確認してください。加えて、フロントエンドの
　アセットをコンパイルするために Node と NPM か
　Bun のどちらかを入れる必要があります）
  • PHP。Laravel が書かれている言語そのもの。これが無いと1行も動きません。
  • Composer。PHP用の「必要な部品を集めてくる係」。3章で詳しくやります。
  • Laravelインストーラ。laravel new というコマンドを追加するだけの小さな道具。新しいプロジェクト一式を作ってくれます。
  • Node と NPM、または Bun。CSSとJavaScriptをブラウザ用に変換するために使います。原文は either Node and NPM or Bun なのでどちらか片方でよいのですが、情報量が多いのはNode側です。PHPのアプリなのにJavaScript側の道具が要るのは、画面まわりだけそちらの仕組みに乗っているためです。

この4つを入れたあと、公式が案内している最短手順はこれだけです。ターミナル（macOSなら「ターミナル」アプリ、WindowsならPowerShell）を開いて、プロジェクトを置きたいフォルダで打ちます。

Laravel 13.x「Installation」に載っている手順
laravel new example-app

cd example-app
npm install && npm run build
composer run dev
  • laravel new example-app。example-app という名前のフォルダが作られ、その中に一式が入ります。名前は好きに変えて構いません。
  • cd example-app。「作られたフォルダの中に移動する」という意味。以降のコマンドは全部この中で打ちます。
  • npm install && npm run build。CSSとJavaScriptを組み立てます。
  • composer run dev。開発用のサーバーが立ち上がり、http://localhost:8000 で画面が見られます。止めるときは Ctrl+C。

laravel new は途中で「テストフレームワークはどれにする?」と対話で聞いてきます。インストーラのソースを読むと、Pest と PHPUnit の2択で、既定は Pest でした。

laravel/installer の NewCommand.php（320行目付近）
$input->setOption('pest', select(
    label: 'Which testing framework do you prefer?',
    options: ['Pest', 'PHPUnit'],
    default: 'Pest',
) === 'Pest');
この記事の検証は laravel new ではなく composer create-project で行いました
なぜ
対話で聞いてくるコマンドは自動実行に向かないためです。composer create-project laravel/laravel example-app は、同じ雛形を対話なしで展開します。実際 laravel new の中身も、ソースを読むと composer create-project laravel/laravel ... --no-scripts を呼んでいました。
違いが出るところ
create-project ではテストフレームワークは PHPUnit のままです（Pestに差し替えるのはインストーラ側の仕事）。この記事の実行ログはすべてPHPUnit側のものです。あなたが laravel new で Pest を選んでいたら、テストの書き方だけが変わります。この記事で扱う「落ちる理由」は両方に共通です。
もう1つの違い
laravel new は --no-scripts を付けて呼ぶので、雛形側の後処理は走りません。代わりにインストーラ自身が key:generate などを実行しています。結果として「鍵が作られる」点は同じです。
どのバージョンを選ぶか（2026年8月時点）

公式のサポート表を取得して確認しました。数値はすべてその表からの引用です。

版PHPリリースバグ修正の期限
Laravel 128.2 - 8.52025年2月24日2026年8月13日
Laravel 138.3 - 8.52026年3月17日2027年 第3四半期

Laravel 12 のバグ修正期限は2026年8月13日で、この記事を書いた時点で既に過ぎています。新しく始めるなら 13 です。

注意点が1つ。Laravel 13 本体が要求するPHPは 8.3 以上ですが、テストフレームワークの Pest は公式サイトに「PHP 8.4+ が必要」と書かれています。Packagist（PHPの部品の配布サイト。3章で出てきます）のメタデータJSONで確認したところ Pest 5系は ^8.4、Pest 4系は ^8.3.0 でした（^ の意味は3章で説明します。ここでは「8.4以上の8系」くらいの理解で十分です）。ここから考えるとPHP 8.3 で Pest を選ぶと入るのは 4系になるはずですが、laravel new は対話が必要で自動実行できなかったため、これは実測ではなく制約からの推論です。

Unit は通ったのに Feature だけ落ちた。継承元が違うから

同じ鍵の問題なのに、2つあるテストのうち片方だけ落ちています。理由は、最初から入っている2つのファイルを並べると分かります。継承（extends）とは、あるクラスの機能をまるごと引き継いで、その上に自分の処理を足す仕組みのことです。引き継ぐ相手が違えば、テスト開始時にやることも変わります。

tests/Unit/ExampleTest.php（落ちなかった側・<?php とdocblockは省略）
namespace Tests\Unit;

use PHPUnit\Framework\TestCase;

class ExampleTest extends TestCase
{
    public function test_that_true_is_true(): void
    {
        $this->assertTrue(true);
    }
}
tests/Feature/ExampleTest.php（落ちた側・同じく省略あり）
namespace Tests\Feature;

// use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

class ExampleTest extends TestCase
{
    public function test_the_application_returns_a_successful_response(): void
    {
        $response = $this->get('/');

        $response->assertStatus(200);
    }
}
  • Unit側は PHPUnit\Framework\TestCase を直接継承。Laravelアプリを起動しません。だから鍵が要りません。
  • Feature側は Tests\TestCase を継承。こちらはLaravelを起動します。起動時に鍵を読むので、そこで落ちます。
  • だから 1 failed, 1 passed になります。「テストが全部落ちない＝設定は正しい」ではありません。
Laravel 13.x「Testing: Getting Started」— 原文
Tests within your "Unit" test directory do not
boot your Laravel application and therefore are
unable to access your application's database or
other framework services.

（「Unit」ディレクトリ内のテストは Laravel アプリを
　起動しないため、アプリのデータベースやその他の
　フレームワークのサービスにアクセスできません）

Q. これから書くテストは、どちらのフォルダに置くべき?

正解。フォルダ名は分類ではなく動作の違いです。Unit に置いたテストはLaravelを起動しないので、そこで User::create() のようなコードを書くと動きません。「速そうだから Unit」で始めて詰まる、というのが最初の事故です。

3Composer は「部品を集める係」。vendor/ が無いと最初の require で死ぬ

パソコン全体に入れる apt や brew とは別のもの。プロジェクトの中に入れます

なぜ Composer が要るのか。Laravelアプリは、自分が書いていないコードの塊に頼って動くからです。この「他人が作った部品」を依存（dependency）と呼びます。

Composer 公式「Introduction」— 原文
Composer is a tool for dependency management in
PHP. It allows you to declare the libraries your
project depends on and it will manage
(install/update) them for you.

Composer is not a package manager in the same
sense as Yum or Apt are. ... it manages them on
a per-project basis, installing them in a
directory (e.g. vendor) inside your project. By
default, it does not install anything globally.

（Composer は PHP における依存管理のツールです。
　プロジェクトが依存するライブラリを宣言でき、
　Composer が管理してくれます。

　Composer は Yum や Apt と同じ意味でのパッケージ
　マネージャではありません。…プロジェクト単位で
　管理し、プロジェクト内のディレクトリ（例: vendor）に
　インストールします。既定では何もグローバルには
　インストールしません）
  • 入る場所はプロジェクトの中の vendor/。パソコン全体には何も足しません。だからプロジェクトごとに別のバージョンを使えます。
  • 部品を取りに行く先は Packagist。Composer 公式の配布サイトです。
  • vendor/ は Git に入れません。雛形の .gitignore（Gitで共有しないファイルの一覧）に /vendor が書かれています。だから clone したら composer install が必要です。.env がcloneで付いてこないのも、同じファイルに書かれているからです。

composer.json は「宣言」、composer.lock は「記録」

この2つの違いが分かると、チームで環境がズレる事故がほぼ消えます。生成されたファイルの実物です。

生成された composer.json（require は全部、require-dev は先頭と末尾だけ）
"require": {
    "php": "^8.3",
    "laravel/framework": "^13.17",
    "laravel/tinker": "^3.0"
},
"require-dev": {
    "fakerphp/faker": "^1.23",
    ...
    "phpunit/phpunit": "^12.5.12"
},
ファイル中身誰が書く
composer.jsonどの部品の、どのバージョン範囲が要るか人間
composer.lock実際に入れた正確なバージョンComposer（自動）

^13.17 の ^（キャレット）は「13系の範囲なら新しくしてよい」という意味です。範囲なので、いつ入れるかで実際に入る版が変わります。それを固定するのが composer.lock です。

Composer 公式「Basic usage」— 原文
running install when a composer.lock file is
present resolves and installs all dependencies
that you listed in composer.json, but Composer
uses the exact versions listed in composer.lock
to ensure that the package versions are
consistent for everyone working on your project.

（composer.lock がある状態で install を実行すると、
　composer.json に列挙した全依存を解決して
　インストールしますが、Composer は composer.lock に
　記載された正確なバージョンを使い、プロジェクトに
　関わる全員でバージョンが揃うようにします）
  • composer install。composer.lock どおりに入れる。普段はこれだけ使います。
  • composer update。範囲内で新しいものを取り直し、composer.lock を書き換える。初学者が何気なく打つと、チーム全員の環境が動きます。
  • require-dev は開発時だけ。テストツールなどが入ります。本番では入れません。

app/Models/User.php が App\Models\User になるのは、規約で決まっている

クラスとは、データとその操作をひとまとめにした設計図で、PHPでは基本的に1クラス＝1ファイルです。Laravelには「そのクラスを使おうとした瞬間に、対応するファイルを自動で読み込む」仕組みがあります。これをオートロードと言います。ファイルを require して回る必要がありません。

では、どのクラスがどのファイルかをどう決めているのか。composer.json に書いてあります。

生成された composer.json の autoload
"autoload": {
    "psr-4": {
        "App\\": "app/",
        "Database\\Factories\\": "database/factories/",
        "Database\\Seeders\\": "database/seeders/"
    }
},
  • App\ は app/ に対応する。だから app/Models/User.php の中身は App\Models\User という名前になります。
  • 名前空間（namespace）はクラス名の「姓」です。User という名前は他の部品にもあり得るので、App\Models\ を前に付けて区別します。
  • この対応づけは PSR-4 という規約。PHP-FIG という団体が定めた「名前空間とディレクトリ構造を対応させる」仕様です。Laravel独自のルールではありません。
PSR-4 の原文（何を定めているか）
PSR-4: Autoloader（PHP-FIG）
This PSR describes a specification for
autoloading classes from file paths. ...
This PSR also describes where to place files
that will be autoloaded according to the
specification.

（この PSR はファイルパスからクラスをオートロード
　するための仕様を記述します。…またこの PSR は、
　オートロードされるファイルをどこに置くかも
　記述します）

つまり「ファイルをどこに置くか」は好みではなく、規約で決まっているということです。5章のディレクトリの話も、この上に乗っています。

php artisan ○○ の artisan は、コマンド名ではなくファイル名です。cd したフォルダの中に、拡張子なしで置かれています。

Q. app/Events/ や app/Jobs/ が見当たらない。壊れている?

正解。公式のディレクトリ構造のページに、Events / Jobs / Mail / Notifications / Policies / Rules は既定では存在せず make:* コマンドで作られる、と明記されています。app/Console も make:command を実行するまでありません。「チュートリアルにあるフォルダが無い」の大半はこれです。

生成された bootstrap/app.php の中身です。ここでLaravel本体が組み立てられます。

bootstrap/app.php（抜粋）
return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    ->withMiddleware(function (Middleware $middleware): void {
        //
    })
    ->withExceptions(function (Exceptions $exceptions): void {
        ...
    })->create();
  • web: の行が、routes/web.php を使うという宣言です。「なぜあのファイルにURLを書くのか」の答えがここにあります。
  • health: '/up'。最初から /up というURLが生えています。アプリが生きているかを外から確認するための入口です。
  • withMiddleware。ミドルウェアとは、リクエストが本体に届く前後に挟まる処理。ログイン確認やCSRF対策がここで動きます。

7ルートを1本足して、動くところまで

最初の1行は routes/web.php に書きます

生成直後の routes/web.php はこれだけです。/ にアクセスが来たら welcome という画面を返す、という意味。

routes/web.php（生成直後）
use Illuminate\Support\Facades\Route;

Route::get('/', function () {
    return view('welcome');
});

ここに1本足します。コントローラもモデルも作らずに、URLを1つ増やせます。

routes/web.php の末尾に追記する
Route::get('/hello', function () {
    return ['message' => 'hello', 'laravel' => app()->version()];
});

配列（['キー' => '値'] の形でまとめたデータ）をそのまま返すと、Laravelが自動で JSON に変換して返します。JSONは {"message":"hello"} のような、プログラム同士がデータをやりとりするときの標準的な書き方です。php artisan serve でサーバーを立てて、実際に叩きました。
