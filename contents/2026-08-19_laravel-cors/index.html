LaravelのCORS設定はどこに書くか — 既定で開いている api/* と、絞るときの落とし穴

自社がWebView側を作り、Laravel/AWSは別会社が運用している構成の話です。CORS設定の置き場所を実測で確かめ、絞るときに踏む穴と、CloudFrontが挟まるときに相手へ何を頼むかまで詰めます。

⏱ 約12分 会社をまたぐ連携 実測は Laravel 13.26.1 AWSはドキュメントのみ(実機なし)

⭐ 3行で言うと

  1. CORSで「止める」のはブラウザです。サーバーは200と本文を返しています 同じサーバーに curl と Chromium を当てて確かめました。curl は本文まで受け取り、ブラウザだけが TypeError: Failed to fetch で止まります。だからLaravelのログを見ても異常は出ません。
  2. Laravelの置き場所は config/cors.php。ただしファイルが無くても api/* は既定で全オリジンに開いています 作りたてのプロジェクト(実測は13.26.1)にこのファイルはありません。それでも api/ で始まるURLには Access-Control-Allow-Origin: * が付きます。絞りたくなって初めて php artisan config:publish cors で出します。

1curlは通る。止めたのはブラウザ

同じサーバー・同じ設定に、curlとChromiumを当てた

まず言葉を2つ。CORSとは、別のオリジンにあるAPIを、ブラウザ上のJavaScriptから呼んでいいかを決める仕組みです。オリジンとは「スキーム＋ホスト＋ポート」の組のこと(https://example.com:443 なら https がスキーム、example.com がホスト、443 がポート)。

もう1つ。curlとは、ブラウザを介さずコマンドラインからHTTPリクエストを送る道具です。この記事ではブラウザとの比較役です。

Laravel側の許可リストには game.example.com と app.example.com だけを書き、実験ページのオリジン http://127.0.0.1:8130 は入れていません。この状態で両方から叩きます(リクエストを送ります)。出力中の $API は、APIのURL(http://127.0.0.1:8123/api/hello)を入れた変数です。

curl から(2026年8月19日実測。表示はスクリプト側でヘッダー行を抽出し40桁に折り返したもの。文言は無加工、全文は _labs 参照)
-- curl から (ブラウザではない)
$ curl -s -o /dev/null -D - \
 -H "Origin: http://127.0.0.1:8130" \
 "$API"
HTTP/1.1 200 OK
Vary: Origin

$ curl -s "$API"
{"msg":"hello"}
まったく同じサーバーに、Chromium 141(Chromeの元になるブラウザ)から
-- Chromium から
ページのオリジン: http://127.0.0.1:8130
API: http://127.0.0.1:8123/api/hello
fetch: 失敗
TypeError: Failed to fetch
-- ブラウザのコンソール
Access to fetch at
  'http://127.0.0.1:8123/api/hello' from
  origin 'http://127.0.0.1:8130' has
  been blocked by CORS policy: No
  'Access-Control-Allow-Origin' header
  is present on the requested resource.
Failed to load resource: net::ERR_FAILED

サーバーは200を返し、本文 {"msg":"hello"} も渡しています。1バイトも隠していません。エラー文をよく読むと「blocked by CORS policy」、つまり止めたのはブラウザ自身だと言っています。

Fetch仕様(ブラウザの通信処理を定めるWHATWGの標準)も、判定の主体をブラウザ側に置いています。

Fetch Standard §3.3.6 Examples — 原文＋訳
Upon receiving a response from bar.invalid,
the user agent will verify the
Access-Control-Allow-Origin response header.
If its value is either https://foo.invalid
or `*`, the user agent will invoke the
success callback. If it has any other value,
or is missing, the user agent will invoke
the failure callback.

（bar.invalid からレスポンスを受け取ると、
　ユーザーエージェント(ブラウザ)は
　Access-Control-Allow-Origin レスポンス
　ヘッダーを検証する。値が https://foo.invalid
　か * なら成功のコールバックを、それ以外の
　値なら、あるいは無ければ、失敗の
　コールバックを呼ぶ）
  • リクエストは届き、レスポンスも返ってきています。ブラウザがその結果をJavaScriptに渡すかどうかを、ヘッダーを見て決めているだけです。
  • だから「curlで確認できた」はブラウザで動く保証になりません。逆に「curlは通るのにアプリだけ落ちる」は、CORSを疑う典型的な症状です。
  • サーバー側の設定だけで直ります。許可リストにページのオリジンを足して同じ実験をやり直すと、こうなりました。
許可リストに http://127.0.0.1:8130 を足したあと
-- Chromium から(設定を足したあと)
ページのオリジン: http://127.0.0.1:8130
API: http://127.0.0.1:8123/api/hello
fetch: 成功 status=200
本文: {"msg":"hello"}
-- ブラウザのコンソール
(エラーなし)

Q. Laravelのログには200が並んでいるのに、画面にデータが出ない。データを止めたのは誰?

正解。「拒否されたならログに4xxが出るはず」と考えるのは自然ですが、サーバーは200と本文を普通に返しています(上の実測)。ブラウザが応答の Access-Control-Allow-Origin を自分のオリジンと見比べて、合わなければJSに渡しません。だからサーバーのログは無傷で、ブラウザのコンソールにだけエラーが出ます。障害の切り分けでは、この非対称を最初に思い出してください。

2設定ファイルは最初から無い。それでも api/* は開いている

「設定していない」＝「全部拒否」ではない。既定は全部許可

composer create-project laravel/laravel で作った直後のプロジェクト(実測は Laravel Framework 13.26.1)に、config/cors.php はありません。それでも設定は存在します。

以降のコマンドに出てくる php artisan は、Laravelに同梱されているコマンドラインツールです。プロジェクトのディレクトリで打ちます。

ファイルが無い状態での設定値(以降の実測で使う変数もここで定義。⇁ 0 は配列の0番目の意味)
コマンドの中で使う変数:
API=http://127.0.0.1:8123/api/hello
WEB=http://127.0.0.1:8123/hello
OK_ORIGIN=https://game.example.com
NG_ORIGIN=https://evil.example.com

(中略)

-- 1a. それでも設定は存在する
$ php artisan config:show cors

allowed_origins の既定は *(全オリジン許可)です。実際に叩くと、ヘッダーが付くかどうかはURLのパスで決まります。

api/ で始まるパスと、始まらないパス
-- 1b. api/* のGETに Origin を付ける
$ curl -s -o /dev/null -D - \
 -H "Origin: $OK_ORIGIN" \
 "$API"
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *

-- 1c. api/ で始まらないパスに同じことを
$ curl -s -o /dev/null -D - \
 -H "Origin: $OK_ORIGIN" \
 "$WEB"
HTTP/1.1 200 OK

-- 1d. Origin を付けない
$ curl -s -o /dev/null -D - "$API"
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
  • 効く範囲は cors.paths のパターンで決まります。既定は api/* と sanctum/csrf-cookie(Laravel公式の認証パッケージ Sanctum が使うURL)の2つだけ。1cのように api/ で始まらないパスには、CORSヘッダーが1つも付きません。/v1/... にAPIを置くと、ここで詰まります。
  • ルート(URLと処理の対応)をどのファイルに書いたかは関係ありません。routes/web.php に書いても、URLが api/ で始まれば対象です(HandleCors のソースで確認。paths の照合はリクエストのURLに対して行われ、どのルートファイルに書いたかは見ていません)。
  • * 自体は危険ではありません。Fetch仕様の附録は「curlやwgetで誰でも取れるリソースなら Access-Control-Allow-Origin: * は安全(safe)」と書いています。危ないのはIPやファイアウォールで守っているつもりのリソースに付けること、そしてcredentialsとの併用です(6章)。

routes/api.php も最初から無い(実測メモ)
作りたての骨格

3許可リストが1件だと、サーバーは相手を見ない

許可していないオリジンにも、同じヘッダーがそのまま返る

絞ってみます。allowed_origins に https://game.example.com を1件だけ書きました。

config/cors.php(書き換えた行)
'allowed_origins' => ['https://game.example.com'],
1件だけのとき(実測)
-- 2b. 許可したオリジンから
$ curl -s -o /dev/null -D - \
 -H "Origin: $OK_ORIGIN" \
 "$API"
HTTP/1.1 200 OK
Access-Control-Allow-Origin:
  https://game.example.com

-- 2c. 許可していないオリジンから
$ curl -s -o /dev/null -D - \
 -H "Origin: $NG_ORIGIN" \
 "$API"
HTTP/1.1 200 OK
Access-Control-Allow-Origin:
  https://game.example.com

-- 2d. 本文は返ってくるのか
$ curl -s \
 -H "Origin: $NG_ORIGIN" \
 "$API"
{"msg":"hello"}

2cを見てください。evil.example.com を名乗っても、同じヘッダーがそのまま返ります。サーバーは相手を見ていません。「うちは game.example.com からの利用を許可している」と一方的に掲示しているだけです。

それでも安全なのは、掲示と自分のオリジンを見比べて止めるのがブラウザだからです(1章)。そして2dのとおり、本文は誰にでも返っています。CORSは情報を隠す仕組みではありません。

2件以上にすると「合ったときだけ返す」に変わる

同じ設定項目なのに、件数で挙動が切り替わります。2件にしました。

2件のとき(実測)
-- 3a. 許可したオリジンから
$ curl -s -o /dev/null -D - \
 -H "Origin: $OK_ORIGIN" \
 "$API"
HTTP/1.1 200 OK
Access-Control-Allow-Origin:
  https://game.example.com
Vary: Origin

-- 3b. 許可していないオリジンから
$ curl -s -o /dev/null -D - \
 -H "Origin: $NG_ORIGIN" \
 "$API"
HTTP/1.1 200 OK
Vary: Origin

なぜ切り替わるのか。Laravel本体ではなく、php-cors のこの分岐がやっています。

fruitcake/php-cors v1.4.0 src/CorsService.php(抜粋)
private function configureAllowedOrigin(Response $response, Request $request): void
{
    if ($this->allowAllOrigins === true && !$this->supportsCredentials) {
        // Safe+cacheable, allow everything
        $response->headers->set('Access-Control-Allow-Origin', '*');
    } elseif ($this->isSingleOriginAllowed()) {
        // Single origins can be safely set
        $response->headers->set('Access-Control-Allow-Origin', array_values($this->allowedOrigins)[0]);
    } else {
        // For dynamic headers, set the requested Origin header when set and allowed
        if ($this->isCorsRequest($request) && $this->isOriginAllowed($request)) {
            $response->headers->set('Access-Control-Allow-Origin', (string) $request->headers->get('Origin'));
        }

        $this->varyHeader($response, 'Origin');
    }
}
  • 1件のときは固定値の掲示。相手を見ずに常に同じ値を返し、Vary: Origin は付きません。値が誰に対しても同じなので、これで問題ありません。
  • 2件以上は出し分け。リクエストの Origin が許可リストに在るときだけその値を返し、Vary: Origin(この応答はOriginによって変わる、というキャッシュへの注意書き)が自動で付きます。
  • ブラウザから見た結果はどちらも同じです。許可した所だけ通ります。違いは Vary: Origin が付くかどうかで、これはCDNが間に入ると効いてきます(8章)。
  • isCorsRequest() は Origin ヘッダーの有無だけを見ています。つまり出し分けモードでは、Origin がサーバーに届かなければ何も返せません。この1行が、8章のCloudFrontの話に直結します。

4JSONを送った時点で preflight が飛ぶ

POSTの前に、ブラウザが勝手にOPTIONSを送っている

preflight(プリフライト)とは、本番のリクエストの前にブラウザが自動で送る「これ、送っていいですか」という問い合わせです。HTTPのOPTIONSメソッドで飛びます。

いつ飛ぶかはFetch仕様が決めています。Content-Type: application/json を付けた時点で飛ぶ、が実務での答えです。Authorization(ログイントークンなどを載せる認証用ヘッダー)のように、仕様のsafelist(preflight無しで送れるヘッダーの一覧)に無いヘッダーを付けたときも飛びます。

Fetch Standard §2.2.1 / §2.2.2 — 原文＋訳
A CORS-safelisted method is a method that is
`GET`, `HEAD`, or `POST`.

`content-type`: ... If mimeType's essence is
not "application/x-www-form-urlencoded",
"multipart/form-data", or "text/plain",
then return false.

（preflight無しで送れるメソッドは GET / HEAD /
　POST のみ。Content-Type も、この3種類以外
　なら safelist から外れる＝preflightが飛ぶ。
　Authorization など、safelistに
　無いヘッダーも同様）

Laravelがpreflightにどう答えるかを実測しました。許可オリジンは2件のままです。

preflight への応答(実測)
-- 4a. 許可したオリジンから
$ curl -s -o /dev/null -D - -X OPTIONS \
 -H "Origin: $OK_ORIGIN" \
 -H "Access-Control-Request-Method: \
POST" \
 -H "Access-Control-Request-Headers: \
content-type" \
 "$API"
HTTP/1.0 204 No Content
Access-Control-Allow-Origin:
  https://game.example.com
Vary: Origin,
  Access-Control-Request-Method,
  Access-Control-Request-Headers
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers:
  content-type
Access-Control-Max-Age: 0

-- 4b. 許可していないオリジンから
$ curl -s -o /dev/null -D - -X OPTIONS \
 -H "Origin: $NG_ORIGIN" \
 -H "Access-Control-Request-Method: \
POST" \
 -H "Access-Control-Request-Headers: \
content-type" \
 "$API"
HTTP/1.0 204 No Content
Vary: Origin,
  Access-Control-Request-Method
  • preflightは HandleCors が握って即答します。ルートやコントローラには届きません(HandleCors::handle() のソースで確認)。Route::options() を自分で書く必要はありません。
  • 204で答えるのは仕様の要請どおりです。Fetch仕様はpreflightへの応答を「ok status(2xx)に限る」と定めています。認証ミドルウェアがOPTIONSに401(認証エラー)を返す構成だと、ここで全滅します。仕様は「preflightには資格情報が乗らない(a CORS-preflight request never includes credentials)」とも明記しています。
  • Allow-Methods / Allow-Headers には、聞かれた値がそのまま返っています。allowed_methods / allowed_headers の既定 ['*'] は、文字どおりの * を返す実装ではなく、リクエストの Access-Control-Request-* を反射する実装です(php-corsのソースで確認)。この性質が8章で効きます。
  • Access-Control-Max-Age: 0 は「preflightの結果をキャッシュしない」。Laravelの既定 max_age => 0 のためで、リクエストのたびにpreflightが飛びます。ちなみにFetch仕様の既定値は5秒です。減らしたければ max_age を増やします。
  • 未許可のオリジンにも204は返ります(4b)。ステータスで落とすのではなく、Access-Control-Allow-Origin を付けないことで、ブラウザに止めさせています。ここでも判定はブラウザです。

5WebViewの Origin: null は文字列 'null' で通る。ただし勧めない

PHPのnullではなく、クォート付きの文字列 'null' を書く

WebView(アプリに埋め込むWebページ表示部品)からの通信では、Origin: null という値が届くことがあります。Android公式リファレンスに、その条件が名指しで書かれています。

Android Developers「WebView#loadData()」— 原文＋訳
Content loaded using this method will have a
window.origin value of "null". This must not
be considered to be a trusted origin ...
If you need to identify the main frame's
origin in a trustworthy way, you should use
loadDataWithBaseURL() with a valid HTTP or
HTTPS base URL to set the origin.

（このメソッドで読み込んだコンテンツの
　window.origin は "null" になる。これを
　信頼できるオリジンと見なしてはいけない。
　信頼できる形でオリジンを識別したいなら、
　有効なHTTPまたはHTTPSのbaseUrlを渡して
　loadDataWithBaseURL() を使うこと）

Laravel側でこれを通すには、allowed_origins に文字列の 'null' を書きます。PHPの null ではありません。curlで再現しました。

config/cors.php(書き換えた行)
'allowed_origins' => ['https://game.example.com', 'null'],
Origin: null を送る(実測)
-- 5a. null を許可リストに入れていない
$ curl -s -o /dev/null -D - \
 -H "Origin: null" \
 "$API"
HTTP/1.1 200 OK
Vary: Origin

-- 5b. null を許可リストに入れた
(中略)
$ curl -s -o /dev/null -D - \
 -H "Origin: null" \
 "$API"
HTTP/1.1 200 OK
Access-Control-Allow-Origin: null
Vary: Origin
  • 正確に書きます。「file:// は必ずnullになる」とは言えません。URL標準は file: のオリジンを実装依存としています(原文は「left as an exercise to the reader」)。一方 data: URLと、上のとおり loadData() は、一次資料で null になると確認できます。HTML標準では、こうした「不透明なオリジン」が文字列 "null" に変換されると定めています。
  • 通せますが、勧めません。Origin: null はサンドボックス化されたiframeなど複数の状況で出る値で、あなたのアプリだけを指しません。'null' の許可は、null を名乗れる全員の許可と同じです。
  • 先にクライアント側で直せます。Android公式の案内どおり、loadDataWithBaseURL() に有効なhttp(s)のbaseUrlを渡せば、オリジンが正規の値になりこの問題ごと消えます。サーバー会社に「nullを許可して」と頼む前に、こちらで直すのが筋です。詳しくは既存記事「WebViewのfetchが失敗する理由」で、nullを許可すると何が起きるかまで実測しています。
  • この章の実測はcurlで Origin: null を送った再現です。実機のWebViewでは測っていません。実機の挙動はAndroid公式ドキュメントの記述に基づきます。

6いちばん危ない組み合わせ — ['*'] と supports_credentials

エラーにならない。Originがそのまま返って(エコー)、どこからでもCookie付きで通る

Cookieやセッションを使うAPIにしようと、supports_credentials を true にする。allowed_origins は ['*'] のまま。ありがちな途中経過です。見どころは、返ってくる Access-Control-Allow-Origin の値です。

config/cors.php(この2行の組み合わせが問題)
'allowed_origins' => ['*'],
'supports_credentials' => true,
未許可のはずのオリジンから叩く(実測)
-- 6a. Origin を付けたGET
$ curl -s -o /dev/null -D - \
 -H "Origin: $NG_ORIGIN" \
 "$API"
HTTP/1.1 200 OK
Access-Control-Allow-Origin:
  https://evil.example.com
Vary: Origin
Access-Control-Allow-Credentials: true

設定ファイルには * としか書いていないのに、返っているのは * ではなくリクエストのOriginそのものです。しかも Access-Control-Allow-Credentials: true 付き。つまりどのオリジンからでも、Cookie付きで通る状態です。警告もエラーも出ません。

なぜライブラリがこんな変換をするのか。仕様が * とcredentialsの併用を禁じているからです。

Fetch Standard §3.3.5 — 原文＋訳
If credentials mode is "include", then
`Access-Control-Allow-Origin` cannot be `*`.

A serialized origin has no trailing slash.

`true` is (byte) case-sensitive.

（credentialsモードが include のとき、
　Access-Control-Allow-Origin に * は使えない。
　シリアライズされたオリジンに末尾スラッシュは
　付かない(https://example.com/ は不一致)。
　Allow-Credentials の true は小文字のみ）
  • php-cors は3章の分岐の1行目で * を諦めています。allowAllOrigins === true && !supportsCredentials のときだけ文字どおりの *。credentialsが有効だと出し分けモードに落ち、allowAllOrigins のせいで照合が常に真になり、誰のOriginでもエコーします。
  • 設定ファイルを見ても気付けません。* としか書いていないからです。実際のレスポンスヘッダーを見て初めて分かります。
  • 直し方は1つ。supports_credentials => true にするなら、allowed_origins から * を消してオリジンを列挙する。このとき末尾スラッシュを付けないこと(上の仕様のとおり、1文字で不一致になります)。
  • preflightでも同じ値が返ることを実測済みです。出力全文は検証一式(_labs/2026-08-19_laravel-cors/)にあります。

config:cache のあとは、artisanコマンドまで古い値を言う

キャッシュ後に設定を書き換える(実測。$CFG は差し替え用設定の置き場)

  • ファイルは2件に直っているのに、config:show も1件のままと言います。「ファイルは新しい、artisanもcurlも古い」という混乱した状態になります。php artisan config:clear(または config:cache のやり直し)で直ります。

php artisan serve は、直後の2秒間だけ古い設定で答えることがある

こちらはあまり知られていません。この記事の検証中に実際に踏み、同じスクリプトを3回流して3回とも違う結果が出た原因です。

serve の実行環境をサーバー自身に言わせる(実測。$SAPI は検証用に足した確認ルート)
-- 0b. serve は cli-server + OPcache
$ curl -s "$SAPI" | jq -r ".[]"
sapi=cli-server
opcache.enable_cli=0
opcache.revalidate_freq=2
opcache_get_status=true
  • php artisan serve は cli ではなく cli-server という実行形態で動きます。そして opcache.enable_cli=0(CLIではOPcacheを使わない、という設定)でも、OPcache(PHPがファイルの解析結果を使い回す仕組み)は有効でした(opcache_get_status=true)。
  • opcache.revalidate_freq=2 なので、ファイル更新の確認は2秒に1回です。revalidate_freq は「スクリプトの更新を何秒おきに確認するか」という設定で(PHPマニュアル)、値の 2 は上の実測です。つまり設定を保存しても最大2秒は古いまま。「保存して即リロードしたら直っていない、もう一度押したら直った」はこれで説明が付きます。
  • 本番のnginx/php-fpm構成では条件が違います。この節は php artisan serve での実測で、本番構成では測っていません。
おまけの事故: artisan serve は kill してもポートが空かない
何が起きたか
検証スクリプトでサーバーを止めたはずが、前の実行のサーバーが応答して測定値が混ざりました。原因は起動の書き方です。( cd app && nohup php artisan serve … & ) の形だと、$! に入るのは中間シェルのPIDで、killはそこにしか当たりません。本体(artisanと子の php -S)は丸ごと生き残り、ポートを掴み続けていました。
直し方
( cd app && exec php artisan serve … ) & と exec を付けて、$! が本体を指すようにする。止めるときは親(artisan)→子(php -S)の順に。修正後のスクリプトは検証一式(_labs/2026-08-19_laravel-cors/)にあります。

8CloudFrontが挟まると、Laravelだけでは完結しない

Originが転送されなければ、Laravelは何も返せない

ここからはAWSの話です。この章の根拠はAWS公式ドキュメントだけで、この環境ではAWSを実行できないため実機では確認していません。

読者の現場の構成は「ブラウザ/WebView → CloudFront(CDN。利用者の近くに応答のコピーを置き、Laravelの代わりに返すキャッシュサーバー網) → ALB(負荷分散装置) → Laravel」です。

紛らわしい注意を1つ。AWSの用語では、CloudFrontの後ろにいる本体サーバー(ここではALB配下のLaravel)のこともオリジン(配信元)と呼びます。1章の「スキーム＋ホスト＋ポートの組」としてのオリジンとは別物です。

このとき、ブラウザが送った Origin ヘッダーがLaravelまで届くかどうかは、CloudFront側の転送設定で決まります。AWS公式ドキュメントが、CORSを機能させる条件をこう書いています。

AWS「Request and response behavior for custom origins」— 原文＋訳
Cross-origin resource sharing (CORS) —
If you want CloudFront to respect cross-origin
resource sharing settings, configure CloudFront
to forward the Origin header to your origin.

（CORSの設定を尊重させたいなら、Origin
　ヘッダーをオリジンへ転送するように
　CloudFrontを設定すること）

3章で見たとおり、php-cors は Origin ヘッダーの有無だけを見て動きます。転送されなければ、Laravel側の設定が完璧でも出し分けモードではヘッダーが1本も出ません。症状は1章と同じ「curlは通るのにブラウザだけ落ちる」です。

さらに同じドキュメントには Vary の扱いも書かれています。転送対象にしていないヘッダー名がオリジンの返す Vary に入っていた場合、CloudFrontはその値を削除してからビューワー(利用者側)に返します(Accept-Encoding や Cookie など、削除しない例外も列挙されています)。つまり3章の Vary: Origin も、Origin を転送していなければ消されます。オリジン別の出し分けがキャッシュで混ざる条件が揃ってしまいます。

CORSヘッダーを付けられる場所は3つある。だから1か所に決める

CloudFrontにもALBにも、CORSヘッダーを付ける機能があります。全部ドキュメントで確認しました。

場所設定の名前競合したときOriginの出し分け
Laravel config/cors.php — できる(複数指定で照合＋Vary: Origin 自動)
CloudFront レスポンスヘッダーポリシー(CORS設定) Origin override で選ぶ。true=CloudFrontが勝ちオリジンの値は無視 / false=オリジンが勝つ(公式の明文) ドキュメントに記載なし(* か具体値、左端サブドメインのワイルドカード。例: *.example.org)
ALB リスナー属性 routing.http.response.access_control_*(既定オフ) 有効化するとターゲットの値を設定値で上書きする(公式の明文。切り替えの記載なし) 動的に返す機能の記載なし(固定文字列を全レスポンスに付与)
  • 2か所以上で設定すると、必ずどちらかが無効になります。CloudFrontの Origin override=true ならLaravelの値は無視。ALBで有効化すればLaravelの値は上書き。片方に寄せるのが唯一の正解です。
  • AWS既製のCORSポリシー(SimpleCORS / CORS-With-Preflight)は Override origin = No。つまりLaravelがヘッダーを返していればLaravelが勝ちます。既に当たっていても、Laravel側に寄せる方針と両立します。
  • CloudFront/ALB側で付けるときの罠が1つ。Access-Control-Allow-Headers: * は Authorization を許可しません。Fetch仕様が Authorization を「CORS non-wildcard request-header name」と定めており、CloudFrontのドキュメントも「The Authorization header can't use a wildcard and must be listed explicitly.」と明記しています。Laravelの ['*'] が平気なのは、* ではなく要求されたヘッダー名を反射する実装だからです(4章)。固定文字列しか書けないCDN側でやると踏みます。

だから依頼はこうなる。「CORSはLaravelに置く。CloudFrontにはOriginの転送を頼む」

ここから下は、インフラ会社にそのまま送れる文面です。文中のAWS用語を3つだけ。ディストリビューションはCloudFrontの配信設定のひとまとまり(IDで指定)、ビヘイビアはURLパスごとの配信ルール、キャッシュキーはCloudFrontが「同じリクエストだ」と判定する基準です。キャッシュキーに Origin が入っていないと、別のオリジン向けの応答が同じものとして使い回されます。
