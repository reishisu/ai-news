1用語。なぜ登場人物が4人も要るのか

「コンテナを1個動かしたい」だけなのに、覚える言葉が4つ出てくる

ECSを調べ始めると、クラスタ・タスク定義・サービス・タスクという言葉が同時に出てきます。どれを最初に作るのかが分かりません。ここが最初の壁です。

先に用語だけ片付けます。知っている行は飛ばしてください。

  • AWS。Amazon Web Services。サーバーやネットワークやデータベースを、自分で機械を買わずにインターネット越しに借りられるサービス群のこと。
  • Amazon EC2。そのAWSで「仮想サーバーを1台借りる」サービス。OSの更新やディスクの管理は借りた側の仕事です。この記事では7章で比較相手として出てきます。
  • コンテナ。アプリと、それが動くのに必要なライブラリ（アプリが借りて使う部品の集まり）・設定を1つにまとめて、どこでも同じように動かせるようにしたもの。
  • コンテナイメージ。コンテナの元になる読み取り専用のファイル一式。レシピと料理の関係です。イメージがレシピ、コンテナが料理。イメージを作って動かす代表的なツールが Docker です。
  • Amazon ECS。そのコンテナを「何個、どこで動かすか」をAWSが代わりに管理してくれるサービス。この管理のことをオーケストレーションと呼びます。
  • AWS Fargate。サーバーを1台も用意せずにコンテナを動かせる仕組み。公式の言い方は run containers without having to manage servers or clusters of Amazon EC2 instances です。

では登場人物です。AWS公式ドキュメントの「What is Amazon Elastic Container Service?」に、4つの言葉の定義がそのまま並んでいます。ここが記事の骨格です。

Amazon ECS Developer Guide「What is Amazon Elastic Container Service?」— 原文
Task definition — The blueprint for the
application.
Cluster — The infrastructure your
application runs on.
Task — An application such as a batch
job that performs work, and then stops.
Service — A long running stateless
application.

（タスク定義＝アプリの設計図 /
　クラスタ＝アプリが動く土台 /
　タスク＝仕事をして終わるアプリ /
　サービス＝動き続けるアプリ）
登場人物担当実体は何か
クラスタタスクやサービスを入れておく区切り論理的なグループ。サーバーではない
タスク定義どのイメージを、CPUいくつ・メモリいくつで動かすかJSONのテキストファイル
タスク実際に動いているコンテナのまとまりタスク定義から起動した1個
サービスタスクを指定台数だけ維持し続けるECS内部の見張り役
ALB外から来たHTTPを、生きているタスクへ振り分けるECSの外側にある別サービス

作る順番は、この表の上から下です。クラスタ → タスク定義 → （ALB） → サービス。タスクはサービスが勝手に作るので、自分で作るボタンを押すことはほとんどありません。

この記事で「やっていないこと」を先に書きます

この記事の筆者の環境にはAWSアカウントも認証情報もありません。そのため次の操作は一切実行していません。実行していないものを、実行したかのようには書きません。

  • ECSへのデプロイ操作。create-cluster / register-task-definition / create-service のいずれも実行していません。
  • タスクの起動、ALB経由のHTTPアクセス、ヘルスチェックの通過確認。していません。
  • terraform apply。していません。plan までです。
  • docker build。この環境はDockerのデーモン（バックグラウンドで常駐して指示を受け付けるプログラム）が動いていないので、失敗します。

代わりに使ったのは、認証情報が要らない操作だけです。AWS CLIの入力雛形（--generate-cli-skeleton）、CLIがローカルで行うパラメータ検証、CLI同梱のAPI定義ファイル、そして terraform validate と plan。ここから分かることは、思ったより多くありました。

2クラスタは「サーバーの集まり」ではない

作成の雛形を出したら、必須なのは名前だけだった

「クラスタ」という言葉は、普通は「複数台のサーバーの集まり」を指します。ECSでは違います。中身が空の区切りです。

確かめます。AWS CLIには --generate-cli-skeleton という、そのAPIに渡せる項目の雛形を出す機能があります。

「ターミナル」「AWS CLI」「API」だけ先に説明します
  • ターミナル。マウスではなく文字でパソコンに命令する画面のこと。1行打って Enter を押すと、その結果が下に出ます。この記事の「実行結果」は、その下に出た文字をそのまま貼ったものです。
  • API。プログラム同士の窓口。AWSは「クラスタを作る」「タスク定義を登録する」といった操作を、全部この窓口として持っています。
  • AWS CLI。その窓口をターミナルから叩くための公式コマンド。aws ecs create-cluster のように打ちます。この記事では窓口に何を渡せるかを見るためだけに使い、実際に作る操作はしていません。
  • jq。JSON（項目名と値を並べた書式）から一部だけ抜き出して整形するコマンド。長い出力を画面幅に収めるために使っています。
実行結果（aws ecs create-cluster --generate-cli-skeleton を jq で抜粋）

  • 残りの3個も任意項目です。configuration（実行コマンドとストレージの設定）、defaultCapacityProviderStrategy、tags。
  • containerInsights は監視のオン・オフ。serviceConnectDefaults はサービス同士の名前解決（名前からIPアドレスを引く仕組み）の既定値です。

同じページには、クラスタがネットワーク（VPCとサブネット）も含むと書かれています。ここは後でALBと繋がる話なので覚えておいてください。

ここで意外な事実。公式の推奨は Fargate ではありません

クラスタを作るときはインフラ種別を選びます。いまの公式ドキュメントは、そこに3つ並べています。推奨と書いてあるのはFargateではありません。

  • ECS Managed Instances は第3の選択肢です。EC2を使うけれど、用意・パッチ適用・スケールをAWSがやる、という位置づけです。
  • 登場日は2025年9月30日。AWS公式ブログ（AWS News Blog、Micah Walter）に on 30 SEP 2025 と載っています。
  • 「起動タイプ」の話とは別です。この3つはクラスタのインフラ種別であって、公式は起動タイプが3つになったとは書いていません。次の項で原文を並べます。
  • ただしこの記事はFargateを軸に書きます。Managed Instances を筆者は動かしていないためです。動かしていないものの使用感は書きません。

Fargateはサーバーを選ばない代わりに、CPUとメモリを「タスク全体」に対して指定します。しかも組み合わせが決まっています。

4サービスは見張り役。落ちたら勝手に立て直す

「2台動かしていて」と言うだけの相手。数を数え続けるのが仕事です

タスク定義があっても、そのままでは何も動きません。「これを2台、ずっと動かしておいて」と頼む相手がサービスです。その台数を desiredCount と呼びます。

Amazon ECS Developer Guide「Amazon ECS services」— 原文
You can use an Amazon ECS service to
run and maintain a specified number of
instances of a task definition
simultaneously ...
If one of your tasks fails or stops,
the Amazon ECS service scheduler
launches another instance of your task
definition to replace it.
...
The service scheduler also replaces
tasks determined to be unhealthy after
a container health check or a load
balancer target group health check
fails.

最後の段落が重要です。ALBのヘルスチェックに落ちたタスクも、サービスが置き換えます。ECSとALBは別サービスなのに、ここで連動しています。

Q. ALBのヘルスチェックのパスを /health に設定したが、アプリはそのURLで404を返す。何が起きる?

正解。ALBの既定では、成功とみなすステータスは200（Matcher の既定値）で、2回連続で失敗すると切り離されます。そしてECSのサービススケジューラは「ロードバランサーのターゲットグループのヘルスチェックに落ちたタスクを置き換える」と公式に書かれています。つまり切り離す側（ALB）と作り直す側（ECS）が噛み合って、置き換えが繰り返されます。アプリのログにはエラーが出ないので、原因が分かりにくい事故の代表です。なお同じ公式ページには The service scheduler includes logic that throttles how often tasks are restarted if tasks repeatedly fail to start（起動に失敗し続けるタスクは再起動の間隔を空ける）とも書かれています。ただしこれは RUNNING に到達せず停止した場合の話で、ヘルスチェック落ちに効くかは実行して確かめていません。「永久に等間隔で回り続ける」とまでは言えません。

  • サービスは「タスクを作る人」ではなく「数を維持する人」。デプロイもここが担当します。新しいリビジョンのタスク定義を指すと、置き換えていきます。
  • バッチのように1回で終わる処理は、サービスにしません。公式の定義でも、タスクは performs work, and then stops、サービスは long running と書き分けられています。

5ALBは箱が1つではない。中に3人いる

ロードバランサー本体・リスナー・ルール・ターゲットグループ

ALB（Application Load Balancer）は、HTTP/HTTPSを受け取って複数のタスクに振り分けるAWSの窓口です。ただし「ALBを作る」で終わりません。入れ子の部品を順に作ります。

User Guide for ALB「What is an Application Load Balancer?」— 原文
A load balancer serves as the single
point of contact for clients.
You add one or more listeners to your
load balancer. A listener checks for
connection requests from clients,
using the protocol and port that you
configure. The rules that you define
for a listener determine how the load
balancer routes requests to its
registered targets.
...
Each target group routes requests to
one or more registered targets ...
An Application Load Balancer functions
at the application layer, the seventh
layer of the ... (OSI) model.
The default routing algorithm is
round robin;
  • ロードバランサー本体。クライアントから見た唯一の窓口（single point of contact）。DNS名を持ちます。
  • リスナー。「どのポートとプロトコルで待つか」。80で待つ、443で待つ、を決めます。
  • リスナールール。URLのパスやホスト名を見て、どの名簿へ送るか判定します。優先度・条件・アクションの組です。
  • ターゲットグループ。振り分け先の名簿。ここに登録された宛先へリクエストが渡ります。既定の振り分け方はラウンドロビン（順番に1つずつ）。

「第7層で動く」というのは、URLの中身まで見られるということです。だからパスによる振り分けができます。

Fargateの最大の落とし穴。ターゲットタイプは ip にする

ターゲットグループには「名簿の書き方」の指定があります。instance（EC2のインスタンスIDで書く）か、ip（IPアドレスで書く）か。

Amazon ECS Developer Guide「Architect for AWS Fargate for Amazon ECS」— 原文
When you create a target group for
these services, you must choose `ip`
as the target type, not `instance`.
This is because tasks that use the
`awsvpc` network mode are associated
with an elastic network interface,
not an Amazon EC2 instance.

理由がそのまま書いてあります。Fargateのタスクには、そもそもEC2インスタンスIDが無いのです。あるのはENI（Elastic Network Interface。タスク1個に1本生える、仮想的なネットワークの差込口）と、そこに付いたIPアドレスだけ。だからIPで名簿を書きます。

User Guide for ALB「Target groups — Target type」— 原文
After you create a target group, you
can't change its target type.

（作成後にターゲットタイプは
　変更できない）

Q. うっかり instance でターゲットグループを作ってしまった。どう直す?

正解は作り直しです。公式に you can't change its target type と書かれています。3番目を選びたくなりますが、Fargateは awsvpc 固定で bridge を選べません（公式: Fargate tasks always use the awsvpc network mode）。つまりタスク側を曲げて合わせることはできず、ALB側を作り直すしかありません。リスナーがそのターゲットグループを指しているので、そこも同時に差し替えることになります。

ALBを立てる前に用意するもの（VPC・サブネット・AZ・証明書）
VPCとサブネット
VPCはAWS内に作る自分専用のネットワーク領域。サブネットはそれをさらに区切った小部屋です。Fargateのタスクは、この小部屋の中に置かれます。公式に you must specify one or more subnets to attach the network interface and one or more security groups とあり、サブネットとセキュリティグループの指定は必須です。セキュリティグループは「どこからどのポートの通信を通すか」を書いたルールの集まりで、これに書いていない通信は届きません。
アベイラビリティーゾーンは2つ以上
ALBの制約です。原文は You must select at least two Availability Zone subnets. かつ Each subnet must be from a different Availability Zone.。さらに各サブネットに /27 以上のCIDRブロックと、空きIPが8個以上あることを確認せよ、とも書かれています。/27 はサブネットの大きさの書き方で、IPアドレスを32個分まとめて持つ区画という意味です。「サブネットを1つしか作っていなくてALBが作れない」は、最初の30分で必ず踏みます。
HTTPSの証明書はどこに置くのか
コンテナの中ではなくALBのリスナーです。原文は You can use an HTTPS listener to offload the work of encryption and decryption to your load balancer、そして If the listener protocol is HTTPS, you must deploy at least one SSL server certificate on the listener.。アプリ側はHTTPのままで構いません。
そもそもALBは必須なのか
必須ではありません。公式は Your service can optionally be configured to use Elastic Load Balancing と書いています。ただし同じページで We recommend that you use Application Load Balancers とも書かれています。外からHTTPで受けるなら、実質ALBです。

タスク実行ロールとタスクロールは別物です（100%混同するところ）

Terraformの13件のうち2件がIAMでした。ECSには役割の違う権限が2つあります。名前が似ていて必ず混乱します。

名前誰が使うか何のため
タスク実行ロールECS/Fargateの裏方エージェントイメージの取得やログの書き出し。コンテナからは触れない
タスクロールコンテナの中のアプリ自身S3など他のAWSサービスを呼ぶため

公式の原文はこうです。実行ロールは grants the Amazon ECS container and Fargate agents permission to make AWS API calls on your behalf、そして they aren't directly accessible by the containers in the task。タスクロールは This role allows your application code (running in the container) to use other AWS services.

「アプリからS3が読めない」ときに実行ロールへ権限を足しても直りません。足す先はタスクロールです。IAM自体の地図は別記事にまとめています。

7EC2版との違いは「サーバーの面倒」だけではない

EC2版では登場人物が2人増える

EC2で動かす場合、クラスタにEC2インスタンスを登録します。その登録済みインスタンスには専用の名前があります。

Amazon ECS Developer Guide「EC2 container instances」— 原文
An Amazon ECS container instance is an
Amazon EC2 instance that run the
Amazon ECS container agent and is
registered to a cluster.
...
You are responsible for the container
instance management and maintenance.

（コンテナインスタンスとは、ECSの
　コンテナエージェントを動かし、
　クラスタに登録されたEC2のこと。/
　その管理と保守はあなたの責任）
  • コンテナインスタンス。クラスタに登録されたEC2のこと。Fargateには存在しません。
  • ECSコンテナエージェント。そのEC2の中で常駐し、ECS本体と通信してタスクを起動するプログラム。Fargateでは自分で用意しません。
  • 最後の1文が差分の全て。You are responsible for the container instance management and maintenance.
項目FargateEC2
サーバーの用意不要。CPUとメモリを書くだけ自分で用意し、管理と保守も自分（公式明記）
増える登場人物なしコンテナインスタンス／ECSコンテナエージェント
ネットワークモードawsvpc のみawsvpc / bridge / host / none。Linuxの既定は bridge
タスクのIPタスクごとにENIと専用IPbridge ならDockerの仮想ネットワーク経由
ALBのターゲットタイプip 必須（公式明記）この記事では未確認。公式で確認したのはFargate側の規定のみ
分離タスクごとに独立。カーネルもCPUもENIも共有しない同じEC2上のタスクは、そのEC2を共有する

カーネルとはOSの中核部分で、CPUやメモリの割り当てを実際に行っている層です。ここを共有しているかどうかが、隣のタスクの影響を受けるかどうかの分かれ目になります。

「タスクごとに独立」は公式の Each Fargate task has its own isolation boundary and does not share the underlying kernel, CPU resources, memory resources, or elastic network interface with another task. によります。

ポート番号が被る／被らない、という違いが生まれる理由

ネットワークモードの一覧に、違いがそのまま出ています。

  • awsvpc。原文は The task is allocated its own elastic network interface (ENI) and a primary private IPv4 or IPv6 address. タスクごとにIPが別なので、同じ80番を何個並べても衝突しません。
  • bridge。原文は The task uses Docker's built-in virtual network on Linux, which runs inside each Amazon EC2 instance that hosts the task. Linuxで何も指定しなければこれになります。
  • host。原文に Dynamic port mappings can’t be used in this network mode. とあります。動的ポートマッピング（EC2側の空きポートを自動で割り当てて中継する仕組み）が使えないので、1台のEC2に同じポートのタスクを2つ置けません。

つまりポートを取り合うのは host のときです。bridge で動的ポートマッピングを使えば衝突しません。「EC2版はポートが被る」と一般化はできません。

Fargateの側は、そもそもタスクごとにIPが別なので、この悩み自体が発生しません。ポート番号を決め打ちで書けます。

ディスクと料金（読めた範囲だけ）
保存はどうなるのか
Fargateのタスクには一時ディスク（エフェメラルストレージ）が付きます。原文は tasks that are hosted on Fargate using platform version 1.4.0 or later receive a minimum of 20 GiB of ephemeral storage、上限は up to a maximum of 200 GiB。注意点は The pulled, compressed, and the uncompressed container image for the task is stored on the ephemeral storage. — コンテナイメージ自体もこの20GiBに載ります。アプリが使える量は、その分減ります。
何に対して課金されるのか
公式の価格ページには You pay for the amount of vCPU, memory, and storage resources consumed とあります。インスタンスの台数ではなく、使った量です。
いくらか（筆者の計算。参考値）
同ページのサンプル計算の中に、US East（バージニア北部）/ Linux / X86 の単価が書かれています。vCPUが1秒あたり $0.000011244、メモリが1GBあたり1秒 $0.000001235（2026年8月15日参照）。ここから最小構成（0.25 vCPU / メモリ 512 MiB）を1時間動かすと $0.0123 になります（メモリは 0.5 GB として掛けました。512 MiB は厳密には約 0.537 GB です）。この掛け算は筆者が自分でやったもので、公式が提示している金額ではありません。東京リージョンの価格でもありません。ストレージ分は、無料枠の扱いを確認できなかったため含めていません。価格表そのものはページ内のJavaScriptで描画されるため取得できませんでした。実際の見積もりは公式の料金ページで確認してください。

8CloudFrontはALBの前。後ろではない

公式が番号付きで順路を書いています

CloudFrontはAWSのCDNです。世界各地の拠点（エッジロケーション、POP）にコンテンツを置いて、利用者から一番近いところから返します。

「ALBの前なのか後ろなのか」は、公式ドキュメントに手順として書かれています。

Amazon CloudFront Developer Guide「How CloudFront delivers content」— 原文
1. A user accesses your website ...
2. DNS routes the request to the
CloudFront POP (edge location) that
can best serve the request, typically
the nearest CloudFront POP in terms of
latency.
3. CloudFront checks its cache for the
requested object. If the object is in
the cache, CloudFront returns it to
the user. If the object is not in the
cache, CloudFront ... forwards the
request to your origin server
  • 答えは「前」。利用者 → DNS → CloudFrontのエッジ → （キャッシュに無いときだけ）オリジン、の順です。
  • オリジンとは、キャッシュが無いときに取りに行く元の場所。ここにALBを指定します。公式のオリジン一覧に an Application Load Balancer が入っています。
  • キャッシュに有れば、ALBまで来ません。ECSのタスクに届くリクエストは、その分減ります。

つまり全体の順路はこうです。利用者 → CloudFront → ALB → （ターゲットグループ）→ タスク。ECSのサービスはこの線上に居ません。タスクを名簿に登録する係として、横から関わります。

ALBをインターネットに出さない構成もあります

Amazon CloudFront Developer Guide「Use various origins」— 原文
If you have an Application Load
Balancer, Network Load Balancer, or
EC2 instance in a private subnet, you
can use it as a VPC origin. With VPC
origins, your applications can be
accessed only in a private subnet with
a CloudFront distribution, which
prevents your application from being
accessible on the public internet.
  • VPCオリジンを使うと、ALBをプライベートサブネットに置けます。インターネットからは直接叩けず、CloudFront経由でのみ届きます。
  • CloudFrontは内部向けALBにも外部向けALBにもルーティングできます。公式に both internal and internet-facing Application Load Balancers とあります。
  • ディストリビューションとは、CloudFrontの設定一式のこと。「どのオリジンに、どう転送するか」をここで定義します。

この構成は、クライアント側の会社とインフラ側の会社で担当が分かれているとき、「どこに何を設定してもらうか」の境界にもなります。キャッシュとレスポンスヘッダーはCloudFront、証明書とパス振り分けはALB、アプリの挙動はECSのタスク。依頼先が変わります。

9最初の1つを作る順番

依存の向きが決まっているので、順番は選べません

サービスはタスク定義とターゲットグループを指します。ターゲットグループはVPCを指します。指される側から先に作ります。

  • ① VPCとサブネットを2つ以上（別AZ）。ALBの制約です。公式に You must select at least two Availability Zone subnets. とあるので、1つしか無いとALBを作る段階で足りません。
  • ② コンテナイメージを置く場所を決める。ECR（AWS版のイメージ置き場）など。タスク定義はイメージのURLを書くだけなので、先に要ります。
  • ③ クラスタを作る。名前だけです。2章で見たとおり、雛形にサーバーの指定はありません。
  • ④ タスク定義を登録する。Fargateなら awsvpc、CPUとメモリは決まった組み合わせから選ぶ。実行ロールも指定します。
  • ⑤ ターゲットグループを ip で作る。ここを間違えると作り直しです。作成後は変更できません。
  • ⑥ ALBとリスナーを作り、⑤へ向ける。HTTPSにするなら証明書はリスナーに置きます。
  • ⑦ サービスを作る。タスク定義・ターゲットグループ・コンテナ名・ポート・サブネット・セキュリティグループを全部ここで結びます。

この順番は筆者が依存関係から組み立てた手順で、公式が「この順で作れ」と書いているわけではありません。実際に作って通したわけでもありません（AWSアカウントが無いため）。依存の向きだけは、上で見た各ドキュメントの記述どおりです。
