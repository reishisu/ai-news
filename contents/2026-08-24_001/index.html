できることはSlack版とほぼ同じです。Teams のチャネル・スレッド・DMで @GitHub にメンションすると、Copilot のクラウドエージェントのセッションが始まります。会話にいる人は誰でも質問や文脈を足せて、リポジトリの書き込み権限がある人だけが実際の変更を走らせられます。

課金のところが一番大事なので、原文を出します。

The public preview is available with paid GitHub Copilot plans.
GitHub Copilot cloud agent sessions started in Microsoft Teams
consume AI credits. For organizations, cloud agent AI credit usage
is governed by usage-based billing budgets. Cloud sandbox usage is

承認を足したときの挙動（原文）
If you require two approvals in a repository, with this enabled

Chrome for Developers

Chrome 153 で Related Website Sets が消える — Android WebView も同じ153で消える

8/20 告知 9/8 から 削除

同じ Chrome 153 の「Deprecations and removals」に、削除が3件並んでいます。読者に関わるのは次の2件です。Related Website Sets（RWS）と、それに紐づく document.requestStorageAccessFor() です（残る1件は、非標準だった _current 宛てのナビゲーションの削除）。

RWS は、別々のドメインを「同じ運営のサイト群」として宣言し、その中でだけCookieを共有できるようにする仕組みでした。

削除の理由（Chrome 153 beta の原文）
RWS was designed for use in a browser without third-party cookies.
Following Chrome's announcement that the current approach to
third-party cookies will be maintained, Related Website Sets is
now removed from Chrome.

つまり「サードパーティCookieを廃止する前提で作った仕組みだが、廃止しないことにしたので要らなくなった」という筋です。サードパーティCookie自体は残ります。

重要なのは対象の範囲です。ChromeStatus の削除予定を見ると、desktop・android・webview がすべて 153 で、WebViewも同時に落ちます。

ChromeStatus の削除マイルストーンを引く
$ curl -s https://chromestatus.com/api/v0/features/5194473869017088 | tail -c +6   | python3 -c "..."
name: Deprecate and Remove:
      Related Website Sets (RWS)
desktop=153 android=153 webview=153
「status が Proposed のままだが、確定として書いてよいのか」

ChromeStatus の status.text は、この2件ともいまだ Proposed です。字面だけ見ると未確定に読めます。

それでも確定扱いにしたのは、(1) 種別が「機能の削除」で、削除先のマイルストーンが desktop / android / webview すべてに 153 と入っていること、(2) ベータ告知の本文が is now removed from Chrome と現在形で断定していることの2つが揃っているためです。この判断は当方のもので、Google が「確定」と表示しているわけではありません。

同じ153では、XMLの解析エンジンがRust実装に変わる変更も入ります（DOMParser、XMLHttpRequest の responseXML、単体SVG画像などが対象）。こちらは互換性を保ったままの置き換えなので、原則として対応は不要です。

  • 今やること。まず該当するかだけ調べる。コードを requestStorageAccessFor で検索して、1件も出なければ対応は不要です。出たなら、9月8日までに別の方法へ移すか、影響範囲を洗い出しておくこと。RWSの登録をしている配信ドメインがある場合も同じです。WebView内でXMLを解析している画面があるなら、9月8日以降に1度だけ動作確認を。

Google Play「Target API level requirements」の原文

New apps and app updates must target Android 16 (API level 36)

DeepSeek APIに画像を読むモデルが増えた — モデル名を変えるだけで使える

8/21 前号の回収 実験モデル DeepSeek

DeepSeek の API に deepseek-v4-flash-vision-exp が追加されました。スクリーンショットの文字を読ませる、グラフを読み取らせる、といった使い方ができます。

導入の手間はほぼありません。モデル名の文字列を差し替えるだけです。

DeepSeek 公式 Change Log（2026-08-21）の原文
Today, the new multimodal vision understanding model
DeepSeek-V4-Flash-Vision-Exp is now available on the DeepSeek API
platform. This is an experimental model that can be accessed by
setting model='deepseek-v4-flash-vision-exp'.

気になるのは「画像対応にした分、文章が弱くなっていないか」ですが、公式はそこを否定しています。

テキスト性能について（原文）
In terms of pure-text capabilities (agent, reasoning, world
knowledge, etc.), DeepSeek-V4-Flash-Vision-Exp is on par with the
official DeepSeek-V4-Flash.

画像の渡し方は3通りで、それぞれ上限が決まっています。実装前に見ておく値はここです。

対応している画像の形式は JPEG / PNG / GIF / WebP です。公式は「拡張子や宣言されたMIMEタイプではなく、ファイルの中身から判定する」と書いています。拡張子を付け替えただけのファイルは通りません。

公式が併記しているベンチマークの数値と、その注意書き

Change Log には次の数値が並んでいます（原文のまま）: Terminal Bench 2.1: 83.9 / NL2Repo: 57.7 / DeepSWE: 59.3 / DSBench-Hard: 63.6 / AutomationBench (Public): 25.7 / ApexBench (Pass@1): 36.5 / Agents' Last Exam: 27.3 / Chartography: 64.3 / ZeroBench (Pass@5): 35.0。

ただし同じページの脚注が、比較条件が対等でないことを明かしています。原文は in the ApexBench and Agents' Last Exam evaluations, the text model DeepSeek-V4-Flash ignores the multimodal elements within them です。つまりこの2つは、比較相手のテキストモデルが問題文中の画像を見ないまま解いた結果と並べられています。差が大きく見えて当然なので、そのまま「性能が上がった」と読まないでください。

  • 今やること。DeepSeek を使っていないなら対応は不要。使っていて、図やスクリーンショットを読ませたい用途があるなら、モデル名を差し替えて試すところまではすぐできる。ただし末尾が -exp の実験モデルなので、本番に載せるかは別の判断として残すこと。オープンウェイトの公開はなく、API限定です。
