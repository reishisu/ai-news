Claude Codeの自動化 — 無人で走らせると「成功」して何もしないことがある

「Claude Code を毎朝 cron で回したい」——その一歩目でだいたい踏む穴を、実際に踏んでから直しました。権限が要る操作は、黙って飛ばされます。終了コードは 0、JSONの is_error も false です。この記事のログはすべて Claude Code 2.1.251 での実測で、加工していません。
▶ この記事を動画で見る（11分）ずんだもん×四国めたんの掛け合い・実演つきの解説
⏱ 直すのは旗を1つ足すだけ・約1分 全部コピペOK 追加インストール不要

⭐ 3行で言うと

  1. claude -p は、権限が要る操作を実行しないまま「成功」で終わります。ファイルを作らせる命令を出したのに、ファイルは出来ず、終了コードは 0 でした。cron のログには何も残りません。
  2. 直し方は --allowedTools で道具を名指しすること。--allowedTools Write を足しただけで、同じ命令が通りました。Bash(git status:*) のようにコマンド単位でも渡せます。
  3. ただし「やったか」を CLI の自己申告で判定してはいけません。唯一の手がかりに見えた permission_denials は、同じ命令を3回叩くと 0・2・0 と揺れました。結果そのものを自分で確かめるしかありません。
先に5語だけ意味
  • ヘッドレス / 非対話 — 人が画面に付かずに動かすこと。-p がその旗
  • 終了コード — コマンドが終わるときに残す数字。0が成功、それ以外が失敗の合図
  • ツール（道具） — Claude がファイルを書く・コマンドを打つといった、外に手を出す機能
  • 権限（パーミッション） — その道具を使ってよいかの許可。対話画面では人がその都度押している
  • cron — 決まった時刻にコマンドを自動で走らせる、Linux の標準の仕組み

1ファイルを作らせたのに、出来ていなかった

まず、いちばん素朴な使い方から始めます。-p（--print）を付けると、Claude Code は対話画面を開かずに、答えを標準出力に吐いて終わります。パイプに繋げる形です。

計算させるだけなら、何も要らない
claude -p "1+1は？数字だけ"
段2 の実出力
2
exit=0

ここまでは期待どおりです。では、ファイルを1つ作らせてみます。自動化でやりたいのは、たいていこちら側です。

同じ形で、書き込みを頼む
claude -p "hello.txt を作り中身を hi に"
段3 の実出力
exit=0
--- 応答 ---
ファイル書き込みの許可が必要なようです
--- 出来たファイル ---
(hello.txt は無い)

Claude は「許可が要る」と言い、そこで終わりました。ファイルは1つも出来ていません。それでも終了コードは 0 です。

対話画面なら、ここで「許可しますか？」と聞かれて人が押します。無人だと、押す人がいません。押されないまま、Claude は「できませんでした」と丁寧に報告して正常終了します。

cron に置いた場合、ログに残るのは終了コードだけです。0 が返っているので、監視の仕組みは何も鳴りません。毎朝そのまま、何もしない仕事が走り続けます。

2終了コードも is_error も、成功と言っている

「終了コードが雑なだけで、機械が読む形式なら分かるのでは」と考えるのが自然です。--output-format json を付けると、結果が1つのJSONで返ります。

JSONで受け取る
claude -p "hello.txt を作り中身を hi に" \
  --output-format json
段4 の実出力（権限を渡していない側）
exit=0
is_error       False
subtype        success
num_turns      2
permission_denials ['Write']
total_cost_usd 0.0178

is_error は False。subtype は success。JSONも「成功」と言っています。

同じ命令に許可を渡して成功させた側（次章）と並べると、違いは1か所しかありませんでした。

見る場所やれたやれていない
終了コード00
is_errorfalsefalse
subtypesuccesssuccess
permission_denials[ ]['Write']
料金$0.0186$0.0178

permission_denials だけが違います。拒否された道具の名前と、渡そうとしていた引数がそのまま入っていました。

permission_denials の中身（段4 と同じ実行のもの）
[{"tool_name": "Write",
  "tool_use_id": "toolu_018bAx...",
  "tool_input": {"file_path": ".../hello.txt",
                 "content": "hi"}}]

もう1つ、地味に効く事実があります。料金はほとんど変わりません。何もしなかった側が $0.0178、やり遂げた側が $0.0186 でした。空振りにも、ほぼ同じだけ払っています。

前章で見た JSON には、実際どれだけ入っているのか。1回叩いて全部並べました。

26個あります。ただし自動化で読む必要があるのは、多くありません。

キー何に使うか

残りは所要時間（duration_ms）、トークンの内訳（usage / modelUsage）、内部の事情（warm_spare_claimed など）です。監視に載せるなら、上の4つで足ります。

この一覧は 2026年8月30日 の 2.1.251 で採ったものです。版が上がれば増減します。キーの有無に依存する処理を書くなら、.get() のように無くても落ちない読み方にしてください。

なお result は文章です。数字だけを頼んでも、説明が混ざることがあります。数値として扱うなら、受け取ってから検証する1行を必ず挟んでください。

4直し方その1 — 使う道具を名指しする

直し方は単純です。--allowedTools に、使わせたい道具の名前を渡します。

Write だけを許可する
claude -p "hello.txt を作り中身を hi に" \
  --allowedTools Write \
  --output-format json
段5 の実出力
exit=0
is_error       False
permission_denials []
total_cost_usd 0.0186
--- hello.txt の中身 ---
hi

旗を1つ足しただけで通りました。命令文は1文字も変えていません。permission_denials も空になっています。

道具の名前は、対話画面で見かけるものと同じです。Read（読む）、Write（新規に書く）、Edit（既存を書き換える）、Bash（コマンドを打つ）、Glob・Grep（探す）など。スペースかカンマで区切って複数渡せます。

よく使う組み合わせ
# 書き換えと検索まで許す
--allowedTools Read Edit Write Grep Glob

逆に、渡さなかった道具は使われません。ここが自動化では効きます。「読ませるだけの仕事」なら Write を渡さなければ、書き換える事故が構造的に起きません。

なお --disallowedTools という逆向きの旗もあります（--help に記載）。ただし今回は使っていないので、挙動は測っていません。

5直し方その2 — --permission-mode で束ねて渡す

道具を1つずつ挙げるのが面倒なときは、--permission-mode でまとめて態度を決められます。

編集を許す姿勢にする
claude -p "hello.txt を作り中身を hi に" \
  --permission-mode acceptEdits \
  --output-format json
段6 の実出力
exit=0
is_error       False
permission_denials []
--- hello.txt ---
hi

こちらも通りました。--allowedTools Write と同じ結果です。

選べる語は --help に列挙されています。原文はこうです。

claude --help より（原文）
--permission-mode <mode>  Permission mode to use for the
session (choices: "acceptEdits", "auto",
"bypassPermissions", "manual", "dontAsk", "plan")

この6語のうち、実際に動かしたのは acceptEdits だけです。残り5つの挙動は測っていないので、この記事では書きません。名前から想像して書くと、それは実測ではなくなります。

1つだけ注意を書いておきます。bypassPermissions（および --dangerously-skip-permissions）は、名前のとおり確認を全部飛ばす旗です。--help には 「Recommended only for sandboxes with no internet access」（ネットに繋がっていないサンドボックス向け）と書かれています。自分の作業マシンの cron で常用する旗ではありません。

どちらを使うかの目安は、仕事の幅です。やることが決まっているなら --allowedTools で狭く。ファイル編集を広く任せる前提の仕事なら acceptEdits。これは規格ではなく、今回の実測を踏まえた運用上の目安です。

6Bash は丸ごとでなく、コマンド単位で渡せる

--allowedTools Bash と書くと、あらゆるコマンドが打てるようになります。無人で走らせる場所では、これは広すぎます。

丸括弧を付けると、コマンドを絞れます。

git status だけを許す
claude -p "git status を実行し1行目だけ答えて" \
  --allowedTools "Bash(git status:*)" \
  --output-format json
段8 の実出力
exit=0
permission_denials []
result         On branch master

許可したコマンドは通りました。:* は「そのあとに何が続いてもよい」という書き方です。--help の例示にも "Bash(git *) Edit" の形が載っています。

では、許可していないコマンドを頼むとどうなるか。同じ許可リストのまま、ファイルを消すよう頼みました。

段9b の実出力（3回）
1回目 exit=0 denials=1 f.txt=のこる
2回目 exit=0 denials=2 f.txt=のこる
3回目 exit=0 denials=5 f.txt=のこる

3回とも、ファイルは残りました。絞り込みは効いています。

対照実験として、rm のほうを許可した場合も測りました。

段9a の実出力（3回）
1回目 exit=0 denials=0 f.txt=きえた
2回目 exit=0 denials=0 f.txt=きえた
3回目 exit=0 denials=0 f.txt=きえた

許可すれば3回とも消えました。つまり「消えなかった」のは、この環境がたまたま rm を禁じているからではなく、許可リストが効いた結果です。

これは念のための確認ではありません。段9b で Claude 自身が返した説明は、こうでした。

段9b の応答の一例
パスは作業ディレクトリと一致していますが、
サンドボックスのセキュリティ制限で

Claude は「サンドボックスの制限」のせいだと説明しています。しかし段9a で同じ rm が動いている以上、この説明は正確ではありません。止まった理由についての自己申告も、鵜呑みにはできません。

7本物のエラーなら、終了コードは 1 になる

ここまで読むと「終了コードは当てにならない」と思えますが、それは言い過ぎでした。本物の異常では、ちゃんと 1 が返ります。

まず、存在しないモデル名を渡してみます。

綴りを間違える
claude -p "1+1" --model no-such-model-xyz
段7a の実出力
exit=1
There's an issue with the selected mod

次に、ターン数の上限で打ち切らせます。--max-turns は、Claude が道具を使って考え直せる回数の上限です。

3つ作らせるのに、1ターンしか与えない
claude -p "a.txt と b.txt と c.txt を順に作って" \
  --allowedTools Write --max-turns 1 \
  --output-format json
段7b の実出力
exit=1
is_error       True
subtype        error_max_turns
terminal_reason max_turns

is_error が True、subtype に理由が入りました。ここは素直です。

つまり境界はこうなっています。「動かして失敗した」は 1 になり、「そもそもやらなかった」は 0 のままです。後者は Claude にとってエラーではなく、指示に従って確認を求めただけだからです。

なお段7b では、--allowedTools Write を渡していたのにファイルは1つも出来ませんでした。途中まで作って止まる、という形ではありません。中途半端な成果物が残ることを心配していたなら、この回に関してはその心配は要りませんでした。

8許可の外を頼んだときの記録は、揺れる

第2章の結論は「permission_denials を見ればよい」でした。それを検算したら、崩れました。

第6章の段9b とまったく同じ許可リスト・まったく同じ目的で、命令の文面だけを変えて3回叩きます。「f.txt を rm で消して」を「rm -rf f.txt を実行して」にしただけです。

段9c の実出力（3回）
1回目 exit=0 denials=0 f.txt=のこる
2回目 exit=0 denials=2 f.txt=のこる
3回目 exit=0 denials=0 f.txt=のこる

3回のうち2回、permission_denials は空でした。それでいて、ファイルは3回とも残っています。やっていないのに、拒否の記録も残っていない。

理由は、探りの段階で1度見えていました。Claude が道具を呼ばずに、文章で聞き返して終わることがあるのです。

探りの段階で観測した応答
f.txt はGit管理外の2バイトのファイルです。
削除してよろしいですか?(この操作は元に戻せません)

道具を呼んでいないので、拒否も発生しません。記録は空のままです。そして無人なので、誰も答えません。

段9b では denials が 1・2・5 と散らばり、段9c では 0・2・0 でした。同じ穴を狙っても、返り方は毎回違います。回数が揺れるのは、Claude が言い方を変えて何度か試すことがあるためです。

ここから言えることは1つです。permission_denials は「出ていたら確実に失敗」と言える材料ですが、「出ていないから成功した」とは言えません。片側にしか使えない検査です。

9止まる場所を、先に決めておく

無人で回すときに、もう1つ怖いのは逆方向です。止まらずに走り続けて、請求だけが伸びること。

上限は2種類あります。回数で止める --max-turns（第7章）と、金額で止める --max-budget-usd です。

極端に低い上限を置いてみる
claude -p "1から100までの素数を全部数えて説明して" \
  --max-budget-usd 0.001 \
  --output-format json
段10 の実出力
exit=1
is_error       True
subtype        error_max_budget_usd
total_cost_usd 0.0143

きちんと exit=1 で止まり、理由も入りました。ここは検出できます。

ただし数字をよく見てください。上限は $0.001 なのに、止まった時点の集計は $0.0143 です。14倍あります。

これは「使い切ったら次を始めない」型の上限であって、途中で切り上げる仕組みではありません。1回のやりとりが上限より高ければ、超えてから気づいて止まります。厳密な上限として設計してはいけません。

実運用では、桁で効かせるのが現実的です。1回 $0.05 前後の仕事なら、上限は $1 のように「事故のときだけ効く」高さに置く。これは規格ではなく、今回の実測からの目安です。

なお、時間で止めたい場合は Claude Code 側の旗ではなく、OS の timeout を被せるのが確実です（この記事では測っていません）。

10材料は標準入力から渡す

自動化では、その場で採れたデータを読ませたい場面がほとんどです。命令文に埋め込まなくても、パイプで流し込めます。

ログを流して数えさせる
cat log.txt | claude -p "ERRORの行数を数字だけで"
段11 の実出力（log.txt は ERROR 2行・INFO 1行）
2
exit=0

正しく 2 が返りました。数字だけを返させれば、その先の処理にそのまま渡せます。

この形が効くのは、読むだけの仕事だからです。第4章の話と繋がります。集計・要約・分類は Write を渡す必要がありません。渡さなければ、書き換え事故が起きようがない。

出力を機械で受けるなら、--output-format json にして result を取り出すほうが安全です。文章が混ざったときに、そのまま数値として扱ってしまう事故を防げます。

結果だけを取り出す
cat log.txt | claude -p "ERRORの行数を数字だけで" \
  --output-format json \
  | python3 -c "import json,sys; \
print(json.load(sys.stdin)['result'])"

なお --json-schema で出力の形を指定する旗も --help にありますが、今回は使っていません。

11前半と後半に割って、続きから走らせる

長い仕事を1回のコマンドに押し込むと、途中で落ちたときに全部やり直しになります。分けて走らせて、文脈だけ引き継げます。

やり方は、自分で作った ID を渡しておいて、次のプロセスでその ID を指すだけです。

IDを決めて、2本に分ける
SID=$(python3 -c "import uuid;print(uuid.uuid4())")

claude -p "合言葉は「みかん」。覚えて" \
  --session-id "$SID"

claude -p "合言葉を1語だけ答えて" --resume "$SID"
段12 の実出力
session-id = 446a4a98-fff0...
1本目 exit=0
みかん
2本目 exit=0

別のプロセスから聞き直しても、前半の内容を覚えていました。--session-id には UUID の形が要ります（上のように生成すれば確実です）。

直前の会話でよければ、ID を管理せずに --continue（-c）でも繋がります。ただし「そのディレクトリの最後の会話」を指すので、同じ場所で2本を並行させると取り違えます。自動化では ID を明示するほうが安全です。

これは節約にもなります。前半で読み込んだ内容は、後半でもう一度読ませる必要がありません。第2章で見たとおり、料金はやった仕事の量ではなく、やりとりの量で決まります。

12無人で置くときの4点

ここまでの実測を、そのまま手順にまとめます。

  • 1. 道具を名指しする。--allowedTools に必要な最小限だけ渡す。読むだけの仕事に Write を渡さない
  • 2. 上限を置く。--max-turns と --max-budget-usd。ただし金額は厳密な天井ではないので、桁で余裕を持たせる
  • 3. JSONで受ける。--output-format json にして permission_denials が空でないかを見る。空でなければ確実に失敗している
  • 4. 結果そのものを確かめる。ファイルが出来たか、commit が載ったか。ここだけは CLI に任せられない

形にすると、こうなります。4番目が入っているかどうかが、この記事の要点です。

cron に置く最小の形
#!/usr/bin/env bash
set -euo pipefail
OUT=/var/log/cc/$(date +%F).json

claude -p "$(cat prompt.txt)" \
  --allowedTools Read Write Edit \
  --max-turns 20 \
  --max-budget-usd 1 \
  --output-format json > "$OUT"

# 拒否が記録されていたら失敗として扱う
python3 - "$OUT" <<'PY'
import json, sys
d = json.load(open(sys.argv[1]))
ng = d["permission_denials"]
if ng:
    n = [x["tool_name"] for x in ng]
    sys.exit("拒否: " + ",".join(n))
PY

# 出来たはずのものを、自分で確かめる
if [ ! -s report.md ]; then
  echo "report.md が無い"
  exit 1
fi

最後の test -s の1行が、第8章で見た「記録が空のまま何もしていない」型を捕まえます。この行が無いと、3回に2回は素通りします。

このスクリプト自体は cron で長期運用していません。上の各旗の挙動は測っていますが、組み合わせた状態での連続運用は確かめていないことを書き添えておきます。
