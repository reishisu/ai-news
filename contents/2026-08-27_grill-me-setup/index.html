1何をするスキルなのか — 本体は7行しかない

「作って」の前に、決めていないことを全部聞かせる道具

AIに指示を出すと、こちらが決めていないところを勝手に決めて作り始めます。あとで見て「そうじゃない」となる原因はここです。

grill-me は、その前にAIのほうから質問させるスキルです。Matt Pocock 氏が公開している "Skills For Real Engineers" に入っています。

日本語の「グリル」は焼き網ですが、英語の動詞 grill は「厳しく問い詰める」という意味でも使います。取り調べのニュアンスです。

  • grill-me — 質問させるだけ。ファイルは何も書かれません。リポジトリの外でも使えます。
  • grill-with-docs — 同じ質問に加えて、決まった用語を CONTEXT.md、決まった設計を docs/adr/ に書き残します。

中身を開くと拍子抜けします。本文は1行

この2つの SKILL.md は、フロントマターを除くと本文が1行しかありません。実物がこれです。

skills/productivity/grill-me/SKILL.md（全文）
---
name: grill-me
description: A relentless interview to sharpen a plan or design.
disable-model-invocation: true
---

Call the Skill tool with "grilling".
skills/engineering/grill-with-docs/SKILL.md（全文）
---
name: grill-with-docs
description: A relentless interview to sharpen a plan or design, which also creates docs (ADR's and glossary) as we go.
disable-model-invocation: true
---

Call the Skill tool twice, for "grilling" and "domain-modeling".

つまりこの2つは入口だけで、実体は grilling と domain-modeling という別のスキルにあります。この構造が、あとで出てくる「静かに壊れる」の原因です。

なぜこんな分け方をしているのか

呼ぶ側と中身を分けておくと、中身のほうを他のスキルからも使い回せます。実際 grilling は、この作者の別のスキル（triage・wayfinder など）からも呼ばれています。

また grill-me 側には disable-model-invocation: true が付いています。人が打ったときだけ動くという指定で、AIが勝手に取り調べを始めないようにしてあります。実体側の grilling には付いていないので、AIから呼べます。

動くとこういうものが返ってきます

実体の grilling には、返し方の型まで書かれています。番号を振って、それぞれに推奨案を添えろという指定です。

grilling/SKILL.md に書かれている出力の型（原文）
Ask the whole frontier in one round: number each question and give your recommended answer. Then wait for the user's answers before the next round.

この環境で実際に「社内の問い合わせ管理を作りたい」と投げたら、こう返ってきました。

実際の返答（5問中の1問目。無加工）
❓ **Q1** - **対象範囲**: 「社内問い合わせ」とは何を
指しますか？IT/総務/人事など特定部門向けの問い合わせ
窓口ですか、それとも部門を問わない全社共通の何でも
受け付ける窓口ですか？

➡️ まずは「全社共通・カテゴリ分けあり（IT/総務/人事
など）」で、各カテゴリに担当者/担当チームを割り当てる
形を推奨します（後から部門追加しやすい設計にする）。

この ❓ **Q1** と ➡️ の形が出れば、セットアップは成功しています。後半の確認手順はこれを使います。

2入れ方は2通り。どちらか片方だけにする

両方やると同じスキルが二重に入ります

公式READMEには入れ方が2通り書かれています。そして片方だけにしろと明記されています。

README「Installation」の原文
Pick one: installing both leaves you with every skill twice.

性格がまったく違うので、先に選んでください。この環境で両方を実測した数字が下の表です。

選ぶ基準A: プラグインB: skills CLI
入るもの 25スキル全部 選んだものだけ
置かれる場所 自分の環境（共通） プロジェクトの中
中身を書き換えられるか できない（読み取り専用） できる（ただのファイル）
更新 作者が出すと自動で届く 自分で skills update
かかった時間 11秒 2秒
ディスク 39MB 40KB（2スキル）
  • とりあえず試すならA。25個まとめて入り、飽きたら1コマンドで消せます。
  • チームのリポジトリに入れるならB。ファイルがリポジトリに入るので、コミットすれば全員に配れます。日本語に書き換えることもできます。

3経路A: プラグインで入れる（ここで詰まる）

READMEどおりに叩くと失敗しました

READMEには、そのまま入れられると書かれています。

README「Claude Code」の原文
It's in Claude Code's official marketplace, so there's nothing to add first, and updates arrive automatically.

この記述は間違っていません。公式マーケットプレイスの中身を数えたら、289個のプラグインがあり、mattpocock-skills は確かに入っていました。

それでも、この環境では失敗しました。

実際の出力（長い行は fold で折り返し）
$ claude plugin install mattpocock-skills
Installing plugin
"mattpocock-skills"...× Failed to
install plugin "mattpocock-skills":
Plugin "mattpocock-skills" not found in

「どのマーケットプレイスにも見つからない」。お店が1軒も登録されていない状態でした。

原因は公式ドキュメントに書いてありました

公式マーケットプレイスが登録されるのは、対話画面で1回起動したときです。

公式ドキュメント「Create plugins」の原文
Claude Code registers it automatically the first time you start Claude Code interactively. If you run Claude Code non-interactively before that first interactive launch, or a marketplace policy blocked an earlier attempt, register it yourself with `claude plugin marketplace add anthropics/claude-plugins-official`.

つまり、claude をコマンドとしてしか使っていない環境（CI、コンテナ、この検証環境）では登録されません。会社のルールで止められている場合も同じです。

対処は1行です。登録してから入れ直せば通ります。

この2行で入る
claude plugin marketplace add \
  anthropics/claude-plugins-official
claude plugin install mattpocock-skills
実際の出力（長い行は fold で折り返し）

claude-plugins-official (declared in
user settings)
$ claude plugin install mattpocock-skills

"mattpocock-skills"...√ Successfully

mattpocock-skills@claude-plugins-officia
l (scope: user)

すでに対話画面で使っている人は、1行目は要りません。打っても害はなく、登録済みならそう言われるだけです。

入ったかを見る。ついでに常駐コストも分かります

claude plugin list で一覧、claude plugin details で中身が出ます。

実際の出力（折り返しなし）

    Version: 1.2.3
    Scope: user

4経路B: skills CLIで入れる（ここで壊れる）

コマンドは1行。ただし選ぶ画面が出ます

こちらは npx で動く別のツールです。プロジェクトのフォルダに移動してから叩きます。

対話で選ぶ場合
npx skills@latest add mattpocock/skills

37個のスキルが一覧で出るので、矢印キーで選びます。選ばなかったものは入りません。ここが落とし穴です。

選ぶものが決まっているなら、引数で渡せば画面は出ません。

grill-me を使う場合（これが正解）
npx skills@latest add mattpocock/skills \
  --skill grill-me grilling \
  --agent claude-code -y
grill-with-docs を使う場合
npx skills@latest add mattpocock/skills \
  --skill grill-with-docs grilling domain-modeling \
  --agent claude-code -y

grill-me だけ選ぶと壊れます

1節で見たとおり、grill-me の本文は「grilling を呼べ」の1行です。呼ばれる側を入れ忘れると、そこで切れます。

実際に grill-me だけ入れて叩いた結果がこれです。

grill-me だけ入れた状態（実際のエラー）
$ claude -p "/grill-me 社内の問い合わせ管理を作りたい"
<tool_use_error>Unknown skill:
grilling</tool_use_error>

このあとAIは自分でファイルを読みにいき、こう報告してきました。

そのときの返答（抜粋・無加工）
その `SKILL.md` の中身は「'grilling' という名前の
スキルを呼び出せ」と書かれているのですが、そのような
スキルは登録されていません。つまりこのプロジェクトの
`/grill-me` コマンドは壊れている状態です。

エラーで止まらず、それらしく会話が続いてしまうのが厄介なところです。気づかないまま「なんか普通の返事だな」で終わります。

Q. grill-with-docs を skills CLI で使うとき、一緒に入れるべきものは?

2つです。grill-with-docs の本文は Call the Skill tool twice, for "grilling" and "domain-modeling". なので、片方でも欠けるとそこで切れます。用語集とADRを書くのは domain-modeling のほうなので、これを落とすと「質問はされるが何も残らない」状態になります。

プラグイン（経路A）にはこの問題がありません。25個まとめて入るので、呼ばれる側も必ず入っています。迷うならAです。

5セットアップ完了の確かめ方

3つの状態で、返ってくるものが違います

画面を開かずに確かめられます。-p を付けると対話画面なしで1往復だけ実行できるので、これで判定します。

確認用のコマンド（プロジェクトの中で叩く）
claude -p "/grill-me 動作確認"

返ってくるものが、状態によってはっきり違います。同じ入力を4つの状態で1回ずつ叩いた実測です。

状態返ってくるもの判定
何も入れていない Unknown command: /grill-me 未導入
grill-me だけ Unknown skill: grilling のあと、普通の会話 壊れている
実体も入れた ❓ **Q1** と ➡️ が並ぶ 完了
プラグイン 同上（呼ばれる名前に mattpocock-skills: が付く） 完了

どのスキルが動いたかを機械で数える

返答の見た目だけだと、本当にスキルが動いたのか、AIが空気を読んだだけなのかが分かりません。記録で確かめられます。

--output-format stream-json を足すと、途中で使った道具が1行ずつJSONで出ます。

呼ばれたスキルだけ抜き出す
claude -p "/grill-me 動作確認" \
  --output-format stream-json --verbose \
  > v.json
grep -o '"skill":"[^"]*"' v.json | sort -u
プラグインで入れた場合の実出力
"skill":"mattpocock-skills:grilling"
  • プラグイン経由だと名前に接頭辞が付きます。プラグイン名:スキル名 の形で、他のスキルと名前がぶつからないようにするためです。
  • 何も出なければ動いていません。返答が自然でも、それはスキルの中身を使っていない普通の返事です。

6通しでやる — 用語集とADRができるまで

お題: 社内ヘルプデスクに「クローズ」を足す

grill-with-docs が本当にファイルを書くのかを、最後まで通して確かめました。用意したのは15行のリポジトリです。

app/Ticket.php（用意したもの）
<?php
class Ticket {
    public string $status;   // open / closed
    public int $userId;      // 問い合わせた人
    public ?int $ownerId;    // 担当者
    public function close(): void {
        $this->status = 'closed';
    }
}

ここで /grill-with-docs 問い合わせを「クローズ」できるようにしたい と投げます。

3往復かかりました。書き始めるのは最後です

実際に流した3ラウンドの記録です。質問が尽きるまでファイルは1つも書かれません。

ラウンド動いたスキル書かれたファイル
1
お題を渡す		 grilling なし（Q1〜Q3）
2
3問に回答		 （続き） なし（Q4〜Q8）
3
残りに回答		 domain-modeling CONTEXT.md
docs/adr/0001-….md

2ラウンド目までで止めていたら、ドキュメントは1文字も残りませんでした。途中で満足して離脱しないでください。

3ラウンド目に「これで認識は揃いました」と伝えたところで domain-modeling が動きました。

できたもの — 用語集

こちらが「userId は紛らわしいので依頼者と呼びたい」と言ったことが、そのまま用語として残りました。

CONTEXT.md（実際にできたものから抜粋）
## クローズ (Close)

Ticket を open から closed にする操作。

- 実行できるのは、その Ticket の担当者のみ。
  依頼者や他のスタッフは実行できない。
- 担当者が未アサインの Ticket はクローズできない。
- 既に closed の Ticket を再度クローズしようとする
  操作は無効であり、エラーとして扱われる。

これは仕様書ではなく用語集です。実装の話を書かないよう、スキル側で釘が刺されています。

domain-modeling/SKILL.md の指定（原文）
`CONTEXT.md` should be totally devoid of implementation details. Do not treat `CONTEXT.md` as a spec, a scratch pad, or a repository for implementation decisions. It is a glossary and nothing else.

できたもの — ADR（なぜそうしたかの記録）

ADRは Architecture Decision Record の略で、「なぜこの作りにしたか」を1件1ファイルで残す書き方です。半年後の自分が読む用のメモだと思ってください。

docs/adr/0001-… （実際にできたものから抜粋）
## Decision

`Ticket` の `close` / `reopen` は実行者のIDを引数として
受け取り、`Ticket` 自身が担当者と一致するかを判定する。
認可チェックは呼び出し側が済ませてある前提を置かない。

## Consequences

- `close` / `reopen` を呼び出す経路がどこであっても、
  認可チェックを迂回できない。
- 将来、認可ルールが変わる場合、`Ticket` のメソッド
  シグネチャや内部ロジックの変更が必要になる。

何でもADRにされると邪魔なので、条件が3つ指定されています。3つ全部そろったときだけ書きます。

  • 取り返しがつかない。あとで変える費用が大きいもの。
  • 説明なしだと不思議に見える。将来の読み手が「なぜ?」と思うもの。
  • 本当に迷った。他の案があって、理由があって選んだもの。
この結果をどう受け止めたか（正直な話）

1回通しただけです。「毎回3ラウンドで終わる」とは言えません。お題が小さかったので短く済んだ可能性が高いです。

また、ファイルを書く段階では書き込みの許可が要ります。この検証では --permission-mode acceptEdits を付けて自動で許可しました。対話画面なら都度聞かれます。

実際に生成された CONTEXT.md とADRの全文は _labs/2026-08-27_grill-me-setup/artifacts/ にそのまま置いてあります。
