Laravel

キュー投入したリスナーを「最後の1回だけ」にできる — #[DebounceFor]

v13.26.0 / 8/18 新機能 Laravel

先に言葉の確認です。イベントは「何かが起きた」という知らせ、リスナーはそれを受け取って動く処理です。リスナーに ShouldQueue を付けると、その場では動かずキュー（あとで処理する行列）に積まれます。

困るのは同じイベントが短時間に何度も飛ぶときです。商品を5回編集すれば検索インデックスの更新が5回積まれます。最後の1回で結果は同じなのに、4回ぶんが無駄になります。

この環境で実際に動かしました。0.5秒おきに同じイベントを4回投げて、リスナーが何回動いたかを数えたものです。

Laravel 13.26.1 / PHP 8.4.19 で実行（加工せずそのまま）
# QUEUE=database(sqlite) CACHE=file

$ php artisan demo:debounce plain
 1回目を発火
 2回目を発火
 3回目を発火
 4回目を発火
 4秒待つ
 キューを流す

 発火 4 回 / 実行 4 回

$ php artisan demo:debounce debounce
 1回目を発火
 2回目を発火
 3回目を発火
 4回目を発火
 4秒待つ
 キューを流す

 発火 4 回 / 実行 1 回

属性を付けただけで 4回 → 1回 になります。再現用の一式は _labs/2026-08-23_001/laravel/ に置きました。

書き方はこうです。

公式ドキュメント（Events）に載っている例
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Queue\Attributes\DebounceFor;

#[DebounceFor(30)]
class UpdateProductSearchIndex implements ShouldQueue
{
    public function handle(ProductUpdated $event): void
    {
        // 検索インデックスの更新…
    }

    public function debounceId(ProductUpdated $event): string
    {
        return (string) $event->product->getKey();
    }
}

debounceId が「どれとどれを同じ扱いにするか」を決めます。上の例は商品ごとなので、商品Aの連打と商品Bの連打は別々にまとまります。ここを書かないと全部が1本にまとまってしまうので、実質必須だと思ってください。

1つ落とし穴があります。ずっと連打され続けると、いつまでも実行されません。上限を付けるのが maxWait です。

最長120秒で必ず1回は走らせる
#[DebounceFor(30, maxWait: 120)]
class UpdateProductSearchIndex implements ShouldQueue
{
    // …
}

ECS on Fargate で動かすなら、キャッシュの置き場所が条件になります。

「何回目か」を数えているのはキャッシュです。ECS on Fargate は同じコンテナを複数動かす仕組みなので、キャッシュがコンテナごとに分かれていると、それぞれが別々に数えてしまいます。

公式ドキュメントもこれを条件として書いています。

laravel.com/docs/13.x/events の原文
If your application dispatches events from multiple web servers or containers, you should ensure that all of your servers are communicating with the same central cache server.

つまり CACHE_STORE が file や array のままだと、タスクの数だけ処理が走ります。ElastiCache などを共通で指す設定が要ります。リスナー単位で変えたいときは debounceVia を生やします。

このリスナーだけ redis で数える
public function debounceVia(ProductUpdated $event): Repository
{
    return Cache::driver('redis');
}

「重複を防ぐ」機能は2つあります。混ぜると例外で落ちます。

Laravel には似た機能の ShouldBeUnique が前からあります。目的が違うので、使い分けが要ります。

やりたいこと使うもの結果
処理中に来た同じものを捨てたい ShouldBeUnique 最初の1回が走る。後は消える
連打が落ち着くまで待って最後を拾いたい #[DebounceFor] 最後の1回が走る

「最新の内容で1回だけ更新したい」なら debounce、「二重決済を止めたい」なら unique です。

そして両方を同じリスナーに付けることはできません。これも実際に試しました。

両方付けたリスナーにイベントを投げた実行結果
$ php artisan demo:conflict
 LogicException
 A debounced listener cannot also
 implement ShouldBeUnique.

起動時ではなくイベントを投げた瞬間に落ちます。テストで踏むまで気付かない種類のものなので、先に知っておく価値があります。

どうやって「最後の1回」にしているのか（読まなくても使えます）

イベントが飛ぶたびに DebounceLock がキャッシュに印を置き、ジョブは debounceFor 秒だけ遅らせてキューに積まれます。

後から来たイベントが印を上書きするので、先に積まれたジョブは実行される時点で「自分はもう持ち主ではない」と分かり、何もせず終わります。最後に印を置いたものだけが実際に動きます。

maxWait を超えていた場合は遅延が0になり、その場でキューに積まれます。

使う前に確認することです。 0 / 4

  • 今やること。Laravel 13系を使っていなければ対応は不要。使っていて「同じ処理が連続で走って重い」箇所に心当たりがあるなら、#[DebounceFor] とキャッシュの置き場所を確認する。

Anthropic のガイドの原文

A working rule helps here. When Claude makes a mistake twice, the correction goes into CLAUDE.md.

エージェントに記憶を持たせた5手法が、全部「記憶なし」に負けた — MemTrapBench

8/21 エージェント設計

エージェントに「前のやりとりを覚えさせる」機能を足すのは、いま定番の改善策です。この論文はそこに待ったをかけています。

これまでの記憶系ベンチマークは「正しく保存され、正しく取り出せたか」を測ってきました。この論文が測るのは別のことです。取り出した記憶が、いま解いている問題の推論をどう歪めるか。

Abstract の原文
Experiments across two model families and five representative memory frameworks show that MemTrapBench is challenging: all evaluated memory strategies underperform the no-memory setting, with even the strongest methods suffering drops of more than 10%.

評価した5つの記憶手法が、全部「記憶なし」より成績が悪くなりました。一番マシなものでも10%以上落ちています。正しく記録された、内容も関連している記憶であっても、そうなったという主張です。

ただし読むときの注意が2つあります。

  • 試したモデルは2種類だけ。Gemini-3-Flash-Preview と Qwen3-30B-A3B-Instruct-2507 です。Claude や GPT の上位機は入っていません。「記憶機能は害」と一般化はできません。
  • 対策もセットで提案されている。AdaptiveMem という、推論時に「記憶の罠を避けろ」と指示する手法で、罠を緩和しつつ通常のベンチマークの成績は保てたとしています。
  • 今やること。対応は不要。ただしエージェントにメモリ機能を足すなら、「記憶なし」の対照群を必ず一緒に測ること。足せば良くなる前提で進めないための材料として使える。
