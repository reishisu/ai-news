🗺 全体像 — 4段の階段

「ループエンジニアリング」は4段目。1段目から上がれば怖くない

最近よく聞くループエンジニアリングやグラフエンジニアリング。いきなり手を出すと難しいだけです。

実際は階段の上のほうにあるだけ。順番に上がれば勝手に着きます。

  • 1. 頼む。毎回プロンプトを打つ。多くの人がここで止まっている、というのが筆者の実感です。
  • 2. 型にする。よく使う頼み方をファイルに保存する。
  • 3. 見張る。テスト（期待値を書いた小さなプログラム）を用意して、編集のたびに自動実行。ここが山場。
  • 4. 回す。「テストが通るまで直して」と投げて、席を立つ。

1頼む — 効くのは3つだけ

プロンプト術は忘れていい。効き目があるのはこの3つ

コツは山ほど流通していますが、筆者が実務で効くと感じたのはこの3つです。計測した比率ではなく、運用上の目安として読んでください。

  • ①ゴールを先に書く。「3000円ちょうどは送料無料が正しい。直して」の順。
  • ②現物を貼る。説明を書くより、失敗したテスト出力をそのまま貼るほうが速くて正確。
  • ③禁止事項を1行。「テストは書き換えないで」。これを書き忘れたときが、いちばん静かに事故ります。
そのまま使える頼み方
shipping.py の送料計算を直してください。

正しい仕様:
- 購入額 3000円以上 → 送料 0円
- 3000円未満 → 送料 500円

いま失敗しているテスト:
FAILED test_shipping.py::test_ちょうど3000円は送料無料 - assert 500 == 0

条件:
- test_shipping.py は書き換えないでください
- shipping.py 以外は触らないでください

Q. ③の「テストは書き換えないで」を書かないと、何が起きる?

テストは仕様書です。緩められると、バグが残ったまま緑になります。1行の禁止事項でこれを防げます。

2型にする — 2回言ったら保存

同じ説明を2回した時点で、それはファイルにすべき

Claude CodeはAnthropicのAIコーディングツールです。公式ドキュメントによれば、ターミナル・IDE拡張・デスクトップアプリ・ウェブで動きます。以降の設定は全部これの話（この記事はターミナルでの利用が前提。入手方法は公式の Get started）。

これにはスキルがあります。手順書を置くと /名前 で呼べる仕組みです。

やることはフォルダを1つ作るだけ。⏱ 約1分

.claude/skills/fix-test/SKILL.md
---
name: fix-test
description: 失敗しているテストを直す。テスト自体は書き換えない。
---

# 失敗テストを直す

1. `python3 -m pytest -q` を実行して、失敗しているテストを確認する
2. 失敗の原因をコード側で直す(テストファイルは変更しない)
3. もう一度テストを実行し、全部通ったことを確認する
4. 通らなければ 2 に戻る。5回試して直らなければ、原因を報告して止まる

## やらないこと
- テストファイルの書き換え
- 関係ないファイルの整形やリファクタリング
  • 置き場所は2つだけ。そのプロジェクト用なら .claude/skills/、全部で使うなら ~/.claude/skills/。
  • 中身はただのMarkdown。冒頭の項目に必須はありません。公式ドキュメントは description だけを「推奨」としています。本文は日本語でOK。
  • /fix-test を決めるのはフォルダ名。name: は一覧に出る表示名です。フォルダ名を変えると呼び名も変わります。
  • 「やらないこと」が本体。禁止事項のないスキルは、いつか事故ります。
description の書き方のコツ
ポイント
この一文を見てAIが「いま使うべきか」を決めます。「〜のとき使う」と用途で書くと呼ばれやすくなります。省略すると本文の最初の段落が代わりに使われます。
注意
スキルの書式は更新が入る領域です。使う前に公式ドキュメントで最新を確認してください。

3見張る — ここが本番

「直ったか」を機械が判定できる。それだけが全部の土台

ここで言うテストとは、「shipping_fee(3000) は 0 を返すはず」のような期待値を書いた小さなプログラムです。

人が目で確かめる代わりに、機械が一瞬で○×を出します。この○×があるから、AIに丸投げできるわけです。

ここは飛ばせません。逆にここさえ作れば4段目は一瞬です。

実際に動かした例で見ます。まずバグ入りのコード。

shipping.py
FREE_THRESHOLD = 3000
SHIPPING_FEE = 500


def shipping_fee(total: int) -> int:
    """購入額に応じた送料を返す。3000円以上で送料無料。"""
    if total > FREE_THRESHOLD:      # ← 本当は >= が正しい
        return 0
    return SHIPPING_FEE
test_shipping.py — テスト名は日本語でいい
from shipping import shipping_fee


def test_安い買い物は送料がかかる():
    assert shipping_fee(2999) == 500


def test_ちょうど3000円は送料無料():
    assert shipping_fee(3000) == 0


def test_高額は送料無料():
    assert shipping_fee(5000) == 0
実行結果(この環境で実際に出た出力)
$ COLUMNS=40 python3 -m pytest -q
.F.                              [100%]
=============== FAILURES ===============
_________ test_ちょうど3000円は送料無料 __________

    def test_ちょうど3000円は送料無料():
>       assert shipping_fee(3000) == 0
E       assert 500 == 0
E        +  where 500 = shipping_fee(3000)

test_shipping.py:9: AssertionError
======= short test summary info ========
FAILED test_shipping.py::test_ちょうど3000円は送料無料
1 failed, 2 passed in 0.02s
  • この出力をそのまま貼る。どのテストがどの値で落ちたか全部入り。説明文を書くより速い。
  • テスト名は日本語でいい。Pythonは日本語の関数名が使えます。そのまま仕様書になります。
  • まずは3件から。境界(3000)・その手前(2999)・普通の値(5000)。off-by-oneはこれで捕まります。
  • COLUMNS=40 は幅を詰めるため。付けないと === FAILURES === や [100%] の行が端末幅いっぱい(80桁)に伸びます。スマホで読むには長すぎるので、この記事では40桁で取り直しています。
やってみて分かった、pytest の幅指定のクセ
40未満を指定しても効かない
COLUMNS に 34 / 30 / 26 を入れて実測しましたが、いずれも80桁の出力に戻りました。pytest には下限があります。40が実質の最小値です。
日本語のテスト名だと、40を指定しても超える
pytest は幅を「文字数」で数えていて、全角文字が表示上2桁ぶん占めることを見ていません。_________ test_ちょうど3000円は送料無料 __________ は40文字ちょうどですが、表示幅は50桁あります。日本語のテスト名を使うなら、ここは諦めどころです。
ループの中では --tb=no を足す
後で出てくる loop.sh は pytest -q --tb=no にしています。やり直すたびにトレースバックが全部出ると、肝心の「何回目で通ったか」が流れて読めなくなるためです。

編集するたび、勝手にテストが走る状態にする

毎回自分で打つのはすぐ飽きます。編集したら自動でテストにします。⏱ 約1分

この「◯◯したら自動で走る仕組み」をフックと呼びます。まず走らせる中身をファイルにします。

.claude/hooks/pytest.sh（実行権限を付ける）
#!/bin/bash
f=$(jq -r '.tool_input.file_path // empty')
case "$f" in *.py) ;; *) exit 0 ;; esac
python3 -m pytest -q --tb=no >&2 || exit 2
  • 1行目の jq。フックには「どのファイルを触ったか」がJSONで渡ってきます。そこからパスを取り出しています。
  • 2行目で拡張子を絞る。Python以外なら何もせず終了。Markdownを直すたびにテストが走ると邪魔です。
  • 3行目が肝。出力を >&2 で標準エラーに出し、落ちたときだけ終了コード2で終わります。理由は下に書きます。

次に、これを「AIがファイルを書いた直後」に呼ぶ設定です。

.claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/pytest.sh",
            "args": []
          }
        ]
      }
    ]
  }
}
  • PostToolUse。「AIが道具を使い終わった直後に」という意味のきっかけです。
  • matcher の Write|Edit。その道具が「新規書き込み」か「編集」のときだけ、という絞り込み。
  • ${CLAUDE_PROJECT_DIR}。プロジェクトの根っこを指す変数です。どこで実行されてもスクリプトを見つけられます。

書いたら起動する前に動作確認します。渡ってくるJSONを手で流し込めば、単体で試せます。

フック単体の動作確認(実際の出力)
$ IN='{"tool_input":{"file_path":"shipping.py"}}'
$ echo "$IN" | .claude/hooks/pytest.sh
.F.                              [100%]
======= short test summary info ========
FAILED test_shipping.py::test_ちょうど3000円は送料無料
1 failed, 2 passed in 0.01s
$ echo $?
2

# バグを直して、もう一度叩く
$ echo "$IN" | .claude/hooks/pytest.sh
...                              [100%]
3 passed in 0.01s
$ echo $?
0
  • 壊したとき赤くなるかまで確認する。緑しか見ないと、何も検査してないフックが完成します。
  • 落ちたら終了コード2。ここを間違えるとAIに何も届きません。Hooksリファレンスの「Exit code 2 behavior per event」表は、PostToolUse の行を Shows stderr to Claude; the tool already ran と書いています。逆に終了コード0だと、標準出力も標準エラーもデバッグログ行きでAIには見えません。
  • 成功時は何も伝わらない。それでいい。通ったときにAIへ渡すことは何もありません。伝えたいのは落ちたときだけです。
「テストが通ったこと」もAIに伝えたい場合
方法
終了コード0のまま、標準出力にJSONを出します。{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"…"}} の additionalContext がAIに渡る文面です。Hooksリファレンスの「Run tests after file changes」に、jq -nc --arg msg … で組み立てる公式例があります。
注意
同リファレンスの「Exit code 0」節は “Stderr from a hook that exits 0 goes to the debug log only, never the transcript, and Claude never sees it.” としています。0で終わるなら、JSONを出さない限り何も伝わりません。
テストが遅いとき
公式例は "async": true を併用しています。ただし出力は次のターンまで届きません（同リファレンス Limitations）。
効かないときの確認順
1. JSONが壊れていないか
jq -e . .claude/settings.json で先に確かめます。壊れたまま起動すると、Settingsドキュメントによれば対話セッションでは起動時に Settings Error ダイアログが出て、「直す／終了する／壊れた設定なしで続行する」を選ばされます。続行を選ぶと、そのファイルの設定は効きません。どれが問題かは /status と claude doctor で確認できます。
2. スクリプト単体で動くか
上のように手でJSONを流し込む。実行権限（chmod +x）の付け忘れが多いです。
3. 読み込まれているか
セッション開始後に作った設定は読まれないことがあります。読み直すか起動し直してください。

4回す — ここまで来たら10行

止まる条件さえあれば、ループはこれだけ

「テストが通るまで直す。ただし5回まで」をそのまま書きます。

まずAI抜きで、骨組みがちゃんと止まるか確かめます。

loop.sh
#!/bin/bash
MAX=5
for i in $(seq 1 $MAX); do
  echo "--- $i 回目 ---"
  if python3 -m pytest -q --tb=no; then
    echo "✅ 全部通ったので終了"
    exit 0
  fi
  echo "🔧 直します"
  ./fix_agent.sh          # ここを実際はAIの呼び出しに差し替える
done
echo "⛔ $MAX 回やっても直らないので打ち切り"
exit 1

コマンドには成否の合図（終了コード）があります。0が成功、0以外が失敗。直感と逆なので注意。

if はこれを見て分岐しています。echo $? と打つと、直前のコマンドの終了コードが見られます。

実行結果(実際に走らせたログ)
$ ./loop.sh
--- 1 回目 ---
.F.                              [100%]
======= short test summary info ========
FAILED test_shipping.py::test_ちょうど3000円は送料無料
1 failed, 2 passed in 0.01s
🔧 直します
--- 2 回目 ---
...                              [100%]
3 passed in 0.01s
✅ 全部通ったので終了

$ echo $?
0
  • 落ちて、直して、止まった。これがループの全部です。難しい概念はゼロ。
  • 上限は必ず付ける。MAX=5。止まらないループは時間とお金だけ溶かします。
  • AIの差し込み口は1行。./fix_agent.sh をAI呼び出しに変えれば、そのまま自走します。
Claude Codeの機能で回す場合
状態で終わるなら
完了条件を渡してターンを跨いで自走させる仕組み(/goal)。「pytest -q が全部通る。20ターンで打ち切り」のように書きます。
時間で回すなら
一定間隔で繰り返す仕組み(/loop)。CI待ちなど外の状態が変わるのを待つ用途向け。

💣 私が事故った話

パイプを1本足しただけで、ループが堂々と嘘をついた

この記事を書きながら実際にやらかしました。出力が長いのが嫌で | tail -1 を足しただけ。

結果、テストが落ちているのに「✅ 全部通った」と言って終了しました。

壊れていたときの実際の出力
$ ./loop.sh
# if python3 -m pytest -q --tb=no | tail -1
--- 1 回目 ---
1 failed, 2 passed in 0.01s
✅ 全部通ったので終了
       ↑ 落ちてるのに成功扱い

Q. なぜ「成功」になった?

パイプでつなぐと、シェルが見るのはいちばん最後のコマンドの成否です。tail は常に成功するので、判定も常に成功になります。

  • 直し方は簡単。判定に使う行ではパイプを使わない。出力を減らすなら -q など引数で。
  • 教訓。停止条件はわざと失敗させて赤くなるかを必ず確認する。
  • 緑しか見ないのが一番危ない。何も検査していない仕組みが、静かに完成します。
どうしてもパイプを挟みたいとき
方法
bashなら ${PIPESTATUS[0]} で最初のコマンドの終了コードが取れます。set -o pipefail もありますが、判定行を分けるほうが読みやすく事故りません。

訂正と追記

2026年8月15日、フックの説明を全面的に直しました

公開後の事実検証で、ステップ3の土台そのものが間違っていたことが分かりました。記事の教訓どおりの事故です。

  • 訂正1（重大）。フックの || true。初出時は「テストが落ちてもフック自体は失敗にせず、結果だけAIに見せます」と書いていました。逆でした。終了コード0で終わると出力はデバッグログ行きで、AIには何も届きません。落ちたことを伝えるには終了コード2で標準エラーに出す必要があります。設定例ごと差し替え、additionalContext を使う別解も追記しました。
  • 訂正2。スキルの冒頭項目。「決まりは name と description だけ」と書いていましたが、公式ドキュメントは全項目を任意（description は推奨）としています。また /fix-test という呼び名を決めているのは name: ではなくフォルダ名です。
  • 訂正3。壊れた settings.json。「黙って無効になる」と書いていましたが、対話セッションでは起動時に Settings Error ダイアログが出ます。
  • 訂正4。「事故の9割はこれで消えます」。出どころのない数字だったため削除し、筆者の運用上の実感である旨に書き換えました。同様に「実務で差が出るのは3つだけ」「3件で十分」も断定を外しています。
  • 追記。初学者の視点で読めなくなる箇所を補いました。テストの定義、Claude Codeが何か、PostToolUse と matcher の意味、終了コードの説明、そして定義されていなかった $CMD の削除（スクリプトファイル方式に変更）。
