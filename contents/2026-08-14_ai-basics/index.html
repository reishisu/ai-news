🗺 全体像 — 4段の階段

「ループエンジニアリング」は4段目。1段目から上がれば怖くない

最近よく聞くループエンジニアリングやグラフエンジニアリングは、いきなり手を出すと難しい話です。実際には下の階段の上のほうにあるだけで、順番に上がれば自然にたどり着きます。

  • 1. 頼む。毎回プロンプトを打つ。いまここにいる人が大半です。
  • 2. 型にする。よく使う頼み方をファイルに保存して、名前で呼び出せるようにする。
  • 3. 見張る。テストを書き、編集のたびに自動で走らせる。ここが山場です。
  • 4. 回す。「テストが通るまで直して」と投げて、席を立つ。

1頼む — 効きが変わる3つの型

「良いプロンプト」の話は忘れていい。効くのはこの3つだけ

プロンプトのコツは山ほど流通していますが、実務で効き目が大きいのはこの3つです。それ以外は誤差だと思って構いません。

  • ①ゴールを先に、条件を後に。「送料計算のバグを直して。3000円ちょうどは無料が正しい」のように、達成状態を先頭に書きます。
  • ②現物を渡す。「このファイルを見て」ではなく、失敗しているテストの出力をそのまま貼る。これだけで精度が跳ねます。
  • ③やってほしくないことを1行。「他のファイルは触らないで」「テストは書き換えないで」。事故の9割はここで防げます。
そのまま使える頼み方
shipping.py の送料計算を直してください。

正しい仕様:
- 購入額 3000円以上 → 送料 0円
- 3000円未満 → 送料 500円

いま失敗しているテスト:
FAILED test_shipping.py::test_ちょうど3000円は送料無料 - assert 500 == 0

条件:
- test_shipping.py は書き換えないでください
- shipping.py 以外は触らないでください
なぜテストを書き換えさせてはいけないのか
よくある事故
「テストが通るようにして」とだけ頼むと、コードではなくテストのほうを緩めて通してくることがあります。テストは仕様書なので、触らせない指定を1行入れておくのが安全です。

2型にする — 毎回同じ説明をやめる

同じ頼み方を2回したら、その時点でファイルに保存する

Claude Codeにはスキルという仕組みがあります。手順書をファイルに置いておくと、/名前 で呼び出せるようになります。作り方はフォルダを1つ作るだけです。

.claude/skills/fix-test/SKILL.md
---
name: fix-test
description: 失敗しているテストを直す。テスト自体は書き換えない。
---

# 失敗テストを直す

1. `python3 -m pytest -q` を実行して、失敗しているテストを確認する
2. 失敗の原因をコード側で直す(テストファイルは変更しない)
3. もう一度テストを実行し、全部通ったことを確認する
4. 通らなければ 2 に戻る。5回試して直らなければ、原因を報告して止まる

## やらないこと
- テストファイルの書き換え
- 関係ないファイルの整形やリファクタリング
  • 置き場所は2つ。そのプロジェクトだけなら .claude/skills/、全プロジェクトで使うなら ~/.claude/skills/。
  • 中身はただのMarkdown。冒頭の name と description だけが決まりごとで、あとは日本語の手順書で構いません。
  • 「やらないこと」を必ず書く。ここがスキルの実質的な本体です。禁止事項のないスキルは事故ります。
もう少し詳しく
description の書き方
この一文を見てAIが「いま使うべきか」を判断します。「〜のとき使う」と用途を書くと呼ばれやすくなります。
注意
スキルの仕様は更新が入る領域です。使う前に公式ドキュメントで最新の書式を確認してください。

3見張る — ここが本番

「直ったか」を機械が判定できるようにする。それが全部の土台

ここだけは飛ばせません。テストが通ったかどうかを機械が判定できる状態を作れば、あとの自動化は全部その上に乗ります。実際に動かした例で見ます。

shipping.py — わざとバグを入れた状態
FREE_THRESHOLD = 3000
SHIPPING_FEE = 500


def shipping_fee(total: int) -> int:
    """購入額に応じた送料を返す。3000円以上で送料無料。"""
    if total > FREE_THRESHOLD:      # ← 本当は >= が正しい
        return 0
    return SHIPPING_FEE
test_shipping.py — 仕様を日本語のまま書ける
from shipping import shipping_fee


def test_安い買い物は送料がかかる():
    assert shipping_fee(2999) == 500


def test_ちょうど3000円は送料無料():
    assert shipping_fee(3000) == 0


def test_高額は送料無料():
    assert shipping_fee(5000) == 0
実行結果(この環境で実際に出た出力)
$ python3 -m pytest -q
.F.                                                                      [100%]
=================================== FAILURES ===================================
_____________________________ test_ちょうど3000円は送料無料 ______________________________

    def test_ちょうど3000円は送料無料():
>       assert shipping_fee(3000) == 0
E       assert 500 == 0
E        +  where 500 = shipping_fee(3000)

test_shipping.py:9: AssertionError
=========================== short test summary info ============================
FAILED test_shipping.py::test_ちょうど3000円は送料無料 - assert 500 == 0
1 failed, 2 passed in 0.02s
  • この出力をそのままAIに貼る。どのテストが、どういう値で落ちたかが全部入っています。説明文を書くより早くて正確です。
  • テスト名は日本語でいい。Pythonは日本語の関数名が使えます。仕様書としてそのまま読めるので、AIにも人にも伝わります。
  • 3件で十分。境界(3000)・境界の手前(2999)・普通の値(5000)。この3点で off-by-one は捕まります。

編集のたびに自動でテストを走らせる(フック)

毎回自分でテストを打つのはすぐ飽きます。ファイルが編集されたら自動でテストを走らせる設定を置きます。設定ファイル1つで終わります。

.claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | { read -r f; case \"$f\" in *.py) python3 -m pytest -q ;; esac; } 2>&1 || true"
          }
        ]
      }
    ]
  }
}

設定を書いたら、Claude Codeを起動する前に動作確認します。フックには編集情報がJSONで渡ってくるので、それを手で流し込めば単体で試せます。

フック単体の動作確認(実際の出力)
$ echo '{"tool_name":"Edit","tool_input":{"file_path":"shipping.py"}}' | eval "$CMD"
...                                                                      [100%]
3 passed in 0.00s

# わざとバグを戻してから、もう一度叩く
$ echo '{"tool_name":"Edit","tool_input":{"file_path":"shipping.py"}}' | eval "$CMD"
FAILED test_shipping.py::test_ちょうど3000円は送料無料 - assert 500 == 0
1 failed, 2 passed in 0.01s
  • 壊したときにちゃんと赤くなるかまで確認する。「通ったログ」だけ見て安心すると、実は何も検査していないフックが出来上がります。
  • 末尾の || true は意図的。テストが落ちてもフック自体はエラーにせず、結果だけをAIに見せる形にしています。
  • 拡張子で絞る。case "$f" in *.py) の部分。Markdownを直すたびにテストが走ると邪魔になります。
設定が効かないときの確認順
1. JSONが壊れていないか
jq -e . .claude/settings.json で確認。JSONが壊れているとファイル全体の設定が黙って無効になります。
2. コマンド単体で動くか
上のように手でJSONを流し込んで確認します。
3. 設定が読み込まれているか
セッション開始後に作った設定は読み込まれないことがあります。読み直すか、起動し直してください。

4回す — やっとループ

止まる条件があるなら、ループはたった10行

ここまで来ればループは簡単です。「テストが通るまで直す。ただし5回まで」をそのまま書き下します。まずは骨組みを、AI抜きで動かして確かめます。

loop.sh
#!/bin/bash
# 「テストが全部通るまで直す」ループ。最大5回で打ち切る。
MAX=5
for i in $(seq 1 $MAX); do
  echo "--- $i 回目 ---"
  if python3 -m pytest -q; then
    echo "✅ 全部通ったので終了"
    exit 0
  fi
  echo "🔧 直します"
  ./fix_agent.sh          # ここを実際はAIの呼び出しに差し替える
done
echo "⛔ $MAX 回やっても直らないので打ち切り"
exit 1
実行結果(実際に走らせたログ)
$ ./loop.sh
--- 1 回目 ---
.F.                                                                      [100%]
FAILED test_shipping.py::test_ちょうど3000円は送料無料 - assert 500 == 0
1 failed, 2 passed in 0.02s
🔧 直します
--- 2 回目 ---
...                                                                      [100%]
3 passed in 0.01s
✅ 全部通ったので終了

$ echo $?
0
  • 1回目で落ちて、直して、2回目で止まった。これがループの全てです。難しい概念は何も要りません。
  • 上限(MAX=5)は必ず付ける。止まらないループは、時間とお金だけを溶かします。
  • 終了コードを返す。exit 0 / exit 1 にしておくと、このループ自体を他の仕組みから呼べます。
  • AIの差し込み口は1行だけ。./fix_agent.sh のところを実際のAI呼び出しに置き換えれば、そのまま自走ループになります。
Claude Code側の機能で回す場合
状態で終わるなら
完了条件を渡してターンを跨いで自走させる仕組み(/goal)があります。「python3 -m pytest -q が全部通る。20ターンで打ち切り」のように書きます。
時間で回すなら
一定間隔で繰り返す仕組み(/loop)。CIの結果待ちなど、外の状態が変わるのを待つ用途向けです。

💣 実際に踏んだ落とし穴

パイプを1本足しただけで、ループが「嘘の成功」を返した

この記事を書きながら実際にやらかした話です。出力が長いのが嫌で | tail -1 を足したところ、テストが落ちているのにループが「✅ 全部通った」と言って終了しました。

壊れていたときの実際の出力
$ ./loop.sh          # if python3 -m pytest -q | tail -1; then と書いていた
--- 1 回目 ---
1 failed, 2 passed in 0.01s
✅ 全部通ったので終了     ← 落ちているのに成功扱い
  • 原因は単純。パイプでつなぐと、シェルが見るのはいちばん最後のコマンドの成否です。tail は常に成功するので、判定が常に成功になります。
  • 直し方も単純。判定に使う行ではパイプを使わない。出力を減らしたいなら -q などコマンド側の引数で減らします。
  • 教訓。停止条件はわざと失敗させて赤くなるかを必ず確認する。緑しか見ていないと、何も検査していない仕組みが完成します。
どうしてもパイプを挟みたいとき
方法
bashなら ${PIPESTATUS[0]} で最初のコマンドの終了コードが取れます。set -o pipefail を使う手もありますが、判定行を素直に分けるほうが読みやすく事故りません。

🎯 次は何をすればいいか

今日やるなら、ステップ3だけでいい

全部を一気にやる必要はありません。手元のプロジェクトにテストを3件書いて、フックで自動実行にする。ここまでで自動化の土台は完成します。

  • 今日: テスト3件 + フック1個。境界・境界の手前・普通の値。これだけで壊れたら気づける状態になります。
  • 今週: よく使う頼み方をスキルに1つ。2回同じ説明をしたものが候補です。
  • 来週: ループを1本。上限付きで、小さい対象(1ファイル、1種類のエラー)から始めます。
  • その先: グラフ。ループが同じ失敗を繰り返し始めたら、そこで初めて工程を分割する話になります。
