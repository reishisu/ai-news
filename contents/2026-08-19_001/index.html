Laravel

Laravel 12.67.0 / 13.26.0で inバリデーションが厳密比較に — '01'や' 1'が通らなくなる

8/18 ✓ 公式確認済 ⚠ 挙動変更 Laravel

in:1,2,3は「値が候補のどれかと一致するか」を検査するルールです。PHP 8は数値文字列どうしの==を数値として比べるため、これまで'01'や' 1'が候補に無いのに素通りしていました。8月18日リリースの2系統(v12.67.0 / v13.26.0)で、この比較が厳密になりました。

PR #61146の変更(1行)
-  return ! is_array($value) && in_array((string) $value, $parameters);
+  return ! is_array($value) && in_array((string) $value, $parameters, true);

追加されたテストが「通らなくなる入力」を明示しています。' 1' / '1 ' / "\t1" / "1\n" / '01' / '+1' / '1.0' / '1e0'はすべてfalse、'1'だけがtrueです。

  • 対象は文字列ルートとRule::in()の両方。どちらも同じvalidateIn()を通ります。値が配列のときは従来どおり別経路で、変化はありません。
  • 12系にも入った。13に上げていない現場も、次のcomposer updateで挙動が変わります。アップグレード前にgrep -rn "'in:" app/ routes/とRule::in(で既存ルールを列挙し、候補が1.0や01のような表記になっていないか確認してください。見つけたら、ルール側の候補を実際に来る文字列へ揃える(またはフォーム側で正規化してから検証する)のが直し方です。なお空白については、Laravelは既定で入力の前後空白を自動で削ります(TrimStringsミドルウェア)。この自動削除を除外設定している項目だけが、空白入りの入力の影響を受けます。
  • 同じリリースにもう1件、ローカルディスクの一時URLの修正。PR #61145で、uploadフラグの読み取りが$request->boolean('upload')(クエリとボディの両方を見る)からクエリ文字列限定に変わりました。ボディにupload=1を混ぜると配信/受信の分岐を外から動かせたためです。localドライバのtemporaryUrl()系を使っている場合のみ関係します(S3なら無関係)。
  • 13.26.1の取り消しに注意。直後(JST 8/19 5:31)のv13.26.1は、13.26.0で入ったばかりのorWhereKey / orWhereKeyNotをrevertしています。この2メソッドは使い始めないでください。

古くなった規約ファイルは「無い」より悪い — 正しい規約100%・規約なし33%・古い規約0%

8/17投稿 ✓ 原文読了 エージェント設計 査読前

コーディングエージェントが規約(コーディング標準)にどう従うかを、7モデル系列×5ハーネスで測った査読前論文です(arXiv:2608.16630)。ハーネスとは、Claude Codeのように、モデルへツールと作業環境を与えて動かす実行環境のことです。同じ判定箇所を3条件で比べると、正しい規約があれば100%良い書き方、規約なしでコードだけなら33%、古い規約が残っていると0%でした(各10試行・3,385判定、両端は分散ゼロ)。

結論の原文は「A stale standard is therefore worse than silence. … Deleting an out-of-date convention file beats leaving it in place.」——古い規約は沈黙より悪く、削除が上回る。CLAUDE.mdやAGENTS.mdを置いている人に直接効く結果です。

  • 文書はコードに勝つ。規約文書と実コードが矛盾する39試行で、エージェントは全ての係争判定で文書側に従いました。文書をわざと悪い作法にしても文書に従った——つまり間違った記述は、コードから読み取れるはずの正しい慣習を上書きして潰します。
  • 事実が無いと、止まらずに捏造する。必要な情報を伏せたとき「できません」と言えた率はモデルでほぼ決まり、プール全体で37%でした。エージェントがファイルを読んだかのログ監視では、この穴は見えません。
  • コストは12.8倍違う。全テストが通った18構成の間で、累積入力トークンは293,882から3,752,134まで開きました。「トークンを多く食う=賢い」ではありません。
  • 著者の誠実な但し書き。自分たちの指標がSWE-bench Verifiedの成否を予測しないこと(AUC≈0.49。0.5で当てずっぽうと同じ)を明記し、初期版の高いAUCはリークだったと自白しています。ハーネスの優劣を語る論文ではありません。
  • 今日やること。リポジトリのCLAUDE.md / AGENTS.mdの棚卸し。実装と食い違ったまま放置している記述は、直すか消す。

「あなたが調整役です」とプロンプトに書いても効果ゼロ — マルチエージェント1,902実行の実測

8/17投稿 ✓ 原文読了 エージェント設計 査読前

Claude Code(2.1.x系)にモデルを固定して1,902回実行した査読前論文です(arXiv:2608.16801、事前登録あり)。8体構成でflat(全員対等)とcoordinator(調整役を指名)を比べると、成功率に差がありません(p=0.53〜1.00。p値が大きいほど「偶然でもこの程度の差は出る」の意)。プロンプトで役割名を書くだけでは通信のハブは生まれません。強制的なルーティング(調整役を実装で必ず経由させる構成)の効果は未検証の今後の課題だと、著者自身が明記しています。

  • 連絡のファイル化はタスク形状で効き方が逆転する。全員が同じ仕様を見る分散型では出力トークンが4体で約25%減・8体で約42%減。前工程の出力を次が読むチェーン型では逆に増える(4体で約17%増)。すでにファイルが調整を担っている所に強制すると純コストです。

ツール検索を自社の書き方でfine-tuneすると、別の文体で静かに全滅する — 91.8%が0.0%へ

8/17投稿 ✓ 原文読了 エージェント設計 査読前

昨日の「Skillを100個入れると選択率3.3%」の実務的な続きです。査読前論文(arXiv:2608.16502)によると、ツール群を一切変えなくても、クエリの文体が変わっただけでfine-tune(自社データでの追加学習)済み検索器の再現率——必要なツールを取りこぼさず見つけられた割合——が91.8%から0.0〜8.3%に崩壊しました(source-style collapse)。語彙の重なりでは説明できないと確認されています。

  • 専用化の利得は4.5ポイントだけ。汎用学習の87.3%に対し専用化で91.8%。得るものは小さく、文体が外れたときの損失は桁違いです。しかもエラーにならず静かに落ちます。
  • 素のBM25が勝つ場面がある。崩壊した領域では、キーワード検索のBM25単体59.4% > 融合54.2% > fine-tune済み単体1.6%。原文は「This supports routing away from an unsafe dense specialist instead of blending it with a lexical branch.」——混ぜるのではなく、危ない専用検索器から逃がす。
  • 逃げ道は安い。クエリのTF-IDF距離(単語の出現頻度で文書どうしの近さを測る古典的な方法)で「訓練分布から遠い」を検知し、汎用検索器へ切り替えるだけで、混合クエリの再現率が22.3%から86.1%に戻りました。埋め込みモデルを新調する前に試す価値があります。
  • 読者への含意。Skill / MCPツールの検索を自前のクエリログで専用化する前に、この失敗モードを知っておくべきです。キーワード検索の経路は消さずに残す。自前でツール検索やRAGを組んでいないなら、読み物として知っておけば足ります。
