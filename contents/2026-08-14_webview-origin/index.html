WebViewのfetchが失敗する理由 — Origin: null とCORSの関係

スマホアプリの中に埋め込んだWebページ表示部品（WebView）。ブラウザでは動く。アプリの中に入れた瞬間だけAPIが落ちる。その理由を実測で突き止めます。
⏱ 約7分 Androidは公式で確認 / iOSは未確認 CORS 4パターン実測

⭐ 3行で言うと

  1. file:// や loadData で読み込むと、APIには Origin: null が届く ブラウザは「このページはどこから来たか」を Origin ヘッダーでAPIに伝えます。端末内のファイルを直接開く file://（アドレス欄に file:// と出るあれ）や、HTML文字列をWebViewに直接渡す loadData では、名乗る先が無いので null になります。Androidの公式ドキュメントの言葉では「不透明なオリジン(opaque origin)」です。
  2. だから許可リスト方式のAPIは100%落ちます。nullは絶対に一致しないからです CORSの返し方4通りを実際に叩いて、どれが通るか表にしました。
  3. 「じゃあnullも許可する」が一番危ない。Cookie付きで誰でも通れる穴になります これも実測しました。正しい直し方は、そもそもnullにしないことです。

1症状 — ブラウザでは動くのに

同じHTMLなのに、アプリに載せた瞬間だけAPIが落ちる

Webとして作っているときは完璧に動きます。アプリのWebViewに載せると、APIの呼び出しだけが失敗する。

しかもエラーメッセージが不親切です。JS側には TypeError: Failed to fetch としか出ません。ネットワークの問題にも、サーバー障害にも見えます。

  • HTMLの中身は関係ありません。1文字も変えなくても、読み込み方が違うだけで結果が変わります。
  • 画像やCSSは普通に表示されます。だから「通信自体はできている」と思ってしまい、原因から遠ざかります。
  • Androidは公式ドキュメントで裏が取れています。iOSでも同じ相談をよく見ますが、WebKit側の一次資料は見つけられませんでした。この記事ではiOSの挙動を断定しません（第2章と第5章で切り分け方だけ書きます）。

Q. 同じHTMLなのに、WebViewの中だけAPIが落ちるのはなぜ?

正解。ブラウザは「このページはどこから来たか」をAPIに伝えます。ローカルのファイルから読み込むと、名乗る先が無いので null になります。次でその実物を見ます。

2Originに何が入るかを測る

同じHTMLを2通りの方法で開いて、APIに届いた値を記録した

推測をやめて実物を見ます。APIサーバー側で、受け取った Origin ヘッダーをそのまま記録しました。

APIサーバーが受け取ったOrigin（実測 / パス名は次章の4パターンに対応。none=CORSヘッダー無し、star=*、allowlist=許可リスト）
$ cat api.log

GET /star  Origin: null
GET /allowlist  Origin: null

GET /star  Origin: http://127.0.0.1:8802

上3行が file:// で開いた場合、下3行がサーバーから配信した場合です。HTMLの中身は完全に同一です。

  • Androidの公式ドキュメントも同じことを言っています。「file:// URLと data: URLは不透明なオリジンとみなされ、fetch() や XMLHttpRequest のような強力なWeb APIを利用できません」
  • iOSは未確認です。Appleの loadFileURL(_:allowingReadAccessTo:) リファレンスを全文取得して検索しましたが、origin / CORS の語は1件も出てきません。だから「iOSでも null になる」とは書きません。第5章の手順で実機のログを取って確かめてください。
  • 保存系は動くので切り分けが遅れます。デスクトップのChromium 141で file:// のページを開くと localStorage は普通に読み書きできました（実測）。WebView実機での挙動は測っていません（AndroidはWebView側の setDomStorageEnabled にも左右されます）。

3CORS設定4通りの結果表

APIの返し方を4通り用意して、全部叩いた

CORSは、別の住所（オリジン）のサーバーを呼んでいいかをブラウザが判定する仕組みです。許可はサーバーが返すヘッダーで表明します。

file:// のページ（つまり Origin: null）から呼んだ結果です。表の「拒否」はサーバーが断ったという意味ではありません。サーバーは正常に応答を返していて、ブラウザがその結果をJSに渡さず握りつぶしています。

APIの返し方ふつうのfetchCookie付きfetch
CORSヘッダーを返さない 拒否拒否
Allow-Origin: *
全部許可する		 通る拒否
Allow-Origin: https://app.example.com
許可リスト方式		 拒否拒否
届いたOriginをそのまま返す
＋ Allow-Credentials: true		 通る通る
  • 許可リスト方式は絶対に通りません。null が許可リストに載ることはないからです。ここで多くの人が詰まります。
  • Allow-Origin: * は通りますが、Cookieが送れません。これは仕様です。* と認証情報は併用できません。
  • つまり「ログインが必要なAPI」は、file:// のWebViewからは正攻法では呼べません。これが問題の本質です。

この4行は、仕様書の8ステップを写しただけ

なぜこの結果になるのか。Fetch仕様に判定手順がそのまま書いてあります。上から順に読むだけで、表の4行が全部説明できます。

Fetch Standard §4.10「CORS check」— 全8ステップ（原文＋訳注）
1. Let origin be the result of getting
   `Access-Control-Allow-Origin` from
   response's header list.
2. If origin is null, then return failure.
   （注: Null is not `null`. ＝「ヘッダーが無い」と
     「文字列 null が入っている」は別物）
3. If request's credentials mode is not "include"
   and origin is `*`, then return success.
   （注: Cookieを送らない呼び方で、かつ値が `*`
     なら、ここで合格）
4. If the result of byte-serializing a request
   origin with request is not origin,
   then return failure.
   （注: 送ったOriginの文字列と、返ってきた値が
     完全一致するか。違えば不合格）
5. If request's credentials mode is not "include",
   then return success.
   （注: Cookieを送らないなら、ここまでで合格）
6. Let credentials be the result of getting
   `Access-Control-Allow-Credentials` from
   response's header list.
7. If credentials is `true`, then return success.
8. Return failure.

よく「6ステップ」と紹介されますが、原文の <ol> は8項目です。6・7・8は別のステップに分かれています。

表の行どのステップで決まるか
ヘッダーなし → 両方拒否 ステップ2で脱落。ヘッダーが無いので即 failure
* → ふつうは通る / Cookieは拒否 ステップ3が「credentials でない場合に限り」success。Cookie付きだとここを通れず、ステップ4で null ≠ * となり failure
許可リスト → 両方拒否 ステップ4で null ≠ https://app.example.com となり failure
そのまま返す → 両方通る ステップ4を null = null で通過し、ステップ7の Allow-Credentials: true で success。ここが穴

仕様は Access-Control-Allow-Origin の値について、「Originリクエストヘッダーの値そのまま（null もありうる）か *」と定義しています。つまり null を返すのは規格違反ではありません。規格の範囲内で、素直に穴が開きます。

4よくある回避策が穴になる

「届いたOriginをそのまま返す」は、鍵をかけずに札を貼るのと同じ

表の一番下だけが両方通ります。だから検索するとこの実装がよく出てきます。これが一番危険です。

やってはいけない実装
self.send_header("Access-Control-Allow-Origin",
                 self.headers.get("Origin", "*"))     # 届いたものをそのまま返す
self.send_header("Access-Control-Allow-Credentials", "true")

このAPIは「null から来たら null を許可する」と答えます。ところが null は誰でも名乗れます。

  • Cookieが付いたまま通ることを実測しました。表の右下です。ユーザーのログイン状態を使って、そのままAPIを叩けてしまいます。
  • サーバー側に見分ける手段がありません。あなたのアプリのWebViewも、攻撃者のHTMLも、まったく同じ Origin: null です。
  • 攻撃側は端末を触らなくても null を作れます。ページの中に別ページを埋め込む枠(iframe)に sandbox 指定を付けると、その中身は意図的にオリジンを剥がされます。HTML仕様の言葉では「sandboxed origin browsing context flag が content を不透明なオリジンに強制する」（allow-same-origin を書かない限り付く）。普通のWebページからでも null を名乗れる、ということです。
  • 「アプリ内でしか使わないから大丈夫」は成立しません。APIはインターネットに面しています。呼ぶ側を制限しているのはCORSだけです。

Q. Originをそのまま返す実装で、いちばんまずいのはどれ?

正解。CORSは「呼んでいいのは誰か」を決める仕組みです。届いた名前をそのまま許可するのは、名乗った人を全員通すのと同じことです。しかもCredentialsを許可しているので、被害者のログイン状態が使われます。

どうしても許可リストを動的にしたい場合
最低条件
受け取ったOriginを自分の許可リストと照合してから返すこと。一致したときだけ、その値をそのまま返します。一致しなければCORSヘッダーを返しません。
絶対にやらないこと
null を許可リストに入れること。前方一致や部分一致で判定すること（https://app.example.com.evil.com が通ります）。

5正しい直し方（Android / iOS）

CORSをいじるのではなく、そもそもnullにしない

ローカルのファイルを https:// のURLとして読み込ませます。普通のWebページと同じ扱いになるので、CORSの話が全部普通に通ります。

Android は公式に専用のクラスがあります。androidx.webkit の WebViewAssetLoader です。

Android — 公式ドキュメントのサンプル（後半はActivityの onCreate() に置く）
// app/build.gradle.kts に依存を追加（標準搭載ではありません）
// implementation("androidx.webkit:webkit:1.17.0")

private class LocalContentWebViewClient(private val assetLoader: WebViewAssetLoader) : WebViewClientCompat() {
    @RequiresApi(21)
    override fun shouldInterceptRequest(
        view: WebView,
        request: WebResourceRequest
    ): WebResourceResponse? {
        return assetLoader.shouldInterceptRequest(request.url)
    }
}

val assetLoader = WebViewAssetLoader.Builder()
                       .addPathHandler("/assets/", AssetsPathHandler(this))
                       .addPathHandler("/res/", ResourcesPathHandler(this))
                       .build()
webView.webViewClient = LocalContentWebViewClient(assetLoader)

webView.loadUrl("https://appassets.androidplatform.net/assets/index.html")
  • 読み込むURLが https://appassets.androidplatform.net/… になります。実際に通信は出ません。アプリ内のファイルを返しているだけです。
  • このドメインをAPIの許可リストに書けます。これで通常のCORS運用に戻せます。ドメインは setDomain() で自分のものに変えられます。
  • 「安全なコンテキストになるから」ではありません。よくある説明ですが、file:// は元から安全なコンテキストです。W3C Secure Contexts の判定手順に「If origin's scheme is "file", return "Potentially Trustworthy".」と書かれています。効くのは、あくまでオリジンが null でなくなることです。
file:// のページで測った値（Chromium 141 / 実測）
isSecureContext: true
origin: null
serviceWorker in navigator: true
register NG: Failed to register a
  ServiceWorker: The URL protocol of
  the current origin ('null') is not
  supported.

Service Workerが登録できないのも、安全なコンテキストかどうかではなくスキームとオリジンが理由です。エラーメッセージが ('null') と言っています。

この実測を再現する（コピペ用）
やったこと
HTMLに window.isSecureContext / window.origin / navigator.serviceWorker.register() を書いて file:// で開き、出力をそのまま貼りました。折り返しは表示のためスクリプト側で36桁に指定しています（文言は無加工）。
注意
これはデスクトップのヘッドレスChromiumでの結果です。Android WebView・WKWebViewの実機では測っていません。

iOS には同名のクラスはありません。WKURLSchemeHandler で独自スキームを処理するか、loadFileURL(_:allowingReadAccessTo:) を使います。

iOSでの選び方
ローカルHTMLを表示するだけ  → loadFileURL(_:allowingReadAccessTo:)
APIも呼ぶ                → WKURLSchemeHandler で独自スキームを実装
                          （例: myapp://appassets/index.html）
どうしても間に合わない      → アプリ側(ネイティブ)で通信し、結果をJSに渡す
  • 独自スキームにすればCORSが通る、とは書けません。Appleの WKURLSchemeHandler / setURLSchemeHandler のリファレンスにも origin の記述はありません。Chromium側（Android WebView）の文書はむしろ逆で、「独自スキームは不透明なオリジンとして処理されるため、Access-Control-Allow-Origin には * か null が必要」と書いています。
  • だからiOSは、まず実機でOriginをログに出す。第2章と同じやり方で、APIサーバー側の Origin ヘッダーを見てから設計を決めてください。null が届くなら、許可リスト方式は選べません（ネイティブ側で通信するのが確実です）。
Androidで必ず false にしておく設定（WebViewを作った直後に）
val s = webView.settings
s.setAllowFileAccessFromFileURLs(false)
s.setAllowUniversalAccessFromFileURLs(false)

この2つを true にすると file:// の制限を回避できます。ただし公式が明確に推奨していません。

既定値は、リファレンスによれば JELLY_BEAN（API 16）以上を対象にするアプリでは false、ICE_CREAM_SANDWICH_MR1 以下では true。API 30 で非推奨になり、「この設定は安全ではありません。ファイルの内容を安全に読み込むには androidx.webkit.WebViewAssetLoader を使ってください」と書かれています。書かなくても今どきのアプリは false ですが、明示するのが公式推奨です。

  • 公式の言葉。「これらを true にすることは推奨しません。ファイルベースの攻撃に対して脆弱になるためです。最も強い安全性のために、すべてのAPIレベルで明示的に false を設定することを推奨します」
  • 回避策ではなく、根本を直す。CORSを緩めるのも、この設定を有効にするのも、穴を開ける方向です。読み込み方を変えるほうが速くて安全です。

6今すぐ確認するリスト

iOS 26.4の loadFileURL 騒ぎは、公式リファレンスに答えが書いてある

Appleの開発者フォーラムに、loadFileURL(_:allowingReadAccessTo:) の第2引数に関する投稿があります（2026年2月投稿、Appleからの回答なし）。

  • 投稿内容。原文は「Before iOS 26.3」＝26.3より前は第1引数と第2引数に同じパス（h5path/index.html）を渡しても動いていた、というもの。iOS 26.4 Beta ではエラーになり、第2引数は親ディレクトリを指す必要がある、と書かれています。投稿者自身の記述で境界が26.3と26.4に食い違っており、そこは曖昧なままです。
  • iOS 26.4はもうベータではありません。Appleのセキュリティアップデート一覧によれば、iOS 26.4 の公開は2026年3月24日。この記事の5か月前です。確認するならベータではなく26.4以降の実機で。

ただし、この件は公式リファレンスを読めば未確認のままにしなくて済みます。第2引数 readAccessURL の説明にこう書かれています。

Apple「loadFileURL(_:allowingReadAccessTo:)」readAccessURL の説明 — 原文
The URL of a file or directory containing
web content that you grant the system
permission to read. ...
To prevent WebKit from reading any other
content, specify the same value as the URL
parameter. To read additional files related
to the content file, specify a directory.
  • 同じパスを渡す形は「そのファイル以外を読ませない」ための書き方です。CSSやJSなど関連ファイルも読むならディレクトリを渡せ、と公式が明記しています。ローカルHTMLがCSS/JSを読み込むなら、最初からディレクトリを渡すのが文書どおりの使い方です。
  • 26.4の挙動が仕様変更か不具合かは、まだ確定していません。スレッドに回答は付いていません（2026年8月14日時点で返信0件）。ただしディレクトリを渡す形にしておけば、どちらでも文書の範囲内に収まります。報告スレッド

訂正と追記

2026年8月15日: 一次資料に当て直して6か所を直しました

公開後の事実検証で、出典と食い違う記述が見つかりました。直した内容をそのまま残します。

  • Fetch仕様は6ステップではなく8ステップ。原文の <ol> を数え直すと8項目でした。記事は6・7・8を1つに畳んだものを「原文」として載せていました。全8ステップに直し、対応表の「ステップ6で success」もステップ7に訂正しました。
  • iOSの挙動を断定していた箇所を撤回。「loadFileURL だとオリジンが null になる」「Android/iOSどちらも同じ理屈」「独自スキームのオリジンを許可リストに登録する」には出典がありませんでした。Appleのリファレンス本文を取得して検索しても origin / CORS の語は0件です。未確認と明記し、実機でOriginを測る手順に置き換えました。
  • 「https を名乗るので安全なコンテキストになる」は誤り。file:// は元から安全なコンテキストです（Secure Contexts 仕様＋実測 isSecureContext: true）。Service Workerが登録できない理由もスキームとオリジンでした。理由付けを実測に差し替えました。
  • 「iOS 26.3までは」→「26.3より前は」。投稿の原文は Before iOS 26.3 で、26.3を含みません。あわせて投稿日（2026年2月）と iOS 26.4 の公開日（2026年3月24日、Appleのセキュリティアップデート一覧）を明記し、「ベータで確認」という実行できない指示を消しました。
  • 「確定していません」で止めていた件に答えを足した。Appleのリファレンスに「関連ファイルも読むならディレクトリを指定せよ」と書かれています。到達できる一次資料を読んでいませんでした。
  • localStorage の話の測定範囲を明記。デスクトップChromiumでの結果で、WebView実機では測っていません。図版の「loadData / loadFileURL も同じ」も、出典のある「data: URL や loadData」に直しました。
