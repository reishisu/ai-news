# 0001: Ticket owns its own close/reopen authorization check

## Status

Accepted

## Context

「クローズできるのは担当者のみ」というルールをどこで強制するかを決める必要があった。選択肢は大きく2つ:

1. 呼び出し側(コントローラ/サービス層など)が事前に「実行者 == 担当者」をチェックしてから `Ticket` を操作する。`Ticket` 自身は誰が呼んでいるか関知しない。
2. `Ticket` が実行者のIDを受け取り、`Ticket` 自身が担当者と一致するかを判定する。呼び出し側の事前チェックには依存しない。

## Decision

`Ticket` の `close` / `reopen` は実行者のIDを引数として受け取り、`Ticket` 自身が担当者と一致するかを判定する。一致しない場合は例外を投げる。認可チェックは呼び出し側が済ませてある前提を置かない。

## Consequences

- `close` / `reopen` を呼び出す経路がどこであっても、認可チェックを迂回できない。
- `close` / `reopen` を呼ぶすべての箇所が「現在の実行者のID」を把握し、渡す必要がある。
- 将来、認可ルールが変わる(例: 特定の役職なら担当者以外でもクローズ可能、など)場合、`Ticket` のメソッドシグネチャや内部ロジックの変更が必要になる。
